# Plan A2: Deploy-Settle Grace at SoldierState Race-Window Call Sites (revised — Conquest-aligned)

**Status**: Approved 2026-05-27 (pending execution).
**Scope**: Port Conquest's deploy-grace pattern verbatim. Add `deployedAtSecondsByPid` timestamp + `DEPLOY_SETTLE_GRACE_SECONDS` constant + inline grace checks at the two specific Helis call sites that fire `mod.GetSoldierState` during the post-deploy race window.

> First action per [`AGENTS.md`](../AGENTS.md): read [`AGENTS.md`](../AGENTS.md) and [`design_doc/heli_issues_design.md`](./heli_issues_design.md) Section 0.2 (the undeployed-player API call family).

## Context

Reported runtime error: **"ERROR REPORTED BY GETSOLDIERSTATE WHILE: Failed to apply action to player due to player not being deployed"** — fires at spawn time.

Root cause (identified 2026-05-27): there is a race window between `OnPlayerDeployed` firing and the engine accepting `mod.GetSoldierState` calls for that player. During this window:

1. `OnPlayerDeployed` handler runs at [src/index.ts:311](../src/index.ts#L311).
2. We set `State.players.deployedByPid[pid] = true` at [src/index.ts:328](../src/index.ts#L328).
3. The handler then calls broadcast helpers that read soldier state via `safeGetSoldierState*`:
   - `updateHelpTextVisibilityForAllPlayers` → [src/hud.ts:897-899](../src/hud.ts#L897) `safeGetSoldierStateBool(viewer, IsInVehicle)`.
   - `spawnTeamSwitchInteractPoint` → [src/team-switch.ts:49, 54, 57, 58](../src/team-switch.ts#L49) — four `safeGetSoldierState*` calls in sequence.
4. The safe-wrapper precheck `isPlayerDeployed(player)` reads `State.players.deployedByPid[pid]` — which we just flipped true, so the check passes.
5. `mod.GetSoldierState(player, ...)` fires.
6. **Engine isn't fully deployed yet** — logs the "Failed to apply action" error, throws.
7. Safe wrapper's `catch` flips `deployedByPid` back to false (self-healing) — but the engine log is already allocated.

This is a P0-2 family bug. Same heap-pressure mechanism as `#94 → #109` — each cosmetic engine log allocates JS heap; aggregated across many deploy events it contributes to script-termination conditions at higher player counts.

## Conquest reference pattern

Verified 2026-05-27. Conquest does **NOT** put the grace inside the `safeGetSoldierState*` wrappers — those are identical to Helis's (cache precheck + try/catch + cache-correction on throw). Conquest's wrappers at [conquest/src/state/id-helpers.ts:106-135](../../conquest/src/state/id-helpers.ts#L106) confirm this.

Instead, Conquest applies the grace at specific high-risk call sites. From [conquest/src/boundary/enforcement.ts](../../conquest/src/boundary/enforcement.ts):

**Constant** (line 13):
```ts
const GCZ_DEPLOY_GRACE_SECONDS = 1.5;
```

**State field** (in `State.players.deployedAtSecondsByPid: Record<number, number>`).

**Inline grace check** at the boundary classifier (line 243-246):
```ts
const deployedAt = State.players.deployedAtSecondsByPid[pid];
if (deployedAt !== undefined && (mod.GetMatchTimeElapsed() - deployedAt) < GCZ_DEPLOY_GRACE_SECONDS) {
    return undefined;
}
```

**Stamp on deploy** (line 411):
```ts
State.players.deployedAtSecondsByPid[pid] = mod.GetMatchTimeElapsed();
```

**Clear on undeploy/disconnect** (line 571):
```ts
delete State.players.deployedAtSecondsByPid[pid];
```

The pattern repeats at [enforcement.ts:514-518](../../conquest/src/boundary/enforcement.ts#L514) for a second classifier path (teammate inheritance during squad spawn). Two inlined checks, no helper — Conquest accepts the duplication for two call sites.

Revised — inline grace check before the SoldierState read:
```ts
const readyText = safeFind(`ReadyStatusText_${pid}`);
if (readyText) {
    const viewer = safeFindPlayer(pid);
    // Skip the IsInVehicle read during the deploy-settle window to avoid the
    // engine error log (Conquest #94 pattern). Defaults to "not in vehicle" —
    // correct for a just-deployed on-foot player.
    const deployedAt = State.players.deployedAtSecondsByPid[pid];
    const isSettled = deployedAt === undefined
        || (mod.GetMatchTimeElapsed() - deployedAt) >= DEPLOY_SETTLE_GRACE_SECONDS;
    const inVehicle = (viewer && isDeployed && isSettled)
        ? safeGetSoldierStateBool(viewer, mod.SoldierStateBool.IsInVehicle)
        : false;
```

Revised — wait past the grace before the first SoldierState read:
```ts
async function spawnTeamSwitchInteractPoint(eventPlayer: mod.Player) {
    if (!isPlayerDeployed(eventPlayer)) return;
    const playerId = mod.GetObjId(eventPlayer);
    if (!State.players.teamSwitchData[playerId]) initTeamSwitchData(eventPlayer);

    // Wait past the deploy-settle window before reading SoldierState. Engine deploy
    // state is not queryable immediately after OnPlayerDeployed (Conquest #94 pattern).
    const deployedAt = State.players.deployedAtSecondsByPid[playerId];
    if (deployedAt !== undefined) {
        const remaining = DEPLOY_SETTLE_GRACE_SECONDS - (mod.GetMatchTimeElapsed() - deployedAt);
        if (remaining > 0) {
            await mod.Wait(remaining);
            if (!isPlayerDeployed(eventPlayer)) return;
        }
    }

    if (
        State.players.teamSwitchData[playerId].interactPoint === null &&
        !State.players.teamSwitchData[playerId].dontShowAgain &&
        TEAMSWITCHCONFIG.enableTeamSwitch
    ) {
        let isOnGround = safeGetSoldierStateBool(eventPlayer, mod.SoldierStateBool.IsOnGround);
        ...
    }
}
```

## Why this is risk-free

- **Engine-side behavior**: unchanged after 1.5 s. `mod.GetSoldierState` fires normally for all callers post-grace.
- **Helper script-side behavior**: unchanged. `safeGetSoldierState*` wrappers are not modified — they remain identical to Conquest's.
- **Hud call-site behavior**: for 1.5 s post-deploy, `inVehicle` defaults to `false`. The auto-ready text branch only renders when the player is in their main base AND in a vehicle — both conditions a just-deployed on-foot player fails anyway. Visible effect: zero.
- **Team-switch call-site behavior**: interact point spawn delayed by ≤1.5 s vs. v0.631. The function already loops with `await mod.Wait(0.2)` until `isOnGround` returns true, so a small additional pre-loop wait is consistent with the existing behavior.
- **Undeploy race**: not addressed by this plan. Existing catch-block self-healing handles it.
- **Field name parity with Conquest**: `deployedAtSecondsByPid`, `DEPLOY_SETTLE_GRACE_SECONDS`. Same shape as `GCZ_DEPLOY_GRACE_SECONDS` (Conquest), differentiated by name because Helis has no GCZ subsystem — using `DEPLOY_SETTLE_GRACE_SECONDS` reflects the actual purpose ("settle window after deploy").
