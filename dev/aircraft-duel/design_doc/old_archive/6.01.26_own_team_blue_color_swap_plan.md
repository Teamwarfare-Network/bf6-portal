# Viewer-Relative Team Colors — Your Team Always Blue

**Date**: 2026-06-01
**Status**: USER-APPROVED. Scope locked to color-only swap. Layout (T1-left / T2-right) intentionally stays unchanged for this phase. Outcome text colors (WINS! / LOSES) also flip per viewer.

**Origin**: H-P3 "Viewer-Oriented HUD" from [5.27.26_heli_proposed_features.md](./5.27.26_heli_proposed_features.md) is too large for a single ship (~640 T1/T2 refs, ~125 TeamID uses, three orthogonal axes). User asked for a scoped-down version that delivers the most-visible UX win — "my team is blue" — without committing to the full layout flip.

User direction (verbatim):
- "I'm OK if its not always 'on the left' due to complexity for now."
- "lets list out all the coloring differences and be clear on them. There's the ready dialog roster panel color. There's the backplate and text colors in the HUD. I think the Flag progress bar, and the victory screens?"
- "match the color text for wins/loses too, that makes sense doesnt it?"

---

## Goal

Every HUD surface that today binds a color to T1/T2 identity binds it to the **viewer's relationship** instead. A T1 viewer sees T1 as blue everywhere and T2 as red. A T2 viewer sees T2 as blue everywhere and T1 as red. Spectators / no-team viewers fall back to the historical T1=blue/T2=red default.

**Layout stays exactly as today** — T1 data lives on the left, T2 data lives on the right, regardless of viewer team. Only colors flip.

---

## Non-goals (deferred to future H-P3 work)

- Roster ordering / crown position / data placement — no layout flips.
- Engine-owned UI (kill feed, minimap player markers) — cannot be overridden by script; accepted inconsistency.
- World-log message rewording — broadcasts stay team-anchored.
- "Your Team" / "Enemy Team" label rewrites — faction names stay.

## Helper design

Single function added in [state.ts](../src/state.ts) near `safeGetTeamNumberFromPlayer`:

```ts
// v0.737 Viewer-relative team color resolver. Given a viewer pid and a "source team" identity (the
// team whose data is being painted), returns ownColor when viewer's team matches the source, else
// enemyColor. Fallback to ownColor when viewer has no team (joining/spectator/team=0) so the
// historical T1=ownColor / T2=enemyColor default holds when called with sourceTeam=T1 (most
// callers). The two-color shape lets each call site pass its own palette pair -- e.g. score banner
// uses bright-blue/bright-red while victory dialog uses dark-blue/dark-red.
function getViewerOwnTeamColor<T>(viewerPid: number, sourceTeam: TeamID, ownColor: T, enemyColor: T): T {
    const player = safeFindPlayer(viewerPid);
    if (!player || !mod.IsPlayerValid(player)) return sourceTeam === TeamID.Team1 ? ownColor : enemyColor;
    const viewerTeam = safeGetTeamNumberFromPlayer(player);
    if (viewerTeam !== TeamID.Team1 && viewerTeam !== TeamID.Team2) {
        return sourceTeam === TeamID.Team1 ? ownColor : enemyColor;
    }
    return viewerTeam === sourceTeam ? ownColor : enemyColor;
}
```

**~12 LOC.** Polymorphic on color type so RGB tuples (`[number, number, number]`) and `mod.Vector` colors both work.

## Per-surface fixup pattern

Each of the 4 build-time surfaces (score banner, victory dialog, ready dialog roster, overtime HUD) gains an `applyViewerTeamColorsForXxx(pid)` function that:

1. Reads viewer's team via the helper above.
2. For each team-anchored widget on that surface: `mod.SetUIWidgetBgColor` / `mod.SetUITextColor` with the resolved color.

These functions are called:
1. At the END of each surface's `ensureXxxUiBuiltHidden(player)` build function — initial application after first build.
2. From a new central `repaintAllViewerTeamColorsForPid(pid)` orchestrator — called from `processTeamSwitch` after the team change settles.

The build-time literals stay as today's T1/T2 values — they're the seed that the fixup overwrites. If the fixup is skipped or missed for any reason, behavior degrades to today's behavior (not catastrophic).

## Risks

| Risk | Severity | Mitigation |
|---|---|---|
| Missing a fixup call site → one widget stays at the today-default color | Low | Today-default IS valid for T1 viewer (no visible bug); only T2 viewers see the regression. Live test #2-10 catches it. |
| Team-switch repaint misses a surface → stale color after swap | Medium | Centralize via `repaintAllViewerTeamColorsForPid` orchestrator; add new surfaces to it explicitly. List every surface in one file's import block for visibility. |
| Diff-cache invalidation (overtime `lastUiSnapshotByPid`) | None | The snapshot caches text labels + counts, NOT colors. Verified during v0.732 work. Colors live on different writes. |
| Engine-owned UI mismatch (kill feed, minimap shows T1 player as blue even for T2 viewer) | Inherent | Out of scope for this phase. Documented as accepted limitation. Player nameplates ARE already viewer-relative in BF6 (friendly = blue, enemy = red regardless of team), so panel-color-matches-nameplate is MORE consistent post-fix, not less. |
| Voice comms confusion: "the red guy at A2" means different people to different viewers | Inherent | Documented limitation. Patch notes flag this. |
| Pre-deploy / no-team viewers see weird default | Low | Helper falls back to T1=ownColor when viewer has no team. Matches historical behavior. |
| Spectator (future C-P4 work) gets the no-team default | Low | Same fallback path. Spectator sees the historical T1=blue/T2=red mapping. |
