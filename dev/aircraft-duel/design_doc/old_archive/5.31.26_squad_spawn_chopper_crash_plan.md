# Squad-Spawn-Into-Chopper Crash + Related-Risk Audit

**Date**: 2026-05-31
**Status**: DIAGNOSED, FIX READY TO SHIP
**Severity**: P0 — 7/7 repro rate, kills the whole-server script (1000ms eval breach via sandbox)
**Repro**: Player squad-spawns onto a teammate who is currently in a chopper. Whole script dies for all players (host sees error).

---

## 1. Diagnosis (confirmed)

### The bug

[team-switch.ts:58-63](../src/team-switch.ts#L58):

```ts
let isOnGround = safeGetSoldierStateBool(eventPlayer, mod.SoldierStateBool.IsOnGround);

while (!isOnGround) {
    if (!isPlayerDeployed(eventPlayer)) return;
    isOnGround = safeGetSoldierStateBool(eventPlayer, mod.SoldierStateBool.IsOnGround);
}
```

**Synchronous busy-loop with no `await` inside.** Polls `IsOnGround` until the player lands. When a player squad-spawns into a chopper, they are never `IsOnGround` (they're inside a vehicle). The loop spins until the 1000ms sandbox eval budget is breached and the script dies.

### Why every observation matches

| Observation | Mechanism |
|---|---|
| Whole-script dies (Q1=B) | Sandbox eval-budget breach kills the entire JS script for all players |
| Player can still play (Q2) | Script death doesn't affect the player's character or game controls |
| Altitude doesn't matter (Q3) | `IsOnGround` is false regardless of altitude while in a vehicle |
| First connect AND respawn AND pregame all repro (Q4) | All three deploy paths funnel through `OnPlayerDeployed` → `await spawnTeamSwitchInteractPoint(...)` at [index.ts:378](../src/index.ts#L378) |
| 7/7 repro | Deterministic — every squad-spawn-into-vehicle hits this exact code path |

### Provenance — is this our regression?

**No.** The busy-loop is pre-existing. Evidence:

- [Changelog v0.641](../src/Changelog.ts) (much older, Plan A11 probe instrumentation) explicitly references "STIP_01-19 covering... safeGetSoldierStateBool(IsOnGround), while loop, position/facing reads..." — the while loop was already in place during that debug work.
- v0.632 added the deploy-settle grace `await mod.Wait(remaining)` at line 48 — separate from the while loop at lines 60-63.
- The while loop has not been touched in any version we have records for.

**Why it never crashed before**: when a player spawns **on foot**, `IsOnGround` returns `true` immediately and the while loop never executes. Squad-spawn-on-vehicle is the only deploy path that triggers a deploy moment with `IsOnGround === false`. Whether this scenario was rare or simply not systematically tested before, the bug was dormant.

## 2. The fix (v0.713 ship)

Three layers, all surgical, all inside `spawnTeamSwitchInteractPoint`:

### Layer A — Early exit when in vehicle (primary fix)

```ts
async function spawnTeamSwitchInteractPoint(eventPlayer: mod.Player) {
    if (!isPlayerDeployed(eventPlayer)) return;
    // v0.713 fix: interact points cannot be triggered from inside a vehicle (you have to
    // exit first, then triple-tap). Skip the spawn entirely when in-vehicle. If the player
    // exits the vehicle later, OnPlayerExitVehicle re-arms the path.
    if (safeGetSoldierStateBool(eventPlayer, mod.SoldierStateBool.IsInVehicle, false)) return;
    ...
}
```

**Why this is the primary fix**: the interact point is for opening the Ready Dialog via triple-tap. You can't triple-tap from inside a chopper anyway. The function call has no legitimate business proceeding when the player is in a vehicle.

### Layer B — Async yield inside the while loop (defense in depth)

```ts
let isOnGround = safeGetSoldierStateBool(eventPlayer, ...);
let iterations = 0;
while (!isOnGround) {
    if (iterations++ > 300) return;  // 30s hard cap (300 * 0.1s)
    if (!isPlayerDeployed(eventPlayer)) return;
    await mod.Wait(0.1);  // yield to engine each iteration
    isOnGround = safeGetSoldierStateBool(eventPlayer, ...);
}
```

**Why both**: Layer A catches the in-vehicle case at function entry. Layer B prevents future regressions if some OTHER scenario (mid-air-spawn from a hypothetical future feature, deploy bug, etc.) leaves a player not-on-ground for an extended time. The yield + cap together guarantee this loop can never burn the eval budget again.

### Layer C — Re-arm on vehicle exit (UX completeness)

When `OnPlayerExitVehicle` fires, call `spawnTeamSwitchInteractPoint` so the player can use the ready dialog after exiting their chopper. Without this, a player who squad-spawned-into-a-chopper-then-exited would have no interact point spawned.

```ts
// In OnPlayerExitVehicle:
void spawnTeamSwitchInteractPoint(eventPlayer);  // re-arm after the in-vehicle gate
```

**Risk**: low. `spawnTeamSwitchInteractPoint` is idempotent — its existing guard at [team-switch.ts:53-56](../src/team-switch.ts#L53) checks `interactPoint === null` before spawning, so calling it when an interact point already exists is a no-op.

## 5. Process reflection — are we prematurely optimizing?

The user's concern, paraphrased: "We optimized per-tick costs (v0.692, v0.711, v0.712) instead of finding crash-class bugs like this one. The optimizations are speculative; the crash is real."

### Honest assessment

**True**: The crash exists independently of our optimizations. v0.711's seatKind gate (skip `checkMultiClick` in OngoingPlayer when in-vehicle) addressed a *similar* pattern but only at one of two call sites. If we'd been auditing for "code that assumes on-foot," we'd have caught the `OnPlayerDeployed` call to `spawnTeamSwitchInteractPoint` at the same time.

**Also true**: The seatKind insight from the optimization work IS what diagnosed this crash. Without the prior thinking about "what assumes on-foot state," the busy-loop's interaction with chopper-spawn wouldn't have been obvious.

**Where we erred**: We applied the seatKind insight as an *optimization* (saving a bridge call) instead of as a *correctness gate* (preventing bad behavior in the in-vehicle case). Same code change, different framing — but framing it as correctness would have prompted a search for the matching pattern in other call sites.

### Process change going forward

Three rules for the next session:

1. **Crash hunts before optimizations.** When the user reports a crash (even an old one), prioritize diagnosing it over any optimization work. Optimizations should be ROI-justified by measured cost, not theoretical bridge-call counts.
2. **When fixing a pattern at one call site, grep for all call sites of the same function and apply the same fix.** v0.711 fixed OngoingPlayer's call to `spawnTeamSwitchInteractPoint` but not OnPlayerDeployed's call to the same function. A `grep spawnTeamSwitchInteractPoint` at v0.711 ship time would have caught both.
3. **Audit recently-shipped optimizations against the bugs they didn't catch.** v0.711 + v0.712 shipped cleanly but didn't address this crash. The seatKind gate should have been applied universally (inside the function) rather than at one caller. **Recommend folding the v0.711 OngoingPlayer-specific gate INTO the function-level gate from this fix** — eliminates the asymmetry, single source of truth.

### Recommended retroactive cleanup (post-v0.713)

After shipping v0.713 (function-level in-vehicle gate), the v0.711 OngoingPlayer gate becomes redundant:

```ts
// In OngoingPlayer (current v0.711):
const inVehicle = safeGetSoldierStateBool(eventPlayer, mod.SoldierStateBool.IsInVehicle, false);
if (!inVehicle && InteractMultiClickDetector.checkMultiClick(eventPlayer)) {
    ...
    spawnTeamSwitchInteractPoint(eventPlayer);  // <-- function-level gate now catches this too
}
```

**Don't immediately remove** — keeping the OngoingPlayer gate is a small bridge-call saving (no IsInteracting poll while in-vehicle). Just **document the redundancy** in a comment so future-us doesn't think the OngoingPlayer gate is the only line of defense.

## 7. What this plan does NOT do

- **Does not remove the v0.711 OngoingPlayer seatKind gate** — keep it as a small bridge-call savings, just document it as defense-in-depth not the only line.

- **Does not audit every "this assumes on-foot" code path** — flagged in §4 as follow-up, not blocking v0.713.
- **Does not pre-emptively rewrite all the other while loops** — they all have proper await yields (audit in §4).
