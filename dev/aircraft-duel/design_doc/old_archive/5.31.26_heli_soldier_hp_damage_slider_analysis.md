# Helis-Only Analysis: In-Game Soldier Tankiness Slider (HP / Damage-Received)

*Investigation only -- created 2026-05-31 against Helis v0.721. **This is an analysis, not an approved plan.** No edits have been made. Decisions (range, default, which knob) need user sign-off before an implementation plan is drafted.*

---

## 0. The question

> How could we make an in-game slider for soldier HP / damage received by a soldier -- to make the player soldier tankier?

Short answer: **yes, this is directly supported by two verified engine APIs, and the codebase already has a finished, battle-tested template** -- the Vehicle Health Multiplier slider shipped in v0.648-v0.721. A soldier-tankiness slider is ~85% a clone of that feature. The one material difference is the *application site*: soldier durability is a **per-Player** property applied on **deploy**, whereas vehicle health is a **per-Vehicle** property applied on **spawn**.

---

## 1. The engine APIs (verified in SDK 1.3.1)

Two distinct, independent levers exist. Both make the soldier tankier; they stack multiplicatively.

### Lever A -- Bigger health pool: `SetPlayerMaxHealth`

[reference_sdk_1.3.1/code/types/mod/index.d.ts:26691](../../reference_sdk_1.3.1/code/types/mod/index.d.ts#L26691)

```ts
// Sets the max health of a target player from 1 to 500.
// The value will be multiplied by the target's max health multiplier.
export function SetPlayerMaxHealth(player: Player, maxHealth: number): void;
```

- **Range:** absolute HP value, **1 to 500**. Vanilla soldier base is **100**, so this is effectively a 0.01x - 5.0x range.
- **Semantics:** raises the *ceiling*. A soldier at `SetPlayerMaxHealth(200)` has a 200-point bar and dies in roughly twice as many bullets.
- **Display:** the on-screen health bar reflects the new max -- the player *sees* they are tankier. Health-regen thresholds scale with it.
- **GOTCHA (confirmed in our own codebase):** setting max health does **not** refill current health. The vehicle feature hit the exact analog of this -- see [Changelog.ts:161-169](../src/Changelog.ts#L161) (v0.714): raising the max ceiling left *current* health at the old value (e.g. bar shows 100/200). The fix was to call `mod.Heal(...)` immediately after to lift current up to the new max. **The same `Heal` follow-up will be mandatory for soldiers.** There is no `SetPlayerCurrentHealth` API; `Heal` clamped-to-max is the only way.

### Lever B -- Less damage taken: `SetPlayerIncomingDamageFactor`

[reference_sdk_1.3.1/code/types/mod/index.d.ts:26619](../../reference_sdk_1.3.1/code/types/mod/index.d.ts#L26619)

```ts
// Sets damage taken factor on player (Will be rounded to the nearest 5%).
// The value will be clamped between 0 - 200%.
export function SetPlayerIncomingDamageFactor(player: Player, amount: number): void;
```

- **Range:** `0.0` - `2.0`, **rounded to nearest 5% (0.05)** and clamped by the engine.
- **Semantics:** scales all incoming damage. `0.5` = take half damage (tankier); `0.0` = invulnerable; `2.0` = glass cannon. The displayed health bar is unchanged -- the soldier still has a 100 bar, the bullets just chip it slower.
- **No `Heal` needed** -- this knob never touches current/max health, so it has none of Lever A's refill race.
- **Coarser granularity** than Lever A (5% steps vs 1-HP steps), but that is plenty for a tankiness dial.

### Which lever to expose?

| Property | Lever A: `SetPlayerMaxHealth` | Lever B: `SetPlayerIncomingDamageFactor` |
|---|---|---|
| Player-facing label | "Soldier HP: 150%" (bar grows) | "Soldier Damage Taken: 50%" (bar same, lasts longer) |
| Range | 1-500 (0.01x-5x of base 100) | 0%-200%, 5% steps |
| Refill gotcha | **Yes** -- needs `mod.Heal` after | No |
| Regen behavior | scales with bigger pool | unchanged |
| Effective tankiness | linear in HP | inverse in damage factor |

**Recommendation:** expose **Lever A (`SetPlayerMaxHealth`) as the primary "Soldier HP %" slider** -- it is the most intuitive ("tankier soldiers have more HP"), the bar visibly grows, and it is the exact conceptual twin of the existing Vehicle Health % slider (so the UI reads consistently: "Vehicle Health: 130% / Soldier HP: 150%"). The `mod.Heal` follow-up is a known, solved pattern we already ship for vehicles.

Lever B is the better choice **if** the design wants tankiness *without* a visibly larger health bar (e.g. to keep the HUD looking vanilla), or as a *second* advanced knob. Both can coexist and stack. For a first cut, ship one (Lever A) and keep B as a documented follow-up.

> Note: the doc for Lever A mentions "the target's max health multiplier" -- there is **no** `SetPlayerMaxHealthMultiplier` exported in SDK 1.3.1 (only `SetVehicleMaxHealthMultiplier` at [index.d.ts:27558](../../reference_sdk_1.3.1/code/types/mod/index.d.ts#L27558) exists, and that is vehicle-only). For soldiers we set an **absolute** value, treating base 100 as the reference: `maxHealth = Math.round(100 * soldierHpMultiplier)`.

## 3. The one structural difference: where you apply it

Vehicle health is applied to each **Vehicle** object in `OnVehicleSpawned`. Soldier durability is a property of a **Player** and must be (re)applied **every time the player deploys**, because a fresh soldier each life resets to engine defaults.

The application site is **`OnPlayerDeployed`** at [index.ts:329](../src/index.ts#L329). It already runs per-life, already adds the supply-crate equipment in `try/catch` blocks ([index.ts:350-363](../src/index.ts#L350)), and already stamps alive-state -- it is the natural home. Proposed insertion (after the existing equipment block, before the HUD/interact-point work):

```ts
// Soldier tankiness: apply confirmed HP multiplier on each deploy. Base soldier HP is 100.
// SetPlayerMaxHealth raises the ceiling but does NOT refill current health (same race the
// vehicle feature hit in v0.714) -- Heal afterward lifts current up to the new max.
try {
    const hpMult = State.round.modeConfig.confirmed.soldierHpMultiplier ?? 1.0;
    if (hpMult !== 1.0) {
        mod.SetPlayerMaxHealth(eventPlayer, Math.round(100 * hpMult)); // clamp 1..500 upstream
        mod.Heal(eventPlayer, 99999); // clamp-to-max refill, mirrors index.ts:689
    }
    // Optional Lever B: mod.SetPlayerIncomingDamageFactor(eventPlayer, State.round.modeConfig.confirmed.soldierDamageTakenFactor ?? 1.0);
} catch (_e) {}
```

### Timing caveats to validate (carried over from prior deploy-race scars)

- **Deploy-settle race.** The codebase has a documented history of `GetSoldierState`/player-action engine errors firing in the first ~1.5s of `OnPlayerDeployed` ([Changelog.ts v0.632/v0.641](../src/Changelog.ts#L411); memory: `DEPLOY_SETTLE_GRACE_SECONDS`). `SetPlayerMaxHealth`/`Heal` are *writes*, not the `GetSoldierState` reads that triggered those logs, and BillDukes-style precedent applies these one-shot post-deploy. But the `try/catch` wrap is non-negotiable, and SP smoke-testing should watch for a "player not deployed" log on the very first frame. If it appears, defer the call by one tick or behind the existing deploy-grace gate.
- **Re-apply on every life.** Because each new soldier resets, this must live in the per-deploy path, not a one-time init. `OnPlayerDeployed` satisfies that.
- **Mid-round confirm semantics.** Mirror the vehicle decision: **confirmed-only**, and applies to the **next deploy** (next life). Soldiers already alive keep their current durability until they redeploy. This is automatic given the apply-on-deploy site -- no extra work.

## 4. Proposed feature shape (mirrors the locked vehicle-health decisions)

Unless the user wants to diverge, inherit the vehicle slider's proven decisions:

| Decision | Proposed for Soldier HP | Rationale |
|---|---|---|
| Knob | Lever A `SetPlayerMaxHealth`, stored as float multiplier `soldierHpMultiplier` | intuitive, twins the vehicle "%" dial |
| Range / step | e.g. **50%-300%**, 1% fine + 10% coarse buttons | engine allows 1%-500%; 50-300 is a sane competitive band (tune with user) |
| Default | `1.0` (100%), per-map via `MapConfig.defaultSoldierHpMultiplier?` | matches vehicle pattern; future per-map tuning free |
| Apply timing | confirmed-only, next deploy | matches vehicle "next spawn" |
| Game-mode interaction | manual change -> flip to Custom; preset selection resets to map/preset default | reuse `ensureCustomGameModeForManualChange()` + a `getPresetSoldierHpMultiplierForGameMode` |
| UI position | new row under the Vehicle Health row, same `[-10][<] val [>][+10]` widget shape | dialog already has the row-builder + `leftSectionRowGap` cadence |
| HUD summary | always-show "Soldier HP: NNN%" line beneath "Vehicle Health" | matches `settingsVehicleHealthText` |
| World-log on confirm | "{Player} changed Soldier HP to NNN%" | matches `vehicleHealthChanged`, wrap `changedBy` via `safePlayerArg` |
| Strings | ~3 new keys, **require user approval** per AGENTS.md string policy | `readyDialog.modeSettingSoldierHpFormat`, `readyDialog.soldierHpChanged`, `hud.settings.soldierHpFormat` |

## 6. Risks / open questions for the user

1. **Which lever (or both)?** HP-pool (bar grows) vs damage-taken (bar stays, lasts longer) vs both stacked. Recommend HP-pool first.
2. **Range + default band.** Engine allows 1%-500% (HP) / 0%-200% (damage factor). What competitive band do you want exposed, and what default per game mode (e.g. should TWL Ladder run >100% like vehicles do at 160%)?
3. **Interaction with the vehicle-only design.** This mode is vehicle-combat; soldiers are mostly in cockpits. Tankier soldiers mainly matters for the brief on-foot windows (spawn, repair-on-foot, bailout, objective capture on foot). Confirm the intended use case so the range is tuned for it (e.g. surviving a bailout, or surviving long enough to torch-repair under fire).
4. **First-frame deploy-race.** Needs SP smoke validation that the post-deploy `SetPlayerMaxHealth`/`Heal` write does not trip the historical "player not deployed" engine log. Mitigation (one-tick defer / deploy-grace gate) is known if it does.
5. **String approval.** The 3 new strings need explicit sign-off (AGENTS.md String Authorization Policy; non-ASCII guardrail -- use `%`, `--`, plain quotes only).

---

## 7. Bottom line

- **Feasible and low-risk.** Two clean engine APIs (`SetPlayerMaxHealth`, `SetPlayerIncomingDamageFactor`), both verified in SDK 1.3.1.
- **~85% reuse.** The Vehicle Health Multiplier slider is a complete, hardened template -- copy its plumbing across 9 files with `soldier`-prefixed twins.
- **One new idea:** apply on `OnPlayerDeployed` (per-life, per-Player) instead of `OnVehicleSpawned`, and -- if using the HP-pool lever -- pair `SetPlayerMaxHealth` with a `mod.Heal` refill (the same v0.714 fix we already ship for vehicles).
- **Next step:** user picks lever(s) + range + default (section 6 Q1-Q3) and approves the 3 strings; then this becomes a step-by-step implementation plan in the style of the vehicle-health plan.
