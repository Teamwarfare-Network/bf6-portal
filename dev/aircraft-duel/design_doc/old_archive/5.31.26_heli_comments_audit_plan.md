# Helis Comments Audit Plan

**STATUS: SHIPPED in v0.710.** Bundle 1 (A1, A2, A4, A5) and Bundle 2 (C1, C2) applied. A3 skipped (warm-up was already deleted in v0.692, no code to comment). B1 + B2 skipped (already done in earlier versions). Bundle size unchanged because the build's comment-strip postbuild was already stripping these comments before; the readability improvement is source-only.

**Date**: 2026-05-31
**Goal**: Identify specific places where the WHY behind code is non-obvious to a fresh reader. Add comments only where omission would force a reader to reverse-engineer intent from behavior. Avoid commenting WHAT (well-named identifiers carry that already).

**Guiding rule** (from project CLAUDE.md + Conquest AGENTS.md): *"Default to writing no comments. Only add one when the WHY is non-obvious: a hidden constraint, a subtle invariant, a workaround for a specific bug, behavior that would surprise a reader."*

**Scope**: Code paths added/touched during the lazy-load refactor (v0.687-v0.691) + a handful of long-standing under-commented hotspots. Not a full-codebase pass.

---

## Audit methodology

For each candidate site, I ask three questions:
1. **Would a fresh reader infer the intent from the code alone?** If yes — no comment needed.
2. **Is there a hidden constraint, invariant, or workaround that breaks if ignored?** If yes — comment required.
3. **Has the existing comment drifted from the code?** If yes — update or delete.

Items below are ordered by ROI. Each names the file, the specific site, and the proposed addition / change / removal.

## A — Add (the WHY is non-obvious)

### A1 — `ensureEagerHudShellForPlayer` cache invariant: `cached.settingsGameModeText` (HIGH ROI)

**Where**: `hud.ts:1008`.

**Problem**: The cache-hit check uses `cached.settingsGameModeText` as the load-bearing eager ref. A reader unfamiliar with Phase B will assume this is arbitrary and may "improve" it later by changing the check to a top-HUD ref, which would silently fail because top-HUD refs are now lazy.

```ts
// reliable "did we run the eager pass?" sentinel. Do NOT change this to a top-HUD ref --

if (cached && cached.settingsGameModeText) {
```

**Risk**: Documentation only. Single line.

### A2 — `updateVictoryDialogForPlayer` gated `triggerLazyBuild` call (HIGH ROI)

**Where**: `hud.ts` around the call to `triggerLazyBuild('victoryDialog', pid)`.

**Problem**: The `if (State.match.victoryDialogActive) triggerLazyBuild(...)` gate is critical — without it, `ensureEagerHudShellForPlayer`'s cache-init path calls `updateVictoryDialogForPlayer` defensively, and an ungated trigger would fire the build during OPJG, defeating Phase A entirely. The existing comment ("only fire the build when the dialog actually needs to be shown") is adequate but could be more specific about the OPJG path.

**Proposed**: Strengthen existing comment:
```ts
// Phase A gate: this function is called both from round-flow.ts at match-end AND from
// ensureEagerHudShellForPlayer's cache-init path as a defensive no-op for late joiners.
// The gate ensures the OPJG path doesn't fire the lazy build -- only the real match-end
// path should. Without this gate, the Victory dialog widget tree builds during the join
// tick, defeating Phase A.
if (State.match.victoryDialogActive) triggerLazyBuild('victoryDialog', pid);
```

**Risk**: Documentation only.

### A3 — `OngoingPlayer` UI warm-up build-and-hide pattern (HIGH ROI)

**Where**: `index.ts:404-410`.

**Problem**: The pattern `createTeamSwitchUI(player); ... ; deleteTeamSwitchUI(player); state.uiBuilt = true;` looks like "build then immediately discard" — a reader might delete it as dead code. The actual intent is "warm-build the cached widget tree so the first real open is snappy" (deleteTeamSwitchUI is now a hide-not-delete since the cache refactor).

The existing one-line comment ("warm-up: build the Ready Up dialog once per player so the first real open is snappy") is too thin. A reader needs to know:
1. `deleteTeamSwitchUI` hides, doesn't destroy (post-refactor semantics).
2. This warm-up does NOT defeat lazy-load: OngoingPlayer ticks are per-player and naturally staggered, so the build cost spreads.
3. Removing this would make first triple-tap take ~50ms.

**Proposed**:
```ts
// UI warm-up: build the Ready Up dialog widget tree on the first OngoingPlayer tick per
// player. The widgets stay cached but hidden -- deleteTeamSwitchUI is hide-not-delete post
// cache-refactor. First triple-tap then opens instantly (visibility flip on cached tree)
// instead of paying a ~50ms hitch.
//
// Why this is safe for the lazy-load refactor: OngoingPlayer ticks fire per-player at
// engine cadence; they're naturally staggered across time so this build doesn't dogpile
// the way an OnPlayerJoinGame build would. Don't move this to OPJG.
if (State.players.teamSwitchData[pid] && !State.players.teamSwitchData[pid].uiBuilt) {
```

**Risk**: Documentation only.

### A5 — `runAircraftWarningLoop` STAGE constants need link to v0.666 spec (LOW-MEDIUM ROI)

**Where**: `ready-dialog.ts:2618-2620`.

**Problem**: The three stages (GREEN/YELLOW/BLACK) and their thresholds are tuned per the v0.666 3-stage layered ceiling spec, but a reader has to grep the Changelog or guess. The thresholds are non-obvious (soft = ceiling - warnBuffer, warning = ceiling, hard = ceiling + hardBuffer).

**Proposed**:
```ts
// Three-stage altitude warning, per v0.666 H-P1 layered ceiling spec.
// Thresholds (all world-Y, derived from State.round.modeConfig.confirmed.aircraftCeiling):
//   - STAGE_GREEN  altimeter green text, no warning  (posY <= softY)
//   - STAGE_YELLOW altimeter yellow + "ALT WARNING"  (softY < posY <= warningY)
//   - STAGE_BLACK  STAGE_YELLOW + 960x540 black-screen dialog with countdown (posY > warningY)
//
// softY    = floorY + ceiling - warningBufferM     (configurable via admin warn buffer)
// warningY = floorY + ceiling                       (the "you are AT the ceiling" line)
// hardY    = floorY + ceiling + hardBufferM         (engine pushback, set via SetMaxVehicleHeightLimitScale)
//
// Hysteresis: see AIRCRAFT_SOFT_CEILING_ENTER_BUFFER / EXIT_BUFFER for stage-flip thresholds.
const STAGE_GREEN = 0;
const STAGE_YELLOW = 1;
const STAGE_BLACK = 2;
```

**Risk**: Documentation only.

## C — Remove (comment is noise)

### C1 — Verbose `// position: [x, y] offset; direction depends on anchor` repeated in every ParseUI block

**Where**: hud-dialog-lazy.ts + hud-scoring-lazy.ts + hud.ts ParseUI tree literals. ~50+ occurrences.

**Problem**: The comment repeats on every position field across thousands of lines of widget config. Adds noise; reader becomes blind to it. The semantics it explains (positive Y = down, anchor-relative) are universal across the codebase — belongs in a single file-header or README note, not inline.

**Proposed**:
- Remove all inline repeats.
- Add a single canonical note at the top of `hud.ts` (and reference it from the two lazy-build files):
  ```ts
  // Widget position convention: position [x, y] is anchor-relative. +X = right of anchor,
  // +Y = down from anchor. Verify visually in-game for non-center anchors -- TopCenter
  // children with negative X don't always render exactly where the math suggests (v0.684
  // diagnosed negative-X clipping on TopLeft-anchored parents).
  ```

**Risk**: Low — pure noise removal. Bundle size shrinks. Diff is large (line removals).

**Where**: All widget construction blocks.

**Pattern**: Hardcoded pixel positions like `[5, 5 + TOP_HUD_OFFSET_Y]`, `[970.93, 44.35]`. Some are derived from formulas, some are visually tuned. A reader can't tell which is which without git blame.

## What's deliberately NOT being added

Per the "default to no comments" rule, the following are NOT proposed despite being non-trivial code:

- **Every ParseUI block's children: [] tree**: the structure is self-documenting via the `name:` field convention. Adding "this is the team-1 panel" comments above each is noise.
- **Defensive null checks**: `if (!player || !mod.IsPlayerValid(player)) return;` is the canonical safe-entry pattern across the codebase. Doesn't need per-site comments.
- **`safeFind`/`safeGetPlayerId`/`safe*` wrappers**: their names already say what they do.
- **`State.X.Y.Z` paths**: hierarchical state structure is documented in `state.ts` type definitions; commenting each access site is duplication.
- **Long admin-panel button cases in `teamSwitchButtonEvent`**: each case's action is named via its widget ID; visible at a glance.
