# Plan A10: `isAliveByPid` Cache Guard Pattern (Conquest CQ_Bug_37/38 Port)

**Status**: Approved 2026-05-27 (pending execution).
**Scope**: Add `isAliveByPid: Record<number, boolean>` cache. Flip proactively in `OnVehicleDestroyed` (using `popLastDriver` to identify the victim), `OnPlayerUndeploy`, `OnPlayerDeployed`, `OnPlayerLeaveGame`, and the safe-wrapper catch blocks. Add cache check at 5 per-tick callsites before invoking safe `mod.GetSoldierState` wrappers.

## Context

Reported runtime error: **"ERROR REPORTED BY GETSOLDIERSTATE WHILE: Failed to apply action to player due to player not being deployed"** — fires on plain death + round end. Still present in v0.637.

Root cause: race window between engine internal undeploy (which starts when player dies) and `OnPlayerUndeploy` event firing (which flips `deployedByPid[pid] = false`). The safe `mod.GetSoldierState*` wrappers precheck `isPlayerDeployed(player)` which reads the cache — during the race, cache stale-true → wrapper proceeds to engine call → engine logs error → wrapper catch self-heals (flips cache to false), but engine log already allocated.

## Conquest reference pattern

[conquest_issues.md:323-327](../../conquest/design_doc/conquest_issues.md) CQ_Bug_37/38 v1.074:
> "Added vehicle occupancy cache guard — `safeGetVehicleFromPlayer` checks `State.players.posDebugVehicleObjIdByPid[pid]` **before querying the engine**. Cache set on `OnPlayerEnterVehicle`, cleared on exit/undeploy."

Pattern: maintain a separate event-driven cache that's authoritative for the specific query, check it before the engine call.

For Helis #2, the analogous cache is `isAliveByPid`. Conquest's own caveat: *"Residual edge case: in-vehicle death has a brief window where cache shows a vehicle but engine rejects the query. Try-catch handles this gracefully."* For Helis this exact edge case (vehicle-destroyed = player dies) is the common case, so the cache approach won't fully eliminate the residual — but proactively flipping in `OnVehicleDestroyed` closes the window much earlier than `OnPlayerUndeploy`.

## The helper + cache field

In [src/state.ts](../src/state.ts), extend `GameState.players` interface:
```ts
players: {
    ...
    deployedByPid: Record<number, boolean>;
    deployedAtSecondsByPid: Record<number, number>;
    isAliveByPid: Record<number, boolean>;   // NEW
    disconnectedByPid: Record<number, boolean>;
    ...
};
```

And initializer:
```ts
deployedByPid: {},
deployedAtSecondsByPid: {},
isAliveByPid: {},                            // NEW
disconnectedByPid: {},
```

Helper:
```ts
// Cache-based isAlive check. The cache is flipped to false by:
//   - OnPlayerUndeploy
//   - OnVehicleDestroyed (proactive, for the vehicle's popLastDriver victim)
//   - safeGetSoldierState* catch blocks (self-healing)
// Flipped to true by OnPlayerDeployed. Conquest port (CQ_Bug_37/38 cache-guard pattern).
function isPlayerAlive(player: mod.Player | null | undefined): boolean {
    if (!player) return false;
    const pid = safeGetPlayerId(player);
    if (pid === undefined) return false;
    return State.players.isAliveByPid[pid] === true;
}
```

## Why this is risk-free

- **Success path** (player genuinely alive): cache says true → guard passes → identical behavior. Same engine call as before.
- **Race window** (player just died, cache stale-true initially, then flipped by event/wrapper-catch): subsequent ticks see `isAliveByPid=false` and skip the engine call. **The first race tick still fires the engine log** — same residual as Conquest acknowledges in CQ_Bug_37/38. But **dramatic reduction** in frequency: instead of every tick continuously firing the error while the player is in the deploy screen, only the first tick after death fires it; the proactive flip in `OnVehicleDestroyed` closes the window for subsequent ticks immediately.
- **Most common Helis death scenario**: player's vehicle destroyed. `popLastDriver` returns the driver. The proactive flip happens in the same engine frame as the vehicle destruction. Subsequent per-tick reads are guarded.
- **Self-healing**: even if the cache is wrong for any reason, the safe wrapper's catch block updates it to false on engine throw. Cache converges to correct state automatically.
- **No new state mutations from per-tick paths**: cache writes happen only in event handlers (rare).
- **Disconnect cleanup**: cache deleted in `OnPlayerLeaveGame`. Same lifecycle as other per-pid caches.

## Performance

- **Per-tick cost added**: 1 cache read (`State.players.isAliveByPid[pid]`) at each of 5 guarded callsites. Pure JS object property access. ~O(1), nanoseconds.
- **Per-event cost**: 1 cache write at each mutation site. Negligible.
- **Net per-tick impact**: when the cache says true (normal case), one extra property read. When the cache says false (player undeployed), one extra property read PLUS skips the much more expensive engine call. Net: same or faster.
