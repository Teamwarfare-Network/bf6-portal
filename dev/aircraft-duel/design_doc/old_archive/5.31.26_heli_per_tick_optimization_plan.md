# Helis Per-Tick Optimization Plan

**Date**: 2026-05-31
**Goal**: Reduce baseline per-tick work in the main game loop and ancillary tick loops. Frees frame budget for concurrent-join headroom (defense-in-depth on top of Phases A+B lazy-load) and removes wasted iteration when nothing has changed.

**Scope**: Audit of every recurring `await mod.Wait(...)` loop and `OngoingPlayer` per-player work. Identify removable work (gated short-circuits), throttled work (rate-limited cache checks), and fusable work (single AllPlayers iteration instead of N).

**Not in scope**: Frame-budget instrumentation (separate work). Phase C registry routing (deferred).

## Findings (ordered by ROI)

### F1 — `syncKillsHudFromTrackedTotals` runs unconditionally every tick (HIGH ROI)

**Where**: `vehicles.ts:611`, called from `OnGameModeStarted` main loop with `false` arg.

**Problem**: Iterates AllPlayers + calls `setCounterText` × 2 per player every 1s — even when totals haven't changed (the common case). The `_force` parameter is unused. Compare to sibling `syncRoundKillsHud` (line 628) which DOES the early-return cache check using `lastHudRoundKillsT1/T2`.

State already allocates `State.hudCache.lastHudScoreT1/T2` (`state.ts:1067-1068`) for this exact purpose — but the cache check was never wired in.

**Fix**: Mirror `syncRoundKillsHud` pattern:
```ts
function syncKillsHudFromTrackedTotals(force: boolean): void {
    if (!force
        && State.hudCache.lastHudScoreT1 === State.scores.t1TotalKills
        && State.hudCache.lastHudScoreT2 === State.scores.t2TotalKills) return;
    State.hudCache.lastHudScoreT1 = State.scores.t1TotalKills;
    State.hudCache.lastHudScoreT2 = State.scores.t2TotalKills;
    // ... existing iteration
}
```
Rename `_force` → `force`. Update call sites that need force=true (e.g. admin panel kill adjustments).

**Effect**: Eliminates one AllPlayers iteration per second in the steady-state. At 8 players that's 8 `setCounterText` calls (16 with leftKills + rightKills) deduplicated per second when kills aren't changing.

**Risk**: Low. Pattern is identical to existing `syncRoundKillsHud`.

### F2 — `updateAllPlayersClock` toggles vehicles-alive visibility unconditionally (MEDIUM ROI)

**Where**: `clock.ts:166-183`.

**Problem**: `mod.SetUIWidgetVisible(refs.leftVehiclesAliveText, showVehiclesAlive)` + same for right are called every tick for every player. When `showVehiclesAlive` doesn't change tick-over-tick (the common case during a round), this is wasted engine work.

**Fix**: Track last-visible state, skip toggle when unchanged:
```ts
if (State.hudCache.lastVehiclesAliveVisible !== showVehiclesAlive) {
    // toggle widgets
    State.hudCache.lastVehiclesAliveVisible = showVehiclesAlive;
}
```
Also gate the inner `safeSetUITextLabel` calls behind a per-team last-count cache to skip same-value re-writes.

**Effect**: ~16 `mod.SetUIWidgetVisible` calls/sec eliminated when nothing changes. Per-team count writes also deduped.

**Risk**: Low. Pure-value caching with a single state field.

### F3 — `updateVictoryDialogForPlayer` called per-player every tick even when victory inactive (MEDIUM ROI)

**Where**: `clock.ts:162`, inside `updateAllPlayersClock`'s per-player loop.

**Problem**: Function early-returns on `!State.match.victoryDialogActive`, but the function call itself + pid resolution still runs N times per second. Cheap individually but stacked across 8 players × 1s = 8 wasted calls/sec.

**Fix**: Hoist the gate outside the per-player loop:
```ts
const showVictory = State.match.victoryDialogActive;
// ... existing AllPlayers loop ...
for (...) {
    // ...
    if (showVictory) updateVictoryDialogForPlayer(player, remaining);
}
```

**Effect**: Eliminates the 8 function-call-and-return-fast cycles per second when victory dialog isn't active (the vast majority of match time).

**Risk**: Minimal — defensive checks inside `updateVictoryDialogForPlayer` are unchanged, just moved one frame up.

### F4 — `runAircraftWarningLoop` iterates AllPlayers in vanilla mode just to tear down (MEDIUM ROI)

**Where**: `ready-dialog.ts:2625-2647`.

**Problem**: When `State.round.aircraftCeiling.customEnabled === false` (i.e. Vanilla mode + all maps that don't use custom ceilings), the loop still iterates AllPlayers at 5Hz to tear down altimeter widgets — but they're already torn down after the first iteration. Wasted iteration thereafter.

**Fix**: Add a "torn-down" sentinel that flips true after the tear-down completes; skip the AllPlayers iteration on subsequent ticks until `customEnabled` flips back to true.

```ts
let teardownDone = false;
// ... inside loop ...
if (!State.round.aircraftCeiling.customEnabled) {
    if (!teardownDone) {
        // ... existing teardown ...
        teardownDone = true;
    }
    continue;
}
teardownDone = false;  // reset on re-enable
```

**Effect**: In Vanilla mode, eliminates 5 AllPlayers iterations per second + 5× `safeGetPlayerId` + 5× setAltimeterVisible × N players. Significant relative to baseline.

**Risk**: Low. Sentinel reset on the enable-side branch makes the state self-correcting.

### F5 — Main loop fires 5× `mod.AllPlayers()` per tick (MEDIUM ROI, requires care)

**Where**: `index.ts:120-134`. Each of `updateAllPlayersClock`, `updateOvertimeStage`, `checkTakeoffLimitForAllPlayers`, `applyAutoReadyForAllPlayers`, `syncKillsHudFromTrackedTotals` calls `mod.AllPlayers()` independently.

**Problem**: `mod.AllPlayers()` is sandbox-bridged — non-trivial cost. 5 calls/sec when 1 would suffice.

**Fix**: Hoist AllPlayers to the outer loop, pass the array (or a cached per-tick `ActivePlayers` snapshot) into helpers:
```ts
while (true) {
    const tickPlayers = mod.AllPlayers();
    const tickCount = mod.CountOf(tickPlayers);
    updateAllPlayersClock(tickPlayers, tickCount);
    if (State.round.phase === RoundPhase.NotReady) {
        checkTakeoffLimitForAllPlayers(tickPlayers, tickCount);
        applyAutoReadyForAllPlayers(tickPlayers, tickCount);
    }
    // ...
    await mod.Wait(1.0);
}
```

**Effect**: 4× `mod.AllPlayers()` calls eliminated per second. Each helper still iterates the same array but the bridge call is shared.

**Risk**: Medium. Signature changes on 5 functions; need to ensure no callers pass stale arrays. Suggest doing this alongside an `ActivePlayers` snapshot type (we already have `getActivePlayers()` — could be the shared cache).

### F6 — Phase short-circuits in main loop (LOW-MEDIUM ROI)

**Where**: `index.ts:120-134`.

**Problem**: `updateOvertimeStage` and `checkTakeoffLimitForAllPlayers` both already short-circuit internally, but the function call overhead still occurs. Could hoist the round-phase check to the main loop to skip the call entirely.

**Fix**:
```ts
const phase = State.round.phase;
const cleanupActive = State.round.flow.cleanupActive;
if (phase === RoundPhase.NotReady && !cleanupActive) {
    checkTakeoffLimitForAllPlayers(tickPlayers, tickCount);
    applyAutoReadyForAllPlayers(tickPlayers, tickCount);
}
// updateOvertimeStage stays unconditional -- it manages stage transitions even pre-round
```

**Effect**: Marginal — saves 2 function calls/sec during round-live. Mostly cleanliness.

**Risk**: Low. Identical logic; just moves the gate up one level.

### F7 — `OngoingPlayer` UI warm-up still builds Ready Dialog eagerly (LOW ROI, philosophical)

**Where**: `index.ts:404-410`.

**Problem**: First `OngoingPlayer` tick per player calls `createTeamSwitchUI(eventPlayer)` then immediately `deleteTeamSwitchUI(eventPlayer)` (which is a hide-not-delete). This builds the entire ~600-line Ready Dialog widget tree per player shortly after join — defeating most of the lazy intent for that surface even though it's not in OPJG.

**Trade-off**: First triple-tap is instant. Without warm-up, first triple-tap pays ~50ms hitch.

**Fix options**:
- **Keep as-is**: warm-up doesn't break frame budget because OngoingPlayer ticks are per-player and naturally staggered.
- **Defer to first triple-tap**: removes the warm-up; first triple-tap is slower (~50ms hitch); subsequent opens cached.
- **Stagger warm-up across N ticks**: split the warm-up by phase (e.g. first tick = T1 container, second = T2 container, etc.).

**Recommendation**: Leave as-is. The warm-up doesn't cause crashes (per-player ticks are naturally spread). Removing it makes first-triple-tap feel laggy without measurable frame-budget benefit.

**Effect**: None if we leave it. Marginal if we defer.

## Sequencing recommendation

Ship as one bundle, one version bump:

1. **F1** (syncKills cache check) — wire the existing unused state. Single-function fix.
2. **F2** (vehicles-alive visibility cache) — single-function fix.
3. **F3** (hoist victory gate in updateAllPlayersClock) — single-function fix.
4. **F4** (aircraft loop teardown sentinel) — single-function fix.

Skip F5 + F6 in this bundle (signature changes; merit separate review). Skip F7 (philosophical).

**Estimated total LoC delta**: +30, -10 net. Single version bump (e.g. v0.692).

**Risk**: All four are pure caching/gating; no behavior changes. Validation: run a round, observe HUD updates correctly when scores change (positive test) and when nothing changes (no visible churn).
