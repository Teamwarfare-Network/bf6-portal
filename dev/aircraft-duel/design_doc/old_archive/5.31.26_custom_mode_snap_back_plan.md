# Snap-Back from Custom to Preset When Knobs Revert

**Date**: 2026-05-31
**Status**: DIAGNOSED, plan ready
**Severity**: Low — cosmetic UX issue, misleading label. Functionally everything works (Confirm correctly applies the actual values regardless of label).

---

## 1. Diagnosis (confirmed)

### The bug

User flow:
1. Select "Helis Only - TWL 2v2" preset → all knobs set to TWL 2v2 defaults → label shows "Helis Only - TWL 2v2"
2. Edit a knob (e.g., Vehicle HP 130% → 150%) → label flips to "Helis Only - Custom" (correct — values diverged)
3. Edit the knob BACK to the preset value (150% → 130%) → **label STILL says "Custom"** even though all values now match TWL 2v2

### Root cause

[ready-dialog.ts:3098](bf6-portal/dev/helis-only/src/ready-dialog.ts#L3098) — `ensureCustomGameModeForManualChange()` is **one-way**:

```ts
function ensureCustomGameModeForManualChange(): void {
    if (suppressReadyDialogModeAutoSwitch) return;
    if (State.round.modeConfig.gameModeIndex === READY_DIALOG_GAME_MODE_CUSTOM_INDEX) return;  // <-- early return if already Custom
    // ... flip to Custom ...
}
```

Called from every knob setter (`setReadyDialogGameModeIndex`, `setReadyDialogVehicleHealthMultiplier`, `setReadyDialogVehicleIndexT1`, ceiling +/-, ceiling override toggle, matchup +/-, player count +/-, best-of +/-). All 8+ call sites flip TO Custom on divergence; **none of them ever flip BACK** to a preset on convergence.

### Conquest comparison

Conquest has the **identical** pattern in [conquest/src/ready-dialog/mode-config-presets.ts:112](bf6-portal/dev/conquest/src/ready-dialog/mode-config-presets.ts#L112). Conquest also has no snap-back. Worth noting: user's hypothesis ("Conquest has this somewhere") doesn't match the code — Conquest behaves the same way (sticky Custom).

`isReadyDialogModePresetActive(gameModeKey)` exists in both codebases ([ready-dialog.ts:3116](bf6-portal/dev/helis-only/src/ready-dialog.ts#L3116)) — it's the right tool for the job. Today it's only used inside `confirmReadyDialogModeConfig` for the OPPOSITE direction: when user confirms with diverged values from a preset, force-flip to Custom. It's never used proactively to detect convergence back to a preset.

### Functional impact

- **Visual only.** The label says "Custom" but the actual values are what they are. Confirm applies them correctly. Vehicle spawns get the right HP. Rounds play correctly.
- **UX cost**: confusing to players ("why does it say Custom when nothing's changed from TWL 2v2?"). May discourage adjusting knobs ("if I touch this I'll be in Custom forever").
- **Dirty-state interaction (v0.703 work)**: the dirty-state RED highlighting on values correctly turns back to GREEN when the user reverts a value (because dirty compares pending vs confirmed, not vs preset). So the values look "clean" (green) while the game mode label still says "Custom" — visually inconsistent.

## 2. The fix

### Approach

Add a complement helper `detectAndApplyMatchingPreset()` that:
1. Returns early if current mode is NOT Custom (nothing to revert).
2. Iterates non-Custom preset keys (TWL 2v2, TWL 1v1, Vanilla Practice).
3. For each, calls existing `isReadyDialogModePresetActive(modeKey)`.
4. If any returns true → flip `gameModeIndex` + `gameMode` to that key.
5. If none match → stay Custom.

```ts
// New helper. Mirrors ensureCustomGameModeForManualChange's role but in the opposite direction.
function detectAndApplyMatchingPreset(): void {
    if (suppressReadyDialogModeAutoSwitch) return;
    if (State.round.modeConfig.gameModeIndex !== READY_DIALOG_GAME_MODE_CUSTOM_INDEX) return;

    // Iterate non-Custom presets and snap-back to any that matches current pending values.
    for (let i = 0; i < READY_DIALOG_GAME_MODE_OPTIONS.length; i++) {
        if (i === READY_DIALOG_GAME_MODE_CUSTOM_INDEX) continue;
        const modeKey = READY_DIALOG_GAME_MODE_OPTIONS[i];
        if (isReadyDialogModePresetActive(modeKey)) {
            State.round.modeConfig.gameModeIndex = i;
            State.round.modeConfig.gameMode = modeKey;
            return;  // first match wins (presets shouldn't overlap; see edge case below)
        }
    }
}
```

### Call sites

Two options for where to invoke:

**Option A — call from each knob setter** (parallel to `ensureCustomGameModeForManualChange`):
```ts
function setReadyDialogVehicleHealthMultiplier(clamped: number): void {
    ensureCustomGameModeForManualChange();
    State.round.modeConfig.vehicleHealthMultiplier = Math.round(clamped * 100) / 100;
    detectAndApplyMatchingPreset();  // <-- NEW: try to snap back if value matches a preset
    updateReadyDialogModeConfigForAllVisibleViewers();
}
```

Pro: explicit, every setter has the same shape.
Con: 8+ setters need the call added. Easy to miss future ones.

**Option B — call once from `updateReadyDialogModeConfigForAllVisibleViewers`** (the centralized refresh function called after every change):
```ts
function updateReadyDialogModeConfigForAllVisibleViewers(): void {
    detectAndApplyMatchingPreset();  // <-- NEW: check before rendering
    for (const pidStr in State.players.teamSwitchData) {
        // ... existing per-pid render loop ...
    }
}
```

Pro: one call site, automatically covers any future knob setter that calls `updateReadyDialogModeConfigForAllVisibleViewers`.
Con: slightly indirect — the snap-back happens during a "refresh" rather than at the mutation. State briefly inconsistent between knob change and refresh, but updates happen synchronously so observers never see the in-between.

**Recommendation: Option B.** Single source of truth, future-proof, matches the existing pattern of "knob setter mutates state, refresh function rebuilds derived view." Snap-back logic is derived view, not state mutation.

### Edge cases

1. **Multiple presets matching simultaneously.** Could TWL 2v2 and TWL 1v1 ever have the same values such that both pass `isReadyDialogModePresetActive`? Looking at the existing check ([ready-dialog.ts:3116](bf6-portal/dev/helis-only/src/ready-dialog.ts#L3116)), `autoStartMinActivePlayers` is per-mode (TWL 2v2 = 2, TWL 1v1 = 1) — so these two presets cannot match the same pending state. Similar player-count differentiation between Vanilla/TWL presets. **Practical risk: very low.** The "first match wins" loop guarantees deterministic behavior.

2. **`suppressReadyDialogModeAutoSwitch` flag**. This flag exists specifically to prevent the auto-switch from firing during `applyReadyDialogModePresetForGameMode` (when we're intentionally setting all knobs to preset values atomically). The new helper must respect this flag the same way `ensureCustomGameModeForManualChange` does. **Already in the proposed code (line 3 of the helper).**

3. **Dirty-state interaction**. The dirty-state check (`buildReadyDialogModeConfigDiffState`) compares pending vs `confirmed`, not vs preset. So:
   - User on TWL 2v2 (confirmed). Edit HP 130→150 (pending diverges, flip to Custom, dirty=true, value RED).
   - User edits HP 150→130 (pending matches confirmed again, dirty=false, value GREEN, **snap back to TWL 2v2**).
   - Both signals (label, color) now agree.

4. **User edits knob → flips to Custom → restarts/resets**. The Restart button calls `triggerFreshRoundSetup` which doesn't reset modeConfig values. Pending stays where user left it. Confirmed stays at whatever was last confirmed. New snap-back logic runs on next refresh — if user reverted the knob before pressing restart, snap-back applies; otherwise stays Custom. Correct behavior.

5. **`confirmReadyDialogModeConfig` interaction**. Confirm runs `updateReadyDialogModeConfigForAllVisibleViewers` via its callers. After Confirm, gameModeIndex either stays preset or got force-flipped to Custom by the existing diverged-value guard at line 3251. The new snap-back check runs but is a no-op when not Custom. **No conflict.**

## 3. Sequencing

- **v0.715 ship**: ~25 LoC across two files (the helper in ready-dialog.ts + one call in updateReadyDialogModeConfigForAllVisibleViewers). Low risk, no signature changes, no state shape changes.

### Test plan (one line per test)

1. TWL 2v2 → edit HP 130→150 → label shows "Custom", value RED. (Regression: confirm existing behavior unchanged.)
2. From state #1 → edit HP back to 130 → label snaps to "TWL 2v2", value GREEN.
3. TWL 2v2 → edit best-of 3→5 → label "Custom" → edit best-of back to 3 → label snaps back.
4. Vanilla Practice → edit ceiling override → label "Custom" → edit back to map default → label snaps back to "Vanilla Practice".
5. Multi-knob revert: edit HP + ceiling, then revert ONE of them → stays "Custom" (other knob still diverged). Revert the other → snaps back.
6. Confirm with diverged values → confirm-time force-flip to Custom still works (no regression on line 3251 path).

## 4. Risks

- **None functional.** Pure UI label correctness. Confirm semantics, vehicle HP application, scoring — all unchanged.
- **One minor risk**: if `READY_DIALOG_GAME_MODE_OPTIONS` order ever changes and the Custom index is no longer at `READY_DIALOG_GAME_MODE_CUSTOM_INDEX`, the iteration's `continue` would skip the wrong entry. Already true of the existing `ensureCustomGameModeForManualChange`, so not new exposure. Defensible.

---

## 5. What this does NOT do

- Does not add new state fields.
- Does not change Confirm semantics.
- Does not touch the dirty-state RED/GREEN coloring (that's already correct — compares pending vs confirmed, not vs preset).
- Does not change the existing one-way `ensureCustomGameModeForManualChange` — keeps it as-is. The new helper is the complement.
- Does not modify `applyReadyDialogModePresetForGameMode` — preset application path unchanged.
