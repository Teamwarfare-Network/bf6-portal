# Plan A3: Drop Empty-Slot RemoveEquipment Calls in OnPlayerDeployed

**Status**: Approved 2026-05-27 (pending execution).
**Scope**: Delete the 2 `mod.RemoveEquipment` calls in `OnPlayerDeployed`. Wrap the 2 `mod.AddEquipment` calls in try/catch. Conquest v1.448 finding.

> First action per [`AGENTS.md`](../AGENTS.md): read [`AGENTS.md`](../AGENTS.md) and [`design_doc/heli_issues_design.md`](./heli_issues_design.md) Section 0.2.b.

---

## Context

Reported runtime error: **"Received undefined values as arguments"** — 2 instances at the beginning of the game (first deploy). Plan A1 (v0.632 roster-validity guard) closed the roster-render source but the 2-instance variant remained, indicating a different source firing twice.

Root cause (identified 2026-05-27): [src/index.ts:332-343](../src/index.ts#L332) `OnPlayerDeployed` calls `mod.RemoveEquipment` twice on the GadgetOne and GadgetTwo slots before `mod.AddEquipment`. On a fresh player's first deploy, those slots are empty. Calling `RemoveEquipment` on an empty slot generates an engine error log (Conquest #84 v1.341 documented this exact pattern as the source of "RemoveEquipment JS Error"; the engine has since generalized the message to "Received undefined values as arguments").

The "2 instances" exactly matches the 2 RemoveEquipment calls.

## Conquest reference pattern

Verified 2026-05-27.

**v1.341 (#84) initial fix**: gate every slot-based `RemoveEquipment` behind an `isSlotEmpty` precheck.

**v1.448 (#94 follow-up) refined fix**, per [conquest/src/Changelog.ts:65](../../conquest/src/Changelog.ts#L65):
> drop isSlotEmpty + slot-targeted RemoveEquipment from non-Engineer give helpers (giveMedicSmoke, giveAssaultItem, giveReconItem). isSlotEmpty was the remaining GetInventoryAmmo source on placement paths. **AddEquipment clobbers cleanly**. Dup prevention via HasEquipment + lockerSlots gray-out remains.

Conquest's current pattern at [conquest/src/interaction/ammo-resupply-menu.ts:1297-1301](../../conquest/src/interaction/ammo-resupply-menu.ts#L1297):
```ts
try {
    mod.AddEquipment(eventPlayer, gadget, targetSlot);
} catch {
    return false;
}
```

For Helis's case — every deploy gets 2x Supply Crate, no swap logic — the simplest Conquest-aligned port is to delete the RemoveEquipment calls entirely and wrap AddEquipment in try/catch.

## The diff

[src/index.ts:331-343](../src/index.ts#L331):

```ts
// BEFORE
    //Remove existing gadgets and give deployable vehicle supply crates
    mod.RemoveEquipment(eventPlayer, mod.InventorySlots.GadgetOne);
    mod.RemoveEquipment(eventPlayer, mod.InventorySlots.GadgetTwo);
    mod.AddEquipment(
        eventPlayer,
        mod.Gadgets.Deployable_Vehicle_Supply_Crate,
        mod.InventorySlots.GadgetOne
    );
    mod.AddEquipment(
        eventPlayer,
        mod.Gadgets.Deployable_Vehicle_Supply_Crate,
        mod.InventorySlots.GadgetTwo
    );

// AFTER
    // AddEquipment clobbers cleanly without a prior RemoveEquipment (Conquest v1.448 / #94 finding);
    // skipping the RemoveEquipment calls eliminates "Received undefined values" engine error logs
    // on empty gadget slots at first deploy. try/catch wraps mirror Conquest's pattern at
    // ammo-resupply-menu.ts:1297-1301 to absorb engine transients.
    try {
        mod.AddEquipment(
            eventPlayer,
            mod.Gadgets.Deployable_Vehicle_Supply_Crate,
            mod.InventorySlots.GadgetOne
        );
    } catch {}
    try {
        mod.AddEquipment(
            eventPlayer,
            mod.Gadgets.Deployable_Vehicle_Supply_Crate,
            mod.InventorySlots.GadgetTwo
        );
    } catch {}
```

## Why this is risk-free

- **End state identical**: both gadget slots end up with `Deployable_Vehicle_Supply_Crate`. AddEquipment replaces whatever was previously in the slot.
- **Empty-slot first-deploy path**: previously fired 2 engine error logs (the bug). Now: AddEquipment populates each slot; no error.
- **Occupied-slot redeploy path** (player redeploys with existing gadgets): previously fired RemoveEquipment (worked) then AddEquipment. Now: AddEquipment alone clobbers the existing gadget. Same end state.
- **No new state, no new constants, no new imports.**

## Performance

- **Per-deploy work**: 2 fewer engine calls (`mod.RemoveEquipment` × 2).
- **Per-tick work**: unchanged. This is event-driven (fires only on deploy), not in any loop.
- **Bundle**: net flat-to-slightly-negative. Removes 2 statements, adds 2 try/catch wraps + comment.
