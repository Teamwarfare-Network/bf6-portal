# Conquest Spectator Cam — Ship 4 Plan: Exit Mechanism

**Date:** 2026-05-08
**Baseline:** v1.485 (Ship 3 free-cam shipped + sprint=35 tuned)
**Goal:** Spectator can exit back to "normal player" state via triple-tap interact, with no dialog. After exit: body returns to deploy flow on foot, camera restored to FirstPerson, COACH button re-enables, they can re-claim using the same flow as before.

---

## Trigger Choice — Triple-Tap Interact (Recommended)

The user offered two options: **(a)** detect Reload key press, **(b)** triple-tap interact. SDK research findings ([reference_sdk_1.2.3](../../reference_sdk_1.2.3)):

| Option | Verdict | Reason |
|---|---|---|
| Triple-tap interact | **Use this** | Reuses the existing `InteractMultiClickDetector` ([utils/multi-click.ts:8-48](../src/utils/multi-click.ts#L8-L48)). Polls `mod.SoldierStateBool.IsInteracting` transitions — agnostic to `EnableInputRestriction` (it tracks state, not events). Same pattern users already know from ready-up. 2s window, 3 clicks. |
| Reload key press | Reject | No `OnPlayerReload` engine event. No `IsAttemptingToReload` SoldierStateBool. `IsReloading` is the animation state — with `RestrictedInputs.Reload` locked, the animation may never play, so the bool may never flip. Risky without an empirical SDK test. |

**Required prep before triple-tap can work:** **REMOVE `Interact` from `SPECTATOR_LOCKED_INPUTS`** ([spectator-action.ts:34-48](../src/spectator/spectator-action.ts#L34-L48), currently 13 locked inputs). The body is sealed in a 5mm cube at Y=-500 with no `InteractPoint` authoring in range — releasing Interact has no downside in the hide room, and guarantees the detector's `IsInteracting` poll sees clean state transitions. New lock count: 12.

### Step 2 — Add `exitSpectatorMode(player, pid)` function
File: [src/spectator/spectator-action.ts](../src/spectator/spectator-action.ts) (new function near `enterSpectatorMode`)

Mirror of `enterSpectatorMode`, in reverse order:

```ts
function exitSpectatorMode(eventPlayer: mod.Player, pid: number): void {
    if (State.players.spectatorPid !== pid) return;        // defensive idempotency

    // Cancel free-cam loop within one tick.
    _spectatorFreeCameraLoopToken += 1;

    // Tear down hide-room geometry.
    despawnSpectatorHideRoom();

    // Restore camera + release input lock. Order: input release first so the
    // soldier can act on the FirstPerson view immediately after the swap.
    applySpectatorInputLock(eventPlayer, false);
    try { mod.SetCameraTypeForPlayer(eventPlayer, mod.Cameras.FirstPerson); } catch (e) {
        try { console.log(`[spectator] exit camera reset threw for pid=${pid}: ${String(e)}`); } catch {}
    }

    // Clear the slot before the broadcast refresh so every viewer sees vacant.
    State.players.spectatorPid = null;
    markHudDirty();

    // Send body back to deploy screen so they re-enter the match on foot.
    try { mod.UndeployPlayer(eventPlayer); } catch (e) {
        try { console.log(`[spectator] exit UndeployPlayer threw for pid=${pid}: ${String(e)}`); } catch {}
    }

    // Broadcast self-confirm + world-log.
    sendHighlightedWorldLogMessage(
        mod.Message(STR_PLAYER_STOPPED_SPECTATING, eventPlayer),
        true,
        undefined,
        STR_PLAYER_STOPPED_SPECTATING
    );
    try { mod.DisplayNotificationMessage(mod.Message(STR_PLAYER_STOPPED_SPECTATING, eventPlayer), eventPlayer); } catch {}

    // Refresh fan-out re-enables the COACH button on every viewer's panel + dialog.
    refreshAllVisiblePlayerReadyPanels();
    renderReadyDialogForAllVisibleViewers();
    updatePlayersReadyHudTextForAllPlayers();
}
```

### Step 3 — Wire triple-tap detection in ongoingPlayerImpl
File: [src/index/player-loop-inputs.ts:3-8](../src/index/player-loop-inputs.ts#L3-L8)

Add an early check before the existing ready-dialog dispatch:

```ts
function ongoingPlayerImpl(eventPlayer: mod.Player): void {
    if (!isValidPlayer(eventPlayer)) return;
    if (!isPlayerDeployed(eventPlayer)) return;

    // Spectator triple-tap exit. Must run BEFORE the ready-dialog dispatch so a
    // spectator's triple-tap routes to exitSpectatorMode instead of spawning a
    // ReadyDialogInteractPoint on their (sealed-in-cube) location.
    const pid = safeGetPlayerId(eventPlayer);
    if (pid !== undefined && isSpectator(pid)) {
        if (InteractMultiClickDetector.checkMultiClick(eventPlayer)) {
            exitSpectatorMode(eventPlayer, pid);
        }
        return;
    }

    checkReadyDialogInteractPointRemoval(eventPlayer);
    if (InteractMultiClickDetector.checkMultiClick(eventPlayer)) spawnReadyDialogInteractPoint(eventPlayer);
}
```

## Edge Cases

| Case | Behavior |
|---|---|
| Triple-tap during exit transition | The detector keeps per-pid state in `STATES[playerId]`; on exit, the click counter resets to 0 organically. A re-claim via COACH starts a fresh detector counter on next tick. No glitch. |
| Exit during pregame countdown | Harmless. Player stays ready (`readyByPid[pid] === true` unchanged) → countdown continues. They pop to deploy screen and can claim back, or deploy normally and play. |
| Exit while match-end is pending | `onSpectatorMatchEnd` is idempotent. If exit + match-end fire same-tick, the second is a no-op due to `if (State.players.spectatorPid !== pid) return`. |
| Exit while disconnect is pending | Same idempotency guard. `onSpectatorPlayerLeave` runs after disconnect; exit is no-op if the slot is already cleared. |
| Triple-tap with no slot owner (defensive) | The `isSpectator(pid)` gate filters this out before the detector even runs. |
| `UndeployPlayer` fails or is a no-op | try/catch logs but doesn't crash. Body remains at Y=-500 inside despawned-room space (now empty). User can be told to use admin reset; or we add a Teleport-to-HQ fallback in a follow-up. |

- **HUD discoverability hint** ("Triple-tap interact to exit"). Could be a per-pid text widget while in spectator mode. Ship 4b polish if user wants discoverability — defer for now (the user already knows the triple-tap pattern from ready-up).
- **Re-claim cooldown.** None needed. Immediate re-claim is acceptable.

## Risks

| # | Risk | Likelihood | Mitigation |
|---|---|---|---|
| R1 | `IsInteracting` doesn't flip if Interact is implicitly suppressed by some other engine state | Low (detector works in pre-live ready-up flow today) | Step 1 explicitly removes Interact from the lock list; SP smoke (gate 4) catches this. |
| R2 | `UndeployPlayer` no-ops or throws | Low | try/catch wraps the call. Fallback path (Teleport-to-HQ) deferred unless this fires. |
| R3 | Triple-tap false positive during normal spectate use | Very Low | 3 clicks in 2s is the same threshold ready-up uses; battle-tested. Spectator use case (camera flying) doesn't involve interact attempts. |
| R4 | Free-cam loop doesn't bail on token bump | Very Low | `if (_spectatorFreeCameraLoopToken !== token) return;` ([spectator-action.ts:326](../src/spectator/spectator-action.ts#L326)) is the existing pattern, already verified working at v1.482. |
