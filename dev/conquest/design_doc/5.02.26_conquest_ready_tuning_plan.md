## Context

**The bug.** Today, a player who clicks READY in the pre-game Player Ready Up Panel (or full Ready Dialog) gets auto-unreadied by *several* gameplay events the user did not intend. Specifically:

- **Death + respawn** clears their ready state (annoying — they have to re-click after every death).
- **Walking out of their main base pre-live** clears their ready state (annoying — they can't even walk around their HQ without losing ready status).

**The fix.** Reduce auto-unready triggers to exactly **two**:

1. **Team switch** (clicking SWAP TEAMS — preserved).
2. **Admin changes match configuration** (every other ready player gets auto-unreadied + the admin themselves on APPLY — preserved).

Everything else that currently auto-unreadies the player should stop. Players keep their READY state through deaths and through wandering in/out of HQ.

**What this change does NOT touch.** The vehicle deploy timer HUD (M1 cache) and any deploy-cooldown logic. The "deploy" word in this plan refers exclusively to the engine event `OnPlayerDeployed` — the callback BF6 fires when a player's character spawns into the world. It is *not* the vehicle deploy timer. Two unrelated systems share the word.

**Conversation history caveat.** A prior implementation attempt scoped too broadly (touching deploy paths) without explicit user confirmation and was reverted. The user re-clarified the rule (only team-switch + admin-config-change). This plan provides a complete itemised inventory so nothing is missed and the scope is unambiguous before any code is touched.

## Scope clarification on Site #9 (the deploy-event clear)

The engine event `OnPlayerDeployed` fires for **every** body-into-world event, not just respawn-after-death. After this change:

- **Respawn after death (pre-live or live)** → no longer auto-unreadies. ✓ Matches user intent ("through death").
- **Initial spawn into world** (after triple-tap-ready completes the deploy chain) → no longer auto-unreadies. The previous clear was overwriting the just-set `true` flag, so removing it is the right behaviour.
- **HQ Deploy / Forward Deploy / Air Deploy** → these are LIVE-game features. Ready state during a LIVE match is read-only (the match is already running, the gate already passed); whether the flag is true or false is cosmetic at that point. No functional impact.
- **Lifecycle phase transition** → verified by exploration: match-start does NOT force-redeploy already-deployed players. The bulk reset at Site #6 (`resetReadyStateForAllPlayers`) handles fresh-cycle resets independently. Removing Site #9 does not break the reset path.

**Bottom line:** removing Site #9 affects only pre-live behaviour in any meaningful way, and that effect is exactly what the user asked for — the "death-respawn unreadies you" path goes away.

## Edge Cases Considered

1. **`readyNeedsReconfirmByPid` field stays alive.** Two writers remain (`requireReadyReconfirmAfterConfigChange`, `forceUnreadyApplierAfterConfirm`); one reader (`roster-render.ts:217`) drives the ready-toggle button visual that warns the player they need to re-confirm post config change. All behaviour intact.
2. **Pre-live "X / Y players ready" HUD count.** Removing Sites #9 and #10 means a player who readies up and then dies/respawns/wanders out of HQ stays counted in the ready total. Matches user intent.
3. **Match-start auto-start gate.** Auto-start fires when N players are ready; players who stay ready through pre-live shenanigans stay counted, so the gate may now trip at moments it didn't before (e.g. a ready player wanders out of HQ — gate still considers them ready). Per user intent.
4. **Boundary kill at LIVE start.** A player who readies up but is outside the HQ when LIVE begins still gets boundary-killed by the live-phase enforcement (separate code path, untouched). They just won't have been pre-emptively unreadied by wandering out.
5. **Rejoin / reconnect.** Rejoining player's `readyByPid[pid]` is `undefined` from the leave-cleanup; they show as not-ready and can re-click. Untouched.

## Verification

### SP smoke (run before MP)

1. **Cold launch + triple-tap ready + die** → player should remain READY after respawn. Pre-fix would have shown them as NOT READY.
2. **Cold launch + triple-tap ready + walk out of HQ + walk back** → player remains READY throughout. Pre-fix they'd have been NOT READY the moment they crossed the trigger.
3. **Cold launch + triple-tap ready + click SWAP TEAMS** → player flips to NOT READY. (Site #3 still works.)
4. **Cold launch + triple-tap ready + admin opens dialog and changes vehicle config + clicks APPLY** → every ready player including the admin themselves shows NOT READY with the reconfirm warning visible. (Sites #4 + #5 still work.)
5. **Cold launch + triple-tap ready + click NOT READY explicitly** → flips to NOT READY. (Sites #1/#2 still work.)
6. **Cold launch + ready up enough players to trigger LIVE start, then RESET via admin** → all players go to NOT READY at fresh-cycle start. (Site #6 still works.)
7. **Bot disconnect mid-match** → no crash, no orphan widgets, no stuck ready state.
