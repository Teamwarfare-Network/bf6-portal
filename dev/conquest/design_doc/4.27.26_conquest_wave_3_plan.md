## Context

### Why this matters

Per [`conquest_optimization_analysis.md`](./conquest_optimization_analysis.md) "Why memory, not bytes": the **binding constraint flipped from CPU frame budget to runtime JS heap**. The current architecture (`prebuildAllUiFamiliesHidden` warming Combat HUD + Vehicle Deploy Timer + Ready Dialog + top HUD shell + Gadget Locker for *every* player on join, then revealing on gate release) was the right answer when CPU was the budget — eliminating cold first-open hitches that breached the 1000ms eval limit (`CQ_Bug_30`, `CQ_Bug_40`). It's the wrong answer now because every prebuilt-and-hidden UI per player is paid in retained heap from join to disconnect.

Wave 3 is the architectural reversal: **build on demand, accept controlled hitches, free heap**.

### What "lazy-load" means in this codebase

Today: every UI surface is built hidden during the warm-prime, indexed in `State.hudCache.*`, revealed on gate release.

After: each UI surface is built *the first time it's needed* (interaction trigger, deploy event, first dirty render — depends on the surface), held while in use, optionally torn down when the use window closes.

### What "loading-gate removal" means

Today: [`src/interaction/actions.ts`](../src/interaction/actions.ts) (763 lines) orchestrates a per-player state machine: `beginLoadingGate` → `prebuildAllUiFamiliesHidden` → `runLoadingGateUntilReady` → `revealAllUiFamilies` → `releaseLoadingGate`. The gate owns deploy authorization (`mod.EnablePlayerDeploy`), input mode (`mod.EnableAllInputRestrictions`), and the loading overlay. ~30+ per-pid state fields in `interaction/hud-warm-state.ts` track gate phases.

After: most of that goes away. Deploy authorization becomes simpler (just check disconnect state + match phase). Input mode becomes per-UI-surface (the menu opens, it grabs input; menu closes, it releases). The loading overlay becomes optional or trivial.

### What's NOT changing

- Per-PID UI scope. Locked rule. The interactivity + responsivity reasons hold.
- Dirty-flag HUD contract. Locked rule. Combat HUD render still gates on `markHudDirty()`.
- The two leak fixes from Wave 1 stay. The phase-prefix renames from Wave 2 stay.
- Ready Dialog admin model (Wave 4) — that's a separate stack. Wave 3 may or may not move the Ready Dialog to lazy build; depends on Q4 below.

### Q1: How aggressive is the rip-out?

**Options:**

- **A) Hard cut** — single coherent commit / single bumpVersion. Delete `prebuildAllUiFamiliesHidden`, delete `runLoadingGateUntilReady`, delete the warm-prime sequencing. Replace each prebuild call with the corresponding "build on demand" trigger. Big diff, atomic, easier to reason about end-state but harder to bisect if something breaks.
- **B) Soft cut** — leave the gate machinery in place but neuter prebuild. `prebuildAllUiFamiliesHidden` becomes a no-op (or near-no-op). The release path still fires but doesn't build anything. Lazy paths are added incrementally. Cleanup pass removes the dead gate later.
- **C) Incremental, per-UI** — keep gate machinery; pull one UI surface at a time out of prebuild and into lazy build. Test SP gate between each. Slower but each step is independently revertable.

**AI's first-pass recommendation:** **B (soft cut)**. Reasoning:
- Hard cut (A) is a one-shot bet on getting hitch mitigation right; if first-open hitches manifest, we have no easy bisect to find which UI surface caused them.
- Incremental (C) is the safest but slowest, and the gate's complexity is itself a bug source (it's a 763-line orchestrator with ~30 per-pid state fields). Leaving it alive across multiple shipped versions delays the heap reclaim.
- Soft cut (B) gets the heap reclaim immediately (prebuild is now a no-op = no per-pid widget allocation at warm-time), preserves the gate's release-authority machinery as a safety net during transition, and queues the gate's deletion as a follow-on cleanup once we're confident.

### Q2: What's the player-facing acceptable first-open hitch budget?

When a player first interacts with a lazy-built UI (e.g. opens the Supply Box, or first deploy spawns the Vehicle Deploy Timer), there will be a measurable build hitch. How long is acceptable before we engineer it down?

**Options:**

- **<50ms** — invisible to players. Effectively requires we keep some prebuild for the largest UIs (Vehicle Deploy Timer, Supply Box, Combat HUD).
- **50–150ms** — a perceptible but not disruptive pause. Most lazy builds will fit if we yield-point them across 1–2 frames.
- **150–500ms** — visible but tolerable for a one-time menu open. Per-build yield points needed only for the heaviest UIs.
- **500ms+** — only acceptable if we show a "Loading…" indicator on the affected surface during the build.

**AI's first-pass recommendation:** **150–500ms ceiling for menus** (Supply Box, Ready Dialog, settings); **<50ms for tactical UI** (Combat HUD, Vehicle Deploy Timer). Reasoning: tactical UI is in the player's combat path and any hitch is felt. Menus open at the player's choice and a moderate delay is industry-standard.

### Q3: What happens if a player triggers an interactive UI build *during* the build?

Edge case: Player presses E to open Supply Box, build starts, mid-build they press E again (or click a button on the half-built menu). Today the prebuild is fully hidden so this doesn't happen. Lazy build introduces this race.

**Options:**

- **A) Per-UI build lock.** While the UI is building, ignore further open requests and clicks. The lock releases when the build completes.
- **B) "Loading…" placeholder.** Show a minimal placeholder during the build; the placeholder has no interactive elements. Replaced when the real build finishes.
- **C) Atomic build.** Run the entire UI build inside a single synchronous frame even if it costs the hitch budget. Lock-free but trades against Q2.

**AI's first-pass recommendation:** **A (per-UI build lock)** as the default, with **B (placeholder)** for any UI whose build exceeds the Q2 budget. The build lock matches the existing `_prebuildBusy` lock pattern from `CQ_Bug_40`, just narrowed in scope.

### Q5: What does "loading" look like to a player after the gate is gone?

Today players see a full-screen loading overlay while the gate runs. After lazy-load, there's no warm phase to show.

**Options:**

- **A) No loading screen at all.** Player joins, immediately sees deploy screen, presses deploy, lazy paths build during the deploy → spawn frames.
- **B) Brief minimal loading screen** — 1–2 seconds while critical UI surfaces (Combat HUD, top HUD shell) build, then dismiss. Exists to mask the largest first-build hitches without being a multi-second wait.
- **C) Per-surface "Loading…" indicators** — no global overlay; each lazy UI shows its own placeholder during build.

**AI's first-pass recommendation:** **B** with a 2-second cap. The Combat HUD has to be ready before the player is in the world (otherwise tickets/flags are invisible during their first life), so SOMETHING has to build pre-deploy. A brief overlay during that build is honest UX and avoids the "deploy and see a half-built HUD pop in" problem.

### Q6: Late-joiner cold-open — acceptable?

A player who joins mid-LIVE today gets the warm-prime sequence (long), then drops into a fully-rendered match. After lazy-load they get the new flow, whatever Q5 lands on.

**Question:** are there any *additional* loading affordances for late-joiners specifically, or is it the same flow as initial join?

**Options:**

- **A) Same flow** — late-joiners get the same Q5 experience as initial joiners.
- **B) Extra grace** — late-joiners get a slightly longer "Catching up..." overlay so the first deploy doesn't feel like a cold drop.
- **C) Auto-deploy** — late-joiner is auto-deployed after their lazy UIs build, skipping the deploy screen.

**AI's first-pass recommendation:** **A**. Simpler is better. If the deploy-screen experience is fast (Q5 = B), late-joiners are fine.

### Q7: Team swap — what happens to per-PID UI?

Today team swap goes through `runTeamSwapLoadingGate` — destroys per-pid HUD, runs gate again, prebuild + reveal in the new team perspective.

**Options:**

- **A) Swap = lazy rebuild** — destroy current HUD on swap, lazy paths rebuild on next deploy. Same hitch budget as initial join.
- **B) In-place perspective flip** — keep the widget tree, swap the team coloring / data without destroying widgets. No build hitch but more code per surface (every render path needs a perspective-flip helper).
- **C) Brief rebuild overlay** — show a short "Switching teams..." overlay during the rebuild. Hides the hitch.

**AI's first-pass recommendation:** **A**. Team swap is a deliberate user action; a brief hitch during rebuild is acceptable. Option B is more work for less gain.

### Q8: Hitch mitigation — engineering details

Once Q1–Q7 are decided, these are engineering questions for the AI to take a position on (not strict user decisions, but flag if you want to weigh in):

#### Q8a: Yield points inside heavy builds

Heavy UI builds (Combat HUD entry graph, Vehicle Deploy Timer cache, Ready Dialog, Supply Box) issue dozens-to-hundreds of `mod.AddUIContainer` / `mod.AddUIText` / `mod.AddUIImage` calls. To stay under the Q2 hitch budget for the largest surfaces, the build path can yield to the engine between groups of calls.

**Mechanism:** insert `await mod.Wait(0)` (or `Timers.setTimeout(..., 0)`) between sub-builds. Lets the engine tick a frame between batches.

**AI position:** Implement yield points only for surfaces where measured build time exceeds 80% of the Q2 budget. Don't pre-emptively yield everywhere — yields turn synchronous code into async, complicating call-site contracts.

**User notes (override / additional concerns):**
*[ ]*

#### Q8b: Concurrent-open serialization

When multiple players join in the same frame, today the `_prebuildBusy` lock + 0.25s stagger in `actions.ts` serializes their warm-primes. After lazy-load, the equivalent risk is: multiple players triggering their first-deploy lazy build in the same frame.

**AI position:** Keep a global serial-build mutex (similar to `_prebuildBusy`) for the heaviest two surfaces (Combat HUD, Vehicle Deploy Timer). Lighter surfaces can build in parallel without serialization. Reuse the existing mutex; don't invent a new one.

**User notes:**
*[ ]*

#### Q8c: Frame-budget breaker

If a build exceeds 800ms in a single frame (the engine's documented 1000ms eval limit), kill the script. The defensive move: instrument lazy builds with elapsed-time checks; if a build is approaching the budget, force a yield even if the original code path didn't include one.

**AI position:** Wrap each heavy build path with a "budget-aware" helper that yields if `mod.GetMatchTimeElapsed()` shows we've consumed >70% of the safe budget. This is an emergency brake, not the primary mitigation — Q8a's planned yield points are the primary.
