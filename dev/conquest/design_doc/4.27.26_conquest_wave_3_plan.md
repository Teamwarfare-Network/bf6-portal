## Context

The binding constraint flipped from CPU frame budget to runtime JS heap (per [`conquest_optimization_analysis.md`](./conquest_optimization_analysis.md) "Why memory, not bytes"). The current `prebuildAllUiFamiliesHidden` warm-prime — building Combat HUD + Vehicle Deploy Timer + Ready Dialog + top HUD shell + Gadget Locker for *every* player on join, then revealing on gate release — was correct when CPU was the budget; it is the wrong answer now because every prebuilt-and-hidden UI is paid in retained heap from join to disconnect.

Wave 3 is the architectural reversal: **build on demand, accept controlled hitches, free heap.** The user's v0.1 answers narrow this to a parameterized soft-cut (gate machinery stays as a safety net during transition; prebuild is replaced with per-UI lazy triggers; each surface has a tunable config controlling whether it shows a placeholder, paces its build via Clocks, etc.).

### What's NOT changing

- Per-PID UI scope. Locked.
- Dirty-flag HUD contract. Locked.
- Wave 1 leak fixes (A6, A7) and Wave 2 phase-prefix renames (F1) stay.
- Ready Dialog admin model is **Wave 4**. Wave 3 only converts the Ready Dialog *build trigger* to lazy; it does not change who sees it.

## New analysis (v0.2)

### A. Per-UI lazy-load config registry (Q1 generification)

User: "I want specific parameterization in the code, which instruments any tuning about this... Perhaps a binary flag around showing a loading interstitial, or a set time of '1 second' to let it load/cache? Think about how we genericize this."

**Proposal: a single registry typed config keyed by UI surface.**

Place at [`src/interaction/lazy-build-registry.ts`](../src/interaction/lazy-build-registry.ts) (new file). Shape:

```ts
type LazyBuildConfig = {
    name: 'combatHud' | 'topHudShell' | 'vehicleDeployTimer'
        | 'supplyBox' | 'readyDialog' | 'boundaryPrompt';
    showPlaceholder: boolean;        // Q3 — show "Loading…" placeholder during build
    placeholderDelayMs: number;      // 0 = show immediately; >0 = only show if build runs longer than this
    hitchBudgetMs: number;           // Q2 — max sync time before pacer kicks in
    builder: 'sync' | 'paced';       // sync = single-frame burst; paced = Clocks-driven N-per-tick drain
    pacedOpsPerTick: number;         // for paced builders — ops drained per Clocks tick (see B)
    serializesWith: string[];        // Q8b — names of other surfaces that share the global heavy-build mutex
    teardownTrigger: 'disconnect' | 'roundEnd' | 'matchEnd' | 'menuClose' | 'never';
};
```

Why a registry, not per-call params: the table is read once at module load; call sites stay simple (`triggerLazyBuild('supplyBox', pid)`); future tuning is one edit per surface. Test instrumentation (e.g. forcing all surfaces to show placeholders, or forcing all builders to paced for a soak test) is one config-row override, not a code change at every call site.

**Shape (locked v0.3):** the registry is a **`const` exported map**. To retune any value, edit the registry file and bumpVersion. No runtime mutation API. This matches AGENTS.md's "explicit human approval" preference and keeps the mutation surface small.

Initial values:

| name | showPlaceholder | placeholderDelayMs | hitchBudgetMs | builder | pacedOpsPerTick | serializesWith | teardownTrigger |
|------|:-:|:-:|:-:|:-:|:-:|---|---|
| `combatHud` | `false` | – | 500 | `sync` | – | `[vehicleDeployTimer]` | `disconnect` |
| `topHudShell` | `false` | – | 500 | `sync` | – | `[]` | `disconnect` |
| `vehicleDeployTimer` | `true` | 100 | 300 | `sync` | – | `[combatHud]` | `disconnect` |
| `supplyBox` | `false` | – | **50** | `sync` | – | `[]` | `disconnect` |
| `readyDialog` | `true` | 200 | 500 | `sync` | – | `[]` | `roundEnd` |
| `boundaryPrompt` | `false` | – | 200 | `sync` | – | `[]` | `matchEnd` |

`paced` is opt-in safety; we ship with all `sync` and only flip a row when measured build time exceeds budget.

### B. Clocks-based build pacer (Q8a resolution)

User: "Use the clock widget module... do a certain amount of operations at a time, vs maximizing speed. Don't use mod.waits."

**Mechanism.** The Clocks module ([`src/foundation/bf6-utils/clocks.ts`](../src/foundation/bf6-utils/clocks.ts)) currently exposes `BaseClock` with drift-corrected recurring `_tick()` via `Timers.setTimeout`. The `onSecond` callback is the only existing ≥1Hz hook; sub-second pacing requires a faster recurring `Timers.setTimeout` loop — same pattern as `BaseClock` but at e.g. 100ms (10Hz) or 50ms (20Hz).

**Design:**
- A new module [`src/interaction/build-pacer.ts`](../src/interaction/build-pacer.ts).
- Owns a FIFO `pendingOps: Array<() => void>` and a single recurring `Timers.setTimeout(drain, intervalMs)` started lazily when the queue becomes non-empty and stopped when it drains to zero.
- `enqueueBuildOp(op, opsPerTick)` appends an op tagged with the surface's per-tick budget; on each tick the pacer pops up to `opsPerTick` ops and runs them.
- The global heavy-build mutex (Q8b) sits in front: a build path either owns the mutex (synchronous) or is queued.
- **Hard rule: no `mod.Wait` anywhere in the pacer or in build paths.** The existing `_prebuildBusy` spin-wait at [`src/interaction/actions.ts:266-270`](../src/interaction/actions.ts) (uses `mod.Wait(0.05)`) is replaced by enqueue-and-callback semantics.

**Decision (locked v0.3):** **`intervalMs = 100` (10Hz).** Sub-second responsiveness; ~1 second to drain a 100-op queue at 10 ops/tick. Fast enough that paced builds feel "in progress, not stuck"; slow enough that each tick has clear frame budget headroom for ops it dispatches.

### C. Loading placeholder UX (Q3 + Q5 reconciliation)

User on Q3: "Ensure it is visible, but not center screen which would block anything for the player where they're aiming." User on Q5: "Keep existing prompt style, shorten, remove hard gate to deploy."

The current [`src/ready-dialog/loading-overlay.ts`](../src/ready-dialog/loading-overlay.ts) renders a 520×220 blurred center-screen blocker (`mod.UIAnchor.Center`). Two concerns: it is center (Q3 violation) and it is full-screen-feeling for a brief interstitial.

**Decision (locked v0.3):**
- **Reuse the loading-overlay scaffold**, but parameterize size + anchor. New shape: **~280×60 slim strip, anchored `mod.UIAnchor.BottomCenter`**, body text **"Loading UI..."**. Keeps the build/show/hide functions; changes layout constants and the message string.
- Behavior: shown when a lazy build is in progress AND the surface has `showPlaceholder=true` AND elapsed > `placeholderDelayMs`. Hidden when build completes.
- Q5 form: same prompt during the brief join-warm window (top HUD shell building) — reused widget tree at the slim-strip size. **Deploy button is enabled regardless** of whether the loading placeholder is showing (this is the "remove hard gate to deploy" line).
- New string entry needed in `src/strings.json` (per AGENTS.md `mod.Message` rule): a key for "Loading UI..." (e.g. `mod.stringkeys.twl.hud.loadingPlaceholder.body`). String addition requires explicit human approval per AGENTS.md "String Change Authorization Policy" — this plan documents the proposed string but the addition itself is gated on user sign-off at edit time.

### D. Boundary prompt: cache at LIVE phase transition (1s-batched stagger)

User: "Cache on round start=live, otherwise first violation event. There are violations pre-game but don't prioritize them. Ensure teardown." On burst risk: "Stagger, but do it in batches every 1s. We have at minimum 10 seconds here on the count down."

Current [`src/boundary/prompt-ui.ts`](../src/boundary/prompt-ui.ts) is already lazy on first violation (12-widget tree built via `safeParseUI`, cached at `State.hudCache.boundaryPromptCache[pid]`). Wave 3 adds an explicit **prebuild hook on conquestPhase3 → LIVE transition**, but **batched across the LIVE countdown window**: at LIVE+0s build batch 1 of pids; at LIVE+1s build batch 2; etc. With a minimum 10-second countdown the schedule fits 64 players in **≤7 players per batch × 10 batches = 64 pids in 10s**.

**Mechanism (locked v0.4):**
- Schedule via `Timers.setTimeout` (not `mod.Wait`); each batch runs at its scheduled offset.
- Batch size = `ceil(connectedPidCount / 10)` — divides evenly across the 10s window. Conservative ceiling caps at 8 per batch.
- All batches are scheduled at LIVE transition. If players join mid-countdown they fall to the first-violation fallback.
- Late-joiners *after* LIVE start: no LIVE prebuild path; their boundary prompt builds on first violation. Cheap; no change from today.
- Cancellation: if `conquestPhase` exits LIVE during the 10s window (rare; only on early match end), pending batches are cancelled.

Teardown: on match end (`teardownTrigger: 'matchEnd'`) and on disconnect (existing path). Build itself remains synchronous per pid (12 widgets is well within `hitchBudgetMs: 200`).

This is the only UI in Wave 3 where the trigger is a **phase event**, not an interaction — but the registry's `teardownTrigger: 'matchEnd'` covers the lifecycle pairing.

### E. Top HUD shell ASAP vs Combat HUD on deploy — reconciliation

User: top HUD shell "build as soon as we can"; Combat HUD entry graph "on first deploy."

Confirmed separable. [`src/interaction/actions.ts:201-216`](../src/interaction/actions.ts) builds the shell via `prebuildTopLeftUiFamilyWhileHidden`; [`src/interaction/actions.ts:228-235`](../src/interaction/actions.ts) builds the entry graph separately via `prebuildCombatHudFamilyWhileHidden`. The split:

- **Top HUD shell**: clock, branding, help text, status dock, admin panel — built immediately on `onPlayerJoinGameImpl` finish (after spawn-point assignment). Uses `topHudShell` config row. Synchronous; budget 500ms; serialized with no other surface (the shell is small, not a contention risk).
- **Combat HUD entry graph**: tickets, objective flags, popout, engagement meters — built on first `OnPlayerDeployed` for that pid. Uses `combatHud` config row. Synchronous; budget 500ms; serialized with `vehicleDeployTimer` so two heavy builds in the same frame can't stack.

Risk: combat HUD on first deploy could mean the player sees an undecorated world for a frame or two before tickets/flags render. Mitigation: the build is synchronous (single frame) with the global mutex — it lands in the same frame as the deploy, before the player's first paint. Pacer activated only if budget breach measured.

### F. R6 reframe — hide-while-caching contract (user push-back)

User on R6: "I don't get why flickering should be a thing. It seems to me that you can hide things while they cache, we're just deferring when they cache and load. Only show the things when they're done loading."

Agreed — and this is the architectural rule for the wave: **all lazy builds construct widgets in their `Hidden` state; visibility is flipped to `Visible` only after the build completes and the entry-graph cache is fully populated.** The flickering bugs from CQ_Bug_32/33 are pre-existing race conditions in *show-then-mutate* paths, not consequences of lazy build. Wave 3 inherits the same hide-build-show contract the prebuild path already used; it does not introduce new flicker.

**Updated R6 wording:** the risk is no longer "flickering" but "build path forgets to set initial visibility=Hidden, exposing half-built widgets." Mitigation is a registry-enforced contract: every builder function returns a `BuildResult` whose visibility is `Hidden` at construction, and the trigger function flips to `Visible` only on receipt of the result. Reviewable in PR.

### G'. Build-error semantics (locked v0.4)

User: "Retry on next trigger."

**Mechanism:**
- Every builder function executes inside a try/catch in the `triggerLazyBuild(name, pid)` dispatch.
- On throw: log via existing world-log helper; tear down any partial widgets (loop the cache entry's known node names + delete via `mod.RemoveUI*`); clear the cache entry; release the global mutex if held; release the per-surface build lock; re-emit nothing to the player.
- The next call to `triggerLazyBuild(name, pid)` for the same surface re-runs the builder cleanly. The retry is observationally indistinguishable from a first-time build.
- Throws are not silently dropped — every throw produces a world-log entry tagged `[lazy-build:<name>:<pid>]` so failures are visible in soak tests.

This contract holds for `sync` and `paced` builders alike. For `paced` builders, a throw in any single op aborts the whole queued sequence for that pid+surface; the partial widgets (already-completed ops) are torn down via the same teardown path.

### Ship 3.5 — Supply box LIVE-phase warm stagger (follow-up to Ship 3)

**Status:** Approved 2026-04-30 (post-Ship-3 review). User directive: "auto-cache this player by player after the round starts, one player every 2 seconds." Late joiners during LIVE get appended to the queue tail.

**Why:** Ship 3 makes supply-box first-interact-only by default. Most players in a Conquest round never visit the supply crate before they actually need a gadget, so the ~50ms first-open hitch lands at exactly the moment they're under combat pressure. A slow staggered warm at LIVE keeps the heap-friendly lazy default but reduces the window where a late first-interact incurs the build hitch under fire.

**What lands:**
- *(new)* [`src/interaction/supply-box-warm-scheduler.ts`](../src/interaction/supply-box-warm-scheduler.ts) — a `SupplyBoxWarmScheduler` namespace owning a self-rescheduling `Timers.setTimeout` chain at 2s/op cadence. Persistent queue (not a snapshot): late joiners during LIVE get appended via `enqueueLateJoiner(pid)`.
- [`src/conquest-flow.ts:startMatch`](../src/conquest-flow.ts) — kicks off `SupplyBoxWarmScheduler.startWarmStaggerForLive()` immediately after `lifecycleSetLiveBaseline("pregame-start-match")`.
- [`src/conquest-flow.ts:endMatch`](../src/conquest-flow.ts) and [`src/conquest-flow.ts:triggerFreshMatchSetup`](../src/conquest-flow.ts) — call `cancelWarmStagger()` to nuke any in-flight chain.
- [`src/index/player-join-leave.ts:onPlayerJoinGameImpl`](../src/index/player-join-leave.ts) — call `enqueueLateJoiner(joinPid)` next to the Ship 2 `triggerLazyBuild('topHudShell', joinPid)` line. The function internally no-ops when LIVE is not active.
- [`src/index.ts`](../src/index.ts) — import `./interaction/supply-box-warm-scheduler` after `./interaction/lazy-build-registry`.

**Implementation specifics:**

1. **Cadence: 2 seconds per op.** `WARM_STAGGER_INTERVAL_MS = 2000`. At 16 players the warm wraps in 32s; at 64 players, 128s. Tunable via the constant. At high counts where the warm exceeds match duration, latest-scheduled pids never warm — they fall to the existing first-interact path.

2. **Token-based cancellation.** Each scheduled tick captures `_activeToken` at scheduling time and re-checks before firing; mismatched token aborts silently. `cancelWarmStagger()` bumps the token, clears the queue, and clears the pending `Timers` handle.

3. **Persistent queue with late-joiner append.** `_warmQueue: number[]` survives across the chain's recursive `scheduleNext` calls. `enqueueLateJoiner` checks `_liveActive` and `indexOf(pid)` before pushing. If the chain had self-terminated (queue drained), the append restarts it with a fresh `Timers.setTimeout`.

4. **No "already-processed" tracking.** Reconnects of the same pid number get re-enqueued. The dispatcher's `armCacheOk` short-circuit in the `supplyBox` handler makes the trigger a no-op when the cache survived the disconnect window cleanly; rebuilds it when Wave 1's `destroyArmMenu` cleaned up at disconnect.

5. **Idempotent dispatcher behavior.** Any pid that interacted with a supply box before their scheduled slot fires already has `armCacheOk(...) === true` — the handler runs `prebuildArmMenu` which short-circuits → fast no-op. No double-build, no flicker.

6. **Initial pid ordering: ascending.** Deterministic for soak-test reproducibility. Late joiners are appended at the tail in join order — they get warmed last.

7. **Defensive try/catch on the trigger call.** Even though the dispatcher has its own try/catch, the chain's `scheduleNext` recursion mustn't crash on a thrown error. The chain advances on the next slot regardless.

8. **No use of `LazyBuildPacer`.** Pacer's minimum cadence is 1 op/100ms; cannot throttle to 1 op/2s. A self-contained `Timers.setTimeout` chain is the right shape.

**SP smoke:**

2. **Pre-empt with first-interact.** During the 2s window post-LIVE, walk to a supply box and press interact. Menu builds at first-interact (~50ms, normal Ship 3 path). Scheduler's slot for this pid is a no-op when it fires (`armCacheOk` returns true). No double-build, no flicker.

4. **Cancellation via fresh-setup.** Trigger admin "Fresh Setup" mid-LIVE. Scheduler stops; subsequent LIVE start fires fresh stagger.

### Ship 8 — Loading-gate deletion (cleanup)

**Recon (post-Ships-1-7) revealed the gate is still load-bearing:**

- **Race-condition safety on first-join** — gate-loop force-undeploy (`actions.ts:593-598`) catches engine races where players reach deploy state before lazy builds complete. Tied to CQ_Bug_35 (`EnableAllInputRestrictions` spam) and CQ_Bug_36 (`UndeployPlayer` on undeployed).
