# OngoingPlayer Cost Analysis

**Date:** 2026-05-12
**Baseline:** v1.514
**Status:** Analysis only -- no code change recommended yet pending Step 1 (cadence measurement) and user direction.
**Context:** User question 2026-05-12 -- "Isn't this the single most expensive function? We need to protect it." Triggered by the per-tick `safeGetSoldierStateBool(IsInteracting)` poll in the `InteractMultiClickDetector` path which appears to fire for every player including vehicle occupants. Related to the open `CQ_Bug_Aircraft_OOB_Misclassification` (#116) investigation -- specifically H7 (vehicle-occupant GetSoldierState failure as the source of the `ERROR REPORTED BY GETSOLDIERSTATE` admin-log entries).

---

## Section 1: What `OngoingPlayer` actually is

From the SDK at [`reference_sdk_1.2.3/.../mod/index.d.ts:28242`](../../reference_sdk_1.2.3/code/types/mod/index.d.ts#L28242):

```ts
export function OngoingPlayer(eventPlayer: mod.Player): void;
```

That is the full signature. The SDK does not document the cadence. Our exported handler is at [`src/index.ts:162`](../src/index.ts#L162):

```ts
export function OngoingPlayer(eventPlayer: mod.Player): void {
    ongoingPlayerImpl(eventPlayer);
}
```

### Cadence is UNVERIFIED

[`conquest_optimization_state.md:596`](./conquest_optimization_state.md#L596) categorizes `ongoingPlayerImpl()` as `XL~1` (XL = "Runs every game-loop subtick (~8/sec)"). But that is an **inferred assumption**, conflated with our own game-mode-loop subtick which IS empirically ~120ms per [`hud/perf-diag.ts:6`](../src/hud/perf-diag.ts#L6) (separate script-side loop driven by `mod.Wait`).

The engine's actual `OngoingPlayer` cadence could be:
- **1 Hz** (matching `OngoingGlobal`, which IS confirmed 1 Hz per [`Changelog.ts:393`](../src/Changelog.ts#L393))
- **~8 Hz** (matching subtick -- our current assumption)
- **Higher** (per-frame is possible in Frostbite engines)
- **Variable** (depends on player state -- e.g., paused for spectators)

**We do not actually know.** Step 1 of any rigorous optimization needs to be empirical measurement.

That said, the *work we do per-call* is the load-bearing variable regardless of cadence -- and we fully control that.

## Section 2: Is this the single most expensive function?

It depends on cadence. What makes it dangerous:

- **Scales O(N)** with connected player count. Every player triggers their own call.
- **Currently has NO seatKind / alive / vehicle gating** -- vehicle occupants do the same work as on-foot players.
- **3 `GetSoldierState` engine calls per non-spectator player per tick** in the default branch.
- **Engine errors fire from this path if H7 is correct** (vehicle-occupant state keys fail). Each error generates an admin-log entry.

If cadence is ~8 Hz at 64p, this is **~1,536 engine calls per second** worst case (3 per player x 64 x 8 Hz). At 1 Hz it is ~192/sec. Either way, it is the largest per-tick fanout we control directly. Combat HUD's per-pid VM-build is similar scale but already throttled to 200ms via Tier S3 (v1.497); `OngoingPlayer` has no throttle at all.

The v1.491 1,716ms-frame breach has not been directly linked to `OngoingPlayer` -- but it is currently our largest un-throttled per-player fanout.

## Section 3: Per-tick work itemized

Each call to `ongoingPlayerImpl(player)` at [`src/index/player-loop-inputs.ts:3`](../src/index/player-loop-inputs.ts#L3):

| Step | Cost | Skippable? |
|------|------|------------|
| `isValidPlayer(player)` | 1 type check | NO -- load-bearing |
| `isPlayerDeployed(player)` | 1 cache read (`deployedByPid[pid]`) | NO -- load-bearing |
| `safeGetPlayerId(player)` | 1 engine call (`GetObjId`) | NO -- load-bearing |
| `isSpectator(pid)` | 1 cache read | NO -- load-bearing |
| **SPECTATOR BRANCH** | | |
| `checkMultiClick(player)` -> `GetSoldierState(IsInteracting)` | **1 engine state call** | YES -- only relevant on-foot |
| `exitSpectatorMode(...)` on triple-tap | rare (only fires on actual triple-tap) | n/a |
| **DEFAULT BRANCH** | | |
| `checkReadyDialogInteractPointRemoval(player)` -> `GetSoldierState(IsDead)` | **1 engine state call** | YES -- only relevant if interact-point exists |
| `isVelocityBeyond(...)` -> `GetSoldierState(GetLinearVelocity)` (conditional) | **1 engine state call** | YES -- only if interact-point exists |
| `checkMultiClick(player)` -> `GetSoldierState(IsInteracting)` | **1 engine state call** | YES -- only relevant on-foot |
| `spawnReadyDialogInteractPoint(...)` on triple-tap | rare | n/a |

**Default branch per call:** 3 GetSoldierState calls + 1 GetObjId + 2 cache reads.
**Spectator branch per call:** 1 GetSoldierState + 1 GetObjId + 2 cache reads.

`GetSoldierState` is the dominant cost. Other ops (cache reads, type checks) are nanosecond-class JS work. `GetSoldierState` is a cross-boundary engine call -- much more expensive (microseconds-class minimum, plus the error-log path if it fails for vehicle occupants).

### Why polling exists (it is NOT spaghetti)

**Triple-tap detection cannot be event-driven on this engine.** The engine exposes:
- `OnPlayerInteract(player, interactPoint)` -- only fires when the player triggers a SPAWNED InteractPoint (`mod.SpawnObject(... InteractPoint ...)`). Requires geometry near the player.
- `IsInteracting` SoldierStateBool -- flips true while the interact button is HELD.

There is no `OnInteractKeyPressed` event. To detect three rapid presses ("triple-tap to open ready dialog") without requiring the player to be next to an interact volume, we have to poll `IsInteracting` and watch for edge transitions (false -> true counts as one "click"). That is literally what the `InteractMultiClickDetector` is doing.

The `OnOngoingPlayer` engine callback is the canonical place to do this polling -- it is the per-player tick the engine gives us for exactly this purpose.

## Section 4: Runtime cost at 12p vs 64p

**Assumptions (best-effort; need empirical confirmation):**
- Cadence: ~8 Hz per player (our current assumption -- needs verification)
- `GetSoldierState` cost: ~5-50 us each (engine round-trip + JS marshalling; varies)
- Player population mix in active combat: ~60% on-foot, ~30% in vehicles, ~10% spec/dead

| Metric | 12 players | 16 players | 32 players | 64 players |
|---|---:|---:|---:|---:|
| `OngoingPlayer` invocations / sec | 96 | 128 | 256 | 512 |
| `GetSoldierState` calls / sec (default branch dominant, 3 per call) | ~288 | ~384 | ~768 | **~1,536** |
| `GetSoldierState` calls / sec (with seatKind gate at 30% vehicle population) | ~202 | ~269 | ~538 | **~1,075** |
| Per-frame at 60 FPS: avg engine calls per frame | ~5 | ~6 | ~13 | **~26** |
| Worst-frame spike potential (cluster) | low | low | medium | **HIGH** |

The 64p column is concerning not because the steady-state is unmanageable (1,536 engine calls/sec is fine for the engine in absolute terms), but because:

1. **If H7 is correct** (vehicle-occupant state keys fail), that is 1,536 error-log entries/sec. Admin error log floods.
2. **Per-frame variance**: if the engine batches per-frame instead of evenly distributing, you could get 26+ engine calls in a single frame, contributing to the v1.491 1,716ms-frame breach pattern.
3. **N-squared interaction risk**: if any logic inside `ongoingPlayerImpl` ever iterates other players (it does not today, but could be added by future code without anyone noticing the cost), it would compound to O(N^2).

## Section 5: What can be moved OUT

Ranked by ROI (savings per ship effort):

### Tier 1: Add seatKind gate (HIGHEST ROI, LOWEST RISK)

**Save ~30-40% of engine calls** at typical vehicle-heavy player mixes. Single-file change.

```ts
function ongoingPlayerImpl(eventPlayer: mod.Player): void {
    if (!isValidPlayer(eventPlayer)) return;
    if (!isPlayerDeployed(eventPlayer)) return;
    const pid = safeGetPlayerId(eventPlayer);
    if (pid === undefined) return;

    // NEW: vehicle occupants cannot triple-tap interact (button is bound to vehicle controls).
    // Skip the polling entirely. Saves 1-3 GetSoldierState calls per tick per vehicle-occupant.
    const zone = State.round.boundary.zoneStateByPid[pid];
    if (zone && zone.seatKind !== "on_foot") return;

    // ... existing branches ...
}
```

**If H7 is correct, this also eliminates the error-log floods as a side effect.**

**Risk:** Low. The seatKind cache is event-driven (`onPlayerEnterVehicle` / `onPlayerExitVehicle`) and may lag reality by one tick. Worst case: a player who just exited a vehicle has one tick where the gate keeps them out of triple-tap detection. Imperceptible to a human (triple-tap window is 2 seconds; the gate would resolve within 125ms).

**Effort:** ~30 min code + bumpVersion + 10 min SP smoke.

### Tier 2: Skip `IsDead` poll when no interact-point exists

The default branch reads `IsDead` even when there is no interact-point to remove. Move the cache check BEFORE the GetSoldierState:

```ts
function checkReadyDialogInteractPointRemoval(eventPlayer: mod.Player) {
    if (!isPlayerDeployed(eventPlayer)) return;
    const playerId = mod.GetObjId(eventPlayer);
    const data = State.players.readyDialogData[playerId];
    if (!data || data.interactPoint == null) return; // <- NEW: skip the whole IsDead+velocity path
    const isDead = safeGetSoldierStateBool(eventPlayer, mod.SoldierStateBool.IsDead);
    // ... rest
}
```

Saves 1-2 `GetSoldierState` per non-spectator per tick (since most players do not have an active interact-point at any given moment -- interact-points are spawned only by triple-tap and live for a bounded lifetime).

**Risk:** Zero. Pure refactor.

**Effort:** ~15 min code + ship.

### Tier 3: Coalesce interact-point lifecycle to Timers

The current architecture polls velocity and lifetime per-tick. Both could move to a single one-shot timer scheduled when the interact-point is spawned:

- Spawn interact-point -> schedule `Timers.setTimeout(removeInteractPoint, interactPointMaxLifetime * 1000)`
- Velocity removal still needs polling but could go to a lower-frequency dedicated loop (e.g., 1 Hz `Timers.setInterval` only running while interact points exist)

Eliminates per-tick velocity polling entirely. **Velocity polling at higher frequency was probably needed historically; check if 1 Hz is sufficient for UX (e.g., does a fast-moving player feel the lag?)**

**Risk:** Low-medium. The velocity threshold is a UX feel; need to confirm 1 Hz captures it well enough.

**Effort:** ~1-2 hour plan + 2-3 hour ship.

### Tier 4: Cache `GetObjId` result

`mod.GetObjId(player)` is called in `ongoingPlayerImpl` AND in `checkMultiClick`. Two engine calls per tick for the same data. Pass `pid` as a parameter once resolved.

**Risk:** Zero.
**Savings:** Minor -- 1 engine call per tick.
**Effort:** ~15 min.

### Tier 5: Spectator-branch sleep (NO-GO)

For the spectator (`seatKind === "aircraft"` while parked in hide-room), the multi-click polling is the only thing happening, but it is polling on a body that is restricted from most inputs. Interact IS released for spectators (per v1.486 ship) so triple-tap exit works.

The spectator's triple-tap is the ONLY way to exit. **Polling has to continue. No savings here.**

### Tier 6: Move multi-click to a self-driving Timers loop

Instead of relying on `OngoingPlayer`, run a dedicated `Timers.setInterval(checkAllPlayersForTripleTap, 125)` that iterates `mod.AllPlayers()` and runs the detector. Gives us explicit control over the cadence and lets us throttle it down (e.g., 4 Hz instead of 8 Hz) if needed.

**Tradeoff:** adds one more independent loop; loses the engine's per-player batching.

**Risk:** Medium. Changes the input-detection architecture. Need to verify cadence matches user feel.

**Effort:** 1 hour code + ship + SP feel test.

### Tier 7: Replace polling with event-driven detection (LONG-SHOT)

Is there ANY engine event we could use instead? Some possibilities to investigate:
- `OnPlayerInteract` -- only fires for spawned InteractPoints; does not help for "interact-on-empty-space" detection
- Some other input-related callback we missed in the SDK
- `OngoingInteractPoint` -- specifically when an interact-point is active. Could re-route lifecycle.
- Check `reference_andys_conquest` / `reference_BountyHunter` / `reference_BountyHunter_VehicleDeploy` for alternative patterns

If something exists, polling could be removed entirely. **High research cost, possibly zero payoff.**

**Risk:** High. Architectural change. Need to validate end-to-end UX.

**Effort:** Open-ended research.

## Honest caveats

- The cost numbers above are estimates. We do not have an in-engine profiler for individual API call costs.
- The "30% in vehicles" mix is a rough guess -- actual mix depends on map/mode.
- Cost per `GetSoldierState` may vary by state-key (some may be 1us cached reads, others 50us cross-boundary).
- We do not know if the engine batches `OngoingPlayer` calls within a frame or distributes them.
- v1.491's 1,716ms-frame breach has not been directly linked to `OngoingPlayer` -- but if Tier S3 (vehicle deploy timer throttle, v1.497) was a meaningful reduction, `OngoingPlayer` is the next-largest un-batched per-player fanout we have.
- The H7 hypothesis (vehicle-occupant `GetSoldierState` failure) is unverified and is the link to `CQ_Bug_Aircraft_OOB_Misclassification` (#116). If H7 is correct, the seatKind gate (Tier 1) doubles as a fix for the admin-log flooding observed alongside the false-OOB.

---

## What this document is NOT

- This is **not** a plan-of-record. Per project memory `feedback_plans_are_not_instructions_to_execute`, this analysis is documentation only. Specific code changes require explicit user approval before implementation.
- This is **not** a fix for #116. The seatKind gate would address the admin-log flooding but not the underlying false-OOB classification (which is a separate seatKind-staleness issue documented in #116's revised hypotheses).
- This is **not** an emergency. Bundle and heap are stable; this is a forward-looking optimization triggered by a code-review concern, not by a measured perf issue.
