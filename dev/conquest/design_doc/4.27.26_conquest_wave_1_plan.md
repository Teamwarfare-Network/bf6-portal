## Context

The Lifecycle Map audit in [`conquest_optimization_state.md`](./conquest_optimization_state.md) surfaced two confirmed per-PID memory leaks: state fields with write sites but no `delete` reachable from `onPlayerLeaveGameImpl`. Long-running servers see these leaks accumulate across player join/leave churn — they are exactly the kind of unbounded growth that contributes to the 16-player JS heap termination tracked in issue [#109](./conquest_issues.md). Wave 1 is the zero-design-risk batch in our optimization sequencing: ~3 lines of code in one function, no architectural change, no UX impact, ship-and-playtest before larger waves.

The two leaks:

- **A6 — `State.hudCache.ammoResupplyMenuCache[pid]`** (M2 — second-largest per-PID widget cache, ~100–180 widget refs per pid). When a player opens the Supply Box once and then disconnects, `resetArmState(pid)` clears the small arm-state booleans but the widget cache itself is never freed. The canonical cleanup function `destroyArmMenu(pid)` (which both deletes the engine widgets AND clears the cache entry) is called on join (`resetUiForPlayerOnJoin:18`) but is missing from the leave path.
- **A7 — `State.hqDeploy.lastRequestAtSecondsByPid[pid]`**. Field exists at [`runtime-types.ts:494`](../src/state/runtime-types.ts), written on every HQ-deploy request from `vehicles/hq-deploy.ts` (7 write sites). Has zero `delete` sites anywhere in `src/`. Field grows by one numeric entry per unique pid the server has ever seen. Small per-leak but unbounded.

### Edits in detail

**Edit 1 — A6 cleanup, after line 137 (`resetArmState(pid)`):**

Add a single call right after the existing `resetArmState(pid)` line. `resetArmState` already handles the small per-pid booleans (`armO`, `armI`, `armT`, `armFocusedTileKeyByPid`); `destroyArmMenu` handles the widget tree deletion plus the cache entry deletion (`State.hudCache.ammoResupplyMenuCache[pid]`). They are complementary — pairing them on leave matches the existing pairing on join (`resetUiForPlayerOnJoin:14,18`).

```ts
    resetArmState(pid);
    destroyArmMenu(pid);  // ← NEW (A6: plugs ammoResupplyMenuCache[pid] leak)
    cleanupWorldInteractableRuntimeIconsForPid(pid);
```

**Edit 2 — A7 cleanup, with the other `delete State.X.YByPid[pid]` lines:**

Add a single `delete` line. Natural placement is alongside other deploy-related per-pid deletes — after `delete State.players.liveVehicleDeployMenuVisibleByPid[pid];` at line 156 reads cleanly (both are deploy-state cleanups).

```ts
    delete State.players.liveVehicleDeployMenuVisibleByPid[pid];
    delete State.hqDeploy.lastRequestAtSecondsByPid[pid];  // ← NEW (A7: plugs unbounded growth)
    delete State.players.armO[pid];
```

That's the full code change: 2 added lines.

### Why these placements are safe

- **`destroyArmMenu(pid)` after disconnect** — the function calls `mod.DeleteUIWidget` on widgets named `AmmoResupplyMenuRoot_${pid}` and clears `State.hudCache.ammoResupplyMenuCache[pid]`. Widgets exist in the engine widget registry independent of player connection state; calling `DeleteUIWidget` on a disconnected player's widget is the same as calling it on any widget — it removes the widget. The function is wrapped in try/catch with a 32-iteration ceiling, so it is fail-safe.
- **`delete State.hqDeploy.lastRequestAtSecondsByPid[pid]`** — all 7 read sites in `vehicles/hq-deploy.ts` use the `?? -999` fallback pattern, so the absence of a key reads as "no recent request" which is the correct semantic for a disconnected player. No consumer breaks.
- **No re-entrancy concerns** — `onPlayerLeaveGameImpl` is fired by the Portal engine, not user code; the function is synchronous from start to finish; no other code path can run between these inserts and produce a race.

## Verification

### Testing model

- **SP is the regular validation channel.** Every wave ships through SP smoke testing before any MP exposure.
- **MP is opportunistic.** User runs MP playtests when feasible — playercount target is **minimum 24, ideal 64**. The 16-player number was where the original crash surfaced, not the validation target.
- **MP-only items accumulate** in `design_doc/conquest_mp_ongoing_tests.md`. Each wave appends entries; they get checked off whenever an MP playtest happens.

### Local (SP gate — runs every wave)

1. `cmd /c npx tsc --pretty false --noEmit` — typecheck must pass with zero new errors. (The 2-line addition uses functions already in scope; no import changes.)
2. `npm run bumpVersion -- -c "A6+A7: plug ammoResupplyMenuCache and hqDeploy.lastRequestAtSecondsByPid leaks on player leave (Wave 1)"` — increments version, runs `npm run build`, prints post-bump checklist.
3. After bump: refresh `conquest_optimization_state.md` Project Stats row (bundle size will be ~50 bytes larger), flip the two ❌ rows in the Lifecycle Map to ✓, update Tier A6/A7 status in the analysis doc.

### Single-player smoke test (run by user before next wave)

1. Launch single-player. Verify the game loads (no script termination at startup).
2. Open the Supply Box menu (any HQ supply box). Pick a gadget. Close menu. No errors in world log.
3. HQ Deploy a vehicle. Verify deploy succeeds.
4. Confirm: typecheck passes, game loads, basic interactions work. The leak signal does **not** reproduce in SP — it requires repeated joins/leaves which only happens in MP.
