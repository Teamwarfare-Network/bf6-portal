# Delay-Elapsed Broadcasts (LIVE-Phase Vehicle/Gadget Unlock Announcements)

**Status:** **v1.1 LOCKED + SHIPPED (2026-05-04, v1.455).** New on-screen broadcast system: 4 transient text strings that appear just below the engage panel at the moment each round-start delay tunable elapses. Each broadcast announces a vehicle/gadget configuration becoming available. Visible 5 seconds, then auto-hides. Driven by `Timers.setTimeout` scheduled at `startMatch` against the active map's `roundStart*Delay` values. User Q1-Q5 answered (see Locked Decisions below). Implementation complete; awaiting SP smoke + MP playtest.

This is NOT a wave; it's a single feature ship landing alongside ongoing UI tuning work.

## Context

**What:** at each elapsed-LIVE-time milestone driven by the active map's delay tunables, display a transient on-screen broadcast announcing what just unlocked.

| Delay tunable | Firestorm value | Broadcast string (user-pre-authored) |
|---------------|----------------:|--------------------------------------|
| `roundStartAirDelay` | 30s | `delayAircraftHqBroacast` — "Aircraft can now HQ Ground Deploy (Purple Smoke)!" |
| `roundStartAirDeployDelay` | 60s | `delayAircraftAirBroacast` — "Aircraft can Air Deploy (Purple Smoke)!" |
| `roundStartForwardDeployDelay` | 90s | `delayForwardBroacast` — "Vehicles can Forward Ground Deploy (Purple Smoke)!" |
| `roundStartGadgetDelay` | 120s | `delayGadgetsBroacast` — "Gadgets at the Supply Boxes are available (Yellow Smoke)!" |

(Note on string-key spelling: user wrote `Broacast` — typo or intentional? Q1.)

**Why:** the existing pregame-countdown delay-lines display the FUTURE wait time ("Aircraft can HQ Ground Deploy 30s after the match is Live"). They tell a pre-LIVE player what's coming. They do NOT tell players who are mid-match the moment a thing becomes available — players have to either watch the clock or try to interact with the locked feature and get rejected. This broadcast system fills the live-time announcement gap.

**Display position:** "just under the engage HUD pop-out text (below NEUTRALIZING)" — see Q3 for exact widget-tree position decision.

**Timing constraints:**
- Each broadcast displays for **5 seconds**, then hides.
- **No overlap by design** — Firestorm's tunables are spaced 30s apart (30/60/90/120), so all 4 broadcasts fire sequentially with 30s gaps. The 5s display window is well within each gap.
- Future maps with tighter spacing could trigger overlap; out of scope for this plan but worth flagging in code comments.

## Pre-flight findings (Phase 1 exploration verified)

### Existing delay strings — current usage

`src/strings.json:403-413` defines the 5 existing keys (`delayAircraftHq`, `delayAircraftAir`, `delayForward`, `delayGadgets`, `delayGadgetsLive`).

Consumed in `src/ready-dialog/pregame-ui.ts:14-33` as `PREGAME_COUNTDOWN_DELAY_LINE_KEYS`. Displayed as **static delay-line text** above the pregame countdown via `showPregameCountdownDelayLineForAllPlayers(idx)` — set once per pid pre-LIVE, not per-tick refreshed.

The new broadcast strings will live alongside these in `strings.json` but are **independently consumed** — the pregame delay lines stay as-is; the broadcasts are a separate system.

### MapConfig delay tunables

Type def in `src/config/types.ts:131-135`:

```ts

roundStartAirDeployDelay?: number;      // Seconds after live before the air-deploy button unlocks
roundStartForwardDeployDelay?: number;  // Seconds after live before the forward-deploy button unlocks
roundStartGadgetDelay?: number;         // Seconds after live before gadget locker tiles become interactable
```

Firestorm values at `src/config/maps/operation-firestorm.ts:52-55`: `{ 30, 60, 90, 120 }`.

Gate sites at `src/state/core.ts:22-61` (4 functions: `isRoundStartAirDelayActive`, `isRoundStartAirDeployDelayActive`, `isRoundStartForwardDeployDelayActive`, `isRoundStartGadgetDelayActive`). Each compares `getSecondsSinceLive()` against the delay value.

**Locked mapping** (string ↔ tunable):
- `delayAircraftHqBroacast` ← `roundStartAirDelay` (when ANY aircraft becomes available, the FIRST allowed mode is HQ Ground Deploy because `roundStartAirDeployDelay` is still active)
- `delayAircraftAirBroacast` ← `roundStartAirDeployDelay` (Air-Deploy button unlocks)
- `delayForwardBroacast` ← `roundStartForwardDeployDelay`
- `delayGadgetsBroacast` ← `roundStartGadgetDelay`

### LIVE-elapsed-time tracking

`src/state/core.ts:13-19`:
```ts
function getSecondsSinceLive(): number {
    if (!isMatchLive()) return 0;
    const liveAt = State.round.liveStartedAtSeconds;
    if (liveAt === undefined) return 0;
    return Math.max(0, Math.floor(mod.GetMatchTimeElapsed()) - liveAt);
}
```

LIVE-start timestamp set in `src/conquest-flow.ts:21-25` `startMatch` function via `State.round.liveStartedAtSeconds = Math.floor(mod.GetMatchTimeElapsed())`.

Two scheduling options:
- **(A) `Timers.setTimeout` per delay at `startMatch`.** 4 setTimeouts, one per delay, scheduled at LIVE-start with exact ms offsets. Easy to cancel via stored timer IDs in `endMatch` / `triggerFreshMatchSetup`. Matches the `SupplyBoxWarmScheduler` + `BoundaryPromptLivePrebuildScheduler` pattern. **Recommended.**
- (B) `Clocks.CountDownClock` `onSecond` callback that polls `getSecondsSinceLive()` every tick and fires when it equals each delay value. Robust to clock-time drift but adds a per-second check that's mostly a no-op.

Going with (A) — cleaner and consistent with existing scheduler patterns.

### Existing on-screen broadcast / notification infrastructure

- **World log**: `mod.DisplayHighlightedWorldLogMessage` (used for "X readied up" notifications). Bottom-left log overlay, brief visible duration, NOT under the engage panel. Wrong surface for this use case.
- **No dedicated transient-notification widget exists** in the conquest HUD currently. Closest pattern is the pregame countdown delay-line widgets (per-PID `Text` widgets with explicit visibility toggle).

**Recommended approach:** new dedicated widget cache `delayBroadcastWidgetCache[pid]` (per-PID) hung off the combat HUD root, positioned just below the engage panel. Built once at HUD-init time. Visibility toggled by the scheduler.

### Per-PID vs global rule

`conquest_design.md` locks per-PID for interactive/responsivity-dependent surfaces. Match clock is cited as the one explicit narrow exception for purely passive content.

The broadcast text is purely passive (no clicks, no per-player perspective) and the content is identical for all viewers. It IS a candidate for global scope — but the codebase has zero existing fully-global widget examples. Even the match clock is per-PID-cached.

**Default decision:** build per-PID (matches established pattern). +1 widget/pid in M3. See Q2 for confirmation.

- **A.** Inside the combat HUD widget tree as a NEW widget below the engage panel, parented to `objectivesLane` or `engageRoot`. Inherits the combat HUD's lifecycle (built/torn down with the HUD; per-team-swap rebuild).

### Module sketch — `src/index/delay-broadcast.ts`

```ts
namespace DelayBroadcast {
    const DISPLAY_DURATION_MS = 5000;

    interface ScheduledBroadcast {
        triggerToken: number;
        timerId: number;
        stringKey: number;  // mod.stringkeys.* int id
    }

    let _activeToken: number = 0;
    const _pendingTriggers: ScheduledBroadcast[] = [];

    // Called from conquest-flow.ts:startMatch. Reads the active map's roundStart*Delay
    // tunables and schedules 4 setTimeout callbacks at the corresponding LIVE-elapsed-second
    // offsets. Each callback fires the broadcast for all valid players.
    export function scheduleDelayBroadcastsForLive(): void {
        cancelDelayBroadcasts();
        _activeToken += 1;
        const token = _activeToken;
        const cfg = getActiveMapConfig();
        scheduleOne(token, cfg.roundStartAirDelay,           STR_NOTIFICATION_DELAY_AIRCRAFT_HQ_BROADCAST);
        scheduleOne(token, cfg.roundStartAirDeployDelay,     STR_NOTIFICATION_DELAY_AIRCRAFT_AIR_BROADCAST);
        scheduleOne(token, cfg.roundStartForwardDeployDelay, STR_NOTIFICATION_DELAY_FORWARD_BROADCAST);
        scheduleOne(token, cfg.roundStartGadgetDelay,        STR_NOTIFICATION_DELAY_GADGETS_BROADCAST);
    }

    // Cancels all pending broadcasts. Bumps active token (invalidates in-flight callbacks),
    // clears pending timer IDs, force-hides currently visible broadcasts.
    export function cancelDelayBroadcasts(): void {
        _activeToken += 1;
        for (const p of _pendingTriggers) Timers.clear(p.timerId);
        _pendingTriggers.length = 0;
        forceHideDelayBroadcastForAllPlayers();
    }

    function scheduleOne(token: number, delaySeconds: number | undefined, stringKey: number): void {
        if (!delaySeconds || delaySeconds <= 0) return;  // skip unset/zero delays
        const timerId = Timers.setTimeout(() => {
            if (token !== _activeToken) return;  // cancellation race
            broadcastToAllPlayers(stringKey);
        }, delaySeconds * 1000);
        _pendingTriggers.push({ triggerToken: token, timerId, stringKey });
    }

    function broadcastToAllPlayers(stringKey: number): void {
        const message = msg(stringKey);
        forEachValidPlayer((player, pid) => {
            const cache = ensureDelayBroadcastWidget(pid, player);
            if (!cache?.text) return;
            // Cancel any in-flight hide timer for this pid (handles unlikely overlap edge case)
            if (cache.hideTimerId !== undefined) {
                Timers.clear(cache.hideTimerId);
                cache.hideTimerId = undefined;
            }
            safeSetUITextLabel(cache.text, message);
            safeSetUIWidgetVisible(cache.root, true);
            cache.hideTimerId = Timers.setTimeout(() => {
                cache.hideTimerId = undefined;
                safeSetUIWidgetVisible(cache.root, false);
            }, DISPLAY_DURATION_MS);
        });
    }

    // Lazy build (per-PID per Q2 default). Called from broadcastToAllPlayers if the pid's
    // widget doesn't exist yet. Could be made eager (built at top-HUD-shell init) if we
    // want to avoid the first-broadcast latency hit.
    function ensureDelayBroadcastWidget(pid: number, player: mod.Player): DelayBroadcastWidgetCacheEntry | undefined {
        const existing = State.hudCache.delayBroadcastByPid[pid];
        if (existing?.root && existing?.text) return existing;
        // ... safeParseUI build for root container + text widget
        // Position: just below the engage panel. Approximate Y = TWL_CONQUEST_HUD_COMBAT_Y + ~80
        // Style: white text, fontSize ~22, centered. Background blur container similar to engageStatusBox.
    }

    export function destroyDelayBroadcastWidgetForPid(pid: number): void {
        const entry = State.hudCache.delayBroadcastByPid[pid];
        if (!entry) return;
        if (entry.hideTimerId !== undefined) Timers.clear(entry.hideTimerId);
        if (entry.root) {
            try { mod.DeleteUIWidget(entry.root); } catch {}
        }
        delete State.hudCache.delayBroadcastByPid[pid];
    }

    export function forceHideDelayBroadcastForAllPlayers(): void {
        for (const pid of Object.keys(State.hudCache.delayBroadcastByPid)) {
            const cache = State.hudCache.delayBroadcastByPid[Number(pid)];
            if (!cache) continue;
            if (cache.hideTimerId !== undefined) Timers.clear(cache.hideTimerId);
            cache.hideTimerId = undefined;
            safeSetUIWidgetVisible(cache.root, false);
        }
    }
}
```

## Edge cases

1. **Match end during a pending broadcast.** `cancelDelayBroadcasts()` is called from `endMatch` and `triggerFreshMatchSetup` — bumps the token so any in-flight timer no-ops. Force-hides currently visible broadcasts. ✓
2. **Late-joiner during the LIVE phase.** Player who joins at LIVE+45s missed the LIVE+30s broadcast. **Open: Q5.** Default behavior in the spec above: late-joiners see only future broadcasts (the past one already fired). Replay would require `getSecondsSinceLive()` check on join + replay any broadcasts whose delay has elapsed. **Recommendation: no replay** — the broadcast is a "moment of unlock" announcement, not a state indicator. The player can see what's available by trying to use it.
3. **Multiple broadcasts queued in the same frame.** Each `Timers.setTimeout` fires independently. If two delays happen to be the same value (unusual but possible if a map sets `roundStartAirDelay = roundStartForwardDeployDelay`), both broadcasts fire same frame. The second overwrites the first (the per-pid `hideTimerId` cancellation in `broadcastToAllPlayers` handles this gracefully — second broadcast's text replaces first's text + restarts the 5s timer). Out of scope for tunings to deliberately overlap, but the code handles it.
4. **Disconnected pid mid-broadcast.** The widget gets destroyed in `cleanupHudForPid`. The `hideTimerId` is cancelled. Pending broadcast timers for that pid would call `safeSetUIWidgetVisible` against a destroyed widget — `safe*` wrappers absorb the error. ✓
5. **Map without delay tunables set (`undefined`).** `scheduleOne` early-returns if delay is undefined or zero. Maps that don't set a tunable get no broadcast for that surface. ✓
6. **Match restarts with same map.** `triggerFreshMatchSetup` calls `cancelDelayBroadcasts`, then `startMatch` re-schedules. Clean cycle. ✓
