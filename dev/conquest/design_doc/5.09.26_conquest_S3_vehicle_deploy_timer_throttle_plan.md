# Plan: S3 — Vehicle Deploy Timer HUD Broadcast Throttle

**Date:** 2026-05-09
**Baseline:** v1.496 (long-match audit L1 dead-code-removed; A11 superseded)
**Status:** Awaiting approval
**Target ship:** v1.497
**Tier reference:** Tier S row S3 in [`conquest_optimization_analysis.md`](./conquest_optimization_analysis.md)

## Context

The v1.491 8–10 player MP playtest crashed with `Mod has been running for 1,716ms this frame which exceeds max evaluation time of 1,000ms`. The crash signature is the per-frame eval cap (1,000ms hard), distinct from the v1.406 16-player heap-OOM. User-clarified scope (2026-05-09): the script restarts at match end, so the 1,716ms breach is **within-match accumulation**, not a multi-match drift. Capture-point storm explicit testing did NOT reproduce the spike, weakening the S1/S2 (combat HUD) hypothesis.

**Why S3 is now the leading candidate.** `updateVehicleDeployTimerHudForAllPlayers()` at [`vehicles/deploy-timer-ui.ts:1837`](../src/vehicles/deploy-timer-ui.ts#L1837) is fired by 26 call sites across `src/`, including:
- 7× in `vehicles/hq-deploy.ts` (HQ deploy state changes)
- 7× in `vehicles/vanilla-spawner.ts` (vehicle spawn/destroy/relocate)
- 2× in `index/vehicle-events.ts` (vehicle enter / exit) ← **active-combat hot path**
- 3× in `conquest-flow.ts` (match start / end / fresh setup)
- 2× in `ready-dialog/countdown-flow.ts`
- 1× each in 5 other files
- Plus an unconditional 1Hz call from `onLiveTick` (Tier S6 noted this).

Each call iterates all valid players via `forEachValidPlayer((player) => refreshVehicleDeployTimersForPlayerPreservingVisibility(player))`. The per-player path at [`deploy-timer-ui.ts:1763`](../src/vehicles/deploy-timer-ui.ts#L1763) builds a render plan over all 16 vehicle slots, computes a `lastRenderSignature`, and short-circuits DOM writes if the signature matches — but the **plan-build cost** (the expensive part) runs every time. In active 8–10p combat, vehicle enter/exit storms commonly fire 5–15 broadcasts within a 1-second window; HQ-deploy churn piles on top. **None of the 26 call sites are throttled.**

This plan ships a 200ms coalescing debouncer inside the broadcast wrapper. All 26 call sites stay untouched; the throttle is internal. Bursts within 200ms collapse into 1 broadcast. The existing `lastRenderSignature` short-circuit keeps doing its DOM-write dedupe at the per-player layer.

**This fix is a tool, not a guaranteed v1.491 cure.** It removes one of the strongest Tier S candidates from the picture. Whether it's the dominant cause becomes measurable via the diagnostic-toggle MP playtest — if the spike persists with Vehicle Overlay disabled (which short-circuits this entire surface) but is mitigated with S3 shipped, that's the bisection signal we need.

## Bundle / heap / CPU budget impact

| Budget | Current (v1.496) | Post-S3 estimate | Verdict |
|---|---:|---:|---|
| Bundle bytes (1 MiB cap) | 924,749 (11.81% headroom) | ~924,900 (+~150 B for coalescer logic) | ✅ trivial |
| Heap (16p crash, post-Wave-6 stable) | stable | unchanged (no new persistent state) | ✅ zero impact |
| Per-frame CPU (1,000ms hard cap) | active blocker | **~5–10× fewer vehicle-HUD broadcasts** in active combat clusters | ✅ direct attack on Tier S3 |

**CPU win mechanics.** Each broadcast costs O(N players × 16 vehicle slots × per-row state compute). At 16 players that's ~256 slot-state computes per broadcast. With the throttle:
- Pre-S3: 5–15 broadcasts/sec during active combat = 1,280–3,840 slot-computes/sec
- Post-S3: 1 broadcast every 200ms ceiling = ≤5 broadcasts/sec = ≤1,280 slot-computes/sec
- Steady-state idle (1Hz from `onLiveTick`): unchanged at 1 broadcast/sec — the 1Hz call coalesces into itself harmlessly.

## Goals

1. Replace the `updateVehicleDeployTimerHudForAllPlayers()` body with a 200ms-debouncing coalescer.
2. Preserve all 26 fire-and-forget call sites unchanged.
3. Preserve all per-player render logic (`refreshVehicleDeployTimersForPlayerPreservingVisibility`, `buildVehicleDeployTimerRenderPlan`, signature short-circuits) unchanged.
4. Add a single cleanup line at game-mode init to clear any pending coalesce timer (R4 mitigation).
5. Document the 200ms intentional latency in the function's leading comment so future readers know it's deliberate.

## Implementation

### Phase 1 — Add the coalescer to `vehicles/deploy-timer-ui.ts`

Three additions near the top of the file (just below existing module-local declarations):

```ts
// S3 (v1.497): broadcast-throttle state. updateVehicleDeployTimerHudForAllPlayers()
// is called from 26 fire-and-forget sites + an unconditional 1Hz onLiveTick.
// Coalescing into a 200ms window cuts active-combat broadcast frequency by ~5–10×.
// User-approved 2026-05-09: timer doesn't need hyper-accurate frame-coincident
// updates; "can catch up within reason."
let vehicleDeployTimerHudDirty = false;
let vehicleDeployTimerHudCoalesceTimerId: number | undefined = undefined;
const VEHICLE_DEPLOY_TIMER_HUD_COALESCE_MS = 200;
```

Replace the body of `updateVehicleDeployTimerHudForAllPlayers` at line 1837:

```ts
// S3 (v1.497): debounces N-player broadcast into 200ms windows.
// First call schedules the timer; subsequent calls within the window flip the
// dirty flag and return immediately. After the window fires, the next call
// starts a fresh 200ms window. Per-player render path (refreshVehicleDeploy...)
// is unchanged and still does its lastRenderSignature DOM-write dedupe.
function updateVehicleDeployTimerHudForAllPlayers(): void {
    vehicleDeployTimerHudDirty = true;
    if (vehicleDeployTimerHudCoalesceTimerId !== undefined) return;
    vehicleDeployTimerHudCoalesceTimerId = Timers.setTimeout(() => {
        vehicleDeployTimerHudCoalesceTimerId = undefined;
        if (!vehicleDeployTimerHudDirty) return;
        vehicleDeployTimerHudDirty = false;
        forEachValidPlayer((player) => refreshVehicleDeployTimersForPlayerPreservingVisibility(player));
    }, VEHICLE_DEPLOY_TIMER_HUD_COALESCE_MS);
}
```

### Phase 2 — Add a cleanup helper for game-mode init (R4 mitigation)

Add a small exported helper next to the module-local declarations:

```ts
// S3 (v1.497): clear any pending coalesced broadcast at game-mode init so a
// stale timer can't fire into freshly-reset state.
function clearVehicleDeployTimerHudCoalesceTimer(): void {
    if (vehicleDeployTimerHudCoalesceTimerId !== undefined) {
        try { Timers.clearTimeout(vehicleDeployTimerHudCoalesceTimerId); } catch {}
        vehicleDeployTimerHudCoalesceTimerId = undefined;
    }
    vehicleDeployTimerHudDirty = false;
}
```

**Verified 2026-05-09:** `Timers.clearTimeout(id)` exists at [`foundation/bf6-utils/timers.ts:83`](../src/foundation/bf6-utils/timers.ts#L83) and routes to `Timers.clear(id)` which silently ignores null/undefined/unknown IDs. The cleanup helper above is correct as written; no fallback needed.

### Phase 3 — Wire the cleanup into game-mode init

In [`index/game-mode.ts`](../src/index/game-mode.ts), append one line to the existing per-mode-init reset block (currently lines 53-54):

```ts
vehIds.length = 0;
vehOwners.length = 0;
clearVehicleDeployTimerHudCoalesceTimer();   // NEW
```

This guarantees no stale timer survives across mode-init.

## Risks and mitigations

| # | Risk | Likelihood | Mitigation |
|---|------|:---:|------------|
| **R1** | A caller depends on the broadcast having completed before the next line runs (synchronous read of post-broadcast HUD state). | Very Low | All 26 call sites are fire-and-forget on a `void`-returning function. **Verified** by signature inspection: `function updateVehicleDeployTimerHudForAllPlayers(): void`. No call site awaits or reads post-broadcast state. |
| **R2** | Player joins, broadcast scheduled, player leaves before drain fires. Drain iterates stale player. | Low | `forEachValidPlayer` validates each player at iteration time. `refreshVehicleDeployTimersForPlayerPreservingVisibility` re-validates `isValidPlayer` + `safeGetPlayerId` and short-circuits on either. Existing pattern already handles this. |
| **R3** | Match ends mid-window. Drain fires after teardown, dispatches against destroyed cache. | Low | Same idempotence as R2 — `refreshVehicleDeployTimersForPlayerPreservingVisibility` validates the cache exists at line 1786 (`if (!cache \|\| !cache.root) return false;`). Post-teardown caches are absent → safe no-op. |
| **R4** | Game-mode reinit while a timer is pending. Old timer fires into new game-mode state. | Medium (without mitigation) | Phase 2+3: `clearVehicleDeployTimerHudCoalesceTimer()` called at game-mode init in `index/game-mode.ts` invokes `Timers.clearTimeout` (verified at [`foundation/bf6-utils/timers.ts:83`](../src/foundation/bf6-utils/timers.ts#L83)) and resets the dirty flag. Belt-and-suspenders: even if the timer fires, the false dirty flag short-circuits the drain. |
| **R5** | Admin Toggle Vehicle Overlay flip → 200ms delay before vehicles disappear. | Very Low | Pre-existing accepted UX from v1.494 (admin already accepted ~200ms toggle latency). User-approved 2026-05-09. |
| **R6** | LIVE-burst at startMatch fires multiple broadcasts in `startMatch`. They coalesce into one 200ms-later fire. | Very Low | The user has already documented "slight hitch at LIVE" (Tier S7). S3 makes this *better*, not worse — many broadcasts collapse to one. |
| **R7** | `runRoundStartDelayHudLoop` final `updateVehicleDeployTimerHudForAllPlayers()` is delayed by 200ms. | Very Low | Loop already runs at 1Hz; one extra 200ms after the last tick is imperceptible. The per-second visible-pid path (`updateVehicleDeployTimerHudForViewers`) is NOT throttled and continues to drive the visible countdown updates. |
| **R8** | A test/SP repro that previously saw "instant" HUD update now sees 200ms lag and gets misreported as a regression. | Low | Phase 1 comment block above the function documents the 200ms intentional delay. Changelog entry references S3. Plan doc archived for historical reference. |
| **R9** | `Timers.setTimeout` semantics in Portal sandbox differ from expected. | Very Low | Pattern is battle-tested: same API used at [`delay-broadcast.ts:94`](../src/index/delay-broadcast.ts#L94), [`build-pacer.ts:91`](../src/interaction/build-pacer.ts#L91), [`supply-box-warm-scheduler.ts:87`](../src/interaction/supply-box-warm-scheduler.ts#L87). Project-memory `vanilla-spawner v1.261 fix` lesson (no global `setTimeout`; use `Timers.setTimeout`) already incorporated. |
| **R10** | A vehicle spawns within the 200ms window but the drain renders a stale plan that misses it. | Very Low | Render plan is computed at **drain time**, not at flag-set time. Latest state always wins. The dirty flag is just a "needs refresh" signal; the actual `buildVehicleDeployTimerRenderPlan` reads live state when it runs. |
| **R11** | A future maintainer adds a 27th call site that needs synchronous behavior, doesn't realize the broadcast is throttled, and ships a UX bug. | Low | Phase 1 leading comment documents the 200ms delay. Plan doc archived. If a synchronous use case ever appears, the `force?: boolean` parameter can be added later — explicitly NOT adding it now per locked decision #2 to keep the surface area minimal. |
| **R12** | Combat HUD already throttles at 200ms via a different mechanism (time-based gate). Two surfaces with the same window may collide on the same tick and produce a double-cost frame. | Very Low | The two are independent: combat HUD throttle is owned by `twlConquestHudTickFrame` which is driven by the engine's per-tick callback; vehicle HUD throttle is `Timers.setTimeout`-driven. Even if they fire on the same engine tick, the per-frame work is what we *want* — concentrated, not spread. The 1716ms breach was about per-frame work piling up unbounded, not about two surfaces sharing a frame. |
