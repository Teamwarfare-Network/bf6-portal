## Context

The binding constraint is still runtime JS heap. Wave 5 attacks the **per-element** level for one specific kind of widget: digit-rendering timers. Timer digits are per-pid `Text` widgets that:
1. Carry diff-cache fields (`lastText`) to suppress redundant `mod.SetUITextLabel` calls.
2. Update on every clock tick that has a value change (~1Hz).
3. Live in the M1 vehicle-deploy-timer mega-cache, the boundary prompt cache, and the pregame countdown widget.

Replacing digit timers with non-digit indicators (color shift, bar fill, etc.) potentially:
- Drops `lastText` diff-cache fields from per-pid caches.
- Replaces `SetUITextLabel` calls with `SetUIWidgetSize` / `SetUIWidgetBgColor` calls (similar cost, but no string allocation).
- Reduces visual noise; ambient indication is gentler than a counting digit.

### What's NOT changing

- Master clock (top HUD shell digit display) stays digital — it's the canonical match-time reference.
- Per-PID UI scope.
- Lazy-build dispatcher.
- Wave 1-4 leak fixes + lazy migrations + admin model.
- The vehicle-spawn lifecycle (when vehicles spawn, who can deploy them) — only the *display* of the countdown changes.

The estimated heap win is small because timer digit widgets are themselves cheap. The bigger gain is **CPU + GC pressure** — string allocation per tick × N pids × M timers compounds. Indicator updates (color shift, size change) are allocation-free.

### Q1 — Which timers convert?

The candidate timers in the codebase, ordered by visibility:

| Timer | Where | Currently rendered as | Update cadence |
|-------|-------|------------------------|----------------|
| **Master match clock** | Top HUD shell | Digital "MM:SS" | 1Hz |
| **Vehicle deploy timer** (per-vehicle countdown to next spawn) | Vehicle deploy timer HUD (M1) | Digital "Ns" per row | ~1Hz |
| **Pregame countdown** (3...2...1...LIVE!) | Center-screen overlay | Big digital "N" then "LIVE!" | 1Hz |

**Recommendation:**
- **Convert:** vehicle deploy timer (heaviest, M1) + deploy delay timers (live in same HUD, share cache).
- **Keep digital:** master clock (locked by design doc), pregame countdown (player needs the literal "3, 2, 1"), boundary kill ("You will die in 3s..." reads better as a digit when the duration is short).

**Your answer (list which convert / which stay digital):**

the vehicle deploy timers, and deploy delay timers and vehicle abandon timers all need to go away. We're going to change them to a single string. These are just visual changes. Nothing changes under the hood. The clock style digital timers all need to go way, and we're changing them to behave differently

### Q2 — Indicator style

Once we know which timers convert (Q1), we need to pick the visual style. Options:

- **A. Color shift only** — single existing widget, color interpolates green → yellow → red as time decreases. Smallest code change (no new widget shapes, just per-tick `SetUIWidgetBgColor` calls). Loses the literal "how much time is left" precision.
- **B. Progress bar** — replace the digit text widget with a thin bar widget that fills/empties. Adds a widget per timer (border + fill = 2 widgets vs 1 text), but conveys magnitude clearly. Bar width can be small (e.g., 80×6).
- **C. Bar + color** — bar fills/empties AND color shifts. Most info, biggest widget cost (~3 widgets per timer: border, fill, color overlay).
- **D. Pulse / glow** — single widget that pulses faster as time runs out. Compact but less informative.

**Recommendation:** **B** — progress bar. Conveys magnitude (which players intuitively need for "is the helo about to spawn?") without the per-tick string allocation cost. Keep it minimal (1 border widget + 1 fill widget per row, fill width updates per tick).

**Your answer (A / B / C / D, or per-timer mix): Lets do B, but I don't want it updating per tick, that's obscenely expensive. 

---

### Q3 — Backwards compat: players already deployed when Wave 5 ships?

Switching the deploy timer from digit to bar means widget tree shape changes. Per-pid caches built before the bump have a digit text widget; new pids have a bar widget. Three options:

- **A. Mid-match upgrade — destroy stale caches on first OnPlayerDeployed after the bump, force fresh build.** Brief hitch on each player's next deploy event. Mixed-shape state lasts only until each player's next death/respawn.
- **B. Defer — let stale caches persist for the current match; new pids get the new shape.** Mixed-state during the round but no hitch.
- **C. Restart-required — bumpVersion + plan around a map restart.** Cleanest but inflexible.

**Recommendation:** **A** — destroy on next deploy event. Wave 3's lazy-build dispatcher already handles cache invalidation cleanly (`destroyVehicleDeployTimerHudArtifactsForPid` exists today). Brief hitch is acceptable since the player is in the deploy screen anyway.

**Your answer (A / B / C):** We're changing all the digital stylized timers, so there should be no transition.

### Final locked decisions

| ID | Decision |
|----|----------|
| **L1** | Underlying timer logic untouched. Pure UI swap; clock module + spawn lifecycle + abandon detection + deploy delays all unchanged. |
| **L2** | Master clock stays digital. (Locked by `conquest_design.md`.) |
| **L3** | Pregame countdown stays digital. Player needs the literal "3, 2, 1" cue. |
| **L4** | Boundary kill countdown stays digital. "You will die in 3s..." reads better as a digit at short durations. |
| **L5** | Replacement style is a progress bar. Border + fill widgets per row (2 widgets vs the existing 1 text widget per row). |
| **L6** | No migration logic. Bundle upload → script reload starts every cache fresh; there is no mid-match hot-swap to worry about. |
| **L7** | Per-vehicle name label stays verbatim. Only the digit timer text widget is replaced by the bar. No new state labels, no shared HUD-level string. |
| **L8** | Bar fill updates in **decile chunks (10% increments)**. The 1Hz tick path computes `decile = Math.floor(elapsedFraction * 10)` (0-10 inclusive); `mod.SetUIWidgetSize` fires only when the decile changes vs the last-rendered value. Result: ~10 widget writes per countdown regardless of timer duration. Per-row diff field is `lastDecile: number`. |
| **L9** | Vehicle abandon timer scope is explicit no-op. No widget exists today; nothing to remove. |
| **L10** | **Bar position + dimensions match the existing digit timer slot.** Same widget location, same approximate footprint (~40-60px wide × ~20px tall). |
| **L11** | **Bar fills UP (0% → 100%) over the cooldown duration.** Decile math uses elapsed-fraction (not remaining): `decile = Math.floor(elapsedFraction * 10)`. Fill width = `Math.floor(barMaxWidth * (decile / 10))`. So decile 0 = empty (cooldown just started), decile 10 = full (cooldown complete). |
| **L12** | **Bar fill color = red** (`COLOR_RED`). At 100% the bar HIDES and the existing `statusText` widget becomes visible with label "READY" in green (`COLOR_READY_GREEN`). The READY swap is **not** the responsibility of the bar update function — it's already handled at the deploy-timer-ui call site (which calls `setReusableTimerStatus(row.timer, "ready", ...)` when remaining ≤ 0). The bar function only owns the timer-mode rendering. |
| **L13** | **Pre-Ship-1 finding: actual widget swap is −10 digit widgets + 2 bar widgets = −8 widgets per row** (not the +2 the plan originally estimated). The existing `ReusableTimerWidgetCacheEntry` carries 5 digit widgets (`minTens`, `minOnes`, `colon`, `secTens`, `secOnes`) + 5 shadow widgets — all per row. Replacing them with `barBorder` + `barFill` is a net −8 widgets per row (per pid: ~12 rows × −8 = −96; at 24 pids: ~2,300 widget refs reclaimed). The `statusText` + `statusShadow` widgets stay unchanged (already handle READY/ACTIVE/SPAWNING/DEPLOYING modes). |
| **L14** | **Function signature change: `setReusableTimerSeconds(cache, totalSeconds)` → `setReusableTimerProgress(cache, elapsedFraction)`.** Caller computes elapsed fraction from total + remaining (both already available at every call site: `roundStartAirDelay` for air delay, `slot.respawnDelaySeconds` for vehicle respawn). Function body becomes the decile-chunk update from L8. The `lastDisplayedSeconds` cache field becomes `lastDecile`. Other status modes (READY/ACTIVE/SPAWNING/DEPLOYING) keep `setReusableTimerStatus` unchanged. |

**Implementation note (per L8 + L11 + L14 — decile-chunk fill-up; READY swap stays at deploy-timer-ui call site):**

```ts
// New function in clock/timer-instance.ts
function setReusableTimerProgress(cache: ReusableTimerWidgetCacheEntry, elapsedFraction: number): void {
    // Mode swap to "timer" if needed (mirrors the old setReusableTimerSeconds prologue):
    // hide statusText + statusShadow, show bar widgets.
    if (cache.lastStatusMode !== "timer") {
        safeSetUIWidgetVisible(cache.statusShadow, false);
        safeSetUIWidgetVisible(cache.statusText, false);
        safeSetUIWidgetVisible(cache.barBorder, true);
        safeSetUIWidgetVisible(cache.barFill, true);
        cache.lastStatusMode = "timer";
    }
    // Decile-chunk diff-cache (L8): clamp to 0..10, only fire SetUIWidgetSize on transition.
    const clamped = elapsedFraction <= 0 ? 0 : elapsedFraction >= 1 ? 1 : elapsedFraction;
    const decile = Math.floor(clamped * 10);
    if (decile === cache.lastDecile) return;
    const fillPx = Math.floor(barMaxWidth * (decile / 10));
    mod.SetUIWidgetSize(cache.barFill, mod.CreateVector(fillPx, barHeight, 0));
    cache.lastDecile = decile;
}
```

The READY swap (decile reaches 10 → cooldown complete → show "READY" in green) is **not** in this function. It happens at the deploy-timer-ui call site, which already calls `setReusableTimerStatus(row.timer, "ready", msg(...), COLOR_READY_GREEN)` when `getVehicleSlotRespawnRemainingSeconds(slot) <= 0`. That path swaps `lastStatusMode` from `"timer"` → `"ready"`, hides the bar widgets, and shows `statusText` with the "READY" label. No double-handling.

**Visual flow per row (across one cooldown cycle):**

| Cooldown progress | Decile | Visible | Label | Color |
|---|---|---|---|---|
| 0-9% (just started) | 0 | bar (empty) | — | red fill |
| 10-19% | 1 | bar (10% filled) | — | red fill |
| 20-29% | 2 | bar (20% filled) | — | red fill |
| ... | ... | ... | ... | ... |
| 90-99% | 9 | bar (90% filled) | — | red fill |
| 100% (complete) | 10 | text | "READY" | green |

For a 60s cooldown that's 11 visibility/style transitions total (vs ~60 widget writes with continuous-bar or text approaches).

### Risks (final)

- **R1 (RESOLVED v0.3) — ~~Diff-cache coherence on widget-type change.~~** Per L6, no in-place migration needed. Script reload builds fresh caches with the new shape.
- **R2 (LARGELY MITIGATED v0.3) — `mod.SetUIWidgetSize` CPU cost at scale.** L8's decile-chunk gate caps writes at ~10 per countdown per row. For 24 pids × 12 rows × decile transitions: even if every row's decile crosses simultaneously (vanishingly unlikely outside the wave-of-spawns frame), total writes are bounded at 24 × 12 = 288 per crossing event, and crossings are temporally spread across the countdown. Steady-state is closer to 1-3 writes/sec across the whole HUD. **Mitigation:** L8 already mitigates by design; subjective MP smoke check confirms.
- **R3 — UX readability for short-duration timers (with 10-step decile cadence).** The shortest deploy timers are typically ~10s; bar fills in 10 visible steps regardless of duration, so a 10s timer steps every ~1 second (one chunk per tick — almost continuous-feeling). Long timers (~120s) step every ~12 seconds (visibly chunky). **Mitigation:** L11 + L12 confirm "READY" green text appears at 100% so the cooldown-complete state is unambiguous regardless of how chunky the bar steps felt. Subjective UX check during SP smoke validates the chunkiness is acceptable; if not, drop to 20-step (5%) chunks as a post-ship tune.
- **R4 (RESOLVED v0.3) — ~~Mixed-state appearance during mid-match upgrade.~~** Per L6, no upgrade path; obsoleted.
