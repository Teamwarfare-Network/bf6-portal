## Context

The binding constraint is still runtime JS heap. Wave 5 attacks the **per-element** level for one specific kind of widget: digit-rendering timers. Timer digits are per-pid `Text` widgets that:
1. Carry diff-cache fields (`lastText`) to suppress redundant `mod.SetUITextLabel` calls.
2. Update on every clock tick that has a value change (~1Hz).
3. Live in the M1 vehicle-deploy-timer mega-cache, the boundary prompt cache, and the pregame countdown widget.

Replacing digit timers with non-digit indicators (color shift, bar fill, etc.) potentially:
- Drops `lastText` diff-cache fields from per-pid caches.
- Replaces `SetUITextLabel` calls with `SetUIWidgetSize` / `SetUIWidgetBgColor` calls (similar cost, but no string allocation).
- Reduces visual noise; ambient indication is gentler than a counting digit.

### What's NOT changing

- Master clock (top HUD shell digit display) stays digital — it's the canonical match-time reference.
- Per-PID UI scope.
- Lazy-build dispatcher.
- Wave 1-4 leak fixes + lazy migrations + admin model.
- The vehicle-spawn lifecycle (when vehicles spawn, who can deploy them) — only the *display* of the countdown changes.

| # | Topic | Estimated effort | Estimated heap win |
|---|-------|------------------|---------------------|
| **#5** | Timers everywhere except master clock → color/percentage/bar indicators (no digits) | 1 day | Small per-pid (digit `lastText` diff-cache fields drop), small CPU (no string allocation per tick) |

The estimated heap win is small because timer digit widgets are themselves cheap. The bigger gain is **CPU + GC pressure** — string allocation per tick × N pids × M timers compounds. Indicator updates (color shift, size change) are allocation-free.

### Q2 — Indicator style

Once we know which timers convert (Q1), we need to pick the visual style. Options:

- **A. Color shift only** — single existing widget, color interpolates green → yellow → red as time decreases. Smallest code change (no new widget shapes, just per-tick `SetUIWidgetBgColor` calls). Loses the literal "how much time is left" precision.
- **B. Progress bar** — replace the digit text widget with a thin bar widget that fills/empties. Adds a widget per timer (border + fill = 2 widgets vs 1 text), but conveys magnitude clearly. Bar width can be small (e.g., 80×6).
- **C. Bar + color** — bar fills/empties AND color shifts. Most info, biggest widget cost (~3 widgets per timer: border, fill, color overlay).
- **D. Pulse / glow** — single widget that pulses faster as time runs out. Compact but less informative.

**Recommendation:** **B** — progress bar. Conveys magnitude (which players intuitively need for "is the helo about to spawn?") without the per-tick string allocation cost. Keep it minimal (1 border widget + 1 fill widget per row, fill width updates per tick).

### Q3 — Backwards compat: players already deployed when Wave 5 ships?

Switching the deploy timer from digit to bar means widget tree shape changes. Per-pid caches built before the bump have a digit text widget; new pids have a bar widget. Three options:

- **A. Mid-match upgrade — destroy stale caches on first OnPlayerDeployed after the bump, force fresh build.** Brief hitch on each player's next deploy event. Mixed-shape state lasts only until each player's next death/respawn.
- **B. Defer — let stale caches persist for the current match; new pids get the new shape.** Mixed-state during the round but no hitch.
- **C. Restart-required — bumpVersion + plan around a map restart.** Cleanest but inflexible.

**Recommendation:** **A** — destroy on next deploy event. Wave 3's lazy-build dispatcher already handles cache invalidation cleanly (`destroyVehicleDeployTimerHudArtifactsForPid` exists today). Brief hitch is acceptable since the player is in the deploy screen anyway.

## Risks (preliminary)

- **R1 — Diff-cache coherence on widget-type change.** Old per-pid cache has `lastText: string`; new shape has `lastFillFraction: number`. Migration path must avoid mixed-shape errors. **Mitigation:** mid-match upgrade per Q3=A destroys stale caches; new shape is fresh.
- **R2 — `SetUIWidgetSize` per-tick CPU cost.** If the engine has a per-call cost we don't see in profiling, the conversion could regress CPU even as it saves heap. **Mitigation:** existing diff-cache pattern (skip writes when value unchanged) carries over; bar fill rounded to integer pixels naturally suppresses sub-pixel updates.
- **R3 — UX readability for short-duration timers.** A 5-second progress bar reads worse than "5...4...3...2...1" digits. **Mitigation:** Q1 recommendation keeps short-duration timers (boundary kill, pregame) as digits; only the longer-duration vehicle deploy timer (typically 30s-2min) converts.
- **R4 — Mixed-state appearance during mid-match upgrade.** Players who deployed before the bump see digits; players who deployed after see bars. Visually inconsistent until everyone has redeployed. **Mitigation:** Q3=A destroys the cache on next deploy, so all players reach the new shape within a few death/respawn cycles. Single-round inconsistency is acceptable.
