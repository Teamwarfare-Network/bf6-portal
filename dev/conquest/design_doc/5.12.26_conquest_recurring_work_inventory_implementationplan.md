**Fix (ship BEFORE D1+C1, or fold into W2's preamble):**


This is a 1-line addition. Idempotent (setPlayerSeatKind short-circuits on no-change at line 164). Zero regression risk on its own.

**Why this wasn't caught earlier:** OnPlayerExitVehicle IS reliable in practice, so the stale-seatKind scenario only triggers in edge cases (suicide via /killme, vehicle destruction by engine without exit event, etc.). But D1+C1 amplify the failure mode by gating MORE behavior on seatKind correctness.

**Bump message for the prerequisite:**

## E1 design adjustment (post-verification)

The v2 plan claimed combat HUD's `markHudDirty` contract is a SUPERSET of top-HUD-derived inputs. Verification:

- 16 `markHudDirty()` call sites across 6 files. Covers: cap-point state mutations, ticket changes, engage state changes, ready toggle (via spectator-action.ts:453), spectator enter/exit, team swap, admin toggle, player undeploy.
- **Missing site: `onPlayerDeployedImpl` does NOT call markHudDirty.** It calls `markPregameReadyHudDirty` (line 50) but that gates only the pregame-flush path, not the live combat HUD.

**Impact on E1:** after a deploy event during LIVE, the status/help-ready VMs would not rebuild until the NEXT markHudDirty fires (capture state change, etc.). Worst case: ~120ms staleness window where status dock shows pre-deploy ready counts.

**Resolution options:**

- **E1.b adjusted (recommended):** add one `markHudDirty()` call to `onPlayerDeployedImpl` after `State.players.deployedByPid[pid] = true`. Closes the gap with a single-line addition. Updates E1's regression risk from Medium to Low.
- **E1.b accept staleness:** ship as designed; document the 120ms post-deploy window. Acceptable because: (a) the same frame's deploy event triggers `renderCriticalHudForReveal` which handles per-pid widget refresh directly; (b) the global status counts only update when SOMETHING in the room changes, and a deploy event almost always coincides with a capture-state change anyway.

**Recommendation:** ship E1.b adjusted (add the markHudDirty call). The 1-line addition is essentially free and removes a known staleness window.

## Wave 1: A1 + B7 -- collapse the force-broadcast burst pattern

### A1: Per-pid scope for force-true combat HUD broadcasts

#### Problem

`area-triggers.ts:47` and `area-triggers.ts:66` call `updateConquestCombatHudForAllPlayers(force=true)` on every capture-point enter/exit. A 5-player capture-point cluster in one engine frame produces 5 forced N-player broadcasts. Each broadcast does ~256 widget passes at 64p. The force flag bypasses the 200ms throttle AND the dirty gate.

#### Design alternatives considered

| Option | Mechanism | Why considered | Why accepted/rejected |
|---|---|---|---|
| **A1.a** | New per-pid entry `updateConquestCombatHudForPlayer(player, pid)` that calls existing helpers in sequence | Smallest behavioral change. Clean call-site swap. | **ACCEPTED.** Aligns with existing per-pid helpers (`ensureTopHudDerivedSlicesForPid` already exists at capture-tickets.ts:218). Reuses `twlConquestHudProcessPlayerFrame` from pipeline.ts. No new types. |
| **A1.b** | Modify `updateConquestCombatHudForAllPlayers` to accept an optional pid filter | One fewer function. | **REJECTED.** Adds a branch to a hot-path function. The filter check would run on every subtick's normal broadcast too, paying a permanent cost for an event-driven path. Worse separation of concerns. |
| **A1.c** | Pass `pid[] = [pid]` for the per-pid case, `pid[] = allPids` for broadcast | Unifies the surface. | **REJECTED.** Forces every existing call site to construct an array; adds allocation overhead to the broadcast path that doesn't have one today. |
| **A1.d** | Per-pid dirty flag system: mark pid dirty on event, broadcast picks it up at next subtick | Architecturally cleanest. | **REJECTED FOR W1.** This is solution E3 (Tier 5 in the solutions catalog). Multi-week refactor. Out of scope for Wave 1. |
| **A1.e** | Defer broadcast to next subtick via `Timers.setTimeout(0)` | Removes synchronous N-player work from the event frame. | **REJECTED.** The engaging player's engage HUD lag would be visible (~16-32ms at 60Hz render, plus 100ms+ until next subtick processes). Capture-point feedback UX requirement is immediate-feel. |

#### Recommended approach: A1.a

A new per-pid entry that uses the existing `ensureTopHudDerivedSlicesForPid` helper (already exists, already does the per-pid VM publish) and calls `twlConquestHudProcessPlayerFrame` directly (bypassing `twlConquestHudTickFrame`'s throttle, because the per-pid path is the throttle-bypass case by construction).

**Crucial design choice: do NOT touch global state.** The per-pid path must not:
- Clear `State.conquest.debug.hudDirty` (still set true by the `markHudDirty()` call already in the event handler at line 46/65 -- this ensures the NEXT subtick's broadcast catches the change for ALL OTHER viewers)
- Update `State.conquest.debug.hudLastUpdatedAtSeconds` (that's the broadcast tick stamp; per-pid is not a broadcast tick)
- Call `twlConquestHudTickAnimation` (that's a global animation stamp; next subtick handles it)

This is what changed from v1: v1's draft mistakenly set hudDirty = true inside the per-pid function and called the animation tick. Both wrong.

#### Implementation detail

**File:** [`index/capture-tickets.ts`](../src/index/capture-tickets.ts) -- add new function near the existing `updateConquestCombatHudForAllPlayers` at line 2109.

```ts
// Per-pid forced refresh of the combat HUD. Used by event handlers that need the affected
// player's HUD to update synchronously without paying the cost of a broadcast.
//
// Contract:
//  - Does NOT clear State.conquest.debug.hudDirty: the calling event handler must have
//    called markHudDirty() so the next subtick's normal broadcast catches OTHER viewers.
//  - Does NOT update hudLastUpdatedAtSeconds (that field tracks broadcast cadence).
//  - Does NOT run the animation tick (global; the next subtick runs it).
//  - Hud-mode "off": still tears down the per-pid widgets via twlConquestHudHidePlayer.
function updateConquestCombatHudForPlayer(player: mod.Player, pid: number): void {
    // Top-HUD slices (3 VMs) for this pid only. ensureTopHudDerivedSlicesForPid already exists
    // at capture-tickets.ts:218 -- reuse it instead of duplicating the derive+publish trio.
    ensureTopHudDerivedSlicesForPid(pid);

    const hudMode = getConquestHudMode();
    if (hudMode === "off") {
        twlConquestHudHidePlayer(pid);
        return;
    }

    try {
        const now = mod.GetMatchTimeElapsed();
        // Call twlConquestHudProcessPlayerFrame directly (NOT twlConquestHudTickFrame).
        // twlConquestHudTickFrame has the 200ms throttle that force=true bypasses; the per-pid
        // path bypasses by construction (no throttle gate to clear).
        twlConquestHudProcessPlayerFrame(player, now);
    } catch {
        // Match the broadcast loop's per-pid fault isolation pattern.
        twlConquestHudRecoverEntry(pid);
    }
}
```

**File:** [`index/area-triggers.ts`](../src/index/area-triggers.ts) -- swap 2 call sites.


**Why no broadcast cleanup is needed:** the existing `markHudDirty()` calls at area-triggers.ts:46 and :64 remain. On the next subtick (~120ms later), `runGameModeLoop` calls `updateConquestCombatHudForAllPlayers` with `force=undefined`. **Before A1:**
- Frame N: 5 forced broadcasts = 5 x ~256 widget passes = ~1,280 widget passes
- Frame N+1: 1 broadcast (dirty=true was set by all 5 events, only one broadcast needed) = ~256 passes
- Total: ~1,536 passes across 2 frames, ~1,280 of them in Frame N (over budget)

**After A1:**
- Frame N: 5 per-pid calls = 5 x ~4 widget passes = ~20 widget passes
- Frame N+1: 1 broadcast = ~256 passes
- Total: ~276 passes across 2 frames, peak frame ~256 passes (under budget)

Peak frame reduction: ~1,280 -> ~20 = ~64x. This is THE spike reclaim.

### B7: Suppress duplicate `onCapturePointTick` within 80ms

#### Problem

`area-triggers.ts:44` (inside `onPlayerEnterCapturePointImpl`) calls `onCapturePointTick(cp)` synchronously to refresh capture state before the force-broadcast. The very next subtick's `refreshLiveCaptureStateSubtick` recomputes the same cap-point ~120ms later. Both pay full cost.

#### Design alternatives considered

| Option | Mechanism | Why considered | Why accepted/rejected |
|---|---|---|---|
| **B7.a** | Tick-stamp dedup inside `onCapturePointTick`: skip if last tick was <80ms ago | Catches both event-driven and subtick paths automatically; no caller changes. | **ACCEPTED.** Single-point-of-truth dedup. Caller doesn't need to know about it. |
| **B7.b** | Remove the synchronous call at area-triggers.ts:44 entirely; rely on next subtick | Simplest -- one line delete. | **REJECTED.** The state update is consumed by the force-broadcast at line 47 (A1 per-pid path) for the entering player's engage count. Without it, the entering player's HUD shows stale flag onPointTeam1/2 for one subtick (~120ms visible lag). |
| **B7.c** | Move the synchronous tick into a helper that signals "the next subtick can skip this cap-point" via a per-cap-point flag | More explicit signaling. | **REJECTED.** More state; same outcome as B7.a but with extra plumbing. |
| **B7.d** | Use `Date.now()` for the stamp vs `mod.GetMatchTimeElapsed() * 1000` | Either works; matters for pause behavior. | **B7.a uses Date.now()** because the dedup is about wall-clock script-frame timing, not match time. If the match clock is paused (admin paused match), we still want the dedup to release after 80ms of real time. |

#### Recommended approach: B7.a with Date.now()

Add `lastTickAtMs: number` field on the existing capture-state object. At the top of `onCapturePointTick`, compare `Date.now() - lastTickAtMs` to the 80ms window. If too recent, return.

**Why 80ms specifically:** the subtick is ~120ms (`CONQUEST_LIVE_STATE_SUBTICK_SECONDS = 0.12`). 80ms is shorter, so a regularly-paced subtick is NEVER deduplicated against itself. Only the event-driven path that fires <80ms before the next subtick gets deduplicated. This is exactly what we want.

**Why not 100ms or 120ms:** with 120ms, the dedup window could span an entire subtick. A signature change at frame N inside an event could be deduplicated against the subtick at frame N+1 (also within 120ms), missing the update. 80ms gives ~40ms safety margin.

#### Implementation detail

**File:** [`index/capture-tickets.ts`](../src/index/capture-tickets.ts) -- modify `onCapturePointTick` at line 1728.

```ts
const CAPTURE_POINT_TICK_DEDUP_MS = 80; // <-- declared near line 22 with other capture timing constants

function onCapturePointTick(eventCapturePoint: mod.CapturePoint): void {
    if (!eventCapturePoint) return;
    const objId = safeGetObjId(eventCapturePoint);
    if (objId === undefined) return;
    configureCaptureTimingForPoint(eventCapturePoint, objId);

    const state = ensureCaptureState(objId);

    // B7: dedup against very-recent ticks. The 80ms window is shorter than the 120ms subtick
    // so adjacent subticks never deduplicate each other; only the event-driven path that
    // fires within 80ms of the next subtick gets skipped on the subtick side.
    // Date.now() is intentional (wall-clock, not match-clock) so admin-paused matches still
    // tick the dedup correctly.
    const nowMs = Date.now();
    const lastTickAtMs = state.lastTickAtMs ?? 0;
```

#### Problem

```ts
    const objId = safeGetObjId(eventCapturePoint);
    if (objId === undefined) return;
    configureCaptureTimingForPoint(eventCapturePoint, objId);

    const state = ensureCaptureState(objId);

    // B7 dedup window (already shipped W1).
    const nowMs = Date.now();
    const lastTickAtMs = state.lastTickAtMs ?? 0;
    if (nowMs - lastTickAtMs < CAPTURE_POINT_TICK_DEDUP_MS) return;
    state.lastTickAtMs = nowMs;

    // B1: cheap engine reads first. Used both for the fast-path signature AND for the
    // full-path computation. Computing them once avoids duplication when the fast-path
    // exits.
    let ownerTeam: TeamID | 0 = 0;
    let ownerProgressTeam: TeamID | 0 = 0;
    let progress01 = 0;
    try { ownerTeam = getTeamNumber(mod.GetCurrentOwnerTeam(eventCapturePoint)); } catch {}
    try { ownerProgressTeam = getTeamNumber(mod.GetOwnerProgressTeam(eventCapturePoint)); } catch {}
    try { progress01 = clamp01(mod.GetCaptureProgress(eventCapturePoint)); } catch {}

    // Bucket progress to 100 steps so micro-progress changes during continuous capture
    // don't churn the signature every tick. Each bucket spans 0.01 progress.
    const progressBucket = Math.round(progress01 * 100);

    // Pack into a single 32-bit-safe number for cheap comparison.
    // Multipliers chosen to be coprime so the hash is dense.
    const signature = (ownerTeam * 1000003) ^ (ownerProgressTeam * 100003) ^ progressBucket;

    const lastSignature = state.lastSignature ?? -1;
    const lastFullRecomputeMs = state.lastFullRecomputeMs ?? 0;
    const forceRefreshDue = (nowMs - lastFullRecomputeMs) >= CAPTURE_POINT_SIGNATURE_REFRESH_MS;

    if (signature === lastSignature && !forceRefreshDue) {
        // Fast path: nothing changed in the cheap reads, and we're within the 1s force-refresh
        // window. Skip the per-player loop entirely. ~7 engine calls (the 3 cheap reads above)
        // instead of ~14 + per-player loop.
        return;
    }

    state.lastSignature = signature;
    state.lastFullRecomputeMs = nowMs;

    // ... rest of existing function from line 1735 onward (state mutation, player loop, etc.) ...
    // Note: the existing function re-does the 3 engine reads (ownerTeam, ownerProgressTeam,
    // progress01) inside its body. To avoid double-reading, lift the reads out as we did above,
    // and pass the cached values forward. Or: accept the small duplication for minimal diff.
    // The duplication costs ~3 engine calls per non-fast-path tick. Worth the cleaner diff.
}
```

**Why "single 32-bit-safe number" signature:** number comparison is faster than struct comparison. Bitwise XOR + multiply works in JS (which uses doubles, so up to 2^53 is safe, well above our needs).

**Why "Math.round(progress01 * 100)" bucketing:** progress can change every tick by ~0.01 during active capture. If we don't bucket, every tick is a signature change, defeating the fast-path. 100 buckets is enough resolution for UI (one fill-bar pixel per bucket roughly).

### E1: Audit-heavy refactor of `refreshTopHudDerivedSlicesForAllPlayers`

#### Problem

| Option | Mechanism | Why considered | Why accepted/rejected |
|---|---|---|---|
| **E1.a** | Split into two functions (clock unconditional, status/help-ready dirty-gated), with explicit `markTopHudDerivedDirty()` at every relevant mutation site | Cleanest contract; minimal runtime overhead. | **REJECTED AS PRIMARY.** Audit cost is real and risky. #### Recommended approach: E1.b -- reuse `markHudDirty` contract

**This is a significant design improvement over v1's E1.a.** Instead of auditing every mutation site, we treat the existing combat-HUD dirty flag as a sufficient signal that top-HUD-derived VMs also need rebuilding.

**Why this is correct:**
- Combat HUD dirty contract (per AGENTS.md "Combat HUD Dirty-Flag Contract"): set on every mutation of fields affecting combat HUD projection.
- Top-HUD-derived inputs: ready state, deployed state, perspective team, match phase, spectator pid, roster membership.
- **Every top-HUD input is also a combat-HUD input.** Combat HUD displays ready counts, perspective-team colors, match phase indicators -- all the same fields.
- Conversely, combat HUD has additional inputs (capture state, engage state) that top-HUD doesn't care about. So `markHudDirty` is a SUPERSET signal: setting it for capture-state changes triggers unnecessary top-HUD rebuilds, but that's safe (just wastes a few VM allocations per subtick when capture state churns).

**The trade-off:** combat-HUD-only changes (like capture state) trigger a top-HUD VM rebuild that wasn't strictly needed. This is acceptable because:
1. Combat HUD already paid the cost of detecting dirty + rebuilding pipeline.
2. Top-HUD VM rebuild is cheap relative to combat HUD.
3. The reclaim from skipping top-HUD VM rebuild on truly-clean subticks (no markHudDirty between subticks) is the dominant win.

#### Recommended approach: G3.a with G3.d as a safety net

**Critical design concern: reentrancy.** TickContext as currently implemented (tick-context.ts) is NOT reentrant. `beginTickContext` blindly overwrites the cache. If handler A wraps and synchronously calls something that triggers handler B which also wraps, the inner end clears the cache before A is done.

**Mitigation:** make TickContext ref-counted. Modify `beginTickContext` to count nesting:

```ts
let activeTickContext: ActiveTickContext | undefined;
let contextRefCount: number = 0;

function beginTickContext(): void {
    if (contextRefCount === 0) {
        const players = mod.AllPlayers();
        activeTickContext = { players, playerCount: mod.CountOf(players) };
    }
    contextRefCount++;
}

function endTickContext(): void {
    contextRefCount--;
    if (contextRefCount <= 0) {
        contextRefCount = 0;
        activeTickContext = undefined;
    }
}
```

This is a 6-line change in tick-context.ts that makes nested begin/end safe.

**v1 revision note:** v1 said "audit for nesting" but didn't propose ref-counting. v2 builds in the safety net.

**Async handler caveat:** awaits invalidate the cache (players may change during the await). For async handlers, only wrap the synchronous prelude:

```ts

    for (const objId of State.conquest.capture.mappedObjIdsInOrder) {
        const cp = mod.GetCapturePoint(objId);
        if (!cp) continue;
        const engineList = mod.GetPlayersOnPoint(cp);
        const count = mod.CountOf(engineList);
        const engineSet = new Set<number>();
        for (let i = 0; i < count; i++) {
            const p = mod.ValueInArray(engineList, i) as mod.Player;
            const pid = safeGetPlayerId(p);
            if (pid !== undefined) engineSet.add(pid);
        }
        State.conquest.capture.playersOnPointByObjId[objId] = engineSet;
    }
}
```

**Why 1 Hz instead of every subtick:** the reconciler does the SAME engine reads we're trying to skip. Running it every subtick defeats the purpose. 1 Hz is the right cadence -- accepts up to 1s lag on event-drop drift, in exchange for ~88% cost reduction on the per-subtick path (7 of 8 subticks pay zero engine cost for membership; the 8th reconciles).

#### State changes

`State.conquest.capture.playersOnPointByObjId: Record<number, Set<number>>` -- init empty in runtime-state.ts.

## Wave 8 (new): O1 sound/VO recipient snapshot caching

### Goal

Per Section M.1 of the inventory: `getCaptureSoundRecipientsForEvent` and `getCaptureVoRecipientsForEvent` do `mod.AllPlayers()` per event in the flush loop. At a 10-event capture-point burst, this hits ~4,480 engine calls in one flush. Snapshot the candidate list once per flush.

### Files touched

- [`index/capture-sound.ts`](../src/index/capture-sound.ts) -- `flushCaptureSoundQueue` + `getCaptureSoundRecipientsForEvent`
- [`index/capture-vo.ts`](../src/index/capture-vo.ts) -- `flushCaptureVoiceOverQueue` + `getCaptureVoRecipientsForEvent` (and `refreshRecentPresence`)

### Design alternatives considered

| Option | Mechanism | Why accepted/rejected |
|---|---|---|
| **O1.a (preferred)** | Build a `validPlayerByPid: Map<number, mod.Player>` once at the top of the flush, pass it to the recipient resolution helper | **ACCEPTED.** Smallest diff. Per-event iteration cost stays the same. |
| **O1.b** | Use TickContext: wrap the flush body with `beginTickContext` / `endTickContext`. Recipient resolution uses `safeFindPlayer` (G2-cached if G2 also shipped) | **DEFERRED.** Requires G2+G3 from Wave 6 to be shipped first. Could be the better path long-term. |
| **O1.c** | Cache the recipient set keyed by `(eventKey, objId, sourceTeamId)` | **REJECTED.** Bounded benefit; most events in a burst have different sourceTeamId or objId. Complexity > benefit. |

### Recommended approach: O1.a

```ts
// In capture-sound.ts flushCaptureSoundQueue, after the cadence gate but before the event loop:
function flushCaptureSoundQueue(): void {
    if (!State.conquest.sound.enabled) return;
    if (!isMatchLive()) return;

    const now = mod.GetMatchTimeElapsed();
    if (
        State.conquest.sound.lastFlushAtSeconds >= 0
        && (now - State.conquest.sound.lastFlushAtSeconds) < CONQUEST_CAPTURE_SOUND_FLUSH_SECONDS
    ) {
        return;
    }
    State.conquest.sound.lastFlushAtSeconds = now;

    if (State.conquest.sound.queue.length <= 0) return;
    primeSoundRuntime();

    // O1.a: snapshot the valid player list ONCE per flush. Used by all event recipient resolutions below.
    const validPlayerByPid = new Map<number, mod.Player>();
    const players = mod.AllPlayers();
    const count = mod.CountOf(players);
    for (let i = 0; i < count; i++) {
        const player = mod.ValueInArray(players, i) as mod.Player;
        if (!isValidPlayer(player)) continue;
        const pid = safeGetPlayerId(player);
        if (pid === undefined || isPidDisconnected(pid)) continue;
        validPlayerByPid.set(pid, player);
    }

    const queued = State.conquest.sound.queue.splice(0, State.conquest.sound.queue.length);
    for (let i = 0; i < queued.length; i++) {
        const event = queued[i];
        if (!event) continue;
        const recipients = getCaptureSoundRecipientsForEvent(event, validPlayerByPid);
        // ... rest unchanged
    }
}

// Modify getCaptureSoundRecipientsForEvent to accept the snapshot:
function getCaptureSoundRecipientsForEvent(
    event: ConquestQueuedSoundEvent,
    validPlayerByPid: Map<number, mod.Player>
): mod.Player[] {
    const recipients: mod.Player[] = [];
    for (const [pid, player] of validPlayerByPid) {
        const engagedObjId = State.conquest.capture.engagedObjIdByPid[pid];
        if (!conquestShouldTreatPidAsActiveObjectiveOccupant(pid, engagedObjId)) continue;
        if (engagedObjId !== event.objId) continue;
        if (!shouldCountPlayerAsActiveOnPoint(player)) continue;
        const viewerTeam = safeGetTeamNumberFromPlayer(player, 0);
        if (viewerTeam !== TeamID.Team1 && viewerTeam !== TeamID.Team2) continue;
        recipients.push(player);
    }
    return recipients;
}
```
