## Context

Ship 2 (v1.478–v1.480) shipped the foundation: claim → body teleported into a sealed PCT-pattern underground room → `Cameras.Fixed` attached to a Godot-placed FixedCamera (Operation Firestorm cam ObjId 667) → input restrictions on movement / combat / weapon-slot inputs → world-log + `DisplayNotificationMessage` self-confirmation. **SP-confirmed v1.480 (2026-05-08):** body underground, "is spectating" rendered, camera attached. The spectator now sees a static high-altitude shot of Firestorm.

User direction (2026-05-08, this turn): they want the spectator to *move and control* the camera. The umbrella plan and `spec_cam_integration.md` §6 I-4 explicitly punted on this in Ships 1–2 ("Static Godot camera per map; no path / free-fly / preset modes. PCT-style functionality is explicitly excluded."). This Ship 3 re-enters that territory by lifting PCT's `StartFreeCamera` methodology — proven on a shipped community toolkit — and adapting it to our single-spectator-slot architecture.

The reason this is feasible despite the umbrella plan's per-tick-cost concern: **we have one spectator at a time**, not a director-broadcast model. PCT also enforces a single-director invariant (`spec_cam_functionality.md` §6.10) and runs the per-tick loop only while that one director is active. Same shape applies here.

## PCT Methodology — What We Lift

Per `spec_cam_functionality.md` §6.1 ("Camera-as-Owned-FixedCamera"):

> The toolkit's central trick: there is exactly one `mod.FixedCamera` object, placed in Godot, with its objId injected at init. Every camera mode is a tight `while (...) { await mod.Wait(DT); ... mod.SetObjectTransform(cam, ...); }` loop that re-poses that single object. `mod.SetCameraTypeForPlayer(dir, mod.Cameras.Fixed, fixedCameraId)` just attaches the director's POV to it.

We already do the attachment (Ship 2). Ship 3 adds the **per-tick `mod.SetObjectTransform` loop** that animates the same FixedCamera while the spectator slot is held.

PCT's free-camera pipeline (`StartFreeCamera`, ~880 LOC, `main_module.ts:4428`), distilled to the load-bearing parts:

| PCT pipeline step | What it does | Ship 3 adoption |
|---|---|---|
| **Input read** | `Player.GetLinearVelocity(dir)` → director's WSAD as a velocity vector while body is parked in the control room | Adopt — `mod.GetSoldierState(player, SoldierStateVector.GetLinearVelocity)` already wrapped via `safeGetSoldierStateVector` in our codebase |
| **Decompose against facing** | Project velocity onto `playerFacing` (forward) and `flatRight = cross(facing, up)` (strafe) | Adopt |
| **Camera position lerp** | `camPos += forward * forwardAmount + strafeRight * strafeAmount` per tick, smoothed via `freeMoveForwardSmoothing=0.12`, `freeMoveStrafeSmoothing=0.12` | Adopt — same constants |
| **Camera rotation lerp** | Read `Player.GetFacingDirection(dir)` → derive `targetYaw` and `targetPitch`, lerp via `freeMoveRotationSmoothing=0.18` | Adopt |
| **Apply transform** | `mod.SetObjectTransform(_cameraObject, mod.CreateTransform(camPos, mod.CreateVector(pitch, yaw, 0)))` | Adopt — uses `(mod as any).GetFixedCamera(camId)` already cached from Ship 2 hide-room |
| **Throttle** | `await mod.Wait(0.033)` → ~30 Hz tick | Adopt |
| **Loop guard** | Loop terminates when `_cameraState.isRunning === false` | Adopt — token-based cancellation gated on `State.players.spectatorPid === ourPid` |
| **Player-target tracking** | Jump-key edge fires `PlayerTracking.InitNextTarget` (cycles target) | **Defer to follow-up** (see "Out of Scope" below) |
| **Zoom-out/zoom-in target switch transition** | 3-phase ZoomOut → ZoomIn when target jump exceeds 100m | **Defer** |
| **Raycast wall correction** | Every 5 ticks, `mod.RayCast` from director to desired cam pos; clamp to hit + 0.35m if blocked | **Defer to follow-up** if MP testing shows camera clipping through walls |
| **Focus mode** (close-shoulder offset on target hold) | Toggleable tighter follow distance | **Defer** |

**Ship 3 lands the bare `StartFreeCamera` core: WASD + look + smooth lerps + per-tick transform write.** No tracking, no transitions, no raycast, no focus.

**Out-of-scope-but-cheap follow-ups** (separate ship if user wants them):
- **3b: Player-target tracking on jump** (cycle alive teammates). ~50 LOC. Per-tick math furnace already running, no marginal cost beyond cycle-state.
- **3c: Raycast wall correction.** Add if MP testing reveals camera clipping issues. ~80 LOC + per-pid raycast state machine (`spec_cam_functionality.md` §6.6).
- **3d / 3e: Path mode + 46-preset mode.** Out of scope unless explicitly requested. Path mode alone is ~600 LOC including UI.

## Per-Tick Loop Detail

`runSpectatorFreeCameraLoop(eventPlayer: mod.Player, pid: number, token: number)` in `spectator-action.ts`:

```ts
const FREE_CAM_TICK_SECONDS = 0.033;
const FREE_CAM_FORWARD_SMOOTHING = 0.12;
const FREE_CAM_STRAFE_SMOOTHING = 0.12;
const FREE_CAM_ROTATION_SMOOTHING = 0.18;
const FREE_CAM_MIN_PITCH_RAD = -89 * (Math.PI / 180);
const FREE_CAM_MAX_PITCH_RAD =  89 * (Math.PI / 180);
const FREE_CAM_FORWARD_GAIN = 1.0;     // multiplier on velocity-decomposed forward delta
const FREE_CAM_STRAFE_GAIN = 1.0;      // multiplier on velocity-decomposed strafe delta
const FREE_CAM_SPRINT_MULTIPLIER = 2.5; // applied when IsSprinting

async function runSpectatorFreeCameraLoop(eventPlayer: mod.Player, pid: number, token: number): Promise<void> {
    const camId = ACTIVE_MAP_CONFIG?.spectatorCameraId;
    if (camId === undefined) return;
    let camera: mod.FixedCamera;
    try { camera = (mod as any).GetFixedCamera(camId); } catch { return; }

    // Initial pose: read current camera position so the spectator doesn't snap to (0,0,0)
    let camPos = mod.GetObjectPosition(camera);
    let smoothedYaw: number | null = null;
    let smoothedPitch: number | null = null;
    let smoothedForward = 0;
    let smoothedStrafe = 0;

    while (true) {
        await mod.Wait(FREE_CAM_TICK_SECONDS);

        // Loop-end gates (token bump, slot drop, player invalid)
        if (_freeCameraLoopToken !== token) return;
        if (State.players.spectatorPid !== pid) return;
        if (!isValidPlayer(eventPlayer)) return;
        if (!isPlayerDeployed(eventPlayer)) continue; // body re-deploy churn — wait it out, the OnPlayerDeployed hook re-attaches camera

        // Read input
        const velocity = safeGetSoldierStateVector(eventPlayer, mod.SoldierStateVector.GetLinearVelocity);
        const facing = safeGetSoldierStateVector(eventPlayer, mod.SoldierStateVector.GetFacingDirection);
        if (!velocity || !facing) continue;

        // Decompose velocity against facing
        const flatFacing = flatNormalize(facing);
        const flatRight = cross(flatFacing, mod.CreateVector(0, 1, 0));
        const targetForward = dot(velocity, flatFacing);
        const targetStrafe = dot(velocity, flatRight);

        // Smooth
        smoothedForward = lerp(smoothedForward, targetForward, FREE_CAM_FORWARD_SMOOTHING);
        smoothedStrafe = lerp(smoothedStrafe, targetStrafe, FREE_CAM_STRAFE_SMOOTHING);

        // Apply sprint multiplier (mod.SoldierStateBool.IsSprinting)
        const sprinting = safeGetSoldierStateBool(eventPlayer, mod.SoldierStateBool.IsSprinting, false);
        const speed = sprinting ? FREE_CAM_SPRINT_MULTIPLIER : 1.0;

        // Compose new camera position
        const dt = FREE_CAM_TICK_SECONDS;
        camPos = mod.CreateVector(
            mod.XComponentOf(camPos) + smoothedForward * FREE_CAM_FORWARD_GAIN * speed * dt + smoothedStrafe * FREE_CAM_STRAFE_GAIN * speed * dt * mod.XComponentOf(flatRight),
            mod.YComponentOf(camPos), // Y is independent — no vertical input in 3a; could add Q/E or jump/crouch in a follow-up
            mod.ZComponentOf(camPos) + smoothedForward * FREE_CAM_FORWARD_GAIN * speed * dt + smoothedStrafe * FREE_CAM_STRAFE_GAIN * speed * dt * mod.ZComponentOf(flatRight),
        );

        // Compute target yaw/pitch from facing
        const targetYaw = Math.atan2(mod.XComponentOf(flatFacing), mod.ZComponentOf(flatFacing));
        const targetPitch = clamp(Math.asin(mod.YComponentOf(facing)), FREE_CAM_MIN_PITCH_RAD, FREE_CAM_MAX_PITCH_RAD);

        // Smooth rotation (lerpAngleRad handles wrap-around)
        smoothedYaw = smoothedYaw === null ? targetYaw : lerpAngleRad(smoothedYaw, targetYaw, FREE_CAM_ROTATION_SMOOTHING);
        smoothedPitch = smoothedPitch === null ? targetPitch : lerp(smoothedPitch, targetPitch, FREE_CAM_ROTATION_SMOOTHING);

        // Apply
        try {
            mod.SetObjectTransform(
                camera,
                mod.CreateTransform(
                    camPos,
                    mod.CreateVector(smoothedPitch, smoothedYaw, 0),
                ),
            );
        } catch (e) {
            try { console.log(`[spectator] free-cam transform write threw for pid=${pid}: ${String(e)}`); } catch {}
            return;
        }
    }
}
```

**Notes on the math:**
- Pitch/yaw conventions in Portal: empirically `mod.CreateVector(pitch, yaw, 0)` works for `SetObjectTransform` rotation arg per PCT (`main_module.ts:4960` area). If that's wrong, fall back to PCT's `SetCameraTransform` helper structure.
- Sprint multiplier (×2.5) and the smoothing constants are PCT's empirically-tuned values per `spec_cam_functionality.md` §4.7.2 ("freeMoveForwardSmoothing = 0.12, freeMoveStrafeSmoothing = 0.12, freeMoveRotationSmoothing = 0.18"). Re-used as facts about good camera feel, not as code copy.
- Vertical movement (`Y` axis) is a known limitation of 3a — spectator can only fly horizontally. PCT's free-cam binds Q/E or jump for vertical. **Optional 3a polish:** map `IsJumping` → +Y delta and `IsCrouching` → -Y delta, with similar smoothing. ~5 LOC. Probably worth including in v1 if the SP test reveals horizontal-only feels stuck.

## Risks (Ship 3-specific)

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Per-tick `SetObjectTransform` cost on busy servers | Low-Medium | Frame-time hit at 16 players | Single-spectator scope = one loop, not 16. PCT verifies this is sustainable empirically. Bounded ~30 Hz. |
| Camera clips through walls / terrain | Medium | Cosmetic — view goes inside geometry briefly | Ship 3a: accept it. Ship 3c (follow-up): port PCT's raycast wall correction (`spec_cam_functionality.md` §6.6, ~80 LOC). |
| Pitch/yaw convention mismatch with PCT | Low | Camera rotates wrong axis | Empirically verified in v1.480 SP test (camera attached correctly). If `SetObjectTransform` rotation arg isn't `(pitch, yaw, 0)`, swap to `(0, yaw, 0)` + a separate pitch handle. |
| Body still spawns weapon SFX from inputs we kept locked | Very Low | Audible weapon noise from underground room | Defensive: weapon inputs stay locked. PCT's pattern. |
| Loop survives slot release (zombie loop) | Low | Per-tick `SetObjectTransform` runs forever | Token-based cancel + tail-check on `State.players.spectatorPid` are belt-and-braces. Loop bails within one tick of either guard tripping. |
| Sprint multiplier × velocity gain produces unflyable speed | Low | Camera too fast to control | Tuneable. Start with PCT values; lower `FREE_CAM_FORWARD_GAIN` to 0.6-0.8 if SP testing reveals "too fast." |
| Player's body input drives camera AND moves body inside hide room | Very Low | Body could press against hide-room walls; cosmetic | Hide room is a sealed cube — body is contained by walls + floor + ceiling. PCT proved this works. |
| Vertical movement absent in 3a base | High | Spec can't fly up/down | Polish: include the IsJumping/IsCrouching → ±Y bind. ~5 LOC. Recommend adding in v1. |
| Bundle growth | Very Low | Pushes near 1MB cap | Estimate +2.0-3.5 KB. v1.480 headroom: 170,569 bytes (16.27%). <2% of headroom consumed. |
| Heap pressure | Very Low | New per-tick allocations from `mod.CreateVector` | One transform write per tick = bounded. PCT runs the same shape. |
