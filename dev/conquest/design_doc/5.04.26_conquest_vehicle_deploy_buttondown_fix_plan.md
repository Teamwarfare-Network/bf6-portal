# Vehicle Deploy Buttons — Console ButtonDown Fix

**Status:** **PROPOSED — awaiting approval (2026-05-04).** Fixes a console-controller bug where vehicle deploy buttons fail because the engine's deploy-on-foot action consumes the controller input before the UI button's `ButtonUp` event reaches the userland handler. The fix mirrors the working team-swap button pattern: fire the action on `ButtonDown` (or the first primary-click event seen) via the existing `tryConsumeUIButtonPrimaryClickEvent` dedupe helper. Single ship; one source file edited; no widget tree changes; zero string changes.

This is NOT a wave; it's a targeted bug fix landing alongside ongoing optimization work. The bug is **functional, not cosmetic** — on console it completely breaks the vehicle deploy UI for affected players.

## Context

### The bug

On console (Xbox A button / PlayStation X button — the controller's primary action mapped to UI clicks AND to "deploy on foot" on the deploy screen), pressing a Vehicle Deploy button on the deploy screen produces **no vehicle deploy** — the player is deployed on foot at a normal infantry spawn. The UI button click is effectively swallowed.

The user observed an exact functional contrast: the **Team Swap** button (also on the deploy screen, same pre-LIVE context) **works correctly** on console — pressing it switches the player's team, even though the same controller A button is bound to "deploy on foot."

### Diagnosis: ButtonDown vs ButtonUp

The two buttons fire their userland action on different engine events:

| Button | Userland action triggered by |
|---|---|
| **Team Swap** ([state/ui-helpers.ts:75-76](../src/state/ui-helpers.ts#L75-L76), [interaction/ui-events-ready.ts:25-37](../src/interaction/ui-events-ready.ts#L25-L37)) | First primary-click event (`ButtonDown` *or* `ButtonUp`) seen by [`tryConsumeUIButtonPrimaryClickEvent`](../src/interaction/ui-primary-click.ts#L54-L71). The matching paired event is suppressed via the `(prior.phase === "down" && phase === "up")` branch in [`shouldConsumeUIButtonPrimaryClick`](../src/interaction/ui-primary-click.ts#L21-L52). |
| **Vehicle Deploy** action button ([vehicles/deploy-timer-ui.ts:1633](../src/vehicles/deploy-timer-ui.ts#L1633)) | Only `ButtonUp`. The `ButtonDown` handler at [1617-1632](../src/vehicles/deploy-timer-ui.ts#L1617-L1632) updates visual press state but does NOT fire the spawn request. The spawn request fires at [1657-1675](../src/vehicles/deploy-timer-ui.ts#L1657-L1675), gated by `if (!mod.Equals(eventUIButtonEvent, mod.UIButtonEvent.ButtonUp)) return true;`. |
| **Vehicle Deploy** close button ([vehicles/deploy-timer-ui.ts:1526-1530](../src/vehicles/deploy-timer-ui.ts#L1526-L1530)) | Only `ButtonUp`. Same pattern. |

### Why ButtonUp loses on console

The engine's "deploy on foot" action is bound to the same controller A button used for UI clicks. The full input frame:

1. Console player presses A while a Vehicle Deploy button is focused.
2. Engine fires `ButtonDown` on the focused UI widget → userland's `ButtonDown` handler updates visual pressed state and returns.
3. Engine **also** processes A as the "deploy on foot" action → starts engine-side deploy.
4. The deploy screen dismisses; the player is no longer in deploy-screen UI context.
5. Player releases A → engine *may* fire `ButtonUp` on the original widget, but in the deploy-screen-dismissed context the event delivery is unreliable / lost.
6. Even if `ButtonUp` arrives, the `if (State.players.deployedByPid[pid] && !liveTerminalOpen) return true;` gate at [vehicles/deploy-timer-ui.ts:1634](../src/vehicles/deploy-timer-ui.ts#L1634) blocks the action because the player is now deployed.

Net effect: the vehicle spawn request is never enqueued. The player ends up deployed on foot.

### Why ButtonDown wins on console (team-swap evidence)

Team swap fires its action on `ButtonDown` (or `ButtonUp` if `ButtonDown` is lost). The action — `swapPlayerTeam(player)` ([ready-dialog/swap-action.ts:8-26](../src/ready-dialog/swap-action.ts#L8-L26)) — runs **synchronously** in the same input frame as the engine's deploy-on-foot. It:
1. Sets `State.players.readyByPid[pid] = false`.
2. Calls `processReadyDialogSelection(eventPlayer)` which performs team reassignment + undeploy.

By the time the engine processes the deploy action, the player has already been undeployed and reassigned to the other team. The engine then redeploys them on the new team's spawn — consistent with the user's observed "swapped to NATO/WEST and deployed there" behavior.

### Why moving Vehicle Deploy to ButtonDown should also win

`requestHqVehicleSpawn` (and its forward/air siblings) sets `slot.pendingSpawnOwnerPid = pid` synchronously, then calls `enqueueDispatch(slotIndex)` which enqueues an async vehicle spawn through the mutex chain.

After the fix, the input frame becomes:
1. Console player presses A while a Vehicle Deploy button is focused.
2. Engine fires `ButtonDown` on the focused UI widget.
3. Userland handler runs `tryConsumeUIButtonPrimaryClickEvent` → returns true on the first event → **calls `requestHqVehicleSpawn` synchronously** → `slot.pendingSpawnOwnerPid` is set, async vehicle spawn enqueued.
4. Engine processes A as the deploy-on-foot action → engine-side deploy starts.
5. `OnPlayerDeployed` fires when engine deploy completes → `onHqSeatPendingPlayerDeployed` runs ([vehicles/hq-deploy.ts:338](../src/vehicles/hq-deploy.ts#L338)) → finds `pendingSpawnOwnerPid` set, but `slot.vehicleId === -1` (vehicle hasn't bound yet) → returns early (claim persists).
6. ~0.5–3s later vehicle binds → `onHqVehicleSpawnedForClaim` → `beginHqSeatFlow` → after `HQ_DEPLOY_SEAT_SETTLE_SECONDS` calls `mod.DeployPlayer(player)`.

### Caveat to flag — secondary race in `beginHqSeatFlow` for deploy_menu source

Step 6 is the worry. After the engine deploys the player on foot in step 4, the player's `State.players.deployedByPid[pid] === true`. When `beginHqSeatFlow` runs on the deploy_menu path, it calls `mod.DeployPlayer(player)` on an already-deployed player — likely a no-op. The seat hook never re-fires.

**Two possible outcomes:**

- **Outcome A (likely):** the engine deploys the player on foot in step 4. The seat hook in step 5 returns early (vehicleId=-1). When the vehicle eventually spawns, `beginHqSeatFlow`'s deploy_menu path calls `DeployPlayer` on an already-deployed player → no-op. **Seat never fires.** Player stays on foot; vehicle sits at HQ pad orphaned; 10s claim timeout fires; vehicle is destroyed via `sinkAndDestroyVehicle`. Same observable behavior as today's bug (player on foot), but with a transient orphan vehicle the claim-timeout cleans up.
- **Outcome B (possible):** team-swap "wins" because the request runs before the engine's deploy gets to commit, by some narrow timing margin. Similarly, the vehicle deploy claim might "win" — `requestHqVehicleSpawn` sets the claim and starts the spawn, the engine deploys-on-foot, and somehow the claim survives and seats the player when the vehicle lands. This depends on engine-side commit ordering we can't fully predict from JS-side reading.

**Recommended approach:** ship the simple ButtonDown move first (this plan). Test on console. If Outcome A obtains, add a secondary fix in a follow-up plan: at request-time, inspect `State.players.deployedByPid[pid]` and route to `"on_foot"` source if true (the on_foot path already handles undeploy → redeploy → seat correctly). This secondary fix is a 5-line change once we confirm it's needed; over-engineering it now without console validation data risks shipping unnecessary complexity.

If the user wants to pre-empt Outcome A in this same ship, see §Phase 1-G below for the optional inline upgrade.

## Risks

1. **Outcome A — secondary race in beginHqSeatFlow** (described in §Context): a known plausible failure mode where the simple ButtonDown move is necessary but not sufficient on console. Mitigation: P1-G is the followup fix; cost is 3 lines of TypeScript. Risk score: **medium** (might require a second ship).

2. **Double-fire of `requestHqVehicleSpawn`** if the dedupe tracker doesn't suppress the matching paired event. Mitigation: `tryConsumeUIButtonPrimaryClickEvent` is exercised across three other UI surfaces today (admin panel, player ready panel, ready dialog) without reports of double-fire. Risk score: **low**.

3. **Visual press-state desync** if `ButtonUp` is consumed by the engine and never reaches userland — the `pressed` flag stays `true` in the row cache. Mitigation: when the player deploys, the deploy-timer HUD is hidden + cache state is rebuilt; stale `pressed` doesn't persist into the next visible frame. Risk score: **zero**.

4. **Dedupe tracker leaks per-pid state** if cleanup isn't wired. Mitigation: P1-D adds the `delete` call mirroring the existing pattern. Risk score: **low** (mechanical mistake risk only).

5. **Cross-button debounce within a session** (e.g. clicking Spawn then immediately clicking Ground on same row triggers debounce because they share pid). Mitigation: `tryConsumeUIButtonPrimaryClickEvent` is keyed by `widgetName`, not just pid — different widgets bypass debounce. Risk score: **zero** (verified by reading the dedupe logic at [interaction/ui-primary-click.ts:32](../src/interaction/ui-primary-click.ts#L32)).

6. **Regression on PC mouse clicks** — could the change break existing PC behavior? Mitigation: PC mouse fires `ButtonDown` then `ButtonUp` in sequence on the same widget; with the new dedupe, ButtonDown fires the action and ButtonUp is suppressed. Net behavior on PC is identical to today's "fire on ButtonUp" because there's only one fire per click cycle, just shifted earlier in the cycle. PC users will see the spawn request initiate ~50-100ms earlier than today (negligible). Risk score: **zero**.
