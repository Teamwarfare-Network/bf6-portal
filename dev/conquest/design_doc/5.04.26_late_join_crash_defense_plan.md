## Plan — three sequential phases, each independently shippable

The phases are ordered cheapest-and-broadest-first. **Phase A is the highest-value win regardless of root cause** because it converts engine-killing rejections into logged ones, which both prevents the crash AND surfaces a symptom for the next repro. Phase B is the strongest concrete suspect. Phase C is the cheap correctness fix that compounds with B.

---

### Phase A — Wrap `OnPlayerJoinGame` async export in try/catch (S1)

**Files:** [`src/index.ts`](../src/index.ts) only (1 file, 1 export function touched).

**Scope:** the **single** async engine event export that fires in the pre-deploy late-joiner window. `OnGameModeStarted` is excluded (runs once at mode-boot, not in the crash window). `OnPlayerDeployed` is excluded (Suspect 4 eliminated — player never deployed).

**Target:**
- `OnPlayerJoinGame` — async, currently bare-forward at [index.ts:133-135](../src/index.ts#L133-L135).

**Pattern:**

```ts
export async function OnPlayerJoinGame(eventPlayer: mod.Player): Promise<void> {
    try {
        await onPlayerJoinGameImpl(eventPlayer);
    } catch (err) {
        // Catastrophic: an unhandled rejection here can kill the script context
        // and trigger an engine-side server abort. Swallow + log so the next
        // repro yields a console line we can grep, not a silent crash.
        try { console.log(`[OnPlayerJoinGame] ${(err as any)?.message ?? String(err)}`); } catch {}
    }
}
```

**Reasoning for `console.log` (not a world-log message):** **String Change Authorization Policy** forbids new `mod.stringkeys.*` registration without explicit user approval. Console output is the only no-string surface we can hit on this runtime, and it's sufficient for SP smoke + post-crash triage.

**Risk:** zero behavior change in the no-throw path. In the throw path, current behavior = silent server crash; new behavior = swallowed error + console line. Strictly an improvement.

**Verification:**
- `cmd /c npx tsc --pretty false --noEmit` (must exit 0).
- Cold-launch SP smoke: join a match, no console error, HUD builds normally.
- Bot-driven late-join during LIVE: no console error from the wrapper; existing flow preserved.

### Phase B — Close the cache-mutation race against `runRoundStartDelayHudLoop` (S2)

**Files:** [`src/index/player-join-leave.ts`](../src/index/player-join-leave.ts) only (1 file, 1 function modified).

**Scope:** the `delete State.hudCache.vehicleDeployTimerCache[pid]` call at [player-join-leave.ts:36](../src/index/player-join-leave.ts#L36) inside `resetUiForPlayerOnJoin`.

**The race in detail:**

| Tick | Event | What happens to the late-joiner's cache slot |
|---|---|---|
| `T = engine-bind` | Late-joiner appears in `mod.AllPlayers()` | No cache entry yet. Loop's `for (const pidKey in caches)` skips them (key absent). |
| `T = engine-bind + Δ` | A subsequent tick that calls a builder for `forEachValidPlayer` may create a cache entry for the late-joiner. Concretely: `prebuildAndRevealVehicleDeployTimerHudForAllPlayers` at [deploy-timer-ui.ts:1879](../src/vehicles/deploy-timer-ui.ts#L1879) iterates and builds. | Fresh cache entry created with widget handles bound to engine-side widgets. |
| `T = 0` | Our `OnPlayerJoinGame` fires, sync init runs (lines 109-125). | Cache entry untouched. |
| `T = 100ms` | `await mod.Wait(0.1)` resumes. `resetUiForPlayerOnJoin` runs, including `delete vehicleDeployTimerCache[pid]` at line 36. | **Cache entry deleted, but engine-side widgets still exist.** |
| `T = 100ms+ε` | `triggerLazyBuild('topHudShell', joinPid)` runs sync. | New build path. May call `safeFind(name)` and find the orphaned widget (engine still has it), or may collide on widget-name uniqueness. |
| `T = 150ms` | `Timers.setTimeout(() => triggerLazyBuild('vehicleDeployTimer', joinPid))` fires. | Same risk: re-binds against orphaned engine widgets. |

The classic asserting pattern in BF6 Portal is `mod.SetUIWidget*` against a widget handle that was deleted. If the lazy-build path captures a widget handle, then the loop concurrently writes to the same widget after our delete, an engine-side write to a stale handle is exactly the kind of call that aborts the server.

**Defense — three options, ranked:**

1. **Recommended: delete the cache entry BEFORE the await wait, in the sync prelude.** Move the `delete State.hudCache.vehicleDeployTimerCache[pid]` from line 36 (inside `resetUiForPlayerOnJoin`, called after the await) up into the sync prelude block at lines 109-125 (before the await). This way: late-joiner appears in `mod.AllPlayers()` → first tick after engine-bind tries to build a cache entry → our T=0 sync handler immediately clobbers it back to absent → at T=100ms there's no stale entry to fight over. The lazy-build cohort at T=100ms+ owns cache creation start-to-finish.

2. **Alternative: skip the delete entirely.** If `triggerLazyBuild('vehicleDeployTimer', joinPid)` already handles a stale-cache case (verify before adopting), the delete is unnecessary. Lower-risk but requires verification of the lazy-build path's idempotency.

3. **Belt-and-suspenders: also gate the loop iteration with a "is this pid join-in-progress?" check.** Adds complexity. Not recommended unless options 1 and 2 prove insufficient.

**Recommendation: option 1.** Concrete edit:

- **Add** at the bottom of the sync block (around [player-join-leave.ts:124-125](../src/index/player-join-leave.ts#L124-L125), inside the `if (joinPid !== undefined)` branch):

  ```ts
  // Pre-await cache wipe: late-joiner's pid may have a cache entry from a
  // tick-driven builder that fired between engine-bind and our handler. Wiping
  // here (not after the 100ms await) ensures the lazy-build cohort owns cache
  // creation start-to-finish without racing runRoundStartDelayHudLoop's
  // post-await write window.
  delete State.hudCache.vehicleDeployTimerCache[joinPid];
  ```

- **Remove** [player-join-leave.ts:36](../src/index/player-join-leave.ts#L36) (`delete State.hudCache.vehicleDeployTimerCache[pid];` inside `resetUiForPlayerOnJoin`). NOTE: this function is also called from other paths — verify those paths don't depend on the delete before removing. If any do, leave the delete in place there and only ADD the new one in the sync prelude (idempotent — JS `delete` of an absent key is a no-op).

**Risk:** low. The `delete` is being moved earlier in the same function's call-graph, not removed. The only behavioral change is which side of the `await` it sits on. No new state, no new code paths.

**Pre-flight required before edit:**
- Grep all call sites of `resetUiForPlayerOnJoin` to confirm no other caller depends on the `vehicleDeployTimerCache` delete happening inside it.
- If multiple callers exist with different cache-delete needs, leave the original delete in place and only add the new sync-prelude delete (idempotent).

**Verification:**
- `cmd /c npx tsc --pretty false --noEmit` (must exit 0).
- SP smoke: join match, observe no HUD glitch on join.
- Bot-driven late-join during LIVE: late-joiner gets clean HUD with no double-bind console errors (Phase A wrapper will surface any).
- Repro attempt for the original crash (low probability of repro given user reported "one or two retries didn't reproduce").

### Phase C — Re-read team-bind after the 100ms wait (S3)

**Files:** [`src/index/player-join-leave.ts`](../src/index/player-join-leave.ts) only.

**Scope:** the `safeGetTeamNumberFromPlayer` block at [player-join-leave.ts:120-123](../src/index/player-join-leave.ts#L120-L123).

**Current behavior:**
```ts
const joinTeamNum = safeGetTeamNumberFromPlayer(eventPlayer, 0);
if (joinTeamNum === TeamID.Team1 || joinTeamNum === TeamID.Team2) {
    State.conquest.debug.perspectiveTeamByPid[joinPid] = joinTeamNum;
}
```

This runs at T=0, before the 100ms wait. On a fresh late-join the engine may not have assigned the team yet — `safeGetTeamNumberFromPlayer` returns 0, the validity check falls through, and `perspectiveTeamByPid[joinPid]` is left undefined. Downstream code that reads it gets `undefined`, which is the wrong-but-not-crashing JS path that compounds with S2.

**Defense — re-read after the await:**

- Keep the T=0 read as-is (best-effort early bind).
- After the `await mod.Wait(0.1)` at line 127 and the `mod.IsPlayerValid` check at line 128, **add a second read** that overrides if T=0 returned 0:

  ```ts
  // Late-joiner may not have a team-bind at T=0 (engine assignment lag).
  // Re-read after the 100ms wait — by this point the engine has bound the
  // player to a team. Skip if T=0 already resolved a valid team.
  if (joinPid !== undefined && State.conquest.debug.perspectiveTeamByPid[joinPid] === undefined) {
      const lateTeamNum = safeGetTeamNumberFromPlayer(eventPlayer, 0);
      if (lateTeamNum === TeamID.Team1 || lateTeamNum === TeamID.Team2) {
          State.conquest.debug.perspectiveTeamByPid[joinPid] = lateTeamNum;
      }
  }
  ```

**Risk:** zero. Idempotent re-read of an engine state that should be stable by T=100ms. Only writes if the early read missed.

**Verification:**
- `cmd /c npx tsc --pretty false --noEmit` (must exit 0).
- SP smoke: bot late-joins, perspective-correct ticket layout (blue-on-left if Team1, red-on-left if Team2) renders correctly on first deploy.

## Sequencing recommendation

**Ship in three separate versions, in order, with bumpVersion between each:**

1. **v1.471 — Phase A only.** Highest broad value (also defends paths we haven't audited). Independent of B and C. Lowest implementation risk. **Most importantly: this is the diagnostic enabler.** If the crash repros after Phase A, we get a console line; if it doesn't, the wrapper alone may be the fix.

3. **v1.473 — Phase C.** Cheap compound fix. Could fold into v1.472 if the user prefers, but separate ships preserve a cleaner bisect history if a regression surfaces.

**Rationale for separate ships (not bundled):** the user has previously emphasized git-first verification and that a single repro of a catastrophic bug deserves bisect-friendly history. Three small ships > one big one. Each ship is small enough that bumpVersion + typecheck + console smoke can validate it inside ~5 minutes.

**Alternative bundle (if user prefers):** ship A+B+C together as a single "late-join defense" version. Acceptable since all three are surgical and independently safe; the bisect cost is small if a regression surfaces.

## What this plan does NOT attempt

- **Does not "fix" the root cause.** The repro is too fragile to isolate. The plan closes candidate gaps so the next repro either survives or surfaces a useful symptom.
- **Does not change widget topology.** Per-PID UI scope and the lazy-build cohort timing are preserved exactly.
- **Does not add new strings or stringkeys.** All diagnostic output is `console.log`, not world-log messages.
- **Does not wrap `OnGameModeStarted` or `OnPlayerDeployed`.** Both are async exports with the same structural defense gap as `OnPlayerJoinGame`, but neither fires in the late-joiner pre-deploy crash window. Out of scope per the user's "don't add things beyond what the task requires" guidance. **Documented as a follow-up consideration below if the next repro shifts the symptom into either of those windows.**
- **Does not touch `OnPlayerLeaveGame`, `OngoingPlayer`, or `OnPlayerInteract`.** Sync forwards; throw semantics differ from async and they were not implicated in the late-join symptom.
- **Does not investigate the engine-side `mod.SetRedeployTime` broadcast scope.** The original Suspect 5 was based on an unverified hypothesis from memory and is dropped.
- **Does not investigate `OnPlayerDeployed`-side paths** (KPI init, world-icon sync, boundary state on deploy, scoreboard refresh, ready-dialog interact-point spawn). Eliminated by the new "player never deployed" constraint.
- **Does not re-enable the FEATURE_PERF_DIAG profiler** — confirmed broken per user memory; would not help here.

## Open consideration (not blocking — flag for user)

After Phase A ships and the next repro is observed (or not), we may have new evidence to act on:
- If the next late-join repro produces a `console.log` line from the `OnPlayerJoinGame` wrapper → we have a specific function to instrument inside `onPlayerJoinGameImpl`.
- If the next repro is silent again despite the wrapper → the throw is happening **outside** the async event handler. Most likely vectors: (a) a `Timers.setTimeout` callback for the deferred `vehicleDeployTimer` / `combatHud` builds that bypasses our wrapper (note: `Timers.setTimeout` already wraps callbacks via `CallbackHandler.invokeNoArgs`, so a throw there should be logged not silent — if silent, it suggests an engine-side abort, not a script throw); (b) an engine-side abort on a sync `mod.*` call inside `triggerLazyBuild` whose try/catch wraps the JS exception but the engine asserts before the JS layer sees it; (c) a per-tick iteration (conquest tick, capture tick, scoreboardSyncTick, tickBoundaryEnforcement) hitting a late-joiner with a partially-built per-pid state and triggering an engine-side assert through a write to a stale handle. That changes the next investigation toward sync engine-call audit during the pre-deploy window.
- If no repro after a reasonable test window → the plan's defenses may have closed the underlying bug.

**Follow-up consideration (out of current scope, flagged here):** if the next repro shifts focus to a different async export, wrap the remaining two (`OnGameModeStarted`, `OnPlayerDeployed`) using the same Phase A pattern. They are deferred from this plan only because the current bug doesn't implicate them — the wrapping is itself low-risk and broadly useful.
