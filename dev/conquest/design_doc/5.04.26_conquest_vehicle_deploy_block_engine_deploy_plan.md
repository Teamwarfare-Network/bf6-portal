## Context

### The bug (observed at v1.465)

Console controller player presses A on a Vehicle Deploy button. v1.465's ButtonDown fix correctly fires `requestHqVehicleSpawn` synchronously, sets `slot.pendingSpawnOwnerPid = pid`, and enqueues the vehicle spawn. **However**, the engine's "deploy on foot" controller action also fires for A on the deploy screen — in the same input frame. Resulting timeline:

```
Frame N:    ButtonDown fires → requestHqVehicleSpawn runs
            ├─ slot.pendingSpawnOwnerPid = pid          (claim set)
            ├─ scheduleHqClaimTimeout(slotIndex, pid)   (10s timeout armed)
            └─ enqueueDispatch(slotIndex)               (async vehicle spawn started)
            
Frame N (still): Engine processes A as "deploy on foot" → engine-side deploy starts

Frame N+~1:  OnPlayerDeployed fires (player now on foot)
             → onHqSeatPendingPlayerDeployed runs
             → finds slot.pendingSpawnOwnerPid set, BUT slot.vehicleId === -1
             → returns early (claim persists)

Frame N+~30 (~0.5–3s later):
             Vehicle binds → onHqVehicleSpawnedForClaim → beginHqSeatFlow
             → after 0.5s settle, calls mod.DeployPlayer(player) on
               an ALREADY-DEPLOYED player → engine no-op
             → seat never fires

Frame N+10s: scheduleHqClaimTimeout fires
             → orphan vehicle sinkAndDestroyed
             → claim cleared
             → player stays on foot
```

Root cause: `mod.DeployPlayer(player)` on a player who is already deployed is a no-op. The seat hook only fires inside an `OnPlayerDeployed` event chain that originates from the userland `DeployPlayer` call. If the engine deployed the player first, our seat is dead in the water.

### The fix

Block the engine's deploy-on-foot action for the SPECIFIC requesting player at click time. Re-enable on every claim-clear path. Result:

```
Frame N:    ButtonDown fires → requestHqVehicleSpawn runs
            ├─ slot.pendingSpawnOwnerPid = pid
            ├─ NEW: mod.EnablePlayerDeploy(player, false)   ← BLOCKS engine deploy-on-foot
            ├─ scheduleHqClaimTimeout(slotIndex, pid)
            └─ enqueueDispatch(slotIndex)
            
Frame N (still): Engine processes A as "deploy on foot" → BLOCKED. Player stays at deploy screen.

Frame N+~30:  Vehicle binds → onHqVehicleSpawnedForClaim → beginHqSeatFlow
              → 0.5s settle
              → NEW: mod.EnablePlayerDeploy(player, true)   ← re-enable for the deploy
              → mod.DeployPlayer(player)
              → OnPlayerDeployed fires
              → onHqSeatPendingPlayerDeployed runs
              → ForcePlayerToSeat(player, vehicle, -1)
              → player is in vehicle. ✓
```

The player experience: click button → stay on deploy screen ~1s → land directly in vehicle. No on-foot flash, no orphan vehicle, no clunk.

### Why this respects all the constraints

- ✅ ForcePlayerToSeat still happens inside `OnPlayerDeployed` (BountyHunter pattern preserved)
- ✅ No `mod.Teleport(player, ...)` before seat (pre-seat teleport ban respected)
- ✅ Vanilla mode untouched (gate at `isHqDeployMode()` upstream of every new call site)
- ✅ Global deploy gate (`EnableAllPlayerDeploy`) untouched and unaffected
- ✅ No widget tree changes
- ✅ No string changes

### Helper function strategy

A single centralized helper `setVehicleDeployEngineDeployBlockForPid(pid: number, blocked: boolean): void` that:
1. Resolves `player = safeFindPlayer(pid)`.
2. If `!isValidPlayer(player)` returns silently (player disconnected — no harm, deploy state will reset on reconnect).
3. Calls `mod.EnablePlayerDeploy(player, !blocked)` inside a `try { ... } catch {}` (defensive against engine errors).

All disable / enable sites call this helper. Centralizes the per-player API contract — no caller can accidentally invoke the global API.

### Cross-file impact

Only `src/vehicles/hq-deploy.ts` (5 edit groups) and `src/index/player-join-leave.ts` (1 line). No other consumer of the claim-clear path exists.

### Phase 1 — Edit `src/vehicles/hq-deploy.ts`

**P1-A. Add the centralized helper** near the top of the file (or in the existing helper region):

```ts
// v1.466: per-player engine-deploy block. Used during HQ-deploy claim lifetime to prevent
// the engine's deploy-on-foot action (especially the console A button race) from depositing
// the player on the ground before the requested vehicle spawns. PER-PLAYER ONLY — never call
// mod.EnableAllPlayerDeploy from this module; that is the global gate owned by countdown-flow.
function setVehicleDeployEngineDeployBlockForPid(pid: number, blocked: boolean): void {
    const player = safeFindPlayer(pid);
    if (!isValidPlayer(player)) return;
    try { mod.EnablePlayerDeploy(player, !blocked); } catch {}
}
```

## Risks

1. **🚨 PER-PLAYER ISOLATION VIOLATION** — accidentally calling `mod.EnableAllPlayerDeploy` instead of `mod.EnablePlayerDeploy` would brick deploy for every player. Mitigation: a centralized helper `setVehicleDeployEngineDeployBlockForPid(pid, blocked)` is the ONLY function in this module that touches the deploy-enable APIs. The helper takes a `pid` (single number, not iterable) and resolves to a single `Player`. Code review checkpoint: grep the diff for `EnableAllPlayerDeploy` — must return zero hits in any new code. Risk score: **must verify at code-review time**.

2. **Stuck on deploy screen** — if a claim-clear path is missed, the player stays disabled until next match (when the global re-enable at LIVE transition unblocks them). Mitigation: P1-E and P1-F cover both claim-clear paths. P2-A is defense-in-depth on disconnect. P1-G is the success path. **Test #5** in validation confirms the match-end global re-enable supersedes any leaked per-player disable. Risk score: **medium** (mechanical-mistake risk).

3. **Interaction with global countdown gate** — if countdown starts while a player has a pending claim, both gates are simultaneously `false`. When the claim resolves and per-player re-enables, global may still be `false` (countdown active) so player still can't deploy. This is correct behavior — countdown should suppress deploy. When countdown ends and global re-enables, player can deploy. Risk score: **zero**.

4. **DeployPlayer on disabled player** — does the engine call succeed if `EnablePlayerDeploy(player, false)` was set? P1-G re-enables IMMEDIATELY before `mod.DeployPlayer(player)` to guarantee the engine permits the deploy. Without P1-G's explicit enable, `DeployPlayer` might be a no-op on a disabled player and the seat would never fire. Risk score: **zero with P1-G in place**.

5. **on_foot source interference** — if disable is incorrectly applied to on_foot source, the existing `UndeployPlayer → DeployPlayer` flow would break. Mitigation: every disable site in P1-B/P1-C/P1-D explicitly gates on `source === "deploy_menu"`. on_foot source flows are unchanged. Risk score: **low** (gate is explicit).

6. **Validation rejection path** — `requestHqVehicleSpawn` early-returns on cooldown / claim-in-flight / no-slot / etc. before reaching the disable call. The disable is only applied AFTER the claim is successfully set. So validation rejections do NOT leave deploy disabled. Risk score: **zero** (verified by reading the function structure).

7. **Existing primary-click trackers without per-pid cleanup** (out of scope, flagged for awareness) — admin-panel, ready-dialog, player-ready-panel trackers in v1.465 audit. Not affected by this plan.
