# Recurring / Per-Tick Work -- Solutions Catalog (v2)

**Date:** 2026-05-13
**Baseline:** v1.514
**Status:** Solutions catalog only. User picks. Per project memory `feedback_plans_are_not_instructions_to_execute`, this is a menu, not a plan.
**Companion:** [`5.12.26_conquest_recurring_work_inventory.md`](./5.12.26_conquest_recurring_work_inventory.md).

## Reading guide

Each solution carries:
- **Problem** -- which risk(s) and the concrete behavior to reclaim, with file:line citations
- **Approach(es)** -- multiple ways to solve the same problem where they exist
- **Mechanism** -- what the change actually does
- **Impact estimate** -- order-of-magnitude reclaim, qualified by what assumption it rests on
- **Side-effects** -- what new behavior or risk it introduces
- **Complexity** -- Trivial / Small / Medium / Large
- **Regression risk** -- Very Low / Low / Medium / High
- **Compounds-with** -- which other solutions stack additively or supersede each other

Solutions are grouped by **problem area** (Sections A through N). A master stack rank lives in the closing Section X with multiple reading paths.

**Caveat that applies to every solution below:** sizing relies on the 8 Hz `OngoingPlayer` assumption from K.1. If actual cadence is faster, gains in per-tick reductions scale linearly higher; gains in event-driven coalescing are unchanged.

## Section A -- Force-broadcast burst control (R27, R28)

The single highest-probability cause of the v1.491 1,716ms breach is the unbounded force-true combat HUD broadcast pattern triggered by capture-point enter/exit events. Five solutions, listed strongest-first.

### A1. Per-pid scope: stop broadcasting engage HUD changes to all viewers

**Problem.** [`area-triggers.ts:47,66`](../src/index/area-triggers.ts#L47) calls `updateConquestCombatHudForAllPlayers(force=true)` on every `OnPlayerEnter/ExitCapturePoint` event. Only the entering/exiting player's engage state actually changed; broadcasting to all 64 viewers violates per-PID UI scope (memory `feedback_per_pid_ui_rule`).

**Mechanism.** Add a new entry point `updateConquestCombatHudForPlayer(player, pid, force=true)` that runs the existing per-pid pipeline once: top-HUD slice refresh + `twlConquestHudProcessPlayerFrame` for that pid only. Replace the two area-trigger broadcast call sites with the per-pid version.

**Impact estimate.** At 64p, an N-player broadcast is ~256 per-pid widget passes (~192 top-HUD VMs + 64 combat frames). Per-pid is ~4 widget passes (3 VMs + 1 frame). **~64x reduction** per force event. A 5-player cluster goes from 1,280 per-pid passes to 20. This is the single most impactful change in this catalog.

**Side-effects.** Engage HUD on OTHER players' screens (who can see the capture flag's owner count and progress bar) will lag by up to one subtick (~120ms) until the next `refreshLiveCaptureStateSubtick` sweeps the new state. Imperceptible -- the existing dirty-flag combat HUD path already has this latency baseline.

**Complexity.** Small. The per-pid pipeline already exists (used by warm-build and reveal paths); just expose a public entry point and swap two call sites.

**Regression risk.** Low. Worst case: visual lag of ~120ms on observer screens for cap-point engage UI. Reverting is a one-line change.

**Compounds with.** B8 (suppress event-driven `onCapturePointTick`). Together they eliminate both surfaces of the capture-point event-driven cost.

---

### A2. First-fires/tail-suppresses coalesce on force broadcasts

**Problem.** Same as A1, but treats the force broadcast as the responsibility of the central pipeline rather than fixing it at the call sites.

**Mechanism.** Modify `updateConquestCombatHudForAllPlayers` so `force=true` still triggers an immediate per-pid pipeline, but subsequent `force=true` calls within a 200ms window are downgraded to a dirty mark (no force). After the window, the next subtick's normal dirty path picks up any straggling changes.

**Impact estimate.** A 5-player cluster: 1 forced broadcast + 4 dirty-mark no-ops, then the next subtick's dirty path consolidates the rest. **~5x reduction** per cluster. Significantly less than A1's ~64x.

**Side-effects.** Subtle: if the cluster spans the throttle boundary (rare but possible), some force broadcasts replay. Not a correctness issue.

**Complexity.** Trivial. One file, ~10 lines.

**Regression risk.** Very Low. Pure additive guard.

**Compounds with.** None. Strictly inferior to A1 in impact -- present as a fallback if A1 is blocked for some reason. Don't ship both.

---

### A3. Frame-budget-aware force suppression

**Problem.** The recurring base + force cluster + GC pause is the worst-case stacking shape per K.5. If we could detect that the current frame is already heavy, we could defer non-critical work.

**Mechanism.** Stamp `frameStartElapsed = mod.GetMatchTimeElapsed()` at the start of each subtick. Inside `updateConquestCombatHudForAllPlayers(force=true)`, check `(now - frameStartElapsed) > N`. If true, drop the force flag (force becomes dirty-mark only) and let the next subtick pick it up.

**Impact estimate.** Hard to size without telemetry. Probabilistic -- prevents pathological stack-ups but doesn't help on a cold-load frame. Could plausibly prevent the 1,716ms breach if the breach was caused by a force broadcast landing on an already-loaded frame.

**Side-effects.** Latency-versus-correctness tradeoff: deferred forces feel laggy on busy frames. Player-perceptible if the threshold N is too low.

**Complexity.** Small. One file.

**Regression risk.** Medium. Threshold tuning could mis-fire and defer broadcasts during normal play. Needs telemetry to set N correctly.

**Compounds with.** A1 (per-pid still applies; this just controls when even the per-pid path runs). Adds a safety net on top of A1.

---

### A4. Per-pid invalidation events: never broadcast engage HUD at all

**Problem.** Same as A1 but more aggressive -- treat engage HUD as a pure per-pid concept driven entirely by per-pid state mutation.

**Mechanism.** Remove `updateConquestCombatHudForAllPlayers` entirely. Replace with `markCombatHudDirtyForPid(pid)` per pid; the main subtick pipeline iterates `forEachValidPlayer` and processes only dirty pids. The engine-event handlers mark dirty for the affected pid only.

**Impact estimate.** ~64x reduction (same as A1) PLUS eliminates the base cost of `refreshTopHudDerivedSlicesForAllPlayers` running unconditionally every subtick (this becomes per-pid too). Compounds with E1 implicitly.

**Side-effects.** Major refactor. Every existing call site of the broadcast functions has to change. Higher chance of missing a dirty-mark site, leading to a stale HUD bug.

**Complexity.** Medium-Large.

**Regression risk.** Medium. Touches a hot path; missing a dirty-mark causes a visible-but-subtle desync.

**Compounds with.** Supersedes A1 + E1 if shipped. Don't ship A1 if shipping A4.

---

### A5. Drop the force flag entirely; rely on a faster (50ms) throttle

**Problem.** Same as A1 from a different angle -- the force flag exists to bypass the 200ms throttle. If the throttle were 50ms, the user would not perceive the difference for cap-point feedback.

**Mechanism.** Set `TWL_CONQUEST_HUD_MAIN_UPDATE_SECONDS` to 0.05 (50ms). Remove `force` parameter usage from the two area-trigger call sites; they fall through normal `markHudDirty()` + throttled processing.

**Impact estimate.** Each force broadcast becomes a regular broadcast. At 5-player cluster, instead of 5 forced (each ~256 passes), you get 1 broadcast in the first 50ms window + 4 dirty no-ops + 1 broadcast in the next window. **~2.5x reduction**, less than A2.

**Side-effects.** All combat HUD updates now run 4x more frequently. Steady-state load increases. Inverse of the v1.491 problem -- raises the average cost to lower the peak. **Net negative for spike mitigation.**

**Complexity.** Trivial.

**Regression risk.** Medium-High. Increasing the global cadence trades spike risk for sustained-load risk.

**Compounds with.** Nothing. Listed for completeness but **do not ship this on its own** -- it's a regression for the actual problem.

## Section B -- Capture-point hot path (R1, R2, R3, R4, R5, R26, R28)

`refreshLiveCaptureStateSubtick` is the recurring per-subtick base at ~210 engine calls/subtick at 64p. Seven solutions targeting different facets.

### B1. Signature-based fast-path: skip the per-player loop when nothing changed

**Problem.** R2. Even when ownership and players-on-point are stable, `onCapturePointTick` does ~14 engine reads per cap-point per subtick. At 6 cap-points x 8 Hz = 672 calls/sec of pure churn when LIVE play is in a lull.

**Mechanism.** Inside `onCapturePointTick` ([`capture-tickets.ts:1728`](../src/index/capture-tickets.ts#L1728)), after the cheap reads (owner team, progress team, progress01), compute a signature `(ownerTeam, progressTeam, progressBucket, prevOnPointTeam1, prevOnPointTeam2)` and compare to `state.lastSignature`. If unchanged, write `state.lastUpdatedAtSeconds` and return. Skip the entire `GetPlayersOnPoint` + per-player loop.

**Impact estimate.** Steady-state savings: ~70-80% of `refreshLiveCaptureStateSubtick`'s cost when no capture is contested. At 64p that's ~150 engine calls/subtick reclaimed. **Peak unchanged** (a contested flag still pays full price).

**Side-effects.** The `previousEngagedByPid` snapshot (R3) needs to fire even on no-change subticks because engaged-pid set can change without on-point counts changing. Keep that bit outside the fast-path gate.

**Complexity.** Small. One function.

**Regression risk.** Low. Easy revert via signature equality flip.

**Compounds with.** B2 (reduce 3 GetSoldierState to 1).

---

### B2. Reduce 3 `GetSoldierState` calls to 1 `IsAlive` in `shouldCountPlayerAsActiveOnPoint`

**Problem.** R1. [`capture-tickets.ts:13-20`](../src/index/capture-tickets.ts#L13) `shouldCountPlayerAsActiveOnPoint` calls `IsAlive`, `IsDead`, and `IsManDown`. The latter two are semantic duplicates of `!IsAlive`.

**Mechanism.** Replace the three calls with one `safeGetSoldierStateBool(IsAlive)`. The engine's IsAlive contract: false when dead OR man-down OR not-spawned. Validate by reading the SDK or testing in SP.

**Impact estimate.** Saves 2 engine calls per player-on-point per subtick. At 24 players-on-point average (4 per flag x 6 flags), 48 engine calls/subtick at 64p = **~384 engine calls/sec reclaimed**.

**Side-effects.** If IsAlive's contract drifts from "alive AND fully spawned" (unlikely but possible across SDK versions), this could miscount man-down players. Verify against `reference_sdk_1.3.1` enum docs before shipping.

**Complexity.** Trivial. ~3 lines.

**Regression risk.** Low. Semantically equivalent if SDK contract holds.

**Compounds with.** B1, B4.

---

### B3. Event-driven authoritative cap state: eliminate the script-side poll

**Problem.** R2 + R26. Both `refreshLiveCaptureStateSubtick` and `OngoingCapturePoint` poll redundantly. Most cap-point state transitions ARE engine-event-driven (`OnPlayerEnter/ExitCapturePoint`, `OnCapturePointCaptured`, `OnCapturePointLost`).

**Mechanism.** Remove `refreshLiveCaptureStateSubtick` from the subtick loop. Replace with:
- Authoritative state mutated by the 4 event handlers (enter, exit, captured, lost).
- A 1 Hz reconciliation poll (called from the existing per-second branch) that detects engine-drift and rectifies.

**Impact estimate.** Eliminates ~210 engine calls/subtick = **~1,680 engine calls/sec reclaimed** at 64p. Single biggest steady-state reclaim available.

**Side-effects.** Engine event reliability is asymmetric (memory `project_engine_event_reliability_asymmetric` -- vehicle events drop). If capture events also drop, the 1 Hz reconciler picks up the drift but with up to 1s lag on flag-fill animations.

**Complexity.** Large. Touches the central capture-state mutation contract. Months of capture logic that assumes poll-driven would need an audit.

**Regression risk.** High. Capture progress and bleed are functionally critical; any event miss = wrong score.

**Compounds with.** Supersedes B1 and B2 on the subtick path. B6 still relevant (the OngoingCapturePoint duplicate).

---

### B4. Cached player-on-point Set per cap-point

**Problem.** `GetPlayersOnPoint` + `CountOf` + per-index `ValueInArray` is ~7 engine calls per flag per subtick. The same 4 enter/exit events maintain this membership; the engine call is redundant.

**Mechanism.** Maintain `State.conquest.capture.playersOnPointByObjId[objId]: Set<number>` mutated by `OnPlayerEnterCapturePoint` (add) and `OnPlayerExitCapturePoint` (delete). Inside `onCapturePointTick`, read the Set instead of querying the engine.

**Impact estimate.** Saves ~6 engine calls per cap-point per subtick = ~288 engine calls/sec at 64p. Compounds with B1 (B1 short-circuits when stable; B4 cheapens the heavy path).

**Side-effects.** Same event-reliability concern as B3 (smaller blast radius). Add a 1 Hz reconciler to catch drift.

**Complexity.** Small-Medium.

**Regression risk.** Medium. If an enter/exit event drops, the Set diverges from the engine until reconciler fires. Capture math wrong for up to 1s.

**Compounds with.** B1, B2.

---

### B5. Sparse iteration: skip cap-points that cannot change this subtick

**Problem.** Fully-captured (100% progress, no contesters) flags still pay ~14 engine calls per subtick to confirm they're still fully captured.

**Mechanism.** Maintain a "live cap-points" list: cap-points where progress01 is in (0, 1) OR `onPointTeam1 + onPointTeam2 > 0`. Skip the iteration of cap-points not in this list. An enter/exit event re-adds them to the live list.

**Impact estimate.** Modest -- depends on how often all 6 cap-points are stable. Steady-state with 2-3 stable flags: ~30-40% reduction in subtick cost.

**Side-effects.** Same event-drop risk; reconciler needed.

**Complexity.** Small.

**Regression risk.** Low-Medium. Bounded by reconciler.

**Compounds with.** B1 (B1 is the cheaper version of B5 -- skip per-flag based on signature; this skips before even reading). Could ship both.

---

### B6. Remove `OngoingCapturePoint` export

**Problem.** R26 CONFIRMED in K.3. `ongoingCapturePointImpl` is a single-line forwarder to `onCapturePointTick`. The script-side poll already covers it.

**Mechanism.** Delete the export at [`index.ts:206`](../src/index.ts#L206) and the implementation at [`area-triggers.ts:7-9`](../src/index/area-triggers.ts#L7). Add a comment noting why.

**Impact estimate.** If `OngoingCapturePoint` cadence is similar to the subtick (8 Hz), eliminates ~50% of `onCapturePointTick` invocations = ~80 engine calls/sec reclaim. If cadence is higher (60 Hz), the reclaim is much larger.

**Side-effects.** None known. The cadence is unverified -- if `OngoingCapturePoint` actually fires more often than 8 Hz, the script-side poll is too slow and removing it means slower cap-point UI feedback. Verify cadence first via M3.

**Complexity.** Trivial.

**Regression risk.** Low if cadence verification confirms 8 Hz parity. Medium otherwise.

**Compounds with.** Validation gated on M3 (cadence verification) results.

---

### B7. Suppress event-driven duplicate `onCapturePointTick` from area-trigger handler

**Problem.** R28. [`area-triggers.ts:44`](../src/index/area-triggers.ts#L44) inside `OnPlayerEnterCapturePoint` synchronously calls `onCapturePointTick(cp)`. The very next subtick's `refreshLiveCaptureStateSubtick` recomputes the same cap-point ~120ms later.

**Mechanism.** Stamp `state.lastTickAtMs = now` inside `onCapturePointTick`. At the top of the function, return early if `now - state.lastTickAtMs < 80`. The event-driven path fires immediately; the subtick within 80ms skips.

**Impact estimate.** Saves ~14 engine calls per enter/exit event when within a subtick of the next poll. At a 5-player cluster, ~70 engine calls reclaimed in that one frame.

**Side-effects.** None.

**Complexity.** Trivial.

**Regression risk.** Very Low.

**Compounds with.** A1 (per-pid force) -- shipping both reduces both event-driven cost surfaces.

---

### B8. Replace `previousEngagedByPid` object spread with a version counter

**Problem.** R3. The dirty-diff loop at capture-tickets.ts:2086-2095 spreads `State.conquest.capture.engagedObjIdByPid` (potentially 64 keys) every subtick. JS allocator pressure.

**Mechanism.** Replace the snapshot-and-diff pattern with a version counter. Every mutation to `engagedObjIdByPid` increments `engagedVersion`. The dirty-diff loop compares `prevVersion` to `currentVersion`; if equal, no engaged-set changes, skip the iteration entirely.

**Impact estimate.** Per-subtick: eliminates one 64-key object spread + the iteration. Heap allocation reclaim: ~8 spread objects/sec. CPU reclaim: ~64 iterations/sec. Small individually but compounds with M11 reduction.

**Side-effects.** None.

**Complexity.** Small.

**Regression risk.** Low.

**Compounds with.** E1 (top-HUD dirty gate), B1 (signature fast-path).

---

### B9. Eliminate try/catch frames in `onCapturePointTick`

**Problem.** R4. Five try/catch frames per cap-point per subtick. Each catch is cheap on the no-throw path, but Portal's JS runtime may not have the same try/catch zero-cost-when-not-thrown property as V8.

**Mechanism.** Inline the engine reads with null-coalesce instead of throw-catch. Use `safeGet*` helpers that already exist for this pattern in [`src/state/`](../src/state/).

**Impact estimate.** Speculative -- depends on Portal runtime's try/catch cost. Possible 5-15% per-call overhead reduction. Need to measure.

**Side-effects.** Slightly different error propagation -- a returned 0 vs a caught exception. Semantically equivalent for downstream consumers.

**Complexity.** Small.

**Regression risk.** Low.

**Compounds with.** Anything; structural refactor.

## Section C -- Boundary enforcement (R19, R20, R21)

`tickBoundaryEnforcement` polls every player every second. Six solutions.

### C1. SeatKind-gate the boundary classifier

**Problem.** R19 + R20. `getDesiredBoundaryViolationKind` does an `IsAlive` engine call for every player every second, even vehicle occupants. If H7 holds, this floods admin error log.

**Mechanism.** Add at the top of `getDesiredBoundaryViolationKind` ([`enforcement.ts:223`](../src/boundary/enforcement.ts#L223)) an early-return based on `seatKindByPid[pid]`. Vehicle occupants already return undefined at line 248 (`aircraft`) and have no GCZ classification for non-aircraft seats -- promote those checks above the soldier-state reads.

Two variants:
- **C1.a**: Early-return for `aircraft` and other non-`on_foot` seatKinds BEFORE the `IsAlive` call.
- **C1.b**: Keep the structure; only gate the soldier-state poll behind seatKind. The boundary state lookup still runs (cheap, all cache reads).

**Impact estimate.** Removes ~30-40 engine calls/sec at 64p (assuming half the population is in vehicles during peak play). Eliminates H7 admin-log flood entirely.

**Side-effects.** Aircraft enter-vehicle event-drop scenarios (memory `project_engine_event_reliability_asymmetric`) would leave `seatKind === "on_foot"` for a vehicle occupant. The safety-net at lines 253-269 catches this but only when `inSafeGround === true`. If event-drop AND in aircraft outside GCZ, the player would not get re-classified. This is exactly H8 / #116.

**Complexity.** Trivial.

**Regression risk.** Low for C1.b. Medium for C1.a (compounds with #116's safety-net architecture flaw).

**Compounds with.** D1 (same pattern for OngoingPlayer). C6 (fix #116).

---

### C2. Round-robin: classify N/8 players per second instead of N

**Problem.** Boundary violations are not time-critical at second-resolution. A player crossing OOB is given a 10-second grace + warning prompt; whether classification fires at second 1 or second 8 of that 10s window does not change outcomes.

**Mechanism.** Maintain a `boundaryCheckCursor` index. Per second, classify only `playerCount / 8` players starting from cursor, then advance cursor (wraparound). Each pid is classified once every 8 seconds.

**Impact estimate.** At 64p, drops from 64 engine calls/sec to 8. ~56 engine calls/sec reclaim.

**Side-effects.** A player who teleports / glitches into OOB has up to 8s of unflagged time. With the existing 10s violation grace, this could compound into a 18s window before lethal action. Acceptable design choice but visible to design / playtest team.

**Complexity.** Small.

**Regression risk.** Medium. Latency shift in OOB enforcement is a player-experience change.

**Compounds with.** C1 (smaller per-call cost), C4 (cached IsAlive).

---

### C3. Replace per-second sweep with event-driven only

**Problem.** R20. Most boundary state changes are area-trigger-driven anyway -- the per-second sweep exists only to catch on-foot Y-ceiling violations that don't trigger area triggers (per the comment at [`game-mode.ts:156-158`](../src/index/game-mode.ts#L156)).

**Mechanism.** Add a Y-ceiling check to `OnPlayerEnter/ExitVehicle` and `OnPlayerDeployed`. Add a per-vehicle Y-position cache updated by an ongoing-vehicle handler IF such a thing exists with low cost. Remove `tickBoundaryEnforcement` from the per-second sweep entirely.

**Impact estimate.** Removes ~130-256 engine calls/sec at 64p. Largest single boundary reclaim available.

**Side-effects.** Y-ceiling enforcement for on-foot players ABOVE ceiling (bail from aircraft) becomes event-window-bounded. If no event fires in the relevant window, the player escapes. Need a per-pid Y-delta watchdog from another existing tick.

**Complexity.** Medium-Large.

**Regression risk.** High. Boundary enforcement is the primary safety system for OOB.

**Compounds with.** C1 (per-pid still needs gating).

---

### C4. Cache `IsAlive` at deploy/death events, eliminate the boundary poll

**Problem.** R19. Every boundary classification reads `IsAlive` via engine call. The result only changes on death/deploy/undeploy events, all of which are event-handled.

**Mechanism.** Maintain `State.players.isAliveByPid: Record<number, boolean>` set true on `OnPlayerDeployed`, false on `OnPlayerKilled` / `OnPlayerUndeploy`. Replace `isPlayerAliveForBoundary(player)` body with `State.players.isAliveByPid[pid] === true`.

**Impact estimate.** Saves 1 engine call per player per boundary check = ~64 engine calls/sec at 64p (boundary side) + ~64 engine calls/sec (other consumers).

**Side-effects.** Stale on event-drop. `OnPlayerKilled` event-drop = boundary thinks player is alive when dead. Bounded by next deploy event clearing it.

**Complexity.** Small.

**Regression risk.** Medium. Event reliability dependency.

**Compounds with.** C1, C2, C3.

---

### C5. Y-ceiling delta check: skip when player Y hasn't changed significantly

**Problem.** The safety-net at [`enforcement.ts:253-269`](../src/boundary/enforcement.ts#L253) does `GetSoldierStateVector(GetPosition)` for every on-foot player when their boundary state evaluates -- even if their Y is stable.

**Mechanism.** Cache `lastY[pid]` from previous classification. Skip the position read this tick if `abs(currentY - lastY) < THRESHOLD` AND the player wasn't above ceiling last tick. (Requires fetching Y first to compare -- which defeats the purpose.) **Variant:** poll Y on the existing position-debug or vehicle tick instead, and re-use that cached Y.

**Impact estimate.** Negligible if Y-fetch is unavoidable. Marginal if cached from another path.

**Complexity.** Small.

**Regression risk.** Medium-High (cached-Y staleness during fast-fall).

**Compounds with.** Marginal; mostly listed for completeness.

---

### C6. Fix H8 safety-net architecture (refer to #116 specifically)

**Problem.** R21. The safety-net at lines 253-269 only fires when `inSafeGround === true`. A player in an aircraft OUTSIDE GCZ with stale `seatKind === "on_foot"` returns "ground_combat_zone" at line 251 BEFORE reaching the safety-net.

**Mechanism.** Move the safety-net BEFORE the `if (!inSafeGround) return "ground_combat_zone"` line. The cost is the `IsInVehicle` engine call now runs on every classification (not just safe-ground), but it self-corrects the stale seatKind issue from event-drop.

**Impact estimate.** Functionally fixes #116. Performance cost: ~1 additional engine call per OOB-classified player per second.

**Side-effects.** Slight per-call cost increase. Architectural correctness for the OOB misclassification family.

**Complexity.** Small.

**Regression risk.** Low. Architectural cleanup; covered by #116's test plan.

**Compounds with.** C1 (must ship together or neither; C1 alone exposes #116 worse).

---

## Section D -- OngoingPlayer per-tick polling (R23, R24, R25)

### D1. SeatKind-gate `ongoingPlayerImpl`

**Problem.** R23. [`player-loop-inputs.ts:3`](../src/index/player-loop-inputs.ts#L3) does the same per-pid work for vehicle occupants as on-foot players. The triple-tap detector polls `IsInteracting`; the ready-dialog check polls `IsDead`; vehicle occupants can't triple-tap interact and have no ready dialog.

**Mechanism.** Early-return at the top of `ongoingPlayerImpl` if `seatKindByPid[pid] !== "on_foot"` AND the player is currently deployed.

**Impact estimate.** At 64p with 30 vehicle occupants typical, saves ~90 engine calls/subtick = ~720 engine calls/sec.

**Side-effects.** A vehicle occupant who needs to re-open the ready dialog (e.g., post-deploy spec exit) would not poll until they exit the vehicle. Acceptable -- exiting the vehicle re-enables the tick.

**Complexity.** Trivial.

**Regression risk.** Low.

**Compounds with.** C1 (boundary), D4 (event-driven multi-click).

---

### D2. Round-robin per-tick processing

**Problem.** Speculative reduction. Even after seatKind gating, all on-foot players poll every tick.

**Mechanism.** Process N/K players per tick on a rotating cursor; K=4 means each player ticks every 480ms instead of every 120ms.

**Impact estimate.** 75% reduction at K=4 on the on-foot population.

**Side-effects.** Triple-tap detector window (2 seconds) needs N taps in ~16 ticks -> at K=4 only 4 ticks of opportunity -> could miss legitimate triple-taps. **Likely breaks ready-dialog UX.**

**Complexity.** Small.

**Regression risk.** High. UX-breaking on triple-tap.

**Compounds with.** None; mostly listed to argue AGAINST it.

---

### D3. Replace multi-click polling with a dedicated UX path

**Problem.** R25. The triple-tap interact pattern exists only because there is no `OnInteractKeyPressed` event in the SDK. Polling `IsInteracting` per tick is the cost.

**Mechanism.** Replace the triple-tap interact mechanic with a deploy-screen UI button. Player presses "Open Ready Dialog" instead of triple-tapping interact. UI button click is event-driven (no polling). Removes the multi-click detector entirely.

**Impact estimate.** Eliminates the entire `IsInteracting` poll = ~64 engine calls/subtick. Effectively erases the largest non-seatKind-gated OngoingPlayer cost.

**Side-effects.** UX change. Triple-tap was chosen as the cheapest re-entry into ready dialog without burning a HUD button slot. Discuss with design before considering.

**Complexity.** Medium. Touches ready-dialog UX wiring.

**Regression risk.** Medium-High. Player-facing UX change.

**Compounds with.** D1.

---

### D4. Cache `IsInteracting` state with event-driven invalidation

**Problem.** Same as D3 from a different angle -- can we avoid polling without changing UX?

**Mechanism.** Speculative -- there is no event-driven analog for the interact key. SDK 1.3.1 audit (K.1) confirmed no new event. **Not implementable** unless a hidden API exists. Listed only to note that it has been considered and ruled out.

**Impact estimate.** N/A.

**Complexity.** N/A.

**Regression risk.** N/A.

---

### D5. Cadence verification telemetry (was S13)

**Problem.** R24. All cost numbers depend on the 8 Hz assumption. If actual is 60 Hz, every per-tick reclaim scales 7.5x in importance.

**Mechanism.** Add a per-pid counter inside `ongoingPlayerImpl`. On the per-second boundary, emit one world-log line with the max counter across pids + reset. Single emit per second is below AGENTS.md's world-log rate limit.

**Impact estimate.** Tells us whether per-tick reclaims are 1x or 7.5x more valuable than estimated. Critical prerequisite for sizing every other Tier A and B solution.

**Side-effects.** Adds ~1 line per second to world log during the measurement window. Strip after measurement complete.

**Complexity.** Small.

**Regression risk.** Very Low (telemetry, easy to remove).

**Compounds with.** Foundational. Run this BEFORE deciding which Tier A solutions to fund.

## Section E -- Top-HUD VM rebuild + heap churn (R6, M11)

### E1. Split clock-VM (every tick) from status/help-ready VMs (dirty-gated)

**Problem.** R6 + M11. R6 alone produces ~1,536 VM allocations/sec at 64p. ~1,024/sec of those are redundant per K.4.

**Mechanism.** Split `refreshTopHudDerivedSlicesForAllPlayers` into two functions:
1. `refreshClockVmForAllPlayers` -- runs every subtick. Clock is time-variant.
2. `refreshStatusAndHelpReadyVmsForAllPlayers` -- runs only when `topHudDerivedDirty` is set. Cleared after run.

The dirty flag is set by every mutation to fields that flow into status/help-ready -- ready state, perspective team, deploy state, match phase, etc. Audit: same pattern as the existing combat HUD dirty contract.

**Impact estimate.** Cuts ~1,024 VM allocations/sec at 64p. Direct M11 reduction. Reduces minor-GC frequency by ~2/3 of R6's contribution.

**Side-effects.** Stale status/help-ready VM if a mutation site is missed. Test plan: every existing mutation site of the underlying state fields must be audited.

**Complexity.** Small-Medium. The audit is the cost, not the change.

**Regression risk.** Medium. Missed dirty-mark = subtle stale-UI bug.

**Compounds with.** E2, E3.

---

### E2. Signature-cache the published VM, skip widget write if unchanged

**Problem.** Even if the VM rebuilds, the widget writes can be skipped when the VM is identical to last-published.

**Mechanism.** After building, compute a cheap signature (concatenate the few scalar fields). Compare to `lastPublishedSignature[pid]`. If equal, skip `publishTopHudDerivedSlicesForPid`.

**Impact estimate.** Saves widget-write IPC (Class D in K.6) on unchanged frames. Smaller than E1 (build still happens) but additive.

**Side-effects.** None.

**Complexity.** Small.

**Regression risk.** Low.

**Compounds with.** E1 (E2 alone leaves the build cost; E1 alone leaves the publish cost).

---

### E3. Per-pid dirty flag map

**Problem.** Even with E1, a single ready-state change flips the global dirty flag and forces a rebuild for all 64 players, even though most of their VMs are unchanged (status counts include all players' ready states).

**Mechanism.** Replace `topHudDerivedDirty` with `topHudDerivedDirtyByPid: Record<number, boolean>`. Each mutation marks the relevant pid(s) dirty. The status VM aggregates across all players, so any global change still marks all pids; help-ready and clock are per-pid.

**Impact estimate.** Reduces unchanged-pid work; depends on mutation patterns. Probably ~30-50% additional reclaim beyond E1.

**Side-effects.** More complex audit. Each mutation site now needs to know WHICH pid(s) it affects.

**Complexity.** Medium.

**Regression risk.** Medium.

**Compounds with.** Supersedes E1's global flag if shipped; design as a sequence (E1 first, E3 if heap churn still problematic).

---

### E4. Object pool for ephemeral VMs

**Problem.** Even with E1, M11 churn from short-lived VM objects.

**Mechanism.** Maintain a per-pid VM object pool. Mutate in-place instead of allocating a new object. Publish reads the same object.

**Impact estimate.** Eliminates the allocation entirely for the rebuild path. Larger M11 reclaim than E1 alone.

**Side-effects.** Object identity becomes meaningful -- if any consumer caches the VM reference and expects it to be immutable, this breaks them. Audit all consumers.

**Complexity.** Medium.

**Regression risk.** Medium.

**Compounds with.** E1, E2.

## Section F -- Vehicle HUD broadcast (R11, R31)

### F1. Extend the S3 coalesce window from 200ms to 500ms

**Problem.** R31. A multi-second event burst (one death per second) still produces one broadcast per S3 window.

**Mechanism.** Change `VEHICLE_DEPLOY_TIMER_HUD_COALESCE_MS` from 200 to 500 in [`vehicles/deploy-timer-ui.ts`](../src/vehicles/deploy-timer-ui.ts).

**Impact estimate.** Halves to ~5x reduction on multi-second bursts. Deploy-timer UI updates with up to 500ms lag.

**Side-effects.** Players see deploy timer count down with slight lag. Imperceptible at second-resolution.

**Complexity.** Trivial.

**Regression risk.** Very Low.

**Compounds with.** F2, F3.

---

### F2. Per-pid dirty key set within the S3 window

**Problem.** Even within a coalesce window, the drain refreshes ALL viewers, not just those whose vehicle context changed.

**Mechanism.** Add `vehicleDeployTimerDirtyPidSet: Set<number>` mutated by every dirty-mark site. The S3 drain iterates only the dirty set instead of all valid players.

**Impact estimate.** Reduces per-drain work from N to D (D = dirty pid count). Most bursts dirty 1-2 pids.

**Side-effects.** None.

**Complexity.** Small.

**Regression risk.** Low.

**Compounds with.** F1.

---

### F3. Limit broadcast scope to deploy-screen viewers only

**Problem.** Players who are deployed (not on the deploy screen) cannot SEE the deploy timer HUD -- yet the broadcast still runs the per-pid render plan for them.

**Mechanism.** At the top of `refreshVehicleDeployTimersForPlayerPreservingVisibility`, return early if the pid is not in a "deploy-screen visible" state. Maintain that state via existing deploy/undeploy events.

**Impact estimate.** Reduces broadcast scope to typically 5-10 pids (recently undeployed) instead of 64. **~6-12x reduction.**

**Side-effects.** When a player undeploys, their first deploy-timer render fires via the existing `updateVehicleDeployTimerHudForPlayer` call in `onPlayerUndeployImpl`. F3 must ensure this still works (e.g., by always passing through for the entering-deploy-screen pid).

**Complexity.** Small-Medium.

**Regression risk.** Low-Medium.

**Compounds with.** F1, F2.

---

### F4. Drop the 1 Hz re-assertion from `onLiveTick`

**Problem.** [`capture-tickets.ts:2153`](../src/index/capture-tickets.ts#L2153) `onLiveTick` calls `updateVehicleDeployTimerHudForAllPlayers` every second as a "transient suppression self-heal." Since S3 (v1.497), the coalesce window already handles the dirty path; the 1 Hz re-assertion is redundant in steady state.

**Mechanism.** Remove the call from `onLiveTick`. Leave the explicit event-driven calls intact.

**Impact estimate.** Saves one N-player broadcast per second when the deploy timer is in a stable state.

**Side-effects.** A genuine transient-suppression bug would no longer self-heal at 1 Hz. Verify the suppression races are gone (they should be post-S3).

**Complexity.** Trivial.

**Regression risk.** Low-Medium.

**Compounds with.** F1, F2, F3.

## Section G -- Ready-dialog broadcasts & `safeFindPlayer` (R29, R30, R33)

### G1. 200ms coalesce on ready-dialog broadcasts

**Problem.** R29. Main-base trigger crossings call `refreshReadyStatusForAllBuiltReadyDialogs` + `renderReadyDialogForAllVisibleViewers` synchronously.

**Mechanism.** Apply the S3 coalesce pattern to ready-dialog refresh. `readyDialogRefreshDirty` flag + 200ms drain Timer.

**Impact estimate.** Multi-crossing scenarios drop from N broadcasts to 1 per 200ms.

**Side-effects.** Up to 200ms lag on the IN MAIN BASE indicator update. Acceptable.

**Complexity.** Small.

**Regression risk.** Low.

**Compounds with.** G4.

---

### G2. Cache `safeFindPlayer` via TickContext

**Problem.** R33. Three broadcast functions iterate per-pid and call `safeFindPlayer` each iteration. At 64p that's 4,096 array touches per broadcast.

**Mechanism.** Inside `safeFindPlayer`, check `getActiveTickContext()`. When a context is active, walk the cached players array. Outside contexts, fall back to fresh fetch.

**Impact estimate.** O(N^2) -> O(N) for broadcast loops inside subtick. ~64x reduction on the lookup cost portion of each loop.

**Side-effects.** TickContext is only active within `runGameModeLoop`. Event-driven broadcasts (outside the loop) don't benefit unless wrapped (see G3).

**Complexity.** Small.

**Regression risk.** Very Low (additive guard).

**Compounds with.** G3.

---

### G3. Wrap event handlers with `beginTickContext` / `endTickContext`

**Problem.** Event-driven paths (area-trigger crossings, disconnect) call broadcast helpers but no TickContext is active, so G2 cannot help them.

**Mechanism.** Wrap the body of each event handler that triggers a broadcast with `beginTickContext()` + `endTickContext()`. The cache is built once at handler entry, freed at exit.

**Impact estimate.** Activates G2's benefit on event-driven paths.

**Side-effects.** Slight overhead per handler entry for the cache build (one `AllPlayers` call + one count). Offset by the per-iteration savings.

**Complexity.** Small. Touches ~10 event handler files.

**Regression risk.** Low.

**Compounds with.** G2 (G2 is no-op without G3 on event paths).

---

### G4. Pre-build roster signature at dialog-open, cache for dialog lifetime

**Problem.** `refreshReadyDialogRosterForViewer` ([`roster-render.ts:103`](../src/ready-dialog/roster-render.ts#L103)) computes a signature every call and only re-renders on change. But computing the signature itself is non-trivial.

**Mechanism.** Cache the signature inputs (roster array reference, ready states) per-viewer; invalidate only on mutation events. Reduces the signature-compute step.

**Impact estimate.** Smaller than G1; marginal additive savings.

**Complexity.** Small.

**Regression risk.** Low.

**Compounds with.** G1.

---

### G5. Skip dialog refresh broadcasts if no built dialogs visible

**Problem.** `refreshReadyStatusForAllBuiltReadyDialogs` iterates `readyDialogData` even if zero dialogs are `dialogVisible`. Fast no-op but still iterates.

**Mechanism.** Track `visibleDialogCount: number` mutated by dialog show/hide. Skip the broadcast entirely if zero.

**Impact estimate.** Marginal in steady state (most ready-dialog refreshes happen pre-LIVE when dialogs ARE visible). Helps during LIVE when most dialogs hidden.

**Complexity.** Trivial.

**Regression risk.** Very Low.

**Compounds with.** Anything.

---

### G6. Delta-render: update only changed dialog rows

**Problem.** Every roster refresh rebuilds all rows for all built dialogs even if one player's ready state flipped.

**Mechanism.** Maintain per-pid last-rendered ready state. Compare to current; emit `mod.SetUITextLabel` for changed rows only.

**Impact estimate.** Reduces UI mutation cost (Class D) by ~95% on minor changes. Largest gain on solo ready-flip events; little gain on cohort-flip (everyone ready).

**Complexity.** Medium.

**Regression risk.** Low-Medium.

**Compounds with.** G1, G4.

## Section H -- Game-mode loop & `onLiveTick` structure (R7, R9, R10)

### H1. Move `applyBleedTick` + `checkEndCondition` to `Clocks.CountDownClock.onSecond`

**Problem.** R9. `onLiveTick` packs 4 heavy operations into one second-boundary subtick.

**Mechanism.** The match clock already fires `onSecond` at 1 Hz ([`clock/state.ts:65,88`](../src/clock/state.ts#L65)). Bleed + checkEnd are pure 1 Hz operations. Move them out of `onLiveTick`.

**Impact estimate.** Decouples bleed math from the combat-HUD broadcast tick. The two no longer share a frame budget. Bleed itself is cheap (~4 calls); the benefit is structural (avoid stacking).

**Side-effects.** If the match clock's `onSecond` is slightly offset from the game-mode loop's second-boundary (different `Math.floor` reference), bleed could be 1 frame ahead or behind combat HUD. Probably imperceptible.

**Complexity.** Small.

**Regression risk.** Low.

**Compounds with.** A1, A4.

---

### H2. Adaptive subtick cadence

**Problem.** Fixed 120ms subtick fires regardless of load. Spike-frame doesn't get longer relief; idle-frame doesn't get to update faster.

**Mechanism.** Stamp `frameStartElapsed` at start of each subtick. Compute `frameCost = nowElapsed - frameStartElapsed` before `mod.Wait`. Adjust the wait: `await mod.Wait(Math.max(0.05, 0.12 - frameCost*0.5))` -- shorter wait if last frame was cheap, longer if expensive.

**Impact estimate.** Smooths spike-frame impact but doesn't reduce total work. Probabilistic spike avoidance.

**Side-effects.** Variable cadence makes other rate-limited operations (like the 200ms HUD throttle) trickier to reason about. Per-frame predictability lost.

**Complexity.** Small.

**Regression risk.** Medium.

**Compounds with.** A3 (frame-budget-aware).

---

### H3. Subtick fairness: rotate heavy work across odd/even subticks

**Problem.** Same as R9 -- everything stacks on the second-boundary.

**Mechanism.** Move some heavy ops (e.g., `refreshTopHudDerivedSlicesForAllPlayers`) to odd subticks; combat HUD to even subticks. Each runs at 4 Hz instead of 8 Hz.

**Impact estimate.** Halves per-subtick cost for the rotated operations; doubles latency.

**Side-effects.** Latency increase visible on combat HUD if it rotates to 4 Hz.

**Complexity.** Small.

**Regression risk.** Medium.

**Compounds with.** E1, B1.

---

### H4. Replace `while (true) + mod.Wait` with recursive Timer

**Problem.** Architectural -- the current loop pattern fights the adaptive-cadence work (H2). Recursive Timer would allow each iteration to reschedule with custom delay.

**Mechanism.** Refactor `runGameModeLoop` to `function tick() { ... Timers.setTimeout(tick, computeNextDelay()); }`.

**Impact estimate.** Enabler for H2 + A3; no impact alone.

**Side-effects.** Different exception-handling shape; could affect crash recovery.

**Complexity.** Medium.

**Regression risk.** Medium.

**Compounds with.** H2, A3.

## Section I -- Engine call class & UI write batching

### I1. Batch widget updates via `UpdateUIPanel` instead of per-widget `SetUI*`

**Problem.** Class D (UI mutation) is the dominant ms-cost contributor (K.6). The combat HUD pipeline issues ~10-15 individual `mod.SetUITextLabel` / `mod.SetUIPanelVisible` per pid per frame.

**Mechanism.** Where applicable, group per-pid widget mutations into a single `mod.UpdateUIPanel` call with batched parameters. Requires SDK support -- audit which widget types accept batched updates.

**Impact estimate.** Speculative. SDK may not expose batched mutation for all widget types. Where it does, ~10-15x reduction in IPC overhead per frame.

**Side-effects.** SDK-specific behavior; requires read of SDK 1.3.1 widget-mutation docs.

**Complexity.** Medium (SDK research + refactor).

**Regression risk.** Medium.

**Compounds with.** Anything that reduces broadcast count.

---

### I2. Pre-resolve `mod.stringkeys.*` once at module init

**Problem.** Speculative -- `mod.stringkeys.twl.foo.bar` lookups may resolve every access.

**Mechanism.** Cache string keys in module-local const at file load. Verify via SDK whether `mod.stringkeys` is already a static object lookup (likely is, given how it's typed).

**Impact estimate.** Probably zero (likely already optimized). Listed only to rule out.

**Complexity.** Trivial.

**Regression risk.** Very Low.

## Section J -- Disconnect / join paths (R30, R32)

### J1. Defer disconnect cleanup to next subtick via `Timers.setTimeout(0)`

**Problem.** R30 + R32. `OnPlayerLeaveGame` does 5 N-player broadcasts + ~25 namespace clears synchronously.

**Mechanism.** Wrap the heavy cleanup in `Timers.setTimeout(() => doCleanup(pid), 0)`. The synchronous handler only marks the pid disconnected; cleanup defers to next event loop tick.

**Impact estimate.** Removes ~5 N-player broadcasts from the current engine frame. Defers them; doesn't eliminate them. Helps spike avoidance.

**Side-effects.** Any synchronous code path that reads disconnected-pid state in the next ~10ms gets stale data. Bounded by the `disconnectedByPid` flag check.

**Complexity.** Small.

**Regression risk.** Medium.

**Compounds with.** G1 (coalesce).

---

### J2. Coalesce multi-disconnect into a single batched broadcast

**Problem.** Two disconnects in the same engine frame = 10 broadcasts back-to-back.

**Mechanism.** Maintain `pendingDisconnectPids: Set<number>`. Schedule a single 200ms-coalesce broadcast that processes all pending disconnects in one pass.

**Impact estimate.** Multi-disconnect frames stack from 10x cost to 1x.

**Side-effects.** Slight UI lag on disconnect indicators.

**Complexity.** Small.

**Regression risk.** Low.

**Compounds with.** J1, G1.

## How to read the stack (multiple paths)

**Path 1 -- Single-ship, max-impact:**
Tier 1 only: **A1 + D1 + C1 + B2 + B7**. Five small low-risk diffs that compound. Estimated combined reclaim: ~1,500-2,000 engine calls/sec at 64p PLUS the force-broadcast peak collapse from A1. **This is the recommended starting point if you can only commit to one Wave.**

**Path 2 -- Spike-first, validate-after:**
Ship A1 alone first. Measure with M3. If A1 alone resolves v1.491, defer the rest. If it doesn't, the histogram tells you which next solution to target.

**Path 3 -- Measure-first, then decide:**
Tier D first: D5 cadence verification + M3 histogram + M4 broadcast counts. Two-week diagnostic window. Then choose Tier 1-2 based on data, not inference.

**Path 4 -- Heap-focused:**
E1 + E2 + E4 + B8. Cuts ~1,500-2,000 VM allocations/sec. Reduces minor-GC frequency. Doesn't directly reduce per-frame CPU; reduces probability of GC-pause stack-ups.

**Path 5 -- Hygiene only:**
Tier 4: N1 + K1 + K2 + G5 + L1. All trivial, all very low risk. ~30 minutes of work total. No impact on v1.491 but cleans the floor.

**Path 6 -- Full Tier 1 + 2:**
A1 + D1 + C1 + B2 + B7 + E1 + B1 + B4 + G2 + G3 + F3 + B6. ~12 ships, estimated 1-2 weeks of focused work. Highest single-stack reclaim available without architectural risk.
