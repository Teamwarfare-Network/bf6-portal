## Section D: Deep-dive on every hot-path fan-out

The most important section. Each per-tick consumer is itemized with concrete engine-call counts and risk analysis.

### D.0 -- The game-mode loop structure (`runGameModeLoop`)

Source: [`game-mode.ts:106-182`](../src/index/game-mode.ts#L106). Runs at ~120ms cadence. Each iteration has a single LIVE/non-LIVE branch and a per-second-boundary sub-branch.

**Per iteration (every ~120ms, every game state):**
- `beginTickContext()` + `endTickContext()` (always)
- `nowElapsed = mod.GetMatchTimeElapsed()` (1 engine call)

**Per iteration while LIVE + no victory dialog (every ~120ms):**
- D.1.a `refreshLiveCaptureStateSubtick()` -- HEAVY
- D.1.b `onLiveTick()` ON second-boundary subtick (1 Hz inside the 8 Hz loop) OR `updateConquestCombatHudForAllPlayers()` on non-second-boundary subticks
- D.1.c `flushCaptureSoundQueue()` -- cheap when idle
- D.1.d `flushCaptureVoiceOverQueue()` -- cheap when idle

**Per second-boundary inside the loop (1 Hz):**
- D.2.a `scoreboardSyncTick()`
- D.2.b `ensureActiveWorldInteractablesReady()` -- effectively no-op after first call
- D.2.c `checkTakeoffLimitForAllPlayers()` -- **CONFIRMED NO-OP STUB**
- D.2.d `tickBoundaryEnforcement()` -- HEAVY (per-player iteration)
- D.2.e Victory dialog update (only during victory window)

### D.1.a `refreshLiveCaptureStateSubtick` (per subtick, ~8 Hz)

Source: [`capture-tickets.ts:2141-2145`](../src/index/capture-tickets.ts#L2141). Body:

```ts
function refreshLiveCaptureStateSubtick(): void {
    clearInactiveEngagedObjectiveOwners();
    syncMappedCapturePointsFromEngine();
}
```

Inner: `syncMappedCapturePointsFromEngine()` at [`capture-tickets.ts:2063`](../src/index/capture-tickets.ts#L2063):
- Iterates `State.conquest.capture.mappedObjIdsInOrder` -- 6 capture points on Firestorm.
- For each: `mod.GetCapturePoint(objId)` (1 engine call) -> `onCapturePointTick(cp)`.

Inner-inner: `onCapturePointTick()` at [`capture-tickets.ts:1728`](../src/index/capture-tickets.ts#L1728). PER CAPTURE POINT:
- `safeGetObjId(eventCapturePoint)` (1 engine call)
- `mod.GetMatchTimeElapsed()` (1 engine call)
- `mod.GetCurrentOwnerTeam(eventCapturePoint)` (1 engine call)
- `mod.GetOwnerProgressTeam(eventCapturePoint)` (1 engine call)
- `mod.GetCaptureProgress(eventCapturePoint)` (1 engine call)
- `mod.GetPlayersOnPoint(eventCapturePoint)` (1 engine call, returns array)
- `mod.CountOf(playersOnPoint)` (1 engine call)
- For each player on point:
  - `mod.ValueInArray(playersOnPoint, i)` (1 engine call)
  - `isValidPlayer(pointPlayer)` (1 type check)
  - `safeGetPlayerId(pointPlayer)` (1 engine call -- `GetObjId`)
  - `safeGetTeamNumberFromPlayer(pointPlayer)` (1 engine call -- `GetTeam`)
  - `shouldCountPlayerAsActiveOnPoint(countablePlayer)` -- THIS CALLS 3 `GetSoldierState` CALLS internally ([`capture-tickets.ts:13-20`](../src/index/capture-tickets.ts#L13)):
    - `isPlayerDeployed(player)` (cache read)
    - `safeGetSoldierStateBool(IsAlive)` (1 engine call)
    - `safeGetSoldierStateBool(IsDead)` (1 engine call)
    - `safeGetSoldierStateBool(IsManDown)` (1 engine call)

**Engine-call count per subtick at 64p with avg 4 players on each of 6 flags:**

| Call class | Calls per subtick |
|---|---:|
| Per-capture-point base (6 flags x 7 calls) | 42 |
| Per-player-on-point engine ops (6 flags x 4 players x 4 calls) | 96 |
| Per-player-on-point `GetSoldierState` (6 flags x 4 players x 3 calls) | **72** |
| **Total** | **~210 engine calls per subtick** |

At 8 Hz that is **~1,680 engine calls per second JUST from capture sync.** Tagged Tier S5 in [`conquest_optimization_analysis.md`](./conquest_optimization_analysis.md).

**Risks:**
- R1 (LARGE): `shouldCountPlayerAsActiveOnPoint` calls 3 `GetSoldierState` per player-on-point per subtick. If H7 holds (`GetSoldierState` fails for vehicle occupants), every aircraft passenger above a flag (rare but possible) produces 3 `ERROR REPORTED BY GETSOLDIERSTATE` per subtick. The `IsDead` + `IsManDown` checks are also redundant -- they overlap with `IsAlive`.
- R2 (LARGE): No throttle. Fires every subtick regardless of whether ANY capture point state changed. A flag with stable ownership and zero players-on-point still costs 7 engine calls per subtick.
- R3 (MEDIUM): The `previousEngagedByPid` snapshot at line 2065 spreads-and-copies `State.conquest.capture.engagedObjIdByPid` every subtick. At 64p, this is a 64-key object spread per subtick. JS allocator pressure.
- R4 (MEDIUM): Try/catch around every engine read pattern. If the engine errors (e.g., capture point destroyed mid-subtick), 5 try/catch frames per call still get created.
- R5 (SMALL): The dirty-diff loop at lines 2086-2095 iterates `engagedObjIdByPid` keys every time. O(N) per subtick.

**Current mitigations:** none. There is no fast path for "nothing changed."

### D.1.b1 `updateConquestCombatHudForAllPlayers` -- non-second-boundary path

Source: [`capture-tickets.ts:2109`](../src/index/capture-tickets.ts#L2109). Called on every subtick EXCEPT the second-boundary subtick (which calls `onLiveTick` instead). So fires roughly 7 of every 8 subticks while LIVE.

Body has internal `hudDirty` gate plus a 200ms time-based throttle inside `twlConquestHudTickFrame` ([`pipeline.ts:118-122`](../src/ui/conquest/hud-core/pipeline.ts#L118)):

```ts
const shouldRunFrame = !!force || State.conquest.debug.hudDirty;
if (shouldRunFrame) {
    twlConquestHudTickFrame(force);
    State.conquest.debug.hudDirty = false;
}
```

When dirty AND throttle elapsed -> full per-player VM-build over all N connected players (this is Tier S1/S2's surface).

Also unconditionally calls `refreshTopHudDerivedSlicesForAllPlayers()` BEFORE the dirty gate (top HUD must repaint clock every tick).

**Engine-call count per subtick at 64p (when dirty fires):**

| Call class | Calls per subtick |
|---|---:|
| `refreshTopHudDerivedSlicesForAllPlayers` per-pid VM rebuild | ~5 per player x 64 = ~320 |
| `twlConquestHudTickFrame` per-pid (when dirty + throttle elapsed) | ~64 widget updates x 64 = high |

**Risks:**
- R6 (LARGE): The top-HUD VM rebuild is **NOT gated by dirty** -- it fires every subtick. Per pid, builds 3 VM objects (`hudStatusVm`, `hudHelpReadyVm`, `hudClockVm`). 64p x 3 = 192 VM allocations per subtick = ~1,536 VM allocations per second. M11 churn driver.
- R7 (MEDIUM): The 200ms throttle is time-based, not subtick-aligned. A burst of dirty marks at subtick N triggers the next frame, then 200ms pass, then the next subtick after that triggers again. Two adjacent subticks could both fire if dirty races right.
- R8 (LOW): The `force` parameter bypasses the throttle entirely. Currently invoked from S1/S2 capture-point enter/exit. Documented in Tier S analysis.

**Current mitigations:** `hudDirty` flag (gates expensive write-through), 200ms throttle (rate-limits frame work).

### D.1.b2 `onLiveTick` -- ONCE PER SECOND inside the loop

Source: [`capture-tickets.ts:2148-2154`](../src/index/capture-tickets.ts#L2148). The HEAVY second-boundary path:

```ts
function onLiveTick(): void {
    applyBleedTick();
    checkEndCondition();
    updateConquestCombatHudForAllPlayers();
    updateVehicleDeployTimerHudForAllPlayers();
}
```

**Per-call breakdown:**

- `applyBleedTick()` ([`capture-tickets.ts:1656`](../src/index/capture-tickets.ts#L1656)):
  - 4 cache reads (early returns)
  - `mod.GetMatchTimeElapsed()` (1 engine call)
  - `getOwnershipCounts()` -- iterates capture points, no engine calls (pure cache reads)
  - If bleed applies: `applyTicketDelta()` + `mirrorTicketsToEngineScore()` (~2 `mod.SetGameModeScore` engine calls)
  - **Cost: ~4 engine calls when bleed fires, ~1 engine call when no bleed.**

- `checkEndCondition()` ([`capture-tickets.ts:1698`](../src/index/capture-tickets.ts#L1698)):
  - Pure cache reads. No engine calls in the steady-state path.
  - Only fires `tryLatchEnd` -> `endMatch` on actual end condition.
  - **Cost: nanoseconds in steady state.**

- `updateConquestCombatHudForAllPlayers()` -- same as D.1.b1, but always called here (force=undefined). Subject to the same `hudDirty` gate + 200ms throttle. **At 64p when dirty: ~64 per-pid VM rebuilds + the top-HUD refresh (192 VM allocations).**

- `updateVehicleDeployTimerHudForAllPlayers()` -- **as of v1.497, throttled via 200ms coalesce window** (Tier S3 ship). The actual broadcast may not fire on this exact call; it's queued and drained 200ms later. **Cost when broadcast IS in window: O(N players) per-pid render plan rebuild + widget writes.**

**Engine-call count for `onLiveTick` at 64p (worst case, all paths fire):**

| Call class | Engine calls |
|---|---:|
| `applyBleedTick` (bleed firing) | ~4 |
| `updateConquestCombatHudForAllPlayers` (dirty + force) | ~192 top-HUD VM allocations + 64 widget passes |
| `updateVehicleDeployTimerHudForAllPlayers` (when coalesce drains) | ~64 per-pid plans x ~10 widgets each = ~640 widget writes |
| **Total when everything fires** | **~700-900 engine calls + ~190 VM allocations** |

**This is the per-second-boundary SPIKE pattern.** It happens once per second every second while LIVE. The non-boundary subticks (the other 7 of 8 per second) are MUCH lighter.

**Risks:**
- R9 (CRITICAL): `onLiveTick` concentrates 4 heavy operations into a single subtick. **If they all fire on the same frame -- which they will, by design -- they compound. This is structurally the highest-cost subtick of every second.**
- R10 (CRITICAL): No staggering. Bleed, combat HUD, vehicle HUD all fire back-to-back. A 64p match with active dirty state will see all of them.
- R11 (LARGE): The vehicle HUD coalesce window (200ms) doesn't align with the 1 Hz onLiveTick cadence. The drain could fire ~50-200ms AFTER the second-boundary tick, adding a second spike that's not visible in the same frame budget but still counts toward the per-frame cap if delivered before the next subtick.

**Current mitigations:** `hudDirty` flag, 200ms HUD throttle, S3 vehicle-HUD coalesce.

### D.1.c `flushCaptureSoundQueue`

Source: [`capture-sound.ts:147`](../src/index/capture-sound.ts#L147).

```ts
function flushCaptureSoundQueue(): void {
    if (!State.conquest.sound.enabled) return;          // cache read
    if (!isMatchLive()) return;                          // cache read
    const now = mod.GetMatchTimeElapsed();              // 1 engine call
    // Internal cadence check: throttle by CONQUEST_CAPTURE_SOUND_FLUSH_SECONDS
    if (... < CONQUEST_CAPTURE_SOUND_FLUSH_SECONDS) return;
    State.conquest.sound.lastFlushAtSeconds = now;

```

**Steady-state idle cost: ~3 cache reads + 1 engine call + return. Negligible.**

When active (queue has events):

- For each event: `getCaptureSoundRecipientsForEvent` (iterates players)

**Risks:**

- R13 (SMALL): `lastEventAtByThrottleKey` is a Record that grows with `eventKey:pid:objId` keys. Per the prior long-match audit it's bounded at ~192 entries, but should verify for capture-sound (terminal events different from VO?).

### D.2.a `scoreboardSyncTick` (1 Hz, on second-boundary)

Source: [`kpi/scoreboard-tab.ts:104`](../src/kpi/scoreboard-tab.ts#L104).

```ts
function scoreboardSyncTick(): void {
    if (!scoreboardConfigured) return;
    const now = mod.GetMatchTimeElapsed();
    if (now - scoreboardLastSyncAtSeconds < SCOREBOARD_SYNC_INTERVAL_SECONDS) return;
    scoreboardLastSyncAtSeconds = now;
    updateScoreboardForAllPlayers();
    updateScoreboardTeamScores();
}
```

`SCOREBOARD_SYNC_INTERVAL_SECONDS = 1.0`. Inner work:

- `updateScoreboardForAllPlayers()` iterates `forEachValidPlayer`, calling `updateScoreboardForPlayer` per pid:
  - `safeGetPlayerId(player)` (1 engine call)
  - **Only proceeds if `kpi.dirty` is true** (gated)
  - When dirty: `mod.GetPlayerDeaths(player)` (1 engine call) + `mod.SetScoreboardPlayerValues(player, ...)` (1 engine call)
- `updateScoreboardTeamScores()`: 2 x `mod.SetGameModeScore` (2 engine calls)

**Cost when all 64 players are dirty:**

| Call class | Engine calls |
|---|---:|
| `forEachValidPlayer` iteration | ~1-2 (cached) |
| `safeGetPlayerId` x 64 | 64 |
| `mod.GetPlayerDeaths` x 64 (when dirty) | 64 |
| `mod.SetScoreboardPlayerValues` x 64 (when dirty) | 64 |
| `mod.SetGameModeScore` x 2 | 2 |
| **Total (worst case)** | **~194 engine calls** |

**Cost when nothing is dirty: ~2 cache reads + 1 engine call + 2 SetGameModeScore = ~3 engine calls.**

**Risks:**
- R14 (MEDIUM): The dirty gate is per-pid, but `forEachValidPlayer` still iterates every player. At 64p with a single dirty pid (e.g., one kill happened), we still do 64 iterations + 64 `safeGetPlayerId` calls.
- R15 (LOW): `GetPlayerDeaths` is engine-authoritative; we re-read every dirty sync to align the script's KPI cache with the engine. Per-player engine cost is acceptable, but could be moved event-driven (off `OnPlayerDeath`) -- though no such event exists in this SDK.
- R16 (LOW): `mod.SetScoreboardPlayerValues` writes ALL 5 columns (score, kills, deaths, assists, captures) per call. If only one column changed, we still write all 5.

## Section H: Why this is plausibly the v1.491 spike shape

The v1.491 8-10 player MP playtest crashed with `Mod has been running for 1,716ms this frame which exceeds max evaluation time of 1,000ms` -- a single-frame breach.

Per Section E, the second-boundary subtick at 64p is **~1,500-1,750 engine calls** of recurring work alone. At 8-10 players, that's ~250-350 engine calls per second-boundary subtick. Not enough to breach 1,000ms on its own.

**BUT:** if any event-driven burst lands on the same subtick:

- Vehicle enter/exit cluster (S3 surface, now coalesced)
- Capture-point edge cluster (S1/S2 surface, not coalesced)
- Multiple kills firing OnPlayerEarnedKill (KPI dirty marks; next scoreboardSyncTick processes them)
- Late-joiner connection (T1 staggered builds + initial state seed)
- Boundary violation enter (T2 batch + new enforcement loop spawn)

...the second-boundary subtick could plausibly stack to >1,000ms. The pattern fits "happens after several minutes of active play" because event bursts become more likely as the match heats up.

**No single mitigation prevents the worst-case overlap.** The mitigations we've shipped (S3 200ms coalesce, hudDirty gate, scoreboardSyncTick dirty gate) reduce average cost but don't bound peak.

### K.8 -- Measurement methodology given `FEATURE_PERF_DIAG` is broken

Per project memory `project_perf_diag_broken`: the per-tick section profiler in [`hud/perf-diag.ts`](../src/hud/perf-diag.ts) is non-functional even when the flag is true. Per AGENTS.md: `console.log` is unreliable, world log is not suitable for diagnostic-volume output, and Portal sandbox is non-debuggable from outside.

Available measurement vectors, ranked by signal quality:

1. **Subsystem A/B bisection (HIGHEST signal):** ship the codebase with diagnostic toggle buttons that disable suspect subsystems server-wide, then run the same 8-10p MP playtest with each toggle combination. If disabling subsystem X eliminates the spike, X was the dominant contributor. This is exactly the strategy laid out in `~/.claude/plans/greedy-wobbling-toucan.md` (Toggle Combat HUD / Toggle Vehicle Overlay / Toggle Spectator). NOT endorsed by this doc as a fix, but IS the only available high-signal measurement vector given the AGENTS.md constraints.
2. **Pre-bump vs post-bump dist comparison (MEDIUM signal):** if a regression appears within one version bump, the diff is small enough to bisect on Changelog.ts entries. Per project memory `feedback_git_first_before_narrative`, this MUST be done git-first, not via uncommitted iteration narrative.
3. **Heap-stable proxy (LOW signal but free):** if heap-stable post-Wave-6 (memory notes) but CPU spikes still appear, the spike is per-frame CPU (a fan-out problem), not heap (a leak). The v1.491 1,716ms message body confirms this is a per-frame CPU breach.
4. **Per-frame instrumentation via `mod.GetMatchTimeElapsed` ratchets (LOW signal):** insert manual time-delta checks at top and bottom of suspect functions; emit world-log message ONLY if delta > N ms. Crude but functional. **Caveat:** the timestamp resolution is engine-dependent; sub-ms accuracy is not guaranteed.

**What we CANNOT do:**
- We cannot trust `FEATURE_PERF_DIAG`'s per-section profiler.
- We cannot run an external profiler attached to the Portal sandbox.
- We cannot run `Process.memory()`-style introspection (no API).
- We cannot use `console.log` for high-volume telemetry.

The conclusion is uncomfortable but accurate: **the diagnostic toggle button strategy is the only practical empirical measurement vector for this class of spike**. Even if we found the cause via static analysis, we have no way to verify the fix worked except by shipping it and running the same playtest.

### K.10 -- Per-tick CPU connects to M11 heap churn via VM allocation rate

M11 (HEAP-CHURN) was tagged in `conquest_optimization_state.md` as a per-frame heap allocation pressure point. Per this doc's Section K.4 verification, R6 alone produces ~1,536 VM allocations/sec. Plus:

| Source | Per-second VM allocations at 64p |
|---|---:|
| R6 top-HUD slices (3 VMs/player x 64p x 8 Hz) | ~1,536 |
| R3 `previousEngagedByPid` object spread per subtick (1 spread x 8 Hz) | ~8 (large but few) |

This is consistent with v1.491's all-or-nothing breach pattern: most frames are fine, then one frame stacks (recurring base + event burst + GC pause) and blows the budget.

**R6 reduction = M11 reduction.** Gating top-HUD VM rebuild by per-pid dirty flags (status/help-ready VMs only; the clock VM stays time-variant) would cut ~1,024 of the 1,536 R6 allocations.

### M.1 -- Event-driven `mod.AllPlayers()` per event in sound/VO recipient resolution (NEW)

Sources read:
- [`index/capture-sound.ts:116-135`](../src/index/capture-sound.ts#L116) `getCaptureSoundRecipientsForEvent`.
- [`index/capture-sound.ts:147-202`](../src/index/capture-sound.ts#L147) `flushCaptureSoundQueue`.
- [`index/capture-vo.ts:187-212`](../src/index/capture-vo.ts#L187) `getCaptureVoRecipientsForEvent`.
- [`index/capture-vo.ts:165-185`](../src/index/capture-vo.ts#L165) `refreshRecentPresence`.
- [`index/capture-vo.ts:309+`](../src/index/capture-vo.ts#L309) `flushCaptureVoiceOverQueue`.

What the prior pass said about D.1.c + D.1.d: idle cost is negligible (~3 cache reads + 1 engine call + return). R12 noted "may iterate `mod.AllPlayers()` -- need to verify whether it uses tick-context cache or fresh fetch each time."

**Verified: it does NOT use TickContext.** The flush helpers do their own `mod.AllPlayers()` + `mod.CountOf()` + per-index `ValueInArray` PER EVENT. At capture-point burst (10 events queued from a firefight cluster within one 500ms flush window):

- VO: 1 `AllPlayers` for `refreshRecentPresence` + 10 events x `AllPlayers` per recipient resolution = **11 fresh `AllPlayers` calls** in one flush.
- Sound: similar shape -- 1 `AllPlayers` per queued event.

Each `AllPlayers` is followed by N x (`isValidPlayer` + `safeGetPlayerId` + `isPidDisconnected` + cache lookup + `shouldCountPlayerAsActiveOnPoint` which is 3 GetSoldierState calls + `safeGetTeamNumberFromPlayer`). At 64p that's ~7-10 engine calls per player per event.

**Worst-case at 64p for one VO flush with 10 queued events:** 11 x 64 = ~700 array iterations + per-event recipient loop. The per-recipient cost (~7 engine calls) compounds: 10 events x 64 players x 7 calls = ~4,480 engine calls in one flush.

The flush cadence is bounded by `CONQUEST_CAPTURE_SOUND_FLUSH_SECONDS` / `CONQUEST_CAPTURE_VO_FLUSH_SECONDS` (likely 0.5s each based on naming pattern). So this fires at most 2 Hz when there's queued content, but can hit ~4,480 engine calls in a single flush during a contested capture-point firefight.

**This is a Tier S contributor the existing S-table did not catch.** The S-table has S5 covering `refreshLiveCaptureStateSubtick` per 120ms subtick, but that's a different code path. The sound/VO recipient resolution is **event-driven, not tick-driven**, and the recipient set rebuild per event is the cost.

**New risk R34 (LARGE):** capture-sound + capture-VO recipient resolution iterates `mod.AllPlayers()` once per event in the flush loop, not once per flush. Burst event clusters (capture-point firefight) compound 11x per flush; at 64p this is ~4,480 engine calls in a single flush.

**Compounds with B2 (Wave 3 solution):** `shouldCountPlayerAsActiveOnPoint` is called per player per event. B2 reduces it from 3 GetSoldierState calls to 1, which directly cuts ~67% of the per-recipient cost here. So B2's reclaim estimate (~384 calls/sec at 64p) understates the actual win when burst flushes hit.
