**Status:** **v1.2 SHIPPED (2026-05-05, v1.470) — Option B path executed. 9 consts deleted + function signature simplified (3 ignored params dropped) + 8 call sites updated. Bundle −1,311 bytes. Awaiting SP smoke validation.** See Phase 1 audit findings table for the per-const breakdown. Tier C item from the reclaim ladder in [`conquest_optimization_analysis.md`](./conquest_optimization_analysis.md). Per-symbol grep audit of the 158 module-level `const` declarations in [`ui/conquest/hud-core/constants.ts`](../src/ui/conquest/hud-core/constants.ts) to find HUD-redesign rubble — constants retained from earlier compass-shadow-ring iterations, team-name-backplate experiments, and pre-Wave-6 layouts that no longer have any readers anywhere.

This is a **bundle-bytes optimization, not a heap optimization**. Per the regime-change discussion in the analysis doc, runtime heap is the binding constraint at 16+ players, not upload bytes. C3 is on the ladder anyway because (a) zero risk, (b) every approved delete is verified by per-symbol grep before it ships, (c) cleans up code that misleads future readers about what's still load-bearing.

## Context

**What:** Audit every `const` declaration in `ui/conquest/hud-core/constants.ts`. Identify the ones with zero external readers anywhere in `src/`. Present a candidate-delete list to the user. Apply only what the user approves.

**Why:** That file accumulated constants across multiple HUD iterations:
- Original compass shadow ring system (8-layer profiles, offset constants, alpha values) — reclaimed in **Wave 6 Ship 1c (v1.443)** when `twlConquestHudBuildShadowRingProfile` was rewritten to return `[]`. Many of the underlying offset/scale constants may still be in the file.
- Team-name backplates (v1.449, dropped v1.451) — added 4 dimension constants, then removed 2 of them, then renamed/tightened the engage-status one. Stragglers possible.
- Multiple ticket-bar / chevron / popout iterations — same pattern: introduced, then re-tuned or removed.

The hypothesis: 5–30 consts in the file may have zero readers and just sit as bundle weight + reader-confusion debt.

**Why not just inline (Tier B1)?** B1 is a different lever — it preserves the binding's semantic meaning by reading "this 24px value is the engage-status text size." C3 is **delete only the consts that have no readers at all**. Different categories: B1 is about *single-site* consts that could lose their name; C3 is about *zero-site* consts that can disappear entirely.

## Pre-flight findings (verified)

### Feature-flag stripping interaction (the safety question)

The two-stage strip (per [`conquest_optimization_state.md` Compile-Time Feature Flags](./conquest_optimization_state.md#compile-time-feature-flags)):
1. `prebuild.js` reads `// @feature FEATURE_*` markers above each `import` line in `index.ts` and comments out the import when the flag is `false`.
2. `postbuild.js` then dead-strips `if (FEATURE_*)` blocks.

**Source files remain on disk in `src/` either way.** They just don't reach `dist/bundle.ts`.

**Implication for the audit:** grepping `src/` (NOT `dist/`) catches references inside the currently-flag-stripped files:
- `admin-panel/build.ts`, `admin-panel/events.ts`, `admin-panel/visibility.ts` (FEATURE_ADMIN_PANEL = false)
- `ui/admin/action-counter.ts` (same)
- `hud/position-debug.ts` (FEATURE_POSITION_DEBUG = false)
- `hud/perf-diag.ts`, `hud/ui-cache-perf.ts` (FEATURE_PERF_DIAG = false)

**A const used only by stripped code shows as "still has readers" and gets KEPT.** This is the conservative behavior — preserves the option to flip a flag back on later without re-introducing missing references.

### Re-enable feasibility (separate question, not gating C3)

Current bundle: **866,368 / 1,048,576 (~17.4% headroom).** Re-enabling FEATURE_ADMIN_PANEL + FEATURE_POSITION_DEBUG adds ~46 KB source per the analysis-doc estimate, putting bundle at ~912 KB. Still comfortably under the 1 MB cap.

But re-enabling has costs beyond bundle bytes:
- **Admin Panel:** per-pid widget cost (panel + toggle button) → adds an entry to M-tier; render overhead; functionality currently covered by CLAIM ADMIN + GIVE UP ADMIN paths on the existing Ready Dialog.
- **Position Debug:** developer tool only, zero gameplay value, should never ship enabled in production.

**Recommendation: do NOT re-enable for the audit.** Source files are on disk; grep covers them; conservative behavior preserves the option. Re-enable as a feature decision is its own discussion (see Q1 below).

### Const inventory shape (preliminary)

`ui/conquest/hud-core/constants.ts` is ~415 lines, ~21 KB, ~158 const declarations per the file-map row. The file is structured by family:
- Top-level color constants (referenced widely)
- Ticket bar dimensions + offsets
- Objective slot dimensions + offsets
- Popout panel dimensions + offsets
- Engage panel dimensions + offsets
- Shadow ring offset/profile constants (suspected reclaim hotspot post-Wave-6)
- Backplate dimensions (post-v1.449/v1.451 churn — possible rubble)

Most consts are computed from each other (`SHADOW_OFFSET = max(1, BASE * 0.5)`). Dead-detection has to trace the dependency chain — a const used only by another const that itself has no consumers is also dead.

## Implementation outline

### Phase 1 — Audit (~20 min)

1. **Extract** the full list of `const` declarations from `ui/conquest/hud-core/constants.ts` (one entry per `const NAME = ...` line).
2. **For each const**, run `grep -rn "\\bNAME\\b" src/` (excluding the constants.ts file itself).
3. **Categorize** each into one of 4 buckets:

| Bucket | Action | Reason |
|---|---|---|
| **A. Used in always-on code** (any non-feature-flagged file) | **KEEP** | Live consumer; safe to leave |
| **B. Used only in feature-flagged code** (admin-panel/*, hud/position-debug.ts, hud/perf-diag.ts, hud/ui-cache-perf.ts, ready-dialog/join-prompt-*.ts) | **KEEP** + tag as "flag-flip preservation" | Removing would break the file if the flag is ever flipped back on |
| **C. Used only by other consts in constants.ts itself** | **TRACE** the dependency chain. If chain reaches a real consumer (Bucket A or B) → KEEP. If chain dead-ends inside the file → **DELETE candidate** | Self-referential dead clusters |
| **D. Truly dead** (zero readers anywhere in src/) | **DELETE candidate** | Safe; pure-delete reclaim |

4. **Build a candidate-delete table** annotated per row:
   - Const name
   - Bucket (C or D, only candidates)
   - Estimated bytes saved (declaration line + value)
   - Dependency-chain notes if Bucket C

### Phase 2 — Review (your decision, blocking)

I present the candidate-delete table. You sign off on which entries to actually delete. Anything in Bucket B (flag-flip preservation) is out of scope by default — if you want it deleted, that becomes a separate decision tied to "we're never re-enabling this feature."

Possible outcomes:
- All-approved → straight to Phase 3
- Subset-approved → Phase 3 with the approved subset
- All-rejected → no-op, audit findings filed in this plan-doc as historical record

### Phase 3 — Apply (~15 min)

For each approved deletion:
1. Delete the `const NAME = ...` line from `ui/conquest/hud-core/constants.ts`.
2. If the const's value referenced another const, verify the chain — the parent const should already be in the deletion set or shouldn't have been deleted (caught in Phase 1).
3. `npm run bumpVersion -- -c "C3 audit: dropped N dead consts from hud-core/constants.ts. Bundle delta: −X bytes."`
4. `cmd /c npx tsc --pretty false --noEmit` — if this errors, a reader was missed in the audit. Restore the offending const, log the false negative in this plan-doc.

### Phase 4 — Document (after ship)

- Update `conquest_optimization_state.md` Project Stats with the v1.NNN entry: bundle delta + count of consts deleted + categories.
- Update `conquest_optimization_analysis.md` reclaim ladder C3 row to "SHIPPED v1.NNN" with realized payload.
- Append the audit findings table to this plan-doc (Phase 1 output) as historical record — even rejected candidates stay logged so future audits don't re-litigate them.

## Risk assessment

| Risk | Likelihood | Mitigation |
|---|---|---|
| Audit grep misses a reader (e.g., dynamic property access) | **Very low** — `hud-core/constants.ts` consts are all referenced by literal name; no `[CONST_NAME]` indirection patterns exist in the codebase | Phase 3 typecheck (`tsc --noEmit`) fails on missing-symbol error → restore const, log false negative |
| Const used by a future-enabled feature (re-flip scenario) | **Low** — Bucket B (feature-flag-only consumers) is conservatively kept | Bucket B preserves consts even if you "would never re-enable" the feature. Explicit override required |
| Const value used as input to runtime computation we missed | **Very low** — `hud-core/constants.ts` consts feed into widget builders only; no `eval`, no `import.meta`, no string-keyed lookups | Same as row 1 — typecheck catches it |
| Bundle delta zero or negative | **Possible** — if all 158 consts are alive, audit yields no candidates | Audit findings are still valuable as historical record — confirms file is lean, not rubble. No code change ships. |

**Net risk: zero downside.** Worst case is "audit finds nothing" → no code change → time spent on the audit logged in this plan-doc.

## Open questions (Q1–Q3) — answer to lock to v1.1

### Q1 — Re-enable Admin Panel as a feature?

Independent of C3, the audit will find the admin-panel infrastructure (4 source files, ~28 KB) is still on disk and Bucket B will keep its constants. Question: **do we want to revive the admin panel as a runtime feature**, or is it dead infrastructure preserved for option-value only?

The admin panel would offer (per Changelog history): admin action counter HUD, runtime control buttons (clock adjust, match start/end, position debug toggle, etc.). Most of these are now covered by:
- CLAIM ADMIN + GIVE UP ADMIN flows on the Ready Dialog
- Mode config Apply/Reset on the Ready Dialog
- Match length adjustment via the admin section of the Ready Dialog

If the answer is *"nothing the panel does isn't already on the Ready Dialog"* → leave FEATURE_ADMIN_PANEL = false, keep its consts via Bucket B (zero cost, preserves option), revisit only if a use case emerges.

If the answer is *"there are admin actions the Ready Dialog can't host"* (e.g., mid-match emergency controls during LIVE phase) → flip FEATURE_ADMIN_PANEL = true, ship as a separate plan, NOT bundled with C3.

**Recommendation: A.** Keep flag off; preserve consts via Bucket B; no plan needed unless a use case surfaces.

### Q2 — Re-enable Position Debug as a feature?

Position debug is a developer-only diagnostic (player X/Y/Z + rot rendered as HUD text). Zero gameplay value; only useful when locating spawn anchors / building map configs.

**Recommendation: keep flag off permanently.** Constants stay via Bucket B (so dev can flip the flag locally for debugging). No revive.

### Q3 — Bucket C aggressiveness

If a const is referenced only by other consts in the same file, and that chain dead-ends inside the file (no external consumer reached) — should the entire dead chain be deleted, or just the leaf?

**Recommendation:** delete the entire chain. Phase 1 traces dependencies and reports clusters; Phase 2 review surfaces them as one delete-decision per cluster, not per-const. This avoids "deleted leaf, kept now-orphaned parent."
