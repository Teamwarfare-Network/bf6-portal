## Context

User MP-tested at 13-15 players (v1.442). The match completed cleanly without script termination — major progress vs the pre-Wave-3 #109 termination at 16+ players. But two frame-budget spikes remained noticeable to the user:

- **Player connection** — sync HUD widget allocations after the `await mod.Wait(0.1)` in `onPlayerJoinGameImpl`.

## Findings from Pre-Wave Investigation

### Connect spike — what builds at join

After `await mod.Wait(0.1)` in [`onPlayerJoinGameImpl`](../src/index/player-join-leave.ts#L118), three lazy-build triggers fire **synchronously back-to-back**:

- `triggerLazyBuild('topHudShell', pid)` — small.
- `triggerLazyBuild('vehicleDeployTimer', pid)` — medium (M1 cache).
- `triggerLazyBuild('combatHud', pid)` — **largest, ~372 widgets/pid built**.

Combat HUD breakdown (~372 widgets/pid):

| Section | Widgets | Of which shadows |
|---|---|---|
| Bleed chevron system (7 left + 7 right × (1 chevron + 8-layer shadow ring)) | 140 | 112 |
| Objective slots (7 slots × 21 widgets each) | 147 | 112 |
| Popout panel | 22 | 16 |
| Engage panel | 31 | 24 |
| Containers/frames/team-name | ~32 | 16 |
| **Total** | **~372** | **~280** |

~75% of the M3 cache is drop shadow widgets.

### Disconnect spike — what tears down on leave

[`onPlayerLeaveGameImpl`](../src/index/player-join-leave.ts#L130) runs entirely synchronously (no `await mod.Wait`):

- `twlConquestHudDestroyPlayer` — ~40 `deleteAllByName` calls × **128-pass `safeFind/DeleteUIWidget` loops** = ~5,120 ops (combat HUD; dominant cost).
- `cleanupHudForPid` — 13 root names × 128 passes = ~1,664 ops.
- Other cleanup (`destroyArmMenu`, `destroyBoundaryPromptUiForPid`, `destroyPlayerReadyPanelForPid`, etc.) — smaller.
- **Pass-cap insight**: `deleteAllByName` calls `safeFind(name)` up to 128 times per root, mostly hitting **misses on already-empty keys**. With pid-namespaced widget IDs (via `wn()`), duplicates only arise from interrupted prior cleanups. In the steady-state common case, the 2nd `safeFind` already returns null. The 128 ceiling is wildly over-defensive.
- **6 all-player broadcasts** iterate every surviving viewer at 14 viewers ≈ 84 per-viewer refresh calls stacked: `refreshAllVisiblePlayerReadyPanels`, `refreshBuiltReadyDialogCachesForAllPlayers`, `renderReadyDialogForAllVisibleViewers`, `updatePlayersReadyHudTextForAllPlayers`, `updateHelpTextVisibilityForAllPlayers`, `updateVehicleDeployTimerHudForAllPlayers`.

### Existing pacing infrastructure

- `LazyBuildPacer.enqueueBuildOp` — 10Hz drainer with mutex (`src/interaction/build-pacer.ts`). **Mutex semantics are wrong for cleanup** (cleanup must complete before the next build for the same pid).
- `Timers.setTimeout` — async-backed timeout (`src/foundation/bf6-utils/timers.ts`). Better fit for deferred refresh coalescing.

### BF6 pid recycle hazard (rules out naive cleanup pacing)

BF6 reuses pid integers on reconnect within the same match (confirmed by the `disconnectedByPid[joinPid]` reconnect path at `player-join-leave.ts:98`). If cleanup is deferred and a reconnect lands on the same pid before the drainer flushes, a fresh `triggerLazyBuild('combatHud', joinPid)` will collide with in-flight deletes — `safeFind` returns the still-being-deleted widget, the new build attaches to a doomed parent, and the next drain tick deletes the freshly-built widgets. **Pacer-based cleanup deferral is unsafe without per-pid generation tracking + force-flush on rejoin** — and the force-flush reintroduces the spike on the rejoin path.

## Proposed Ships (revised after Plan agent pushback)

### Ship 0 — `maxPasses` ceiling reduction (one-line fast win)

**Scope:** drop `maxPasses` default in widget-by-name delete loops:

- `cleanupHudForPid` ([player-join-leave.ts:39](../src/index/player-join-leave.ts#L39)): `maxPasses: number = 128` → `4`.
- `resetUiForPlayerOnJoin` ([player-join-leave.ts:19](../src/index/player-join-leave.ts#L19)): `maxPasses: number = 64` → `4`.
- Audit other call sites — `clock/timer-instance.ts:29` `deleteAllReusableTimerWidgetsByName` defaults to 64; the boundary prompt destroy already uses 32.

**Rationale:** widget names are pid-namespaced via `wn()`. The only way a name produces duplicates is if a prior cleanup was interrupted mid-loop (script reload, runtime exception). 4 passes is 4× tolerance for that case while still cutting 96-97% of `safeFind` ops on the dominant common path.

**Heap reclaim:** none. **Build/teardown speedup:** ~95% of `safeFind` calls eliminated on disconnect; ~95% of the join-time `resetUiForPlayerOnJoin` cost too. Estimated **~70% of the disconnect spike** comes from this path alone.

**Files touched:** [`src/index/player-join-leave.ts`](../src/index/player-join-leave.ts) (2 lines); audit `src/clock/timer-instance.ts` and any other `safeFind` retry loops for similar caps.

**Risk:** if a widget is genuinely orphaned with duplicates, 4 passes might not catch them all. Mitigation: bump to 8 if SP smoke or MP playtest surfaces orphan widgets. The risk is observably visible (stuck old widget on screen) and easy to revert.

**SP smoke:** cold launch + ready up + match live + victory + restart × 2 cycles. Confirm no orphan widgets visible. Disconnect a bot and confirm clean teardown.

### Ship 1c — Eliminate combat HUD compass shadow rings (locked, ~280 widgets/pid reclaim)

**Scope:** delete all 8-layer compass-direction shadow ring construction in the combat HUD. Every text-bearing combat HUD element loses its shadow ring entirely: chevrons (14), team names, objective labels (7 slots × multiple text fields), percent text, popout text, engage counts, engage status. Chevron icons themselves stay — they're functional bleed-differential UI, not shadows. Single-offset shadows on non-combat-HUD surfaces (boundary prompt, master clock, deploy timer, ammo menu — ~61 shadows/pid combined) stay intact.

**Reclaim:** **~280 widgets/pid** (~75% of M3 cache — biggest single heap reclaim ever shipped in Conquest). Combat HUD widget count drops from ~372 to ~92 widgets/pid. Both join build cost and disconnect destroy cost drop proportionally — the same widgets that build slow also tear down slow.

**Implementation:** the construction is currently centralized in a shared shadow-ring helper called from each text-bearing widget builder. The shipping change should:

- Delete or short-circuit the shared helper so it returns without producing widgets (single-source change is safer than per-call-site deletion across the build module).
- Remove unused shadow widget refs from `CombatHudWidgetCacheEntry` in [`src/state/hud-cache-types.ts`](../src/state/hud-cache-types.ts) (typecheck will surface every dead ref).
- Audit the destroy path in [`src/ui/conquest/hud-core/lifecycle.ts`](../src/ui/conquest/hud-core/lifecycle.ts) — ensure no `safeFind` / `mod.DeleteUIWidget` calls reference the removed shadow names (also typecheck-driven).
- Any color/sizing constants used only by the shadow ring become orphan; remove them.

**Files touched:** [`src/ui/conquest/hud-core/build.ts`](../src/ui/conquest/hud-core/build.ts) (delete shadow ring construction), [`src/ui/conquest/hud-core/lifecycle.ts`](../src/ui/conquest/hud-core/lifecycle.ts) (audit destroy path), [`src/state/hud-cache-types.ts`](../src/state/hud-cache-types.ts) (remove dead shadow widget refs from cache shape).

**Risk:** visual regression on bright maps (snow, sand) — text becomes dark-on-dark without the dark shadow halo. User accepts: "I can restore from git if I need. I want performance back." If MP playtest shows unacceptable legibility on a specific surface (e.g., engage status), partial restoration via single-offset shadow on that surface only is the rollback path (Wave 7 candidate). Full restoration is a single git revert.

**Heap reclaim impact on rankings:** post-1c, M3 (combat HUD) drops from ~372 to ~92 widgets/pid, which likely moves M3 below M2 (supply box at ~140) in the heap-impact ranking. The `conquest_optimization_analysis.md` Mn ranking refresh is a documentation deliverable for the post-Wave-6 doc pass.

**SP smoke:** cold launch + ready up + match live + bleed event triggered + popout activations + multiple objectives contested + engage state cycling + victory + restart × 2. Confirm: combat HUD reads correctly on a bright map (screenshot comparison vs v1.442 baseline). No orphan shadow widgets on screen. Bundle build clean. Typecheck clean.

### Ship 1d — Stagger 3 join triggers across 3 frames (locked)

**Scope:** replace the synchronous back-to-back lazy-build trigger sequence in [`onPlayerJoinGameImpl`](../src/index/player-join-leave.ts#L121) with a 3-frame stagger:

```ts
// Today (sync, all on one frame after the 100ms wait):
triggerLazyBuild('topHudShell', pid);
triggerLazyBuild('vehicleDeployTimer', pid);
triggerLazyBuild('combatHud', pid);

// Ship 1d (distributed across 3 frames):
triggerLazyBuild('topHudShell', pid);                                       // immediate — clock visible
Timers.setTimeout(() => triggerLazyBuild('vehicleDeployTimer', pid), 50);   // +50ms
Timers.setTimeout(() => triggerLazyBuild('combatHud', pid), 150);           // +150ms (post-1c, ~92 widgets)
```

**Why it works:**

- `topHudShell` stays immediate — player needs the clock and team scoreboard the moment they spawn into the world.
- `vehicleDeployTimer` deferred 50ms — deploy timer rows only become interactive once the player opens the deploy screen (first death/respawn, well after join).
- `combatHud` deferred 150ms — combat HUD isn't visible until first `OnPlayerDeployed`, also well after join.

Combined with Ship 1c's reduction of combat HUD widget count (~372 → ~92 widgets), this distributes a much smaller amount of work across 3 frames — the stagger is belt-and-suspenders, not the primary join-spike lever, but cheap to add.

**Files touched:** [`src/index/player-join-leave.ts`](../src/index/player-join-leave.ts) (~5 lines around the existing trigger block).

**Risk:** see R6 below — pid-validity race during the 50/150ms deferred window if the player disconnects between scheduling and firing. Mitigation: timer cancellation on disconnect via the existing `Timers.setTimeout` token return, OR rely on `triggerLazyBuild`'s existing pid-validity guard (verify during Pre-Ship review).

**SP smoke:** cold launch + bot connect + bot deploy + verify combat HUD appears + bot disconnect immediately after join (race test for R6) + verify no errors logged.

### Ship 3 — DEFERRED (pid recycle hazard rules out the original pacing approach)

The original "pace cleanup across pacer ticks" idea has a subtle but critical bug: **BF6 reuses pids on reconnect within the same match.** If a reconnect lands on the same pid before deferred cleanup flushes, the new build attaches to a doomed parent and the next drain tick deletes the freshly-built widgets.

Mitigation requires per-pid `cleanupGeneration` tracking + a force-flush gate at the top of `onPlayerJoinGameImpl` that synchronously drains pending cleanup for that pid — which reintroduces the spike on the rejoin path. **Net cost is a wash; complexity is real.**

**Decision: Ship 3 is shelved unless Ship 0 + Ship 1 + Ship 2 fail to clear the budget at 24+ players.** Revisit only with explicit MP evidence that residual disconnect cost exceeds frame budget.

## Risks (v0.2 final, post-discovery)

- **R1 — Visual regression on shadow elimination (Ship 1c).** Combat HUD text becomes dark-on-dark without shadow halo on bright maps (snow, sand). Mitigation: user accepts ("restore from git"); partial restoration via single-offset shadow on the most-affected surface (engage status) is the rollback path; full restoration is one git revert. Pre-MP-test SP smoke screenshot comparison vs v1.442 baseline on a bright map identifies whether any surface needs partial restoration before MP playtest.
- **R2 — DROPPED** (was lazy chevron miss-on-first-bleed; Ship 1b dropped per L3).
- **R3 — Stale UI window during Ship 2 coalesce (DEFERRED with Ship 2).** Documented in the Ship 2 spec. Not a v0.2-bundle risk.
- **R4 — `maxPasses=4` insufficient for genuine orphans (Ship 0).** If a prior cleanup was interrupted mid-loop and left ≥5 duplicate widgets, the new ceiling won't catch them all. Mitigation: orphans are visible (stuck widget on screen); if SP smoke or MP surfaces them, bump to 8.
- **R5 — Pid recycle race (Ship 3 only — DEFERRED).** Documented above. Reason Ship 3 is shelved.
- **R6 — Pid-validity race during Ship 1d's deferred join triggers.** If a player disconnects in the 50/150ms window between scheduling `Timers.setTimeout(() => triggerLazyBuild(...))` and the callback firing, the lazy build runs against an invalid pid. Mitigation paths (verify during Pre-Ship review, pick one):
  - **(a) Cancel pending timeouts on disconnect** — store the `Timers.setTimeout` token in per-pid state, cancel in `onPlayerLeaveGameImpl`. Cleanest, but adds 2 lines of state lifecycle.
  - **(b) Rely on `triggerLazyBuild`'s existing pid-validity guard** — if `triggerLazyBuild` already short-circuits on invalid pid, no extra code needed. Pre-Ship review checks `lazy-build-registry.ts` for this.
  - **(c) Wrap in `if (mod.IsValidPlayer(pid))` before dispatch** — defensive but works regardless of guard presence. ~3 lines.
  - Worst case if not mitigated: a console error / silent no-op, not a crash. Still prefer to mitigate.
- **R7 — Shadow ring construction not centralized (Ship 1c).** Pre-Ship review must confirm the shadow ring is built via a shared helper. If construction is inlined per-text-element across many call sites, the deletion footprint widens significantly. Mitigation: Pre-Ship review enumerates the shadow construction surface; if not centralized, decide whether to (a) refactor to a shared helper first then delete, or (b) walk all call sites in one pass. Either way, typecheck on the cache-shape change in `hud-cache-types.ts` will surface every dead reference.
