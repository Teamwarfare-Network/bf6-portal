## Context

The Player Ready Panel and full Ready Dialog both already render a SPECTATE / COACH button as a "planned slot" — built but `mod.SetUIButtonEnabled(false)` + greyed since v0.817 (Phase 5G, ~9 months ago). This plan wires that button to a working single-spectator-slot feature using a Godot-placed FixedCamera per map.

The user's stated requirements (this thread):

> Clicking the coach/spec button turns that player into a spectator. That player is marked as ready when doing so. I don't need any extra functionality besides a single person spectating.

> No in-world interactable for enabling. We use the panel/dialog button.

> A Godot placed camera is fine.

User-confirmed design choices (via AskUserQuestion this turn):

- **Exit path: one-way.** Spectator stays spectator until disconnect or match end. No mid-match exit button.
- **Team strategy: keep on Team1/Team2.** Filter in `getActivePlayers()` via `if (pid === spectatorPid) continue`. No `mod.SetTeam` call.
- **Announcement: dedicated `"{Player} is spectating"` world-log string.** Needs explicit human approval per AGENTS.md String Change Authorization Policy before the Ship 2 implementation lands.
- **Probe-first sequencing.** Ship 1 = minimal in-game probe to resolve the two blocking unknowns (I-4 camera-on-undeployed + I-12 engine spectator UI overlay). Ship 2 = full integration based on Ship 1 results.

- **`mod.Cameras.Fixed`** — present in [`reference_sdk_1.2.3/code/types/mod/index.d.ts:242-247`](../../reference_sdk_1.2.3/code/types/mod/index.d.ts#L242) (enum value 1). NOT documented in `reference_bf6_core` — doc gap, runtime acceptance unverified.

### Patterns to reuse (no new code where existing covers it)

- **Per-pid button sync:** mirror [`syncPlayerReadyPanelClaimAdminButtonForPid`](../src/ready-dialog/player-ready-panel.ts#L337) — refresh-time sync, vacancy-aware, live-state-aware.

- **Match-end / fresh-setup hooks:** [`endMatch`](../src/conquest-flow.ts#L84) and [`triggerFreshMatchSetup`](../src/conquest-flow.ts#L123) are existing reset chokepoints.

- **Map config field addition:** mirror [`groundCombatZoneTriggerId`](../src/config/maps/) pattern in `MapConfig`.

### Locked design rules (from conquest_design.md, must respect)

- **Per-PID UI scope is non-negotiable.** All spectator-related widget mutation flows through per-pid widget IDs. Documented in `feedback_per_pid_ui_rule.md` memory.
- **Single-slot CLAIM ADMIN pattern is the precedent.** Spectator slot mirrors it: nullable scalar, vacancy-aware UI, no auto-promotion.
- **Countdown is uncancellable by ready-state (CQ_Bug_115, v1.474).** Spectator marking ready during countdown does NOT re-trigger auto-start logic; the countdown owns the transition.
- **Ready-state auto-unready is locked to 2 triggers (CQ_Bug_58, v1.445).** Spectator claim sets `readyByPid[pid] = true` synchronously; no auto-unready interaction.
- **State authoritative; HUD is projection.** `State.players.spectatorPid` is the source of truth; no UI-to-state reverse writes.

## Ship 1: Probe

**Goal:** resolve I-4 + I-12 with the smallest viable wire-up, before committing to the full integration shape.

**Two unknowns being probed:**

1. **I-4** — does `mod.SetCameraTypeForPlayer(undeployed_player, Cameras.Fixed, fixedCamId)` actually swap the camera to the Godot-placed FixedCamera? Or does the engine deploy-screen UI override the camera attachment?
2. **I-12** — does the engine render its own spectator overlay UI on top of our Fixed camera attachment? `SetSpectatingFiltersForPlayer` exists in the SDK; if the engine has a built-in spectator UI that auto-activates, we need to know.

### Spec

- Add **one** Godot FixedCamera to **Operation Firestorm** (most-tested map, current default in many flows).
- Capture its objId in `MapConfig.spectatorCameraId?: number` for Firestorm only — leave other maps `undefined` for the probe.
- Add **one** module-level `let _spectatorCameraId: number | null = null` resolved from `ACTIVE_MAP_CONFIG.spectatorCameraId` at game-mode start.
- **Wire COACH button on the Player Ready Panel only** (not the full ready dialog yet) to a probe handler that:
  1. Checks `_spectatorCameraId !== null` (bail with world-log "Spectator camera not configured for this map" if absent).
  2. Calls `mod.UndeployPlayer(eventPlayer)`.
  3. Calls `mod.SetCameraTypeForPlayer(eventPlayer, mod.Cameras.Fixed, _spectatorCameraId)`.
  4. Hides the panel + restores cursor (`closePlayerReadyPanelForViewer`).
  5. Adds a temporary per-pid debug HUD overlay reading `"SPEC PROBE pid=<pid> cam=<id>"` so visual confirmation is independent of camera behavior. Use `mod.AddUIText` per AGENTS.md "Debugging / Diagnostic Output Policy" §4 (HUD widget overlay is the sanctioned diagnostic surface).
- Do NOT implement: ready-state set, slot tracking, button refresh broadcasts, scoreboard skip, lifecycle cleanup hooks, exit paths, match-end reset. Those are Ship 2.
- Keep the COACH button on `dialog-build-sections.ts` (admin's full ready dialog) **disabled** for Ship 1.
- COACH button on Player Ready Panel: **enabled iff** `_spectatorCameraId !== null` (Firestorm only) AND `!isMatchLive()`. Otherwise stays disabled+grey.

- `onSpectatorMatchEnd()` — clear slot + restore camera-type for the (still-connected) spectator. Called from `endMatch`.
- `onSpectatorFreshSetup()` — clear slot. Called from `triggerFreshMatchSetup`.
- `isSpectator(pid): boolean` — predicate.
- `getSpectatorPid(): number | null` — accessor.

New file: `src/spectator/coach-button-sync.ts`. Function:

| Vacant | Pre-live | Yes | Enabled, white |

| Owned by other | Any | Yes | Disabled, grey |
| Any | Any | No | Disabled, grey |

## What This Plan Does NOT Address (Documented Follow-Ups)

- **Multi-spectator support.** If desired later, the single-slot pattern would need to become a `Set<number>` or similar. Out of scope.
- **Spectator UI niceties.** Player-cycling overlay, kill-feed, mini-map etc. are all PCT-territory. Out of scope.
- **Godot FixedCamera authoring for all 9 maps.** Ship 1 covers Firestorm only. Ship 2 author task includes the remaining 8 maps' Godot spatials. If an authoring delay blocks Ship 2, the graceful-degradation path (no spectator on un-authored maps) lets Ship 2 land partial.
- **Engine spectator UI deep dive.** If I-12 reveals the engine UI is heavyweight or interferes, a follow-up plan would need to investigate `SetSpectatingFiltersForPlayer` and possibly the global `SetSpawnMode` interaction. Out of scope of this plan.
