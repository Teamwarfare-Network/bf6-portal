## Context

**The bug.** Opening the supply box (ammo resupply menu) triggers `mod.GetInventoryAmmo` and `mod.GetInventoryMagazineAmmo` calls against the player's `GadgetOne` and `GadgetTwo` slots. When a slot is empty (typical for non-Engineer classes on cold spawn) or holds an item the engine considers non-ammoable in that context, the engine emits `Error reported by GetInventoryAmmo while running JS Script — Failed to return ammo amount due to an invalid player or inventory item.` to the world-log overlay.

**Originally observed (v1.372B):** 2 errors per menu interaction, hypothesised Assault-specific.
**Re-observed (v1.408):** 4 errors per menu interaction, **confirmed class-agnostic via Medic repro**. Trigger path: opening the Supply Box and selecting medic gadgets and/or smoke artillery. Bug body in [`conquest_issues.md`](./conquest_issues.md) explicitly: *"the bug is class-agnostic, fired wherever the slot probe lands on an empty or non-launcher slot."*

**Why prior `try-catch` wrapping doesn't fix it:** the engine logs error to the world-log overlay during the native `mod.*` call execution, BEFORE the JS catch can absorb the throw. The catch prevents JS-side exception fallout but not the visual log noise. Same engine behaviour drove the v1.341 `RemoveEquipment` precheck pattern (added `isSlotEmpty` check before calling `RemoveEquipment` to skip the call entirely on empty slots, eliminating the log).

**Impact (revised — was incorrectly framed as "cosmetic only" in the original bug entry):**

- **Surface:** in the immediate term, the world-log overlay fills with `invalid player or inventory item` lines. Visually noisy. Can mask other supply-box menu issues if the log fills up.
- **Functional:** game continues, gadgets work, supply box still functions. No immediate gameplay regression *visible*.
- **Heap pressure (NEWLY ESCALATED — what makes this NOT cosmetic):** every engine error log entry allocates against the same JS heap budget that crashed the script at 16-player MP playtest in `#109` (`CQ_Bug_16Player_Playtest_JS_Memory_Limit`). Each menu interaction emits 4 error entries. At 13-15 players × multiple supply-box opens per player per match × 4 errors per open, accumulated allocation across a long match can plausibly run into hundreds of KB of pure log overhead — non-trivial against the heap ceiling Wave 6 was specifically built to relieve. Worse, the engine's error-reporting path itself may have backpressure under burst (e.g. 4 players opening menus in the same frame → 16 simultaneous error log writes). Failure mode would be the same `Mod has reached its js script memory usage limit` script termination from `#109`, with this bug as a contributing input rather than the headline cause.
- **Why this matters NOW:** Wave 6 (v1.443+v1.444) reclaimed ~280 widgets/pid in the combat HUD specifically to push the heap envelope further. Letting log spam quietly eat back some of that reclaim defeats the wave's purpose.
- **Could mask other supply-box menu issues** if the log fills up (still true — original framing).

**Conversation history.** This bug has been on the books since 2026-04-25. Two prior fix attempts wrapped more sites in `try-catch` (which addresses JS-side fallout but not engine log noise). No precheck-based fix has been attempted yet. The CQ_Bug_94 body's "Possible fix paths" section enumerates three options; this plan executes the audit work needed to commit to one.

## Audit: Why "skip the probe for non-Engineers" (Path A) DOES NOT WORK

The original CQ_Bug_94 body suggested class-gating as a possibility. The v1.446 audit kills it.

**Claim under audit:** "Non-Engineer classes don't use `GadgetOne`/`GadgetTwo` for any of their gadgets, so skipping `initLockerSlotStateFromProbe` for them is safe."

**Audit method:** grep for every reader of `State.players.lockerSlots[pid]` and trace whether non-Engineer code paths depend on it. 12 references found, all in `ammo-resupply-menu.ts`. The critical reader is at line 2115:

```ts
const slotsState = State.players.lockerSlots[pid];                              // [line 2115]
const launcherSlotKnown = slotWithLauncher(slotsState) !== undefined;
const hasLauncher = launcherSlotKnown;
const smokeCount = Math.max(0, Math.min(cfg.medicSmoke.maxCount, smokeState?.c ?? 0));
const smokeRemaining = ...;
const smokeReady = smokeRemaining <= 0;
const smokeAlreadyHas = tileOwned(eventPlayer, slotsState, cfg.medicSmoke.gadget, cfg.medicSmoke.slot); // [line 2121]
```

`tileOwned()` at [line 1122](../src/interaction/ammo-resupply-menu.ts#L1122):

```ts
function tileOwned(eventPlayer, slotsState, gadgetId, inventorySlot) {
    if (inventorySlot === GadgetOne || inventorySlot === GadgetTwo) {
        return ownedByLockerState(slotsState, gadgetId);  // <-- requires slotsState
    }
    try { return mod.HasEquipment(eventPlayer, gadgetId); } catch { return false; }
}
```

Then check the per-class config in `DEFAULT_GADGET_LOCKER_CONFIG` ([line 60-85](../src/interaction/ammo-resupply-menu.ts#L60)):

| Class | Gadget | Slot |
|---|---|---|
| Assault | Artillery | `Callins` |
| Assault | **SpawnBeacon** | **GadgetTwo** |
| Assault | **AssaultLadder** | **GadgetTwo** |
| Engineer | Launchers / Supply Crate / AV Mine / EOD Bot | GadgetOne and GadgetTwo |
| Medic | **GrenadeIntercept** | **GadgetTwo** |
| Medic | **MissileIntercept** | **GadgetTwo** |
| Medic | Smoke | `Callins` |
| Recon | **Drone** | **GadgetTwo** |
| Recon | **C4** | **GadgetTwo** |
| Recon | AV grenade | `Throwable` |

**Audit conclusion:** all four classes have at least one gadget that lands in `GadgetTwo`. `tileOwned()` for those gadgets routes through `ownedByLockerState(slotsState, …)`, which **requires** `slotsState` to be populated to do dup-dim correctly. **Skipping the probe for non-Engineers would break tile dup-dim** — a Medic with GrenadeIntercept already placed wouldn't see the tile dimmed, would click again, and could either silently no-op or trigger weird state on the second placement.

**Path A is killed.** The probe is load-bearing for ALL classes, not just Engineer.

## Three Fix Paths (re-evaluated)

### Path A — Class-gate the locker probe (KILLED by audit)

Was the simplest option. Now invalid — see audit above. Documented for completeness so future readers don't re-propose it.

### Path B — `HasEquipment`-based slot detection (RECOMMENDED — ~30–45 min)

Restructure `probeSlot()` to determine slot kind via `mod.HasEquipment()` over a candidate gadget set, instead of via `mod.GetInventoryAmmo` / `mod.GetInventoryMagazineAmmo`.

`mod.HasEquipment(player, gadget_id)` does NOT emit an engine error log when the player doesn't have the gadget — verified by existing usages at [line 935](../src/interaction/ammo-resupply-menu.ts#L935), [line 964](../src/interaction/ammo-resupply-menu.ts#L964), [line 1071](../src/interaction/ammo-resupply-menu.ts#L1071), [line 1087](../src/interaction/ammo-resupply-menu.ts#L1087), [line 1126](../src/interaction/ammo-resupply-menu.ts#L1126). Same wrap pattern (`try { … } catch {}`) absorbs any throw cleanly with no log noise observed in normal operation.

**Implementation sketch:**

```ts
// Build the candidate set lazily, ONCE per session.
function buildSlotCandidateGadgetIds(): number[] {
    const cfg = ACTIVE_GADGET_CONFIG;
    const ids: number[] = [];
    // Engineer
    for (const id of ENGINEER_GADGET_CANDIDATES) ids.push(id);
    // Assault GadgetTwo
    for (const a of cfg.assault) if (a.slot === mod.InventorySlots.GadgetTwo || a.slot === mod.InventorySlots.GadgetOne) ids.push(a.gadget);
    // Medic GadgetTwo
    for (const m of cfg.medicItems) if (m.slot === mod.InventorySlots.GadgetTwo || m.slot === mod.InventorySlots.GadgetOne) ids.push(m.gadget);
    // Recon GadgetTwo
    for (const r of cfg.recon) if (r.slot === mod.InventorySlots.GadgetTwo || r.slot === mod.InventorySlots.GadgetOne) ids.push(r.gadget);
    return ids;
}
const SLOT_CANDIDATE_IDS: number[] = buildSlotCandidateGadgetIds();

function probeSlot(player: mod.Player, slot: mod.InventorySlots): { kind: "unknown" | "empty" | "gadget"; gadget?: number; source: "probed" } {
    let active = false;
    try { active = mod.IsInventorySlotActive(player, slot); } catch {}
    // Iterate candidates via HasEquipment (no engine log on miss).
    for (let i = 0; i < SLOT_CANDIDATE_IDS.length; i++) {
        const gid = SLOT_CANDIDATE_IDS[i];
        let owned = false;
        try { owned = mod.HasEquipment(player, gid); } catch {}
        if (owned) return { kind: "gadget", gadget: gid, source: "probed" };
    }
    if (active) return { kind: "unknown", source: "probed" };
    return { kind: "empty", source: "probed" };
}
```

**Caveats / nuances:**

- **HasEquipment doesn't tell us WHICH slot the gadget is in.** If a player has, e.g., the SpawnBeacon (GadgetTwo per config), `HasEquipment(player, SpawnBeacon)` returns true regardless of which slot the beacon is in. So `probeSlot(player, GadgetOne)` might mark slot 1 as "gadget" with id=SpawnBeacon when actually slot 1 is empty and the beacon is in slot 2. **This breaks the per-slot kind tracking** that the existing probe achieves via the populated/empty test on each slot independently.

  Mitigation A: scope the iteration. For `slot === GadgetOne`, only iterate gadgets KNOWN to land in GadgetOne (Engineer launcher set + the engineer non-launcher set: supply crate, AV mine, EOD bot). For `slot === GadgetTwo`, iterate the full candidate set (every class has at least one GadgetTwo gadget).

  Mitigation B: keep the `IsInventorySlotActive` check as the per-slot disambiguator. If `HasEquipment(player, gid)` returns true AND `IsInventorySlotActive(player, slot)` returns true, mark THIS slot as the gadget's home. Otherwise mark this slot as "unknown" (so the existing flow's behavior on "unknown" applies).

- **The launcher case still needs the destructive probe** (probeLauncherSlot at line 921) for correct detection — Engineer can have multiple gadgets in slots 1 and 2 with the launcher in either. probeLauncherSlot is class-gated to Engineer and is invoked separately; it stays as-is. The Medic/Recon/Assault path runs only the `initLockerSlotStateFromProbe → probeSlot` chain.

- **Per-class candidate scoping is the right answer.** Build two candidate sets keyed by which slot each gadget lands in:
  - `GADGET_ONE_CANDIDATES` = Engineer GadgetOne (launchers + supply crate + AV mine + EOD bot)
  - `GADGET_TWO_CANDIDATES` = Engineer GadgetTwo + Assault GadgetTwo (Beacon, Ladder) + Medic GadgetTwo (Intercepts) + Recon GadgetTwo (Drone, C4)

  This avoids the cross-slot false-positive problem entirely.

**Files touched:** [`src/interaction/ammo-resupply-menu.ts`](../src/interaction/ammo-resupply-menu.ts) only.
- `probeSlot()` rewrite (~20 lines).
- New `GADGET_ONE_CANDIDATES` + `GADGET_TWO_CANDIDATES` arrays (~10 lines).
- The two `initLockerSlotStateFromProbe` callers at lines 1063-1064 update to pass slot-specific candidate set (or the new `probeSlot` reads the right one based on the slot arg).

**Risk:** if the candidate set misses a gadget that some player class CAN place in GadgetTwo, that gadget's tile won't get dup-dim correctly (the menu sees the slot as "empty" when it's not). User memory `project_engineer_supply_crate_enum.md` documents the prior bug class — `Class_Supply_Bag` was wrong, `Deployable_Vehicle_Supply_Crate` was right. **Same enum-mismatch hazard.** Mitigation: include all known supply-crate variants in the candidate sets (belt-and-braces); also enumerate all known intercept / beacon / ladder / drone / C4 variants if the engine has alternate enums.

**Heap reclaim:** none (CPU-only — eliminates 4 native-call error-logs per menu open). Bundle delta: +~200 bytes (new candidate arrays + restructured probeSlot).

## Recommended Approach (SUPERSEDED — see "Shipped Approach" below)

The original v1.0 plan recommended Path B. User redirected to a cleaner per-class scoped variant: keep Engineer's `probeSlot` untouched (it works best it can), add 3 dedicated per-class probes for Assault/Medic/Recon. Implementation diverged accordingly.

## Shipped Approach (v1.447 — per-class scoped probes)

**Engineer probe untouched.** `probeSlot()` keeps its ammo-based detection + destructive-probe-via-`probeLauncherSlot` semantics. The launcher-slot identification is genuinely hard without the destructive probe path (variable launcher ammo state, rocket-fungibility across slots, supply-crate-vs-empty disambiguation), so removing the engine error log noise on Engineer is out of scope for this fix.

**3 new per-class HasEquipment-based probes for the other classes:**
- `probeAssaultSlot(player, slot)` — iterates `ACTIVE_GADGET_CONFIG.assault` filtered by slot. Returns `{ kind, gadget?, source }`.
- `probeMedicSlot(player, slot)` — iterates `ACTIVE_GADGET_CONFIG.medicItems` filtered by slot. (Smoke is on `Callins`, correctly skipped.)
- `probeReconSlot(player, slot)` — iterates `ACTIVE_GADGET_CONFIG.recon` filtered by slot. (AV grenade is on `Throwable`, correctly skipped.)

Each probe uses `mod.IsInventorySlotActive(player, slot)` for the "unknown" branch (active slot, no detected gadget) and `mod.HasEquipment(player, gid)` for the gadget detection. Neither call emits the engine error log on miss — verified by existing usage patterns in this file (`probeLauncherSlot`, `tileOwned`, etc.).

**Small dispatcher** `probeSlotForClass(player, slot)` routes by class:
- Engineer → existing `probeSlot` (ammo-based, untouched).
- Assault / Medic (Support enum) / Recon → matching per-class probe.
- Unknown class → safe `{ kind: "empty" }` default.

**Wired into both consumers:**
- `initLockerSlotStateFromProbe` (line 1062) — first-open menu probe. Now calls `probeSlotForClass` for both gadget slots.
- `reprobeSiblingGadgetSlot` (line 1141) — placement-time sibling re-probe. Same dispatcher swap. Also added: if the per-class probe identifies a specific gadget (`fresh.gadget !== undefined`), attach it to the sibling entry (matches the init-time non-launcher attachment loop's behavior, so sibling re-probes are equally annotated).

**Net change (v1.447):** ~+90 lines in `interaction/ammo-resupply-menu.ts`; bundle delta +2,614 bytes (866,137 → 868,751); no changes to other files.

### v1.448 follow-up — placement path also fixed

**User pushback after SP-test of v1.447:** "It still triggers as a medic and as assault." Investigation found the menu-OPEN path was clean (per-class probes work) but the menu-PLACEMENT path was still emitting the engine log via `isSlotEmpty()` ([line 875-880](../src/interaction/ammo-resupply-menu.ts#L875)) which itself calls `GetInventoryAmmo` + `GetInventoryMagazineAmmo`. `isSlotEmpty` is invoked on every tile click from three non-Engineer helpers:
- `giveMedicSmoke` ([line 1356](../src/interaction/ammo-resupply-menu.ts#L1356)) — Medic clicks SMOKE → reads ammo on Callins
- `giveAssaultItem` ([line 1401](../src/interaction/ammo-resupply-menu.ts#L1401)) — Assault clicks Beacon/Ladder OR Medic clicks intercepts → reads ammo on target slot
- `giveReconItem` ([line 1450](../src/interaction/ammo-resupply-menu.ts#L1450)) — Recon clicks Drone/C4/AV → reads ammo on target slot

**User-directed simplification:** "we're letting users choose slot so thats on them. So all we need to do is gray out an option if the player already has that thing?" — confirmed engine behavior is that `AddEquipment(player, gadget, targetSlot)` cleanly clobbers an occupied slot.

**v1.448 fix:** dropped the `if (!isSlotEmpty(targetSlot)) { RemoveEquipment(targetSlot); }` two-line block from all three non-Engineer give helpers. Kept:
- HasEquipment-based dup prevention via `ownedByLockerState(slotsState, gadget)` (GadgetOne/Two — drives gray-out via `tileOwned`) and `mod.HasEquipment(player, gadget)` (Callins/Throwable).

Engineer's `giveLauncher` ([line 1268](../src/interaction/ammo-resupply-menu.ts#L1268)) — which also uses `isSlotEmpty` for its launcher-slot identification — LEFT UNTOUCHED per user direction. The launcher swap-in-place pattern depends on knowing the target slot is empty before placing.

**Net change (v1.448):** −6 lines in `interaction/ammo-resupply-menu.ts` (3 isSlotEmpty calls + 3 RemoveEquipment guards removed; 6 comment lines added); bundle delta −362 bytes (868,751 → 868,389).

**Combined v1.447 + v1.448 result:** non-Engineer classes (Medic, Assault, Recon) emit ZERO `GetInventoryAmmo` / `GetInventoryMagazineAmmo` engine error log entries on either menu-open OR placement. ## Edge Cases Considered

1. **Player switches class mid-match (Engineer → Medic).** `lockerSlots[pid]` carries stale Engineer slot info. Currently this is NOT explicitly cleared on class change (need to confirm — if there's no class-change handler that clears it, the stale state persists). If stale, the next supply-box open re-runs `initLockerSlotStateFromProbe` (line 2506) and overwrites with fresh data. Path B preserves this re-probe behavior. **No regression.** If audit reveals class-change does NOT trigger a re-probe, that's a separate bug worth its own entry.

2. **Same-frame menu open + close cycle.** `setArmOpen(pid, false)` clears focused-tile state but NOT `lockerSlots[pid]` (the cache is intentionally retained across closes since the player's slot state hasn't changed). Path B preserves this. **No regression.**

3. **Player joins mid-match.** Their first supply-box open populates `lockerSlots[pid]` for the first time. Path B works the same. **No regression.**

4. **Engineer with launcher in BOTH slots (rare, possible via dup pickup before swap path matures).** `probeLauncherSlot` would identify both via the destructive probe; HasEquipment-based `probeSlot` for Path B would mark both slots as "gadget" with the launcher id. The distinction "which slot is THE launcher" then falls to `probeLauncherSlot`'s authoritative path which is unchanged by this plan. **No regression.**

5. **Slot active but unowned gadget (engine state bug).** Possible if HasEquipment misses something. The `IsInventorySlotActive` fallback marks it as `kind: "unknown"` — same as today. Existing menu code handles "unknown" gracefully. **No regression.**

6. **Empty-set candidate at session start.** `ACTIVE_GADGET_CONFIG` is mutable via map override (`applyMapGadgetLockerConfig`). If the candidate sets are built lazily once per session at module top, and ACTIVE_GADGET_CONFIG changes mid-session, the candidate sets would be stale. **Mitigation:** rebuild candidate sets inside `probeSlot()` on every call (small cost, ~10-15 array iterations) OR rebuild them inside `applyMapGadgetLockerConfig` whenever ACTIVE_GADGET_CONFIG mutates. Recommended: rebuild on every probe call (maybe ~2x per menu open) — simpler, and the cost is trivial.
