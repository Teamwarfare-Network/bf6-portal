### RQ1 — `mod.GetPlayerName` does not exist in the SDK. How do we resolve host/reclaim?

**The problem:**
- D1 is built on `mod.GetPlayerName(player) → string`. **That function does not exist in `bf6-portal/dev/reference_sdk_1.2.3/code/types/mod/index.d.ts`.**
- I searched for any Player → string/identity API: no `GetPlayerName`, no `GetUserId`, no `GetAccountId`, no `GetGuid`, no `GetPersonaId`. Nothing returns a player's identity as a JS string.
- The only Player-to-identity API is `mod.Message(player)` — produces an opaque Message **token** that the engine renders to the player's name. The script can pass the token to `safeSetUITextLabel` (so "Game Host: Joe" still renders correctly in UI) but **cannot read or string-compare** the underlying name.
- Player handles vanish on disconnect, so even hypothetical equality APIs wouldn't survive reconnect.
- **Result:** the `[Reclaim]` button (which requires recognizing a returning host across pid changes) **cannot be implemented as specified**. There is no SDK mechanism to identify "the same player" across a disconnect.

**Three workable alternatives (pick one):**

- **A. Drop reclaim; host = first-pid only; auto-promote on disconnect.**
  - Original host pid is recorded at first-ever connect (`State.host.firstPid: number | undefined`).
  - When host pid disconnects, host slot transfers to next-in-list (host and admin become indistinguishable).
  - `[Reclaim]` button is removed from the panel design entirely.
  - `Game Host: {name}` line stays — renders the *current* top-of-list player using `mod.Message(player)`. Effectively `Game Host == Game Admin` always after the first transfer.
  - **Smallest deviation from your spec.** Reclaim is gone but everything else is preserved.
- **B. Drop "host" as a separate concept; only "admin" exists.**
  - Panel layout becomes simpler: `Game Admin: {name}` is the only role line. `Game Host:` line is removed.
  - Top of join-list is admin. Auto-transfer on disconnect.
  - No `[Reclaim]` button at all.
  - **Cleanest mental model.** Loses the "Game Host" display entirely; loses the visual distinction between original host and current admin.
- **C. Self-claim "Host" via interact gesture or panel button.**
  - Add a "Claim Host" interaction (e.g., a button on the panel, or a quintuple-tap gesture). First player to claim wins; further claims are no-ops while a host exists.
  - When host disconnects, host slot is unclaimed; first player to claim again gets it.
  - Reclaim semantics preserved in spirit (a player can reassert host) but loses the "originally the host" identity.
  - **UX-heaviest.** Needs new strings + new interaction. Adds complexity to Ship 6.

**My recommendation:** **A.** It's the smallest deviation from v1.0 and the user-visible regression vs your spec is small. The "Game Host:" line still works as long as the host stays connected; once they disconnect, it just shows the new top-of-list player. Reclaim is gone but the whole point of reclaim was unsupported by the SDK anyway.

**Your answer (A / B / C):** We're not dropping host as a concept, and the host can never change. I've said this multiple times. We'll rework the reclaim function later. Lets just turn it into a "Claim" button instead of a reclaim button - that anyone can press and take admin for now.

### RQ4 — How does the new panel's button-event router integrate?

`tryHandleReadyDialogButtonEvent` in `interaction/ui-events-ready.ts:102` is the existing button-click router. It matches `widgetName === widgetBaseId + playerId` against the ready-dialog button widget IDs. The new panel's buttons need DISTINCT widget IDs (e.g., `UI_PLAYER_READY_PANEL_BUTTON_READY_ID + pid`) so the existing router doesn't intercept them.

Two implementation patterns:

- **A. New sibling router function.** Add `tryHandlePlayerReadyPanelButtonEvent(eventPlayer, playerId, widgetName, eventUIButtonEvent)` in a new file `src/ready-dialog/player-ready-panel-events.ts`. Hook it into the global UI-button event chain (probably in `interaction/ui-events.ts` or wherever `tryHandleReadyDialogButtonEvent` is invoked from). Two parallel routers, each handling its own widget IDs. Cleaner separation; easier to evolve independently.
- **B. New branches in the existing router.** Add the new panel's widget-ID matchers as additional branches inside `tryHandleReadyDialogButtonEvent`. Single router; new branches sit alongside the existing ones. Less file churn but conflates two surfaces' click logic in one function.

I recommend **A** — matches the L10 "new module from scratch" decision and keeps the surfaces independent. But B is shorter; flag if you prefer.

**Your answer (A / B):** A

### RQ5 — State location: `State.round` vs new `Admin.*` namespace

v1.0 plan says `State.round.adminJoinList: number[]` and `State.round.hostUsername: string | undefined`. Two concerns:

- **Round-scoped vs server-scoped:** `State.round` may reset between rounds (need to verify). If it does, the admin list and host slot would reset every round — wrong. Wave 3's Ship 3.5 (`SupplyBoxWarmScheduler`) and Ship 6 (`BoundaryPromptLivePrebuildScheduler`) used module-level state inside their own namespace to keep state across resets.
- **Naming hygiene:** even if `State.round` is server-scoped, putting admin/host data under `round` is misleading; admin model is server-lifetime, not round-lifetime.

Two options:

- **A. New `Admin` namespace** (in `src/admin/identity.ts`). Module-level state (`_adminJoinList: number[]`, `_hostFirstPid: number | undefined` per RQ1=A). Public accessors via the namespace. Same pattern as Wave 3's schedulers.
- **B. Keep in `State.round` but verify it's server-lifetime.** I'd verify via a fresh-setup smoke before Ship 1; if it resets per-round, swap to A anyway.

I recommend **A** — matches Wave 3 architectural precedent, avoids the round-vs-server lifetime question entirely, and isolates admin state from State's other top-level buckets.

**Your answer (A / B):** A

Two distinct roles (v1.2 model):
- **Host** — first-ever connected player's pid. Recorded once, never reassigned (per L8/L18). Cosmetic only — no privileges, no special button.
- **Admin** — single-occupancy slot. **First-ever joiner is auto-admin** (one-time, server-lifetime exception, gated on `_hostFirstPid === undefined`). Subsequent vacancies — whether from GIVE UP ADMIN or admin disconnect — stay vacant until someone explicitly presses CLAIM ADMIN. No auto-promotion of next-in-server. While vacant, any non-admin can press CLAIM ADMIN to take the slot. No claim wars (only-when-vacant gate).

## Risks + mitigations (v1.1)

- **R1 (RESOLVED v1.1):** username-collision risk REMOVED — there is no username comparison anymore. Host is identified by pid only.
- **R2 — Admin-leaves-mid-Apply state corruption.** If admin had unsaved config changes and leaves (or is replaced via Claim), the next admin sees the dialog with stale "Unsaved changes" indicator. Wave 4 doesn't address this; Apply already gates on admin-only post-Ship-3. Mitigation: dialog state for the new admin will reflect actual confirmed config (existing `State.round.modeConfig.confirmed` is authoritative). Pending changes are dropped.
- **R3 — Wave 3 MP verification still pending.** If #109 recurs at 24+ players, Wave 4's heap reclaim (~1500 refs net) is a meaningful contributor toward the fix but may not be sufficient alone. Wave 5+ M1/M3 thinning (per L6) is the contingency.
- **R4 — Existing dialog widgets retain a per-pid cache after the dialog stops being built.** Wave 3 Ship 7 already made the existing dialog first-interact-only. Post-Wave-4, only the admin pid triggers the build; other pids never call `triggerLazyBuild('readyDialog', pid)`, so per-pid caches simply never populate. No new cleanup needed.
- **R5 (NEW v1.1) — Cached `mod.Message` token may not survive host disconnect.** D1 caches `mod.Message(player)` at first-join in `Admin._hostNameMessage` so the "Game Host:" line keeps rendering after host disconnect. The Message object holds a Player handle internally; if the engine invalidates the Message when the underlying player handle dies, the line will render as empty / "Unknown" / a fallback. **Untested behavior** — no SDK doc states whether Message tokens are durable across player lifetime. Mitigation: Ship 4 SP smoke explicitly tests post-disconnect rendering. If the token doesn't survive, fall back to a static string (e.g., "(host disconnected)" — would need new approved string) in a follow-up patch within Wave 4.
- **R6 (NEW v1.1, RESOLVED v1.2) — `[Claim]` button claim-wars.** ~~Unrestricted claim could cause repeated bouncing.~~ Resolved by L17 explicit handoff: claim only succeeds against a vacant slot, so a current admin cannot be displaced by claim. Worst case is two non-admins clicking CLAIM ADMIN within the same frame against a vacant slot — first wins, second is a silent no-op (handler returns false from `claimAdmin`).
