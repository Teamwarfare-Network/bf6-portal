> "Now I want to go back to the teleport cleanup when doing the restart/reset. Lets isolate what we need to do differently. Previously when you tried to do the teleport cleanup method, the choppers were not teleporting. I think it would be fine to just teleport ALL empty vehicles in this mode, regardless of position, when they're being cleaned up."

Scope clarifiers:
- **Restart button only** (the "RESTART / FRESH SETUP" path in `triggerFreshRoundSetup`). Round-end cleanup is NOT touched — the earlier rule still holds: "the destroy mechanism in the air should not be a sink and destroy. its not on the pad, it should blow up where it is at. Same with round end cleanup." Restart is pre-round, not round-end.

## 2. Why v0.704 / v0.705 failed — the missing factor

The H_Bug_4 entry lists four hypotheses (slot.vehicleId not set, teleport silently rejected, abandonment system reverts, VFX re-anchors). Re-reading the code side-by-side with Conquest's working `sinkAndDestroyVehicle` reveals **one concrete actionable difference** that nobody pursued:

### The spawner abandonment flags

[helis vehicles.ts:162-163](../src/vehicles.ts#L162-L163):
```ts
mod.SetVehicleSpawnerApplyDamageToAbandonVehicle(spawner, true);
mod.SetVehicleSpawnerAbandonVehiclesOutOfCombatArea(spawner, true);
```

[conquest vanilla-spawner.ts spawner setup](../../conquest/src/vehicles/vanilla-spawner.ts) — neither flag is set. Conquest spawners do NOT auto-damage abandoned vehicles, nor mark out-of-combat-area vehicles as abandoned.

**The race I think we hit:**
1. We teleport vehicle to (X, -1000, Z).
2. The vehicle is now outside the combat area → engine flags it `abandoned`.
3. Engine's abandonment system starts applying damage **at the vehicle's last known spawn position** (cached for VFX anchoring) or yanks the vehicle back to the spawn pad before damage is applied.
4. Either way, the destruction VFX renders at the pad — exactly the symptom the user reported.

This was hypothesis #2 in the v0.708 punchlist ("If teleport is being reverted by abandonment: temporarily disable for the slot before teleport, then restore after destroy"). It was never tried because the v0.708 punchlist required a diagnostic build first, and the user has standing direction against world-log diagnostics.

### What the async-vs-sync hypothesis was NOT

I checked Conquest's `Timers.setTimeout` source ([conquest foundation/bf6-utils/timers.ts:28-37](../../conquest/src/foundation/bf6-utils/timers.ts#L28-L37)). It's literally `await Promise.resolve(); await mod.Wait(ms/1000); callback()`. **Functionally identical** to helis v0.705's `async + await mod.Wait(1.5)`. Async/await was not the difference. No point porting the Timers utility — it would change nothing.

### Why UnspawnObject is out

Conquest's [Changelog v1.272](../../conquest/src/Changelog.ts#L231):
> "replace vehicle UnspawnObject with DealDamage at startup cleanup and prior-vehicle destruction (**UnspawnObject on transitional vehicles emits engine-side errors that try/catch cannot suppress**)"

Conquest tried the silent-removal approach and reverted it. Re-introducing UnspawnObject would put back the exact class of "engine errors that try/catch can't suppress" we just spent today eliminating with H_Bug_1. **Off the table.**

## 3. Design

### 3a. New helper — sinkAndDestroyEmptyVehicle

Goes in [vehicles.ts](../src/vehicles.ts), replacing the dormant `sinkAndDestroyVehicleAtPad` + `sinkOnPadVehiclesForRestart` pair.

```ts
// Teleports an empty vehicle to (X, -1000, Z) then deals lethal damage 1.5s later so the
// explosion VFX renders underground. Caller is responsible for skipping occupied vehicles
// and for toggling spawner abandonment flags around the call window (see iterator below).
async function sinkAndDestroyEmptyVehicle(v: mod.Vehicle): Promise<void> {
    let x = 0;
    let z = 0;
    try {
        const pos = mod.GetObjectPosition(v);
        x = mod.XComponentOf(pos);
        z = mod.ZComponentOf(pos);
    } catch {}
    try { mod.Teleport(v, mod.CreateVector(x, -1000, z), 0); } catch {}
    await mod.Wait(1.5);
    try { mod.DealDamage(v, 9999); } catch {}
}
```

Differences from v0.705's `sinkAndDestroyVehicleAtPad`:
- No `padPos: mod.Vector` parameter — we trust `mod.GetObjectPosition` and fall through to (0, -1000, 0) on failure. This is acceptable for the Restart context because a (0, -1000, 0) sink still puts the vehicle far enough underground that the explosion is silent. The `slot.spawnPos` fallback was Conquest's defense against `GetObjectPosition` returning bad X/Z at countdown-reset (memory note `project_getobjectposition_unreliable_on_destroy`); the Restart-button context isn't that case (no countdown reset happens here), so the fallback adds complexity without proven payoff.

### 3b. Iterator — sinkAndDestroyAllEmptyVehiclesForRestart

```ts
// Iterates mod.AllVehicles() at Restart click, sinking + destroying every UNOCCUPIED vehicle.
// Wraps the work between disabling and re-enabling each spawner's abandonment flags so the
// engine doesn't race our sink by applying its own abandonment damage at the original pad.
function sinkAndDestroyAllEmptyVehiclesForRestart(): void {
    const slots = State.vehicles.slots;

    // Disable abandonment behavior on every slot's spawner so a y=-1000 vehicle isn't
    // instantly flagged "out of combat area" and yanked / damaged by the engine.
    for (let s = 0; s < slots.length; s++) {
        const sp = slots[s]?.spawner;
        if (!sp) continue;
        try { mod.SetVehicleSpawnerApplyDamageToAbandonVehicle(sp, false); } catch {}
        try { mod.SetVehicleSpawnerAbandonVehiclesOutOfCombatArea(sp, false); } catch {}
    }

    const all = mod.AllVehicles();
    const count = mod.CountOf(all);
    for (let i = 0; i < count; i++) {
        const v = mod.ValueInArray(all, i) as mod.Vehicle;
        if (!v) continue;
        let occupied = true; // fail-safe default: don't sink if check throws
        try { occupied = mod.IsVehicleOccupied(v); } catch {}
        if (occupied) continue;
        void sinkAndDestroyEmptyVehicle(v);
    }

    // Re-enable abandonment flags after the sink window (2.5s > the 1.5s helper wait).
    // Use a delayed callback so per-vehicle sinks finish before the engine resumes
    // abandonment-tracking.
    void restoreSpawnerAbandonmentFlagsAfterSink(slots);
}

async function restoreSpawnerAbandonmentFlagsAfterSink(slots: VehicleSlotState[]): Promise<void> {
    await mod.Wait(2.5);
    for (let s = 0; s < slots.length; s++) {
        const sp = slots[s]?.spawner;
        if (!sp) continue;
        try { mod.SetVehicleSpawnerApplyDamageToAbandonVehicle(sp, true); } catch {}
        try { mod.SetVehicleSpawnerAbandonVehiclesOutOfCombatArea(sp, true); } catch {}
    }
}
```

## 4. Test plan

1. **Single-player baseline.** Start fresh round, let vehicles spawn on pads, press Restart. Expected: no audible explosion, no visible pad explosion. Vehicles disappear, new ones spawn for next round.
2. **Drifted vehicle.** Spawn vehicle, manually drag it 30m away from the pad, press Restart. Expected: sinks + silently destroys (this is the difference from v0.705's 15m gate).
3. **Mid-air vehicle.** Take off, fly to (X, 200, Z), undeploy without dying, press Restart from outside the vehicle. Expected: vehicle sinks + silently destroys (no pad-position explosion).
4. **Occupied vehicle.** User sits in a chopper at the pad, a teammate presses Restart from outside. Expected: occupied vehicle is SKIPPED (not yanked from under the occupant). Other empty vehicles sink. The occupied vehicle is dealt with by the existing scheduleRoundEndCleanup DealDamage path on its normal timer.
5. **MP 2v2 round-restart spam.** 4 players in choppers, all undeploy, one presses Restart. Expected: no engine error log spam (this is the H_Bug_1-class concern — `mod.SetVehicleSpawnerApplyDamageToAbandonVehicle(undefined, ...)` would re-introduce the pattern we just killed). Spawner null-guards in the iterator address this.
6. **Round-end (regression check).** Play a round to natural end. Expected: vehicles still blow up where they are (NOT sunk). This path was never modified.

## 5. Risks & rollback

### Risks
- **Abandonment-flag toggle has side effects we didn't model.** If the flags also affect mid-round behavior (e.g., abandonment damage during live play), the 2.5s window could leak into the next round's setup. Mitigation: 2.5s is short, and `triggerFreshRoundSetup` already gates round-live state via `isRoundLive()` early-returns at the top of the function.
- **The flags don't actually fix it.** If the real culprit is engine VFX caching the pad position regardless of entity position (hypothesis #4 in H_Bug_4), this plan won't move the needle. Acceptance: we observe v0.721 has the same failure as v0.705, and we know it's not abandonment-related. We then either accept the symptom or escalate to SDK reference review for `mod.SetVehicleSpawnerForceRespawn` / `mod.RemoveVehicleFromSpawner` style escape hatches.
- **`mod.IsVehicleOccupied` may not exist at runtime** despite the type definition. Conquest doesn't use it (grep returned zero hits in conquest/src). If runtime throws, the `catch {}` keeps `occupied = true` and the vehicle is skipped — safer than yanking a player. Plan B if the API is bogus: replicate Conquest's pattern of checking `mod.GetSeatedPlayer` across all seats.

### Rollback
Same approach as v0.708: comment out the single call in `triggerFreshRoundSetup`. Helpers stay as dead code with a status block. The abandonment-flag-toggle inside the helper is self-contained — disabling the caller fully disables the whole feature.

## 6. What this plan does NOT do

- **Does NOT touch round-end cleanup.** The user's earlier rule ("in-air vehicles should blow up where they are at round end") stands. Only the Restart button path changes.
- **Does NOT add diagnostic broadcasts.** User has standing direction against world-log probes ("no to world log, it's a terrible debug methodology"). The abandonment-flag hypothesis is concrete enough to ship without a diagnostic round.
- **Does NOT use UnspawnObject.** Conquest reverted this in v1.272 because of unsupressable engine errors; we just shipped H_Bug_1 to kill the same error family — re-introducing it would be a regression.
- **Does NOT change spawner setup defaults.** The abandonment flags remain `true` at spawner-creation time (`configureVehicleSpawner` at [vehicles.ts:157](../src/vehicles.ts#L157)) because they're correct for live-round behavior. Only the Restart-cleanup window toggles them.
- **Does NOT touch the ready-dialog HP default change** (v0.720 → 0.721 also includes that, but it's a one-liner already applied as part of the same checkpoint).
