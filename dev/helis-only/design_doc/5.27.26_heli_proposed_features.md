# Track H — Helis-first features (not in Conquest)

## H-P0. Vehicle Health Slider in the Ready Dialog

### Scope

Add a tunable knob on the Ready Dialog that scales the spawning vehicles' max-health by a percentage. Default 100%. Increments of 1%. Range clamps at 5% min, 500% max. Setting is global to the match (not per-team in P0 scope) and snapshots on Confirm, consistent with the existing mode-config keys (`gameModeIndex`, `aircraftCeiling`, `vehicleIndexT1/T2`).

### Where it lands

- [src/types.ts](../src/types.ts) — new `ReadyDialogModeConfig` field (`vehicleHealthPct: number`), new constants (`READY_DIALOG_VEHICLE_HEALTH_PCT_DEFAULT/MIN/MAX/STEP`), string-key consts.
- [src/state.ts](../src/state.ts) — extend `modeConfig` + `confirmed` snapshots; per-pid widget refs (`vehicleHealthPctValueWidget`, dec/inc buttons).
- [src/ready-dialog.ts](../src/ready-dialog.ts) — new row in `createTeamSwitchUI`, new dec/inc + label sync helper (`updateReadyDialogVehicleHealthPctForPid`), new button event cases in `teamSwitchButtonEvent` ([src/team-switch.ts](../src/team-switch.ts) router).
- [src/vehicles.ts](../src/vehicles.ts) — apply multiplier on every successful spawn in `OnVehicleSpawned` / `bindSpawnedVehicleToSlot`. Live re-apply on confirm? See open question Q3.
- [src/hud.ts](../src/hud.ts) — settings-summary HUD line for vehicle health %.
- [src/strings.json](../src/strings.json) — new keys under `twl.readyDialog.vehicleHealthPct.*` and `twl.hud.settings.vehicleHealthFormat`.

### API references

- [reference_bf6_core/mod/functions/SetVehicleMaxHealthMultiplier.md](../../reference_bf6_core/mod/functions/SetVehicleMaxHealthMultiplier.md):

  > Multiplies the maximum health of target vehicle by the provided number greater than 0 and less than or equal to 4.

  **API hard ceiling is 4.0x (400%).** User request is 5.0x (500%). See Q1.

### Conquest references

None — Conquest has no equivalent. The closest analog is the existing Ready Dialog config plumbing (`aircraftCeiling` int knob), already cloned in Helis.

### Open design questions

- **Q1. 500% ceiling vs API 400% ceiling.** `SetVehicleMaxHealthMultiplier` documents `multiplier > 0 && <= 4`. Options:
  - (a) Cap the slider at 400% and ship at the API limit.
  - (b) Cap at 500% but clamp the multiplier passed to the engine at 4.0 (UI lies above 400%).
  - (c) Cap at 500% and stack effects (e.g., apply 4.0x then DealDamage-style heal loop on spawn). Adds runtime cost and complexity; not recommended.
  - **Recommendation: (a).** Match the engine contract; surface 5%-400% in the dialog. The "500%" framing came from a non-binding gut number; the engine has the final say.
- **Q2. Increment cadence.** 1% step over a 5-400 range = up to 395 single clicks worst case. Options:
  - (a) Single button pair `[-]` `[+]` at 1% step plus a separate `[-10%]` `[+10%]` row, mirroring the cadence pattern Conquest uses for round-length.
  - (b) Hold-to-repeat on the existing buttons. Engine UI button-event model unknown for hold semantics; needs validation.
  - **Recommendation: (a).** Add a coarse-step pair as a second row; keeps interaction predictable, matches existing dialog vocabulary.
- **Q3. Apply timing.** Two options:
  - (a) Snapshot on Confirm (Ready-Dialog pattern); apply to vehicles spawned thereafter. Existing vehicles unchanged unless next respawn. Matches `aircraftCeiling` semantics.
  - (b) Apply live to every existing registered vehicle when the slider moves, even before Confirm. Higher engine call volume during pre-game tuning.
  - **Recommendation: (a).** Consistent with the rest of the mode-config snapshot model. Players see the new value take effect at the next round start, which is also when the new vehicles spawn.
- **Q4. Per-team scoping.** User said "any vehicles which spawn" — implies single global value. Confirm: not split per team? If competitive ladder wants asymmetric (e.g., T1 100% vs T2 150% for handicap), a `vehicleHealthPctT1/T2` split is straightforward but doubles the UI surface. **Recommendation: single global value in P0; revisit per-team if asked.**
- **Q5. Settings-summary HUD line.** Current settings summary in [src/hud.ts](../src/hud.ts) (`updateSettingsSummaryHudForPid`) shows mode + ceiling + vehicles. Should health % join? Suggested only when value != 100% to avoid clutter when default.
- **Q6. Reset behavior.** Helis's Ready Dialog has a `Reset` button. Confirm health % is part of the reset scope (back to 100%).
- **Q7. String approval.** New keys required (proposed):
  - `twl.readyDialog.vehicleHealthPct.label` ("Vehicle Health")
  - `twl.readyDialog.vehicleHealthPct.format` ("{0}%")
  - `twl.readyDialog.vehicleHealthChanged` (announce on change)
  - `twl.hud.settings.vehicleHealthFormat` ("HP {0}%")

### Sequencing

- Should land **after** [P0-1 (Ready Dialog warm-build deletion)](./heli_improvement_plan.md) so the new row is built lazily on first dialog open, not at warm-prime time.
- Should land **with or after** [P0-8 (per-pid map consolidation)](./heli_improvement_plan.md): the new mode-config field naturally extends `modeConfig`, no per-pid map needed.

## H-P1. Layered Aircraft Ceiling — Warning Dialog Layer

### Scope

Today's ceiling is single-layer: at `aircraftCeiling`, either `mod.SetMaxAltitude` (hard mode) or a scripted nudge loop (soft mode) pushes the aircraft back down. New behavior is a **three-layer** model:

1. **Cruising layer** — below soft ceiling. Normal.
2. **Warning layer** — between soft ceiling and hard ceiling. A blocking full-screen dialog appears for vehicle occupants: "Altitude warning — descend immediately." Cannot be dismissed by player input; auto-clears when the aircraft descends back below the soft ceiling.
3. **Hard layer** — above hard ceiling. Existing enforcement (engine `SetMaxAltitude` or scripted nudge) kicks in. Hard ceiling is also **shifted higher** than today's value to give the warning layer room to live.

### Where it lands

- [src/types.ts](../src/types.ts) — new constants `READY_DIALOG_AIRCRAFT_SOFT_CEILING_OFFSET` (delta below the configured ceiling, e.g., -150m by default), `AIRCRAFT_SOFT_CEILING_DIALOG_FADE_SECONDS`. Possibly a new mode-config field `aircraftSoftCeilingOffset` if it should be user-tunable; default-only is simpler.
- [src/state.ts](../src/state.ts) — per-pid widget refs for the warning dialog (`altitudeWarningRoot`, `altitudeWarningText`); per-pid state flag `altitudeWarningVisibleByPid` (or a field on the consolidated `PerPlayerState` if P0-8 has shipped).
- [src/ready-dialog.ts](../src/ready-dialog.ts) `runAircraftCeilingSoftEnforcementLoop` — extended to compute three zones per aircraft, drive dialog visibility for each occupant.
- [src/hud.ts](../src/hud.ts) — `ensureHudForPlayer` builds the (initially hidden) altitude-warning dialog widgets per pid.
- [src/strings.json](../src/strings.json) — new keys under `twl.hud.altitudeWarning.*`.

### API references

- [reference_bf6_core](../../reference_bf6_core/) — needed before plan:
  - Confirm `mod.SetMaxAltitude` semantics for "shift hard ceiling up" plan.
  - Identify the occupants-of-vehicle query (`GetOccupantsOfVehicle` or iterate seats with `GetPlayerVehicleSeat`).
  - Confirm `mod.SetUIWidgetVisible` + `mod.AddUIBackground` rendering on top of in-game UI layer (the dialog needs to draw above HUD elements but should not block aircraft input — see Q1).

### Conquest references

- None — Conquest has no aircraft ceiling system. This stays Helis-specific.
- Pattern analog: Conquest's per-pid full-screen overlay surfaces (e.g., spectator hide-room overlays) for how "block-the-screen" UI is composed per-pid.

### Open design questions

- **Q1. "Block the screen" — interaction model.** User said "needs to block the screen." Two readings:
  - (a) *Visual block only* — full-screen-tinted overlay + large text; vehicle controls still respond so the pilot can descend. **Recommendation: (a).** A control-disabling block would make descent impossible and immediately trigger the hard ceiling, which defeats the warning purpose.
  - (b) *Input block too* — `EnableInputRestriction` lock on weapons but not movement. Possible but adds complexity. Defer unless explicitly requested.
- **Q2. Per-occupant vs per-vehicle dialog.** Per memory [`feedback_per_pid_ui_rule`](../../../.. — not a real path; this is a memory ref) the UI must be per-pid. So: each occupant of the offending aircraft gets the dialog on their own widget. Driver, gunner, passengers all see it.
- **Q3. Soft ceiling offset value.** What's the gap between soft and hard?
  - Current Helis `aircraftCeiling` defaults to 550m. If we shift the hard ceiling up by, e.g., +100m to 650m and the soft ceiling is the original 550m, the player has 100m of warning-layer airspace before physics kick in.
  - **Recommendation: hard = configured + 100m; soft = configured.** Keeps the existing Ready Dialog "ceiling" knob as the *warning* threshold (where dialog appears), with the hard physics ceiling sitting 100m above it. Document the gap.
- **Q4. Dialog dwell + hysteresis.** When the player crosses back below the soft ceiling, the dialog should clear. Should there be hysteresis (e.g., must drop 20m below soft before clearing) to prevent flicker at the boundary? **Recommendation: yes, 20m hysteresis.**
- **Q5. Vanilla aircraft ceiling mode.** When `useCustomCeiling = false` (vanilla maps), is the warning dialog disabled entirely, or do we still show a warning at the engine default? **Recommendation: disabled.** Custom-ceiling-only feature so we don't surprise players on vanilla maps.
- **Q6. Interaction with current `AIRCRAFT_CEILING_ENFORCEMENT_MODE = "hard"` constant.** With the new model, "hard" and "soft" are no longer mutually exclusive — both fire, just at different altitudes. Replace the constant with a three-mode model `"layered" | "hard-only" | "soft-only"` (default `"layered"`)? **Recommendation: yes, rename, default to `"layered"`.**
- **Q7. String approval.** New keys required (proposed):
  - `twl.hud.altitudeWarning.title` ("ALTITUDE WARNING")
  - `twl.hud.altitudeWarning.body` ("Descend immediately or aircraft control will be lost")
  - Possibly `twl.hud.altitudeWarning.distanceFormat` ("{0}m above safe altitude") if dynamic distance is shown.

### Sequencing

- Land **after** H-P0 — no dependency, but they share the Ready Dialog config-snapshot mechanism; doing H-P0 first proves out the pattern with a smaller surface.
- Coordinate with [improvement plan P2-4 (aircraft subset cache)](./heli_improvement_plan.md): if the warning-loop iterates `mod.AllVehicles()` per tick, doing P2-4 first reduces the engine-call multiplier.

## H-P3. Viewer-Oriented HUD — Own Team Always on Left, Always Blue

### Scope

Today's HUD binds `T1 = left side = blue` and `T2 = right side = orange/red` as global truth. Every viewer sees the same layout regardless of which team they're on. The proposed change: each viewer sees **their own team** on the left in blue and the **opposing team** on the right in orange/red, with all team-anchored HUD widgets (scores, kill counters, crowns, win counts, victory/round-end dialog rosters, ready-dialog rosters, overtime bars and crowns) flipping per-viewer.

User flagged this as suspected-large up front; that suspicion is correct. **This is an L-effort, high-regression-risk change** — comparable in size to the P2-7 `ensureHudForPlayer` split or the P2-8 `ready-dialog.ts` split tracked in [heli_improvement_plan.md](./heli_improvement_plan.md).

### Scale evidence (grep counts on `src/`, 2026-05-27)

| Surface | Count | Comment |
|---|---:|---|
| `T1\|T2\|Team1\|Team2\|TEAM1\|TEAM2` total references | 607 across 15 files | Includes state names that don't need editing; the render-site subset is the actual work. |
| `teamId === 1 \|\| === 2` and `TeamID`-typed parameters | ~164 across 11 files | The actual T1/T2 branch points where side/color is selected. |
| `setUITextColor` / `TextColor` / `UIWidgetBgColor` writes | 65 across 4 files | Every color write that depends on team. |
| `*T1` / `*T2` widget ref pairs (`scoreT1`, `winsT1`, `crownT1`, `barT1`, ...) | 46 across 6 files | Per-pid widget refs already pair on T1/T2. |
| Files containing T1/T2 logic | 10 of 19 `.ts` files | hud.ts (71), ready-dialog.ts (197), overtime.ts (50), state.ts (63), index.ts (46), round-flow.ts (30), clock.ts (7), team-switch.ts (20), vehicles.ts (21), strings.ts (49). |

### Three orthogonal axes that flip together

1. **Layout binding.** Every `safeSetUIWidgetVisible(refs.leftCrown, winner === Team1)` becomes `safeSetUIWidgetVisible(refs.leftCrown, viewerSideForTeam(viewer, winner) === 'left')`. Mechanical; ~100-150 sites.
2. **Color binding.** Every `SetUITextColor(widget, COLOR_TEAM1_BLUE)` becomes `SetUITextColor(widget, viewerColorForTeam(viewer, sourceTeam))`. ~65 sites.
3. **Messaging.** World-log broadcasts ("Team 1 captured X") are server-global by engine; we cannot per-pid them. Two choices:
   - (a) Keep team-anchored framing in world log (e.g., "USA captured X" / "RUS captured X") while HUD overlays say "Your team" / "Enemy". Surfaces disagree.
   - (b) Shift the affected broadcasts from world log to `mod.DisplayNotificationMessage` (per-pid) so wording can be viewer-relative. Loses the persistent log line.
   - (c) Mix: keep gameplay-critical broadcasts on world log with team-anchored wording, move soft messages to per-pid notifications.
   - **See Q4.**

### Where it lands

- [src/state.ts](../src/state.ts) — new helpers `viewerSideForTeam(viewer, sourceTeam): 'left'|'right'` and `viewerColorForTeam(viewer, sourceTeam): RGB`. Both query `safeGetTeamNumberFromPlayer(viewer)` once. ~30 LOC new.
- [src/hud.ts](../src/hud.ts) — every `For*` and `setTrending*` / `setVictory*` / `setRoundWin*` function. Crown visibility, score banner, win counters, round record, kills counters, victory dialog roster, round-end dialog roster. ~71 reference points.
- [src/ready-dialog.ts](../src/ready-dialog.ts) — ready-dialog roster (`renderReadyDialogForViewer`, `refreshReadyDialogRosterForViewer`, `applyReadyDialogRowColors`, `buildRosterDisplayEntries`, `updateTeamNameWidgetsForPid`, settings-summary HUD). Many sites.
- [src/overtime.ts](../src/overtime.ts) — overtime HUD: bar fills, counts, percent, crowns, vehicle-required indicator (`updateOvertimeHudForPlayer`, `rebuildOvertimeUiForPlayer`). The diff cache `lastUiSnapshotByPid` may need viewer-relative fields too.
- [src/clock.ts](../src/clock.ts) — clock color when close to time (today flips on closest-to-winning team? — verify).
- [src/round-flow.ts](../src/round-flow.ts), [src/vehicles.ts](../src/vehicles.ts), [src/index.ts](../src/index.ts) — broadcast call-sites; decision Q4 determines how many shift to per-pid notifications.
- [src/team-switch.ts](../src/team-switch.ts) — `processTeamSwitch` must trigger a full per-pid HUD repaint after the team change settles. New helper `repaintAllTeamScopedWidgetsForPid(viewer)`.
- [src/strings.json](../src/strings.json) — significant new keys for "Your Team" / "Enemy Team" framing if Q3 picks that direction. If Q3 picks "keep faction names (USA / RUS)", no string churn needed for labels.

### Conquest references

- Conquest does not do this (per [heli_v_conquest_comp.md](./heli_v_conquest_comp.md) — Conquest renders are not viewer-team-oriented). **No direct port; this is Helis-first.**
- Pattern analog: Conquest's per-pid render diff cache for combat HUD (`lastCombatHudSnapshotByPid` family). The technique of "snapshot the rendered values per-pid so renders are idempotent and skip when unchanged" already exists in Helis ([src/overtime.ts](../src/overtime.ts) `lastUiSnapshotByPid`); extend that snapshot shape to include the viewer's team so the diff invalidates correctly on team change.

### Open design questions

- **Q1. What "blue" and "orange/red" exactly?** Today's palette is presumably set by per-team color constants (likely `COLOR_TEAM1_*` / `COLOR_TEAM2_*` in [src/types.ts](../src/types.ts)). The new rule needs two viewer-oriented palettes: `COLOR_OWN_TEAM` (blue) and `COLOR_ENEMY_TEAM` (orange/red). Decide whether to:
  - (a) Repurpose the existing T1/T2 palette as "own/enemy" and accept that the visual identity of "Team 1" is no longer tied to one color — colors describe relationship, not identity.
  - (b) Keep T1/T2 as distinct palettes for any team-identity surfaces (e.g., a kill feed showing the killer's faction) AND add a new "own/enemy" palette for viewer-relative surfaces.
  - **Recommendation: (a).** Adding (b) doubles the color decision matrix at every site.

- **Q2. Spectator default orientation.** If C-P4 lands, the spectator has no team. Two options:
  - (a) Spectator sees the historic global default: T1 left blue, T2 right orange/red.
  - (b) Spectator gets a config-driven default (e.g., the first team that joined gets left).
  - **Recommendation: (a).** Predictable; matches the broadcast wording in world log.

- **Q3. Team naming in strings.** Today, team labels are probably faction-flavored strings ("USA" / "RUS" or similar). Does the new orientation change them?
  - (a) Keep faction names; only sides and colors flip. "Your team is USA, displayed on the left in blue. Enemy is RUS on the right in orange." Players keep their faction identity.
  - (b) Replace faction names with "Your Team" / "Enemy Team" everywhere. Cleaner mapping but loses faction flavor.
  - (c) Use both: roster row says faction name; banner says "YOUR TEAM" / "ENEMY". Mixed; clarifies relationship without dropping identity.
  - **Recommendation: (a).** Minimal string churn; the viewer-relative info comes from layout and color, not labels.

- **Q4. World log messaging.** Today's vehicle-capture and similar broadcasts say "Team 1 captured X". Options for the viewer-orientation world:
  - (a) Keep team-anchored: "USA captured X" / "RUS captured X". World log stays accurate-but-asymmetric to the HUD's "Your team" framing.
  - (b) Shift to per-pid notifications: every viewer gets "Your team captured X" or "Enemy captured X". Loses the persistent world-log surface.
  - (c) Hybrid: gameplay-critical (round-end, victory) stays team-anchored on world log; soft narration shifts to per-pid notifications.
  - **Recommendation: (a).** World log is a server-truth surface; HUD is a viewer-truth surface. Different framings are honest about different scopes.

- **Q5. Mid-match team-swap repaint.** SWAP TEAMS during pre-game flips the swapper's HUD. Need a helper called from `processTeamSwitch` that re-runs every team-scoped per-pid render for that pid. The per-pid render functions exist already (`updateRoundEndDialogForPlayer`, `updateVictoryDialogForPlayer`, etc.); the orchestrator is new. ~30 LOC.

- **Q6. Overtime diff-cache invalidation.** `lastUiSnapshotByPid` in [src/overtime.ts](../src/overtime.ts) compares rendered values to skip redundant `SetUIText*` calls. The snapshot keys assume render is identical across viewers — that breaks when render depends on viewer's team. Two fixes:
  - (a) Add viewer team to the snapshot key: `lastUiSnapshotByPid[pid] = { ...values, viewerTeam: teamOfPid }`. Force a one-time miss when viewer's team changes.
  - (b) Invalidate the snapshot explicitly on `processTeamSwitch` (cheap; manual).
  - **Recommendation: (b).** Local; doesn't touch the snapshot shape.

- **Q7. Pre-deploy / no-team-yet viewers.** `OnPlayerJoinGame` builds HUD before team is finalized. The first-pass HUD must pick an orientation; the second-pass (after team assignment) must repaint. Use the same repaint helper from Q5.

- **Q8. Staging strategy.** Strongly recommend NOT shipping the whole change in one PR. Suggested PR sequence:
  - **PR1**: Land `viewerSideForTeam` / `viewerColorForTeam` helpers + per-pid repaint orchestrator. No behavior change yet — helpers exist, no call sites use them. Catches the architecture review.
  - **PR2**: Migrate the top score banner + win counters + round-kills counter + crowns. Single most visible surface; easiest to screenshot-diff.
  - **PR3**: Migrate the Round-End Dialog.
  - **PR4**: Migrate the Victory Dialog (most complex; many widget refs and rosters).
  - **PR5**: Migrate the Ready Dialog roster + settings summary.
  - **PR6**: Migrate the Overtime HUD (with Q6 invalidation).
  - **PR7**: Resolve Q4 broadcast decision and migrate affected world-log -> notification messages if (b)/(c) was picked.

- **Q9. Bundle-size impact.** ~30 LOC of new helpers + per-call-site re-wiring is net-flat or slightly positive (some sites compress because the helper replaces an inline conditional). Plus any new strings from Q3/Q4. Estimated +2-5KB.

### Dependencies / sequencing

- **Best after**: [P0-8 (per-pid map consolidation)](./heli_improvement_plan.md). The new viewer-team field naturally lives on `PerPlayerState`; consolidation first means one cache invalidation site (Q6) instead of N.
- **Best after**: [P2-7 (`ensureHudForPlayer` split)](./heli_improvement_plan.md) IF that lands. The mega-function is a regression magnet for this change; splitting it first makes the per-sub-panel PRs (PR2-PR6) much easier to scope and review.
- **Conflict with**: C-P4 spectator — both touch the same per-pid HUD orchestration. **Recommendation: H-P3 lands first.** Spectator then plugs in cleanly with the default-orientation rule (Q2).
- **Conflict with**: H-P0 / H-P1 / C-P1 / C-P2 / C-P3 — adding new HUD surfaces concurrently with H-P3 risks each surface being built non-viewer-aware and needing a separate migration pass. **Recommendation: land H-P0 (smallest, simplest) before H-P3 to validate workflow; then H-P3; then everything else gets built viewer-aware from day one.**

### Risk + mitigation

- **Risk: every visible HUD surface changes simultaneously.** A single missed call site = visual bug in production.
  - **Mitigation 1**: Per-PR staging above (PR1-PR7). One surface per PR.
  - **Mitigation 2**: Screenshot-diff each PR. The existing position-debug HUD ([src/ready-dialog.ts](../src/ready-dialog.ts) `positionDebugLoop`) gives precise widget coords; pair with screenshots.
  - **Mitigation 3**: Add a `FEATURE_VIEWER_ORIENTED_HUD` boolean flag (single source const, gated module-load-time) so a regression in production can be reverted in a single line. Helis has no feature-flag machinery today; this would be the first one, but is small (~5 LOC) and well-scoped. After ~2 stable weeks of MP playtest, the flag and the legacy branch get deleted.
- **Risk: confusion when a player teammates discusses "left team" in voice and the listener sees them on the right.** Inherent to the design; not solvable in code. Worth flagging in patch notes.

## H-P4. Per-Map Mode Defaults + Supported-Mode Capability Declarations

### Scope

Each Helis map currently inherits a single global default for every Ready Dialog mode-config field (game-mode preset, matchup preset, vehicle indices, aircraft ceiling, etc.). Add **per-map defaults** to [src/config.ts](../src/config.ts) `MapConfig` so each map declares the values it loads with, and **per-map supported-mode capability flags** so the Ready Dialog can gray out (or refuse) configurations a map cannot physically support — e.g., "this map has no plane spawn points, so the Planes game mode is unavailable here."

This is **foundation work** for the other features in this doc. Every feature that adds a new Ready Dialog knob (H-P0 vehicle health, H-P1 layered ceiling, C-P1 round timings, C-P2 plane support, C-P3 per-slot mixing) will want a per-map default for its setting, and at least one (C-P2 planes) needs the supported-mode declaration to behave correctly. Landing H-P4 *before* the others means each downstream feature plugs into one defaults mechanism; landing it after means each downstream feature ships a one-off default and then has to be retrofitted.

### Where it lands

- [src/config.ts](../src/config.ts) `MapConfig` — extend each map entry with two new optional fields:
  - `defaults?: Partial<ReadyDialogModeConfig & { matchupPresetIndex, roundLengthSeconds, ... }>` — overlay applied on top of the global default when this map activates.
  - `supportedModes?: { vanilla: boolean, ladder: boolean, twl1v1: boolean, custom: boolean, tanksBranch: boolean, planesBranch?: boolean }` — capability declaration; absent means "all default modes supported."
- [src/strings.ts](../src/strings.ts) `applyMapConfig` — after the existing per-map state writes (base positions, spawn specs, overtime zones), apply the `defaults` overlay into `State.round.modeConfig` AND seed it into `State.round.modeConfig.confirmed` so the snapshot reflects the per-map values from the start.
- [src/types.ts](../src/types.ts) — type extensions for the new `MapConfig` fields, plus a helper signature `isModeSupportedOnMap(mapKey, gameModeIndex): boolean`.
- [src/ready-dialog.ts](../src/ready-dialog.ts) — in `setReadyDialogGameModeIndex`, `setReadyDialogVehicleIndexT1` / `T2`, and the matchup preset path: reject (or visually disable) selections that violate the active map's `supportedModes`. New visibility/state for the affected dialog rows.
- [src/index.ts](../src/index.ts) `OnGameModeStarted` — after `applyMapConfig`, the new defaults are already in `State`; no further work other than ensuring the Ready Dialog repaints with the new values when first opened.

### Conquest references

- Conquest currently has only one active map (Operation Firestorm) so it does not exercise per-map defaults heavily, but the pattern of a `MapConfig` table with per-map fields lives at [bf6-portal/dev/conquest/src/config/](../../conquest/src/config/). The Helis `MapConfig` already mirrors the Conquest shape — extending it here is on-pattern, not a divergence.
- Mode-config schema source of truth: [bf6-portal/dev/conquest/src/ready-dialog/mode-config-schema.ts](../../conquest/src/ready-dialog/mode-config-schema.ts) (Helis has analogous shapes in [src/types.ts](../src/types.ts) and [src/state.ts](../src/state.ts)). When picking the field set that participates in per-map defaults, mirror that schema rather than enumerating fields ad-hoc.

### What fields participate in per-map defaults?

Suggested fields (anything with a Ready Dialog knob is a candidate; anything not exposed in the dialog is global):

| Field | Per-map default candidate? | Notes |
|---|---|---|
| `gameModeIndex` (Vanilla / Ladder / TWL 1v1 / Custom) | **Yes** | Some maps may be authored for a specific competitive ruleset. |
| `matchupPresetIndex` (1v1 / 2v2 / 3v3 / 4v4) | **Yes** | Smaller maps may default to 1v1 / 2v2. |
| `aircraftCeiling` | **Yes** | Already partially per-map via `useCustomCeiling`. Promote to a full integer per map. |
| `vehicleIndexT1` / `vehicleIndexT2` | **Yes** | Some maps work better with specific vehicle types. |
| `vehicleHealthPct` (from H-P0) | **Yes** | Tight maps may default to lower health for faster engagements. |
| `roundLengthSeconds` (admin knob) | **Yes** | Bigger maps may default to longer rounds. |
| `roundRestartSeconds` / `roundKickoffSeconds` (from C-P1) | Optional | Probably global; per-map likely not useful. |
| `tieBreakerModeIndex` (LastRoundOnly / AllRounds / Disabled) | Optional | Probably global; per-map override might confuse admins. |
| Active overtime zone letter | **Already per-mode-per-map** | The existing `overtimeZoneLettersByMode` covers this. |

### What fields participate in supported-mode declaration?

| Capability | When relevant | Default if unset |
|---|---|---|
| `tanksBranch: boolean` | All maps support tanks today; defaults true. | `true` |
| `helisBranch: boolean` | All maps support helis today; defaults true. | `true` |
| `planesBranch: boolean` (from C-P2) | Maps without authored plane spawn points must declare false. | `false` until plane spawns authored. |
| `customGameMode: boolean` | If a map shouldn't be configurable (locked competitive layout). | `true` |
| Per-vehicle-list entries (`canSpawn: { tanks: VehicleList[], helis: VehicleList[], planes: VehicleList[] }`)? | If C-P3 lands. Per-map allowlist for which vehicle picks are valid. | `null` (all default vehicles for category). |

### Open design questions

- **Q1. Where do `defaults` live in the type system?** Two options:
  - (a) Each `MapConfig.defaults` is `Partial<ReadyDialogModeConfig & MatchupConfig & RoundFlowConfig>`. Type-safe; verbose; couples MapConfig to the union of every consumer's schema.
  - (b) Each `MapConfig.defaults` is a free-form `Record<string, unknown>` keyed by a string ID and consumers read the keys they care about. Decoupled; loses type safety.
  - **Recommendation: (a).** With `@ts-nocheck` already pervasive in Helis, type safety is less of a hard win, but the type acts as documentation — readers see exactly which fields participate.

- **Q2. Override semantics: global default + per-map overlay, or per-map full spec?**
  - (a) **Overlay** — `MapConfig.defaults` is sparse; each field that's set overrides the global default; unset fields fall through. **Recommendation.** Minimal config churn; obvious how to add a new field.
  - (b) **Full spec** — every map declares the entire defaults blob. Verbose; one new field = N config edits.

- **Q3. Behavior when admin tries to pick an unsupported mode.** When `supportedModes.planesBranch = false` on the active map and the admin clicks "Planes" in the game-mode picker:
  - (a) Gray out the option; click is no-op. Recommended.
  - (b) Allow click but show a toast "Planes not supported on this map." Click still no-op.
  - (c) Allow click and silently fall through to Helis mode.
  - **Recommendation: (a) + (b) combined** — visually grayed AND a one-shot toast on first attempt per pid per match. Avoids the "broken UI" feel of (a) alone when a player wonders why a button doesn't work.

- **Q4. What about settings the admin has already changed?** If admin is in mid-pre-game, has set `gameModeIndex = Planes` on a map that supports it, and then... what? The map can't change mid-match in BF6 Portal — the gamemode-start map is locked. So this is a non-question, but worth confirming. **Confirmed: maps are fixed for the duration of a match; per-map defaults apply once at `OnGameModeStarted` and never again.**

- **Q5. What about competitive ladder maps where we want the defaults locked?** Some TWL maps may want "no overrides allowed" — the per-map default IS the only valid config. Adds a `locked: boolean` flag per default? Or grays out every dialog knob?
  - **Recommendation: defer.** Adds complexity; not currently requested. If lockable defaults are needed, add a single `MapConfig.locked: boolean` flag that grays the entire Ready Dialog mode-config row set on activation. Tracked here for later.

- **Q6. Migration of existing per-map fields.** [src/config.ts](../src/config.ts) already has per-map `useCustomCeiling` and per-mode `overtimeZoneLettersByMode`. Should these be moved into `defaults` for consistency?
  - **Recommendation: no, leave them where they are.** `useCustomCeiling` is a structural flag, not a "default value." `overtimeZoneLettersByMode` is per-mode-per-map (a different shape). Moving them creates churn without gain; new fields go into `defaults`, the existing fields stay where Helis already reads them.

- **Q7. Validation on bundle build.** If a map declares `defaults.gameModeIndex = Planes` but `supportedModes.planesBranch = false`, the config is internally inconsistent. Options:
  - (a) Detect at bundle build (postbuild step) and fail.
  - (b) Detect at runtime in `applyMapConfig` and log to world log.
  - (c) Don't detect; trust the author.
  - **Recommendation: (b).** Postbuild already runs `verify.js`; add one more validator. Runtime log gives developer visibility without blocking ship.

- **Q8. Per-map labels and HUD strings.** A map declaring `defaults.gameModeIndex = TwlLadder` doesn't need any new strings — the existing game-mode labels apply. But if we add a `mapDisplayName` or `mapShortName` field, that's new strings. **Recommendation: defer.** Map names are already in `twl.maps.*` keys; no new strings needed for this feature.

### Dependencies / sequencing

- **Best landed early in the features track**, after H-P0 (smallest feature to prove dialog-row patterns) and C-P1 (mechanical admin port) but before any feature that adds a new knob OR a new capability dimension. Concretely:
  - Before **C-P2 (planes)** — planes need `supportedModes.planesBranch` to gracefully disable on plane-less maps. If C-P2 lands first, every plane-less map gets a runtime warning every time someone tries to pick planes; landing H-P4 first means the picker shows the correct state from the dialog's first paint.
  - Before **H-P1 (layered ceiling)** — ceiling defaults likely want to be per-map (some maps have different airspace constraints). Landing H-P4 first means H-P1 plugs in.
  - Before **C-P3 (per-slot mixing)** — per-slot defaults are valuable per-map.
  - Order-independent with **H-P3 (viewer-oriented HUD)** — no overlap.
- **No dependency on** improvement-plan P0/P1 items; can land any time after the P0 mission-critical tier is complete.

### Risk

- **Low.** The change is additive: new optional fields on `MapConfig`, new optional reader paths. Unset means "use existing global default" — no behavior change on day one. The risk lives at the *consumer* sites (H-P0, C-P2, etc.) — those features see new defaults from day one if H-P4 ships first.

### Suggested PR shape

- **PR1**: Extend `MapConfig` types + `applyMapConfig` to read `defaults` overlay. Add per-map `defaults` for one or two existing fields (e.g., `aircraftCeiling`, `matchupPresetIndex`) per existing global default; no behavior change because the per-map values equal the current global default. This proves the plumbing.
- **PR2**: Add `supportedModes` field + capability-gated UI (Ready Dialog gray-out + toast on first illegal click). With no map declaring `false` for anything yet, no visible change.
- **PR3**: Postbuild validator (Q7).

Then each downstream feature (C-P2 in particular) ships *with* its per-map declarations from PR-1 of that feature, rather than as a follow-up.

## C-P2. Planes as a Vehicle Category, with Separate Spawn Points

### Scope

Today Helis supports two vehicle categories: tanks (`TEAM*_VEHICLE_SPAWN_SPECS` ground specs) and helis (`TEAM*_HELI_SPAWN_SPECS` air specs, derived from tank slots if not authored). User wants **planes** added as a third category, with their own spawn points distinct from helis (different altitude and clearance constraints).

This is **not** the same as Conquest's "Air Deploy" volume system — Conquest's volumes are for player-summoned per-slot spawn-on-demand. Helis spawns vehicles up-front from authored points. The port is the *vehicle-classification + per-category-spawn-spec* shape, adapted to Helis's spawn model.

### Where it lands

- [src/config.ts](../src/config.ts) `MapConfig` — new optional `planeSpawnSpecs` (parallel to `tankSpawnSpecs` and `heliSpawnSpecs`).
- [src/strings.ts](../src/strings.ts) — auto-derive plane spawns from tank/heli specs when unauthored? Or require explicit authoring? See Q1.
- [src/types.ts](../src/types.ts) — extend `isAircraftVehicle` (which today returns true for helis only? confirm) to include jets; add `isJetVehicleType` helper.
- [src/strings.ts](../src/strings.ts) `getReadyDialogVehicleListByIndex` — extend the vehicle list to include jet picks (Su-57, F-35, etc.); add a "Game Mode: Planes" preset row if planes get their own mode preset (see Q2).
- [src/ready-dialog.ts](../src/ready-dialog.ts) — Game-Mode picker. Today it has Vanilla / Ladder / TWL 1v1 / Custom. Add a Planes preset? Or make planes a separate top-level mode like helis/tanks? See Q2.
- [src/vehicles.ts](../src/vehicles.ts) `forceSpawnWithRetry` — handle plane spawn points (likely a non-zero starting altitude; tanks are ground-level).
- [src/ready-dialog.ts](../src/ready-dialog.ts) `runAircraftCeilingSoftEnforcementLoop` — must classify jets distinctly from helis if they have different ceiling tolerance.

### Conquest references

- [bf6-portal/dev/conquest/src/vehicles/vehicle-classification.ts](../../conquest/src/vehicles/vehicle-classification.ts) — jet vs heli classification helpers and the `isJetVehicleType` precedent.
- [bf6-portal/dev/conquest/src/vehicles/air-spawn-volume.ts](../../conquest/src/vehicles/air-spawn-volume.ts) — volume-based air spawning with separate `jetSpawnFloor` / `jetSpawnCeiling` vs `heliSpawnCeiling`. Helis won't use the volume model (we have authored point spawns), but the **per-category altitude offset pattern** is exactly what we need.
- [bf6-portal/dev/conquest/src/foundation/gameplay.ts:204](../../conquest/src/foundation/gameplay.ts#L204) — `VehicleList.AH6M` precedent for vehicle-type casts. Likely also has jet entries.

### API references

- Need to confirm against [reference_bf6_core](../../reference_bf6_core/): the set of plane vehicle types (`mod.VehicleList.SU57` / `F35` / etc.) currently supported by BF6.

### Open design questions

- **Q1. Auto-derive plane spawns from tank specs?** Today `buildHeliSpawnsFromTankSpawns` ([src/strings.ts](../src/strings.ts)) derives heli air-spawns from authored tank ground points by raising Y by some amount. We *could* do the same for planes (raise Y higher, randomize a wider area). **Recommendation: yes for first ship — derive planes from tank specs at a fixed +Y offset, with map-by-map override capability.** Authors override per map if the auto-derivation puts a plane inside a mountain.
- **Q2. Where do planes live in the mode taxonomy?** Three options:
  - (a) New top-level mode: "Helis Only - Planes Variant". Mirrors the existing tank/heli branching. Each preset has only one vehicle category.
  - (b) Planes are a sub-category of the heli mode — players pick at the per-team vehicle level whether they want helis, planes, or mixed (this is what C-P3 enables).
  - (c) Planes are their own mode AND C-P3 enables mixed sets.
  - **Recommendation: (a) for C-P2 ship, then (b) extends naturally via C-P3.** Phase ordering: stand up planes as a "Helis Only - Planes" variant first (proves out plane spawn / ceiling / scoring without the per-slot mixing UI), then C-P3 generalizes to mixed sets per team.
- **Q3. Plane ceiling.** Jets typically fly higher than helis. Re-use the H-P1 layered ceiling system with category-specific thresholds, or one global ceiling? **Recommendation: per-category ceiling.** A heli's 550m and a jet's 1500m want different defaults.
- **Q4. Spawn behavior.** Jets typically spawn at speed and in flight in BF6. Confirm the engine-side spawn behavior so the spawn points work — possibly need `applySpawnYawToVehicle`-style yaw correction for jets at launch.
- **Q5. Tie-breaker overtime zones.** Helis already has per-mode overtime letter overrides (`overtimeZoneLettersByMode: {tanks, helis}`). Add `planes`? **Recommendation: yes, third entry.** Easier to author than reusing heli letters.
- **Q6. String approval.** Substantial new strings: game-mode preset name, plane-mode HUD labels, vehicle names. Get a focused approval pass.

### Sequencing

- Stand-alone, but logically precedes C-P3 (per-slot vehicle-type mixing needs the plane category to exist before it can be picked per-slot).
- The layered-ceiling work (H-P1) should land first; the plane category will want category-specific ceilings on day one and that's cheaper to add to a layered system than to bolt on after.

## C-P3. Per-Slot Vehicle-Type Tuning (Mixed Vehicle Sets per Team)

### Scope

Today: a single `vehicleIndexT1` (and `T2`) selects the vehicle type for all of team 1's (team 2's) slots. So team 1 gets 4 of the same vehicle. User wants per-slot configurability: team 1 could be `[ChopperA, ChopperA, PlaneA, PlaneA]` while team 2 is `[PlaneB, PlaneB, ChopperB, ChopperB]`, or any per-slot combination.

This is a Ready Dialog UI expansion + spawn-spec model change. The number of slots is bounded by the matchup preset (1v1 = 1 slot/team, 4v4 = 4 slots/team).

### Where it lands

- [src/types.ts](../src/types.ts) `ReadyDialogModeConfig` — replace `vehicleIndexT1 / T2: number` with `vehicleSlotsT1 / T2: number[]` (one index per slot). Migration: when matchup changes from 4v4 to 2v2, truncate or pad. When changing to 4v4, default new slots to slot[0]'s pick.
- [src/strings.ts](../src/strings.ts) `applyVehicleOverrideToSpawns` / `refreshVehicleSpawnSpecsFromModeConfig` — apply per-slot picks rather than a single global pick.
- [src/ready-dialog.ts](../src/ready-dialog.ts) `createTeamSwitchUI` — replace the two "Vehicles T1 / T2" rows with up-to-4 per-team rows. Visibility tied to matchup count. New dec/inc buttons per slot index per team.
- [src/team-switch.ts](../src/team-switch.ts) — many new button event cases.
- [src/strings.json](../src/strings.json) — per-slot string keys (probably formatted: `"Slot {0}: {1}"`).
- [src/hud.ts](../src/hud.ts) settings-summary — show one line per slot when active, or a condensed "Mixed" indicator when slot picks differ.

### Conquest references

- Conquest does not have an exact analog. Conquest's vehicle-category mixing comes through the Forward / Air / HQ Deploy vehicles being per-slot at deploy-claim time, not pre-configured per-slot at lobby time. So this is a Helis-specific UX, but the per-slot iteration pattern can borrow from Conquest's HQ Deploy slot UI:
  - [bf6-portal/dev/conquest/src/vehicles/hq-deploy.ts](../../conquest/src/vehicles/hq-deploy.ts) — per-slot UI iteration.

### Open design questions

- **Q1. Slot count tied to matchup, or fixed at 4?** If user picks 1v1, do they only see 1 slot row, or all 4 (with unused ones disabled)? **Recommendation: visible = matchup count.** Easier to scan; matches the rest of the dialog's matchup-driven sizing.
- **Q2. Per-slot or per-team picker.** A picker labeled "Slot 1: ChopperA [-][+]" doubles to 4× the picker count at 4v4. The dialog has finite real estate. Options:
  - (a) Per-team summary line "T1: 2 Chopper / 2 Plane" + a sub-dialog opens when clicked. Adds modality.
  - (b) 4 rows per team always; row visibility = matchup count. Inline; busier dialog. **Recommendation: (b)** — modal dialogs in Helis don't exist yet and adding one is its own scope.
- **Q3. Symmetric mode.** Some matches want symmetric mirror sets across teams (T1 picks = T2 picks). Add a "Mirror T1 -> T2" toggle? **Recommendation: defer to a v2;** ship per-team independent first.
- **Q4. Spawn ordering / heterogeneity.** When team 1 has `[Chopper, Chopper, Plane, Plane]`, does slot 0 always get the chopper-spawn-point and slot 2 always get the plane-spawn-point? **Recommendation: yes — slot index is fixed to the spawn point, the vehicle TYPE varies.** This requires that all map spawn points are usable by all vehicle types (or that the picker forbids invalid combinations).
- **Q5. Compatibility validation.** Should the picker reject "plane in a tank-only spawn point" if the map has a tank-only spec? Maps in Helis have `tankSpawnSpecs` and `heliSpawnSpecs` distinct. **Recommendation: dialog warns + greys out invalid combos.** Need a per-map "spawn-point class" annotation.
- **Q6. Confirm semantics.** Snapshot on Confirm like the rest of mode-config? **Yes.** Mid-pre-game per-slot edits don't apply until Confirm.
- **Q7. Bundle-size impact.** ~8 new widget rows × per-pid = significant bundle bytes. Combined with H-P0 / H-P1 / C-P1 additions, watch the headroom number. (Helis is at ~548k free per features doc Section 2; comfortable for this scope but bears tracking.)

### Sequencing

- **Must land after C-P2** (planes need to be a real vehicle category before per-slot picking can target them).
- **Should land after [P0-1 (Ready Dialog warm-build deletion)](./heli_improvement_plan.md) and [P0-8 (per-pid map consolidation)](./heli_improvement_plan.md)** — the dialog rebuild surface gets denser; doing both refactors first reduces regression risk.

## C-P4. Single-Slot Spectator

### Scope

One reserved spectator slot. The spectator player is not on either team, does not affect kill scoring or vehicle registration, and observes the match via a fixed camera or spectator-style view. They sit out the round; on match end they remain in the lobby with the rest of the players.

### Where it lands

- [src/state.ts](../src/state.ts) — `State.players.spectatorPid: number | undefined` (single-slot claim).
- [src/types.ts](../src/types.ts) — new constants for the spectator camera position per map (if Cameras.Fixed approach is used), spectator-mode string keys.
- [src/config.ts](../src/config.ts) `MapConfig` — new optional `spectatorCameraId` or `spectatorCameraPosition` per map.
- [src/index.ts](../src/index.ts) `OnPlayerJoinGame` / `OnPlayerLeaveGame` — handle spectator slot claim + release.
- [src/ready-dialog.ts](../src/ready-dialog.ts) — new "Spectator" button on the dialog; once claimed, claimant goes spectator-only; if already claimed by someone else, button shows "Spectator Claimed by {name}" and is disabled. Mirror of Conquest's COACH-button pattern.
- [src/round-flow.ts](../src/round-flow.ts) — exclude spectator pid from `getActivePlayers`, ready-up gates, kill-credit, vehicle registration.
- [src/team-switch.ts](../src/team-switch.ts) — block team-swap action for spectator pid; release-spectator-slot action.
- [src/hud.ts](../src/hud.ts) — spectator HUD layout: rosters, match clock, spectator-mode banner.

### Conquest references

- [bf6-portal/dev/conquest/src/spectator/spectator-action.ts](../../conquest/src/spectator/spectator-action.ts) — the load-bearing port. Notes embedded in source:
  - Single-slot, claim-only model via `State.players.spectatorPid`.
  - Mitigation C: do NOT undeploy / redeploy; just swap the camera (works on a deployed player per the I-4 finding documented in memory [`project_setcameratype_undeployed_fail`](../../../.. — memory ref)). Combat HUD persists so the spectator watches the match unfold.
  - `mod.Cameras.Fixed` enum value 1 in SDK 1.2.3 but missing from the vendored types — same `(mod.Cameras as any).Fixed` cast as `VehicleList.AH6M` precedent.
  - `applySpectatorInputLock` — `EnableInputRestriction` for weapons/zoom/select-* inputs; release movement + look so the spectator soldier-body parked at the hide-room cube can drive a free-camera loop later.
  - Lifecycle: `onSpectatorPlayerLeave` (disconnect), `onSpectatorMatchEnd` (round end), `onSpectatorFreshSetup` (admin reset). All three idempotent + null-safe.
- [bf6-portal/dev/conquest/src/spectator/coach-button-sync.ts](../../conquest/src/spectator/coach-button-sync.ts) — the button-state machine for the player-ready-panel + admin-dialog COACH button (claim / claimed-by-other / disabled). This is the UI port target.

### API references

- `mod.Cameras.Fixed` — enum value, currently a cast in Conquest (see above).
- `mod.SetCameraTypeForPlayer` — per memory [`project_setcameratype_undeployed_fail`](../../../.. — memory ref) the swap only takes effect on a deployed player. Spectator must be deployed at the hide-room before camera swap. Conquest landed this as "Mitigation C": triple-tap on COACH is gated on `isPlayerDeployed` and the pre-live boundary keeps players at their HQ trigger pre-match, so they're deployed when the click fires.

### Open design questions

- **Q1. Hide-room location.** Conquest parks the spectator's soldier body at a hide-room cube (Y=-500). Helis maps don't have one. Options:
  - (a) Author a hide-room volume per map (small box below the map).
  - (b) Teleport spectator soldier to far below ground at match start.
  - (c) Use spectator camera + leave the soldier body at the main base (visible to teammates? probably not ideal).
  - **Recommendation: (b) — single-line teleport, no map authoring required.** Verify the engine doesn't render the soldier when below a Y threshold.
- **Q2. Spectator UI.** What does the spectator see?
  - Both team rosters?
  - Match clock?
  - Vehicle-registration messages (so they see the scoring)?
  - Their own version of the overtime HUD?
  - **Recommendation: rosters + clock + kills counter + flag HUD;** essentially the same combat HUD a non-spectator sees, just without their own ammo / health overlay.
- **Q3. Spectator camera placement.** Per Conquest, `mod.Cameras.Fixed` is authored per-map via `spectatorCameraId`. Helis would need to author one camera point per map. Acceptable lift?
  - **Alternative**: don't fix the camera; let the spectator's soldier-body free-fly (Conquest's ship-3 free-camera goal). Adds complexity. **Recommendation: start with Cameras.Fixed (one authored point per map), match Conquest's ship-2 scope.**
- **Q4. Spectator joins ready-up?** A spectator can READY in the dialog (so they're "in") but their READY doesn't count toward auto-start. Auto-start checks "all active non-spectator players ready." **Recommendation: yes — spectator can READY to indicate "I'm watching;" the auto-start gate ignores them.**
- **Q5. Spectator slot conflict.** Two players race to claim. Conquest's `applyCoachButtonState` handles this. Mirror the pattern; first-write-wins.
- **Q6. Match-end behavior.** When the match ends, spectator gets the victory dialog like everyone else? **Recommendation: yes.** Easier than special-casing.
- **Q7. String approval.** Significant new keys: spectator-mode banner, COACH button label, claim/disabled states, victory-dialog spectator team. Get a focused approval pass.

### Sequencing

- **Stand-alone but heavy.** Can land independently of any other feature. Estimated effort comparable to the Conquest ship-2 spectator (medium-large). 
- Land **after** [P0-1 / P0-8](./heli_improvement_plan.md) (Ready Dialog warm-build deletion + per-pid consolidation) — both refactors smooth this port. The Conquest implementation depends on the consolidated per-pid struct.
