## 1. Context

Add a tunable knob on the Ready Dialog that scales spawning vehicles' max-health by a configurable multiplier. The motivation is competitive-ladder tuning: TWL operators want to dial vehicle durability up or down without touching map config or rebuilding the bundle, e.g., to compensate for vehicle-balance imbalances on specific maps, or to run a "glass cannon" event variant.

This is a Helis-first feature (not in Conquest). The closest in-project analog is the **Aircraft Ceiling** knob — same row-builder shape, same pending/confirmed snapshot semantics, same `ensureCustomGameModeForManualChange` flip-to-Custom-on-manual-change pattern, same world-log-on-confirm broadcast. The Vehicle Health Multiplier is a direct clone of that pattern with a different value type and a different application site.

### Why this design (decisions locked 2026-05-27)

User direction on this feature was specific and final on the following points; deviations require explicit re-approval:

| Decision | Locked answer | Source |
|---|---|---|
| Value range | 5% (`0.05`) through 400% (`4.0`), step 1% (`0.01`). 500% upper-bound from original spec **rejected** — engine API caps at 4.0. | User Q-A1 + my [SetVehicleMaxHealthMultiplier.md](../../reference_bf6_core/mod/functions/SetVehicleMaxHealthMultiplier.md) verification. |
| Storage type | **Multiplier (float)**, NOT percent (int). Field name `vehicleHealthMultiplier`. UI converts to % only at display sites via `Math.round(mult * 100)`. | User Q-J answer "Multiplier is the correct name". |
| Default | `1.0` (= 100%) globally. All 9 maps explicitly declare `defaultVehicleHealthMultiplier: 1.0` in MapConfig. | User Q-A3 answer "all defaults will start with 100% for now". |
| Per-map plumbing | Wire `MapConfig.defaultVehicleHealthMultiplier?: number` **now**, not deferred to H-P4. | User Q-G answer "plan to do it like we want eventually, not in phases" + clarification "Wire MapConfig field now". |
| Apply timing | **Confirm-only**. Pending changes do nothing visibly until Confirm fires. | User Q-B answer. |
| Apply scope | **New spawns only**. Vehicles alive at Confirm time keep their previous max-health. | User Q-C answer. |
| UI row position | Same row as Mode Settings; new dec/value/inc widgets positioned LEFT of `leftSectionLabelX`. No separate label widget — value text is self-labeling ("Health: 100%"). | User clarification answer "Same row, buttons left". |
| Game-mode interaction | Manual change → `ensureCustomGameModeForManualChange()` flips to Custom (mirrors ceiling). Preset selection → resets health to map default. | User Q-D answer. |
| Reset button | **Preserves confirmed value** across "RESTART / FRESH SETUP". Matches existing ceiling/vehicles behavior; my Q-I recommendation was based on a faulty assumption (Reset does not currently restore mode config). | User clarification answer "Match existing behavior". |
| HUD settings summary | **Always display**, even at 100%. New text widget on each pid's settings panel. | User Q-E answer. |
| World-log on Confirm | Broadcast `"{Player} changed the Vehicle Health to {N}%"` when confirmed value differs from previous. Mirrors `aircraftCeilingChanged`. | User Q-F answer. |
| String additions | 3 new keys, approved per AGENTS.md String Authorization Policy. | User Q-A7 answer. |

## 2. API references (verified)

- **[reference_bf6_core/mod/functions/SetVehicleMaxHealthMultiplier.md](../../reference_bf6_core/mod/functions/SetVehicleMaxHealthMultiplier.md)** — signature `(vehicle: Vehicle, maxHealthMultiplier: number) => void`. Engine contract: `multiplier > 0 && <= 4`. Same signature in [SDK 1.2.3 index.d.ts:27558](../../reference_sdk_1.2.3/code/types/mod/index.d.ts) and [SDK 1.3.1 index.d.ts:27558](../../reference_sdk_1.3.1/code/types/mod/index.d.ts).
- **Real-world precedent**: [BillDukes VehicleUIUniversal.portal (3).ts:3813-3816](../../conquest/reference_implementations/reference_BillDukes_VehicleDeploy/VehicleUIUniversal.portal%20(3).ts#L3813-L3816) — calls one-shot after seat, wrapped in `try { } catch (_e) {}`, with values 0.5 / 0.6 / 0.7. Confirms: one-shot per spawn (no per-tick re-application), persists for vehicle's lifetime, try/catch wrap is the standard guard.
- **Lower-bound unverified**: No reference implementation uses values below 0.5. The 0.05 floor is contractually legal per the SDK docs (`> 0` is satisfied) but has not been observed in practice. SP smoke step 3 below validates.

function setReadyDialogVehicleHealthMultiplier(nextValue: number, _changedBy?: mod.Player): void {

## 6. Banned patterns guarded against

Per [AGENTS.md](../AGENTS.md):

- **ASCII-only source**: no em-dashes, smart quotes, arrows, non-ASCII in any `.ts` file. Use `--` for em-dash, `->` for arrow. Postbuild step 11.5 hard-fails the build otherwise.
- **`mod.Message` string-key requirement**: all 3 new player-facing message keys are registered in [src/strings.json](../src/strings.json) (step 3.5) and accessed via `mod.stringkeys.twl.*` (step 3.1's STR_* consts). No literal-string `mod.Message("...")` calls.
- **No `mod.AddUIIcon`**: not used by this feature; n/a.
- **No `mod.ForcePlayerToSeat`**: not used by this feature; n/a.
- **No `console.log`**: diagnostic surface is the persistent HUD widget (the new `settingsVehicleHealthText`); not the world log for debug.
- **`try/catch` wrap on engine call**: the `mod.SetVehicleMaxHealthMultiplier` call in step 3.9 is wrapped per the BillDukes precedent.
