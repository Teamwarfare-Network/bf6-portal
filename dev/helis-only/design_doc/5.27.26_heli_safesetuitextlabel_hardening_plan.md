## Context

Reported runtime error: **"Received undefined values as arguments"** — still firing 2 instances at game start on v0.635 after v0.632–v0.635 closed 5 hypothesized sources.

After 4 unsuccessful fixes, search of Conquest changelog and `conquest_issues.md` (per user direction) found **CQ_Bug_18** at Conquest v0.764: a hardening pass on `safeSetUITextLabel` that Helis never received.

From Conquest's v0.764 changelog:
> "make `safeSetUITextLabel` skip nullish labels and normalize numeric string keys before calling the engine so ready-dialog refresh helpers cannot trip SETUITEXTLABEL on transient undefined values"

The corresponding Conquest commit added:
1. **`isUITextWidget(widget)`** — type-checks widget by probing `mod.GetUITextSize(widget)` in a try/catch. If the probe throws, the widget is stale or wrong type.
2. **`resolveLiveUITextWidget(widget)`** — if the passed widget is no longer a live text widget, re-resolves it by name via `safeFind(mod.GetUIWidgetName(widget))`. Closes the "cached HUD handle survives dialog rebuild" race that Helis also has.
3. **`safeSetUITextLabel(widget, label)`** — widened signature accepts `mod.Message | number | undefined | null`. Guards with `if (label === undefined || label === null) return;` before reaching the engine. Normalizes numeric string keys via `mod.Message(label)`.

Helis's current `safeSetUITextLabel` at [src/hud.ts:130-137](../src/hud.ts#L130):
```ts
function safeSetUITextLabel(widget: mod.UIWidget | undefined, label: mod.Message): void {
    if (!widget) return;
    try {
        mod.SetUITextLabel(widget, label);
    } catch {
        return;
    }
}
```

- No label-null guard. If any caller passes `undefined`, it goes straight to the engine which logs "Received undefined values as arguments" before the JS catch swallows the throw.
- No widget re-resolution. Stale cached widget refs from HUD rebuilds fall through to engine.
- Signature is narrow (`mod.Message` only); callers passing numeric string keys would currently be a type error if `@ts-nocheck` weren't on.

84 callsites use `safeSetUITextLabel` across [src/hud.ts](../src/hud.ts), [src/ready-dialog.ts](../src/ready-dialog.ts), [src/clock.ts](../src/clock.ts), [src/overtime.ts](../src/overtime.ts). All benefit automatically from the wrapper hardening.

## The diff

### New helpers (inserted before existing `safeSetUITextLabel` in hud.ts)

```ts
// Probes whether a widget handle is still live and is a text widget.
// Calls mod.GetUITextSize defensively; if the engine rejects (stale handle or
// wrong widget type), returns false. Used by resolveLiveUITextWidget to filter
// stale handles after dialog/HUD rebuild paths.
function isUITextWidget(widget: mod.UIWidget | undefined): widget is mod.UIWidget {
    if (!widget) return false;
    try {
        mod.GetUITextSize(widget);
        return true;
    } catch {
        return false;
    }
}

// Re-resolves cached UI handles by name so reopen/rebuild paths do not keep
// writing through stale widget references after dialog/HUD lifecycle changes.
// Conquest port (hud/status.ts:144) CQ_Bug_18.
function resolveLiveUITextWidget(widget: mod.UIWidget | undefined): mod.UIWidget | undefined {
    if (isUITextWidget(widget)) return widget;
    if (!widget) return undefined;
    try {
        const widgetName = mod.GetUIWidgetName(widget);
        if (!widgetName) return undefined;
        const liveWidget = safeFind(widgetName);
        return isUITextWidget(liveWidget) ? liveWidget : undefined;
    } catch {
        return undefined;
    }
}
```

### Replacement for `safeSetUITextLabel`

```ts
// BEFORE
function safeSetUITextLabel(widget: mod.UIWidget | undefined, label: mod.Message): void {
    if (!widget) return;
    try {
        mod.SetUITextLabel(widget, label);
    } catch {
        return;
    }
}

// AFTER
// Safe text-label write helper used by HUD render paths.
// Some callers build labels through helper chains that can transiently return
// undefined/null during UI lifecycle transitions, so normalize or skip before
// reaching the engine overload boundary. Conquest port (hud/status.ts:161)
// CQ_Bug_18 v0.764 -- closes "Received undefined values as arguments" engine
// error class on UI text writes.
function safeSetUITextLabel(widget: mod.UIWidget | undefined, label: mod.Message | number | undefined | null): void {
    const liveWidget = resolveLiveUITextWidget(widget);
    if (!liveWidget) return;
    if (label === undefined || label === null) return;
    let resolvedLabel: mod.Message;
    if (typeof label === "number") {
        try {
            resolvedLabel = mod.Message(label);
        } catch {
            return;
        }
    } else {
        resolvedLabel = label;
    }
    try {
        mod.SetUITextLabel(liveWidget, resolvedLabel);
    } catch {
        return;
    }
}
```

## Why this is risk-free

- **Success path** (valid widget + valid label): identical end behavior. The engine receives `mod.SetUITextLabel(widget, label)` as before.
- **Stale widget path**: previously fell through to engine and threw; now re-resolved by name via `safeFind` and proceeds with the live widget OR silently skips if not found. Engine no longer receives a stale handle.
- **Null/undefined label path**: previously passed straight to engine which logged "Received undefined values"; now silently skipped at the wrapper before engine sees the call. **This is the actual fix.**
- **Numeric label path**: previously a type error (caught by JS, swallowed); now normalized to `mod.Message(label)` and proceeds.
- **All 84+ existing callers benefit transparently** — no callsite changes needed.

## Performance

- **Per-call cost added**: one extra `mod.GetUITextSize(widget)` probe in the type-check (try/catch), plus one extra equality check on label. Both O(1).
- **Re-resolve path** (`mod.GetUIWidgetName` + `safeFind`) only fires when the initial widget is stale — rare; same cost as existing widget rebuild paths.
- **Net per-tick impact**: imperceptible. The HUD render paths already amortize the cost of widget refs across the same callers; the new probe is similar in shape to existing `safeFind` patterns.

## What this doesn't address

- The "GetSoldierState... player not being deployed" engine error on plain death (#2). Per [conquest_issues.md](../../conquest/design_doc/conquest_issues.md) CQ_Bug_37/38/50, Conquest documents this engine-log-before-JS-catch as "cosmetic residue" and ships with it. Helis already has the same safe-wrapper pattern. No further Conquest port exists for this.
