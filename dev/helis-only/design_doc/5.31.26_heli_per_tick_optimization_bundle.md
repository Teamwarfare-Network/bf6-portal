# Per-Tick Optimization Bundle — Ship Plan

**Date**: 2026-05-31
**Goal**: Ship five low-risk per-tick optimizations as one bundle. Removes wasted work in the steady state and eliminates a previously-unidentified post-join dogpile risk equivalent to the bugs Phase A+B fixed.

**Scope**: Five surgical changes across four files. No new abstractions, no signature changes, no behavior changes visible to players. All five are pure caching, gating, or removal of work that was already a no-op in its trigger path.

**Bundle target**: v0.692 (single version bump).

---

## Fix 1 — `syncKillsHudFromTrackedTotals` cache check

**File**: [src/vehicles.ts:611](../src/vehicles.ts#L611)

**Current behavior**: Called every tick from the main 1Hz loop ([index.ts:126](../src/index.ts#L126)) with `force=false`. Iterates `mod.AllPlayers()` and calls `setCounterText` on `leftKillsText` + `rightKillsText` for every player every tick — regardless of whether the totals have changed. The `_force` parameter is unused. State fields `State.hudCache.lastHudScoreT1/T2` are already allocated ([state.ts:1067-1068](../src/state.ts#L1067)) but never read or written.

**Proposed change**:
```ts
function syncKillsHudFromTrackedTotals(force: boolean): void {
    if (!force
        && State.hudCache.lastHudScoreT1 === State.scores.t1TotalKills
        && State.hudCache.lastHudScoreT2 === State.scores.t2TotalKills) {
        return;
    }
    State.hudCache.lastHudScoreT1 = State.scores.t1TotalKills;
    State.hudCache.lastHudScoreT2 = State.scores.t2TotalKills;

    const players = mod.AllPlayers();
    const count = mod.CountOf(players);
    for (let i = 0; i < count; i++) {
        const p = mod.ValueInArray(players, i) as mod.Player;
        if (!p || !mod.IsPlayerValid(p)) continue;
        const pid = getObjId(p);
        const refs = State.hudCache.hudByPid[pid];
        if (!refs) continue;
        setCounterText(refs.leftKillsText, State.scores.t1TotalKills);
        setCounterText(refs.rightKillsText, State.scores.t2TotalKills);
    }
}
```

**Call-site updates**: search for `syncKillsHudFromTrackedTotals(` and confirm callers that mutate totals pass `true`. Audit candidates:
- Main loop call at [index.ts:126](../src/index.ts#L126): keep `false`.
- Admin T1/T2 total kills +/− buttons (`teamSwitchButtonEvent` in ready-dialog.ts): already pass `true`; no change.
- `OnGameModeStarted` initial seed: already passes `true`; no change.

**Risk**: None. Pattern is identical to existing `syncRoundKillsHud` ([vehicles.ts:628](../src/vehicles.ts#L628)).

**Acceptance criterion**: After ship, push a kill in-game — counter updates. Don't push a kill — counter doesn't churn. (Subjective; full validation requires instrumentation.)

## Fix 2 — Cache vehicles-alive visibility in `updateAllPlayersClock`

**File**: [src/clock.ts:166-183](../src/clock.ts#L166)

**Current behavior**: Every tick, for every player, calls `mod.SetUIWidgetVisible(refs.leftVehiclesAliveText, showVehiclesAlive)` and same for `rightVehiclesAliveText`. The `showVehiclesAlive` value rarely changes (it's `isRoundLive() && !cleanupActive && !isEnded`) — flips at most a handful of times per round.

**Proposed change**: Add a single state field, gate the per-player visibility toggle on global change:

In [state.ts hudCache type block](../src/state.ts#L1066):
```ts
hudCache: {
    lastHudScoreT1?: number;
    lastHudScoreT2?: number;
    lastHudRoundKillsT1?: number;
    lastHudRoundKillsT2?: number;
    lastVehiclesAliveVisible?: boolean;  // <-- new
    // ...
};
```

And in `State` initializer ([state.ts:~1284](../src/state.ts#L1284)):
```ts
lastVehiclesAliveVisible: undefined,
```

In [clock.ts updateAllPlayersClock](../src/clock.ts#L112), after computing `showVehiclesAlive`:
```ts
const visibilityChanged = State.hudCache.lastVehiclesAliveVisible !== showVehiclesAlive;
```

Then inside the per-player loop, gate the `SetUIWidgetVisible` calls on `visibilityChanged`:
```ts
if (refs?.leftVehiclesAliveText) {
    if (visibilityChanged) mod.SetUIWidgetVisible(refs.leftVehiclesAliveText, showVehiclesAlive);
    if (showVehiclesAlive) {
        safeSetUITextLabel(refs.leftVehiclesAliveText,
            mod.Message(mod.stringkeys.twl.hud.vehiclesAliveFormat, vehiclesAliveT1));
    }
}
if (refs?.rightVehiclesAliveText) {
    if (visibilityChanged) mod.SetUIWidgetVisible(refs.rightVehiclesAliveText, showVehiclesAlive);
    if (showVehiclesAlive) {
        safeSetUITextLabel(refs.rightVehiclesAliveText,
            mod.Message(mod.stringkeys.twl.hud.vehiclesAliveFormat, vehiclesAliveT2));
    }
}
```

After the per-player loop, alongside the existing `lastLowTimeState` / `lastDisplayedSeconds` writes:
```ts
State.hudCache.lastVehiclesAliveVisible = showVehiclesAlive;
```

**Risk**: None. Pattern identical to existing `lastLowTimeState` / `lastDisplayedSeconds` caching in the same function.

**Note on text-label deduplication**: not adding count caching in this bundle because vehicle counts can legitimately change per tick during a round (vehicle destroyed → count drops). Keeping the `safeSetUITextLabel` call unguarded.

**Acceptance criterion**: Vehicles-alive HUD appears at round-live transition, disappears at cleanup transition. Count updates live when a vehicle is destroyed.

## Fix 3 — Hoist victory-dialog gate above per-player loop

**File**: [src/clock.ts:162](../src/clock.ts#L162)

**Current behavior**: `updateAllPlayersClock` calls `updateVictoryDialogForPlayer(player, remaining)` for every player every tick. The function early-returns on `!State.match.victoryDialogActive`, but the call + pid resolution overhead still runs N times per second when the dialog isn't active (the vast majority of match time).

**Proposed change**: Hoist the gate to the outer scope so the per-player call is skipped entirely when the dialog isn't active.

Before the per-player loop:
```ts
const showVictory = State.match.victoryDialogActive;
```

Replace the unconditional call inside the loop:
```ts
// before
updateVictoryDialogForPlayer(player, remaining);

// after
if (showVictory) updateVictoryDialogForPlayer(player, remaining);
```

**Risk**: None. The gate inside `updateVictoryDialogForPlayer` is the same value; hoisting it doesn't change semantics. The defensive `triggerLazyBuild('victoryDialog', pid)` inside the function (which is also gated on `victoryDialogActive`) still fires correctly when the dialog activates because the outer-scope `showVictory` is recomputed each tick.

**Acceptance criterion**: Match-end → Victory dialog appears and ticks down normally. Mid-round → no visible regression.

## Fix 4 — Aircraft warning loop teardown sentinel

**File**: [src/ready-dialog.ts:2625-2647](../src/ready-dialog.ts#L2625)

**Current behavior**: `runAircraftWarningLoop` runs at 5Hz (every 0.2s). When `State.round.aircraftCeiling.customEnabled === false` (Vanilla mode + any map with `useCustomCeiling: false`), the entire AllPlayers iteration runs every tick just to tear down altimeter widgets that are already torn down.

**Proposed change**: Local sentinel flag inside the loop closure tracks whether teardown has already completed for the current `customEnabled === false` window.

Inside `runAircraftWarningLoop`, alongside the existing `last*ByPid` declarations:
```ts
let teardownComplete = false;
```

Replace the existing `if (!State.round.aircraftCeiling.customEnabled) { ... }` block:
```ts
if (!State.round.aircraftCeiling.customEnabled) {
    if (!teardownComplete) {
        for (const pidStr in State.players.altitudeWarningVisibleByPid) {
            const pid = Number(pidStr);
            if (State.players.altitudeWarningVisibleByPid[pid]) {
                setAltitudeWarningVisibleForPid(pid, false);
                delete lastCountdownByPid[pid];
            }
        }
        const players = mod.AllPlayers();
        const count = mod.CountOf(players);
        for (let i = 0; i < count; i++) {
            const player = mod.ValueInArray(players, i) as mod.Player;
            const pid = safeGetPlayerId(player);
            if (pid === undefined) continue;
            setAltimeterVisibleForPid(pid, false);
            setAltimeterWarningLabelVisibleForPid(pid, false);
            delete lastAltimeterTextYByPid[pid];
            delete lastAltimeterStageByPid[pid];
            delete lastWarningLabelVisibleByPid[pid];
        }
        teardownComplete = true;
    }
    continue;
}
teardownComplete = false;  // reset when custom ceiling re-enables
```

**Risk**: Low. Sentinel is local to the loop closure (no shared state). Reset path on the enable-side branch makes it self-correcting if the admin toggles `customEnabled` at runtime via ready-dialog Confirm.

**Note**: Players who join during a `customEnabled === false` window after teardown completed don't need teardown — their altimeter widgets were never built (the eager altimeter build still runs in `ensureEagerHudShellForPlayer` but `setAltimeterVisibleForPid(pid, false)` is the default state, so they start hidden anyway).

**Acceptance criterion**: Switch from Custom mode to Vanilla mode via Confirm — altimeter hides once, stays hidden. Switch back to Custom — altimeter re-appears in aircraft. No visible regression in mode-flip scenarios.

## Fix 5 — Remove `OngoingPlayer` Ready-Dialog warm-up build (formerly F7)

**File**: [src/index.ts:402-410](../src/index.ts#L402)

**Critical context**: `OngoingPlayer` fires **every engine tick per player**. The warm-up block builds the entire ~600-line Ready Dialog widget tree on the first OngoingPlayer tick per player, then immediately hides it. The `state.uiBuilt` flag prevents re-entry on subsequent ticks.

**The dogpile risk**: With N concurrent joiners, the first OngoingPlayer tick after their join fires for all N in the same engine tick. That's N × ~600 lines of `modlib.ParseUI` work in one frame — identical risk profile to the Phase A (~745 lines × N) and Phase B (~670 lines × N) bugs we just fixed. At 8 concurrent joiners that's ~4,800 lines of widget construction in a single tick on the second-to-fire frame after join. This is a CQ_Bug_40-equivalent crash window we didn't address in Phases A or B.

**Why this wasn't caught earlier**: I initially assumed `OngoingPlayer` ticks were naturally staggered across players. They aren't — engine fires the event for all players per tick.

**Proposed change**: Delete the warm-up block entirely. Ready Dialog will build on first triple-tap via the existing `createTeamSwitchUI` call in `teamSwitchInteractPointActivated`. The widget tree's own idempotent cache check ([ready-dialog.ts:191](../src/ready-dialog.ts#L191)) ensures subsequent opens are visibility-flip-only.

```ts
// Before (delete this block):
const pid = safeGetPlayerId(eventPlayer);
if (pid === undefined) return;
if (State.players.teamSwitchData[pid] && !State.players.teamSwitchData[pid].uiBuilt) {
    createTeamSwitchUI(eventPlayer);
    State.players.teamSwitchData[pid].dialogVisible = false;
    deleteTeamSwitchUI(eventPlayer);
    State.players.teamSwitchData[pid].uiBuilt = true;
}
```

The `pid` resolution call right after this block is still needed for the multi-click detector, so move that lookup down or keep it.

After-state:
```ts
export function OngoingPlayer(eventPlayer: mod.Player): void {
    if (!eventPlayer || !mod.IsPlayerValid(eventPlayer)) return;
    updateSpawnDisabledWarningForPlayer(eventPlayer);
    if (isPlayerDeployed(eventPlayer)) {
        checkTeamSwitchInteractPointRemoval(eventPlayer);
    }

    if (isPlayerDeployed(eventPlayer)) {
        if (InteractMultiClickDetector.checkMultiClick(eventPlayer)) {
            const pid = safeGetPlayerId(eventPlayer);
            if (pid === undefined) return;
            armJoinPromptTripleTapForPid(pid);
            spawnTeamSwitchInteractPoint(eventPlayer);
        }
    }
}
```

**Trade-off**: First triple-tap per player pays a ~50ms widget-build hitch (cold cache). Subsequent triple-taps remain instant (warm cache via the existing idempotent check). **Triple-taps are player-initiated and cannot dogpile** — they require 3 button presses within 2 seconds, naturally staggered across players over many seconds of gameplay. The ~50ms hitch is single-player, never concurrent.

**Risk**: Low. The only consumer of the warm-up was the warm-up itself — `state.uiBuilt` field is read nowhere else (verified via grep). Field becomes dead code; leaving it in `teamSwitchData_t` is harmless and avoids touching the state shape in this bundle.

**Acceptance criterion**:
- First triple-tap per player opens the Ready Dialog (with one-time ~50ms hitch).
- Subsequent triple-taps open instantly.
- No regression in concurrent-join scenarios (this is the actual fix — MP playtest required to fully validate).

## Cross-reference: Conquest precedent

Conquest ships an equivalent or stronger version of three of these fixes. Cross-references below validate the patterns and direction.

**Fix 5 (warm-up removal) — directly validated by Conquest's Wave 3 ship.**
Conquest had the identical pre-warm pattern (a `prebuildAllUiFamiliesHidden` call building Ready Dialog for every player on join). In v1.418 Wave 3, they **deleted** the pre-warm path rather than refactoring it. The closed bug entries [CQ_Bug_32, CQ_Bug_33](../../conquest/design_doc/conquest_issues.md) attribute the fix to ablation, not optimization. The lazy-load registry ([conquest/src/interaction/lazy-build-registry.ts:84](../../conquest/src/interaction/lazy-build-registry.ts#L84)) gates Ready Dialog with `teardownTrigger: 'roundEnd'` and builds on first interact-point activation, not on join or `OngoingPlayer`. Our Fix 5 matches the production-hardened solution.

**Fix 3 (hoist `victoryDialogActive` gate) — matches Conquest's current pattern.**
Conquest's main tick loop at [conquest/src/index/game-mode.ts:116](../../conquest/src/index/game-mode.ts#L116) already gates per-tick HUD refresh on `if (isMatchLive() && !State.match.victoryDialogActive)` at the outer scope. Our Fix 3 brings helis-only into alignment.

**Fix 4 (aircraft warning loop teardown sentinel) — cadence note.**
Conquest's equivalent `checkTakeoffLimitForAllPlayers` runs at 1Hz; helis-only's aircraft warning loop runs at 5Hz (0.2s) because the altimeter needs real-time altitude feedback. The 5× tighter cadence is intentional and correct for helis-only's aircraft-centric mode — Conquest's 1Hz wouldn't meet our UX bar. The sentinel optimization stands on its own merits regardless of cadence.

**Fix 2 (vehicles-alive visibility cache) — no direct Conquest equivalent.**
Conquest toggles HUD widget visibility on phase transitions (event-driven), not per-tick. Our per-tick caching is more conservative — it tolerates the per-tick polling pattern instead of restructuring it. Acceptable for this bundle.

**Fix 1 (kill counter cache check) — half-measure flagged.**
Conquest's KPI/scoreboard updates are **event-driven**, not per-tick polled. They subscribe to `OnPlayerEarnedKill` and increment counters at the kill site, eliminating the per-tick AllPlayers iteration entirely. Our Fix 1 caches the iteration's no-op case but keeps the polling pattern. This is the right ship for the bundle (low-risk, low-LoC) but flagged as future work: a deeper refactor toward event-driven kill counters would eliminate F1's iteration entirely. See "Out of bundle: deeper patterns" below.

## Out of bundle: deeper patterns flagged for future work

These are Conquest-validated improvements that exceed this bundle's scope. Each warrants its own plan.

**Tick-context `AllPlayers` cache (Conquest v1.219 pattern).**
Conquest caches `mod.AllPlayers()` once per subtick via `beginTickContext()` ([conquest/src/state/tick-context.ts:1](../../conquest/src/state/tick-context.ts#L1)). All `forEachValidPlayer` helpers in the same tick reuse the cached snapshot. This eliminates the redundant `mod.AllPlayers()` bridge calls across multiple per-tick helpers — exactly the F5/F6 pattern I omitted from this bundle as "requires care." Conquest shipped it as a discrete optimization with measurable wins (entry: CQ_Perf_TickContext_AllPlayers_Cache, RESOLVED v1.219). Helis-only main loop currently fires 5× `mod.AllPlayers()` per tick across its five helpers; this pattern collapses them to one.

**Event-driven kill counter (Conquest's KPI architecture).**
Conquest's `src/index/player-kpi-events.ts` increments counters at the kill site (`OnPlayerEarnedKill`) and writes directly to the HUD ref. There is no per-tick `syncKillsHud*` polling helper because there's nothing to poll — every increment is already pushed. Fix 1 brings helis-only's polled pattern into "skip when nothing changed" state; an event-driven refactor would eliminate the helper entirely. Likely a 100-200 LoC refactor with moderate risk (need to ensure every kill source increments correctly). Defer until F1 ships and proves the polling pattern is the bottleneck.

**`OngoingPlayer` baseline reduction (Conquest's `seatKind` gate).**
Conquest's [design_doc/5.12.26_conquest_ongoing_player_cost_analysis.md](../../conquest/design_doc/5.12.26_conquest_ongoing_player_cost_analysis.md) identifies a `seatKind` gate that skips the triple-tap polling for players currently in vehicles (they can't trigger the interact point anyway). Saves ~30-40% of `GetSoldierState(IsInteracting)` bridge calls. Helis-only has the same triple-tap detector path; same gate would apply. Out of scope for this bundle (touches `InteractMultiClickDetector` shape); flagged for separate work.

## Sequencing

Ship as a single bundle. No interdependencies between the five fixes. Fix order within the bundle doesn't matter; doing them in numerical order keeps the diff readable.

**Build steps**:
1. Apply Fix 1 — edit `src/vehicles.ts`.
2. Apply Fix 2 — edit `src/state.ts` (type + initializer) then `src/clock.ts`.
3. Apply Fix 3 — edit `src/clock.ts`.
4. Apply Fix 4 — edit `src/ready-dialog.ts`.
5. Apply Fix 5 — edit `src/index.ts`.
6. `npx tsc --noEmit` — confirm clean type-check.
7. Update [Changelog.ts](../src/Changelog.ts) with v0.692 entry summarizing all five fixes.
8. `npm run bumpVersion` → v0.692.
9. `npm run build` — confirm bundle passes ASCII guard + size check.

**Post-ship**:
- Solo smoke (deploy, end a round, end a match, triple-tap dialog).
- Defer MP concurrent-join playtest until convenient — Fix 5 is the load-bearing crash mitigation that requires MP validation.

## What this bundle does NOT do

- Does not change any visual layout or text.
- Does not change tick cadences (1Hz / 5Hz / 4Hz remain).
- Does not introduce or remove any lazy-build registry surfaces.
- Does not touch Phase C (Ready Dialog / Admin Panel registry routing — still deferred).
- Does not address the broader per-tick baseline cost of `OngoingPlayer` (sustained SoldierState bridge calls per player per tick) — Conquest's `seatKind` gate is the next step here; flagged above.
- Does not hoist `mod.AllPlayers()` into a per-tick cached snapshot — Conquest's `beginTickContext()` pattern is the next step; flagged above.
- Does not refactor kill counters to event-driven — Conquest's KPI architecture is the next step; flagged above.
- Does not clean up the now-dead `uiBuilt` field on `teamSwitchData_t` — left in place to keep this bundle minimal.
