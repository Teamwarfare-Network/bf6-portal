## 1. Goal + locked design

Add a **"Soldier HP %"** slider to the Ready Dialog that scales each soldier's max health by a configurable multiplier, to make players tankier on foot. It must **work identically to the Vehicle Health slider** (4 buttons + value, confirm-only, flip-to-Custom, per-map default, world-log, HUD summary line), and sit **directly above** the Vehicle Health slider, on the **Game Mode row**, aligned in the same far-left columns.

| Decision | Value | Mirrors |
|---|---|---|
| Label / value text | "Soldier HP: {0}%" | `modeSettingVehicleHealthFormat` = "Vehicle HP: {0}%" |
| Storage | float multiplier `soldierHpMultiplier`; UI shows `Math.round(mult*100)` | `vehicleHealthMultiplier` |
| Range / steps | MIN `0.05` (5%), MAX `5.0` (500%), fine STEP `0.01`, coarse `0.10`, DEFAULT `1.0` | engine allows max HP 1..500; `SetPlayerMaxHealth` arg lands in 5..500. NOTE: MAX is **5.0**, not VH's 4.0 -- soldiers are not subject to the vehicle 400% cap |
| 4 buttons | `[-10] [<] Soldier HP: NNN% [>] [+10]` | identical widget block |
| Apply timing | **confirmed-only** | VH |
| Apply scope | **next deploy / next life** (already-alive soldiers keep current HP) | analogous to VH "new spawns only" |
| **Apply site** | `OnPlayerDeployed` (per-Player), NOT `OnVehicleSpawned` | THE structural difference -- see section 3.9 |
| Game-mode interaction | manual change -> flip to Custom; preset select -> reset to map/preset default | VH |
| Per-map default | `MapConfig.defaultSoldierHpMultiplier?` wired now; all maps `1.0` | VH |
| Preset default | all presets = map default (no Ladder override for now) | VH had Ladder=1.6; we keep soldier flat at 1.0 unless operator tunes |
| Reset / Fresh Setup | preserves confirmed value | VH |
| HUD summary | always-show "Soldier HP: NNN%" line | VH |
| World-log on confirm | "{Player} changed the Soldier HP to NNN%" | `vehicleHealthChanged`; wrap `changedBy` via `safePlayerArg` |

## 2. API reference (verified, SDK 1.3.1)

- **`mod.SetPlayerMaxHealth(player, maxHealth)`** -- [index.d.ts:26691](../../reference_sdk_1.3.1/code/types/mod/index.d.ts#L26691). Doc: "Sets the max health of a target player **from 1 to 500**. The value will be multiplied by the target's max health multiplier." This is the **engine limit**: absolute max HP is clamped to **[1, 500]**. Against vanilla base 100 that is a **1%..500%** effective range -- i.e. soldiers can go meaningfully tankier than vehicles (capped at 400% by `SetVehicleMaxHealthMultiplier`'s `<=4` clamp). There is **no** `SetPlayerMaxHealthMultiplier` setter for players (only the vehicle one exists), so we emulate the multiplier in JS: `Math.round(SOLDIER_BASE_MAX_HEALTH * mult)` with `SOLDIER_BASE_MAX_HEALTH = 100`; the engine's 1..500 clamp is the hard backstop if `mult` ever drifts out of our own 0.05..5.0 bounds.
- **`mod.Heal(player, healAmount)`** -- [index.d.ts:26530](../../reference_sdk_1.3.1/code/types/mod/index.d.ts#L26530). **Mandatory follow-up:** `SetPlayerMaxHealth` raises the ceiling but does NOT refill current health -- the same race the vehicle feature hit in v0.714 ([Changelog.ts:161-169](../src/Changelog.ts#L161)). `Heal(player, 99999)` clamps-to-max and closes it. There is no `SetPlayerCurrentHealth`.
- Verification reads (smoke test): `mod.GetSoldierState(player, mod.SoldierStateNumber.MaxHealth)` and `.CurrentHealth` ([index.d.ts:25370](../../reference_sdk_1.3.1/code/types/mod/index.d.ts#L25370)) -- confirm base is 100 at 100% and scales as expected.

```ts
// Soldier HP multiplier: apply on each deploy (per-Player, resets every life). SetPlayerMaxHealth
// raises the ceiling but does NOT refill current health (same race the vehicle path hit in v0.714),
// so Heal afterward lifts current to the new max. Guard on != 1.0: a fresh soldier already defaults
// to SOLDIER_BASE_MAX_HEALTH, so 100% needs no engine call. try/catch per SDK-safety convention.
try {
    const hpMult = State.round.modeConfig.confirmed.soldierHpMultiplier ?? 1.0;
    if (hpMult !== 1.0) {
        mod.SetPlayerMaxHealth(eventPlayer, Math.round(SOLDIER_BASE_MAX_HEALTH * hpMult)); // engine clamps 1..500
        mod.Heal(eventPlayer, 99999);
    }
} catch (_e) {}
```
**Why this site:** `OnPlayerDeployed` runs per-life, after deploy is confirmed, and already issues `AddEquipment` writes here. Confirmed-only + next-life semantics fall out for free -- already-alive soldiers are untouched until they next deploy.

### 10.B Engine-behavior uncertainties to verify early

5. **SDK doc string is ambiguous about a hidden multiplier.** [SetPlayerMaxHealth SDK doc](../../reference_sdk_1.3.1/code/types/mod/index.d.ts#L26691): "Sets the max health of a target player from 1 to 500. **The value will be multiplied by the target's max health multiplier.**" The second sentence implies the engine maintains its own per-player max-HP multiplier on top of the value we pass. We don't know what that value is by default, whether class loadout / gadgets touch it, or whether it's stable across deploys. **Smoke test #2 (read MaxHealth at 100%) is load-bearing -- if base reads anything other than 100, the SOLDIER_BASE_MAX_HEALTH constant assumption is wrong** and every other multiplier maps non-linearly. Run #2 before #3.
6. **OnPlayerDeployed event reliability.** Memory note `project_engine_event_reliability_asymmetric`: events drop under load (we caught `OnPlayerEnterVehicle` doing this). If `OnPlayerDeployed` drops for a fresh deploy, that life gets vanilla 100 HP silently. Acceptance posture is fine -- player just gets a baseline life and the next deploy fixes it -- but worth calling out in the smoke test acceptance criteria. No need to add a polled fallback yet.
7. **SetMax then Heal race.** Vehicle HP v0.714 went through this exact failure mode. Plan correctly mirrors the fix (raise ceiling -> Heal to top off), but the two calls are in one try/catch. If `SetPlayerMaxHealth` succeeds and `Heal` then throws, the soldier deploys at base 100 HP with a 200-cap -- not a bug, just a slightly soft entrance. Worth noting in the smoke test #3 acceptance: "spawns at or near new max". Not a blocker.
