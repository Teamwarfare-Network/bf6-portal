# Helis Lazy-Load HUD Refactor Plan

**Date**: 2026-05-30
**Goal**: Defer HUD widget construction so OPJG (player join) does almost no widget work. Spread heavy `modlib.ParseUI` calls across staged timers and on-demand triggers, mirroring Conquest's Wave 3 lazy-build infrastructure.

**Origin**: Script-termination crash when multiple players join simultaneously. The BF6 Portal sandbox enforces a **~1000ms per-frame engine evaluation budget**; when concurrent OPJG handlers each execute heavy synchronous widget construction in the same engine tick, the per-frame instruction count exceeds the budget and the script is terminated (engine error: `Mod has reached its js script memory usage limit` or the equivalent eval-time termination). Conquest documents this as **CQ_Bug_40** (frame-budget breach) and their Wave 3 lazy-build infrastructure was built specifically to defeat it. Helis hits the same wall: `ensureHudForPlayer` runs ~1,800 lines of widget construction during OPJG. A 5-player simultaneous join means 5× that work in the same tick → dogpile → termination.

**Note**: This is NOT `H_Bug_1` (the 2 "Received undefined values as arguments" engine errors on MP join — that's cosmetic and unrelated, see [heli_issues.md](./heli_issues.md)). The crash bug is a separate frame-budget/instruction-count issue with no current `H_Bug_N` entry. Recommend logging it as `H_Bug_3` (or next available) when this plan ships Phase 0.

**Why lazy loading fixes it**: spreading widget construction across multiple frames means no single frame exceeds the 1000ms budget regardless of how many players join at once. Conquest's staged-trigger pattern (topHudShell @ +0ms, vehicleDeployTimer @ +50ms, combatHud @ +150ms, etc.) is the proven antidote at 16+ players.

**Constraint** (user-specified): EAGER stays for:
- Branding upper-left (`Upper_Left_Container_`)
- Settings summary upper-left (`Upper_Left_Settings_`)
- Tutorial join prompt (triple-tap explainer; already lazy via `shouldShowJoinPromptForPlayer`)

Everything else lazy.

## REVISED EXECUTION ORDER — added 2026-05-30 mid-flight

After Phase 0 shipped, I (Claude) audited the actual Helis source structure and found two architectural facts that change how Phases 1-5 should be sequenced:

### Finding 1: Helis's Victory + Round-End dialogs are NOT separate dialogs

In Helis, the Round-End modal (`RoundEndDialogRoot_${pid}`) is built at [hud.ts:2027](../src/hud.ts#L2027) and the Victory modal (`VictoryDialog_*`) starts at [hud.ts:2112](../src/hud.ts#L2112) — both **nested directly inside `ensureHudForPlayer`'s function body**, NOT in separate files like Conquest. They share `refs.roots[]` for cleanup and share `State.hudCache.hudByPid[pid]` for ref storage. So Phase 3 + Phase 4 are extractions *out of* `ensureHudForPlayer`, not new-file builds.

The update functions (`updateVictoryDialogForPlayer` [hud.ts:568](../src/hud.ts#L568), `updateRoundEndDialogForPlayer` [hud.ts:836](../src/hud.ts#L836)) already defensive-check every ref — so deferring construction is safe: pre-build updates just become no-ops.

### Finding 2: Ready Dialog + Admin Panel are ALREADY lazy

- `createTeamSwitchUI` is only called from `teamSwitchInteractPointActivated` (triple-tap interact point). It has its own idempotent cache check at [ready-dialog.ts:191-199](../src/ready-dialog.ts#L191-L199).
- `ensureAdminPanelWidgets` is only called from the admin toggle button. Same pattern.

Phase 1 + Phase 2 in the original plan are therefore **bookkeeping refactors** (registry routing + layout-version invalidation hook) with **zero frame-budget improvement**. Real value, but should ship LAST, not first.

## Why the altimeter saga matters for this refactor

v0.666–v0.685 we spent ~20 versions getting the altimeter to render where its position constants said. Root causes we hit:
- `modlib.ParseUI` widgets persist across script reloads; lazy-build idempotent paths returned the existing widget without re-applying position
- Negative child positions appear to clip silently in this engine
- Position constants only applied at first construction, never re-applied on idempotent re-entry

v0.686 fixed it by adding `SetUIWidgetPosition` calls to the idempotent path. **Conquest bakes this fix into every widget by default** via its `ensureHudContainer/Text/Image` helpers, which always call `SetUIWidgetParent + Anchor + Position + Size + Depth` regardless of whether the widget was just created or already existed.

The Foundation phase below ports these helpers to Helis so the lazy-build pattern doesn't repeat the altimeter mess across every widget.

## Phase 0: Foundation (no behavior change)

Build infrastructure. No widget converted yet. Safest possible commit — adds helpers without touching widget behavior.

### Deliverables

1. **`safeParseUI({...})`** — try/catch wrapper around `modlib.ParseUI`. Returns the widget on success, undefined on failure. Conquest has this; Helis doesn't.

2. **`wn(base: string, pid: number, suffix?: string|number): string`** — widget name helper. Conquest's pattern: `wn("VictoryDialog_Restart", pid)` produces `"VictoryDialog_Restart_<pid>"`. Cleaner than `BASE_ID + pid` everywhere.

3. **`ensureHudContainer(player, name, parent, anchor, x, y, w, h)`** — atomic per-widget builder.
   ```ts
   let widget = safeFind(name);
   if (!widget) widget = safeParseUI({ name, type: "Container", playerId: player, position: [x, y], size: [w, h], anchor, visible: false, padding: 0, bgAlpha: 0, bgFill: mod.UIBgFill.None }) ?? safeFind(name);
   if (!widget) return undefined;
   try {
       mod.SetUIWidgetParent(widget, parent);
       mod.SetUIWidgetAnchor(widget, anchor);
       mod.SetUIWidgetPosition(widget, mod.CreateVector(x, y, 0));
       mod.SetUIWidgetSize(widget, mod.CreateVector(w, h, 0));
       mod.SetUIWidgetDepth(widget, mod.UIDepth.AboveGameUI);
   } catch { return undefined; }
   return widget;
   ```

4. **`ensureHudText(player, name, parent, anchor, x, y, w, h, textSize, label, color, textAnchor)`** — same shape for Text widgets. Adds `SetUITextSize`, `SetUITextAnchor`, `SetUITextLabel`, `SetUITextColor` after the standard re-applies.

5. **`ensureHudImage(player, name, parent, anchor, x, y, w, h, imageType, imageColor, imageAlpha)`** — same shape for Image widgets.

6. **`LAZY_BUILD_REGISTRY`** — declarative config:
   ```ts
   type LazyBuildSurfaceName = 'readyDialog' | 'adminPanel' | 'victoryDialog' | 'roundEndDialog' | 'topHud' | 'altimeter';
   interface LazyBuildConfig {
       name: LazyBuildSurfaceName;
       teardownTrigger: 'disconnect' | 'roundEnd' | 'matchEnd' | 'menuClose' | 'never';
   }
   ```
   Skip Conquest's `serializesWith` mutex and `pacedOpsPerTick` for v1 — Helis is ≤8 players, less contention than Conquest's 16p.

7. **`triggerLazyBuild(name, pid)`** — dispatcher with:
   - Re-entrancy guard (`_lazyBuildInFlightByName[name].has(pid)` → early return)
   - Disconnect guard (`safeFindPlayer(pid)` → early return)
   - Error counter + console log on throw
   - `finally` block releases the in-flight set

8. **`_resolveLazyBuildHandler(name, eventPlayer, pid)`** — switch returning the per-surface builder closure. Stub all surfaces to no-ops for Phase 0; later phases fill them in.

### Ship criteria
- Build passes
- No widget visually changed
- No regression in existing flows
- Helpers are documented but unused (later phases consume them)

### Files touched
- `src/foundation/safe-parse-ui.ts` (new)
- `src/foundation/widget-name.ts` (new) — exports `wn`
- `src/hud-helpers/ensure-hud-widgets.ts` (new) — exports `ensureHudContainer/Text/Image`
- `src/lazy-build/registry.ts` (new) — exports `LAZY_BUILD_REGISTRY`, `triggerLazyBuild`
- `src/Changelog.ts` — v0.6XX entry

## Phase 1: Ready Dialog (your priority)

The Ready Dialog is the highest-value first conversion:
- Already triggered by an interaction (triple-tap), not by join → clean lazy trigger point
- Single open path (`teamSwitchInteractPointActivated` → `createTeamSwitchUI`)
- Self-contained: widget IDs namespaced `UI_READY_DIALOG_*` and `UI_TEAMSWITCH_*` — no cross-cutting concerns
- Largest single user-facing UI to validate the pattern

### Deliverables

1. **`READY_DIALOG_LAYOUT_VERSION = 1`** constant. Bump on any layout change.

2. **`isReadyDialogUiCacheUsableForPid(pid: number): boolean`** — checks:
   - `state.uiBuilt === true`
   - `state.uiLayoutVersion === READY_DIALOG_LAYOUT_VERSION`
   - `safeFind(UI_TEAMSWITCH_CONTAINER_BASE_ID + pid)` is truthy

3. **`ensureReadyDialogUiBuiltHidden(player)`** — builds the entire dialog tree HIDDEN (idempotent):
   - Find-or-construct path; if layout version mismatch, destroy first
   - Refactors all the `mod.AddUIContainer / mod.AddUIText / modlib.ParseUI` calls inside `createTeamSwitchUI` to use the new `ensureHud*` helpers (this is where nested `children: [...]` trees get flattened to per-widget atomic calls)
   - Sets `state.uiBuilt = true`, `state.uiLayoutVersion = READY_DIALOG_LAYOUT_VERSION`
   - Returns the container base widget (or undefined)

4. **`showReadyDialogUI(player)`** — pure visibility flip:
   - Calls `ensureReadyDialogUiBuiltHidden` first (idempotent — usually a no-op if already built)
   - Refresh content (roster, ready button, mode config, map label) via existing helpers
   - `finalizeReadyDialogVisibility(eventPlayer, pid, containerBase, true)`
   - Sets `state.dialogVisible = true`

5. **`hideReadyDialogUI(playerOrPid)`** — pure visibility flip (no destruction):
   - `setReadyDialogChromeVisible(pid, false)`
   - Sets `state.dialogVisible = false`

6. **`destroyReadyDialogUI(playerId)`** — hard delete:
   - DeleteUIWidget on all chrome IDs + admin panel widgets
   - Resets `state.uiBuilt = false`, `state.adminPanelBuilt = false`
   - Used when layout version mismatches or player leaves

7. **`invalidateHiddenReadyDialogCacheForPid(pid)`** — destroys the hidden cache (only when dialog is closed):
   - If `dialogVisible` → return (don't destroy a visible dialog)
   - Else call `destroyReadyDialogUI`
   - Forces next open to rebuild from fresh state

8. **`invalidateHiddenReadyDialogCacheForAllPlayers()`** — called from state-change owners:
   - Mode config confirm (`confirmReadyDialogModeConfig`)
   - Matchup change (`applyMatchupPresetInternal`)
   - Roster change (player join/leave/team-swap)
   - Map config change (`applyMapConfig`)
   - This ensures cached hidden dialogs reflect current state on next open

9. **Registry entry**: `readyDialog` with `teardownTrigger: 'roundEnd'`

10. **Hook the trigger**: in `teamSwitchInteractPointActivated`:
    ```ts
    // OLD: createTeamSwitchUI(eventPlayer);
    triggerLazyBuild('readyDialog', playerId);
    showReadyDialogUI(eventPlayer);
    ```

11. **Update OPJG path**: remove any eager ready-dialog construction (currently none — already lazy via `createTeamSwitchUI` triggered by triple-tap). Just verify nothing in `ensureHudForPlayer` references ready-dialog widgets.

### What's saved
- First triple-tap pays a one-time ~50-100ms hitch (the cold build)
- Subsequent opens are pure visibility flips (~0ms)
- Closed-dialog rebuilds only happen when relevant state changes
- OPJG saves nothing directly (Ready Dialog was already lazy), but the pattern is proven for Phases 3-7

### Risk
**Medium**. The triple-tap path is well-isolated, but the dialog has admin-panel sub-widgets and the existing `createTeamSwitchUI` function is ~600 lines. The flattening from nested `children: [...]` to per-widget `ensureHud*` calls is the largest mechanical change.

### Files touched
- `src/ready-dialog/lifecycle.ts` (new) — exports invalidation/destroy/show/hide helpers
- `src/ready-dialog/build.ts` (new) — exports `ensureReadyDialogUiBuiltHidden`
- `src/team-switch.ts` — updates `teamSwitchInteractPointActivated` to use trigger + show; keeps existing `createTeamSwitchUI` as a wrapper around `ensureReadyDialogUiBuiltHidden + showReadyDialogUI` during transition
- `src/lazy-build/registry.ts` — wires `_resolveLazyBuildHandler('readyDialog', ...)`
- `src/state.ts` — adds `uiLayoutVersion?: number` to `teamSwitchData_t`

### Ship criteria
- Triple-tap opens the dialog same as before
- Closing and reopening shows current state (roster, config) correctly
- Layout version bump (manual test: change READY_DIALOG_LAYOUT_VERSION from 1 to 2, observe dialog rebuild on next open)
- Admin button toggle still works
- No regression in mode config / matchup / ready / swap flows

## What this DOESN'T do

- Doesn't add the loading-overlay UX (Conquest deleted theirs in Ship 8 — we skip it; ≤8p Helis doesn't need it)
- Doesn't add Conquest's mutex/pacer machinery (overkill for ≤8 players, less concurrent build contention)
- Doesn't add `FEATURE_PERF_DIAG` telemetry counters (can layer in after Phase 8 if useful)
- Doesn't change anything about widget LOOK or POSITION (Phases 0-7 are visually behavior-preserving — only WHEN widgets are constructed changes, not HOW they look)
- Doesn't try to fix `H_Bug_1` (the cosmetic "Received undefined values" errors — separate bug, unrelated to the frame-budget crash this plan targets)
- Doesn't add Conquest's heavy-build mutex (`serializesWith`) — Helis is ≤8p so concurrent heavy builds are rare; if frame-budget breaches re-appear after Phase 5, we'd port the mutex from `conquest/src/interaction/build-pacer.ts` as a follow-up

## Testing checklist per phase

Every phase ships with:
- [ ] Bundle compiles
- [ ] Postbuild ASCII guard passes
- [ ] Bundle size hasn't grown excessively (>20KB ⇒ investigate)
- [ ] Manual in-game test: join → deploy → enter aircraft → check all converted widgets render correctly
- [ ] Manual edge case: bump the corresponding `LAYOUT_VERSION` constant by 1 in source → rebuild → verify widget rebuilds on next show
- [ ] Manual edge case: closed-dialog state change (Phase 1+ only) → verify next open reflects new state
- [ ] Confirm no console errors in standalone test

Frame-budget crash check (after Phase 5+ ships — the load-bearing test):
- [ ] **Concurrent join burst test**: simulate ≥4 simultaneous joins in MP (or use admin debug joins / map-cycle to reproduce). Pre-Phase-5: script terminates with `Mod has reached its js script memory usage limit` or equivalent eval-budget breach. Post-Phase-5: all joiners load cleanly, no termination, no console errors related to frame budget.
- [ ] Single-frame OPJG instruction count audit: console-log timing inside OPJG before and after — a single OPJG should land well below 200ms post-refactor (vs ~500-800ms pre-refactor). Headroom for 5 concurrent joins = 5 × 200ms = 1000ms exactly at the budget; ideal target is 5 × 100ms = 500ms with 2× safety margin.
