# Plan A5: `mod.Message` 3-Format-Arg Limit — Audit + Guardrail

**Status**: Drafted 2026-05-27 (pending review + approval).
**Scope**: Document the SDK-imposed 3-format-arg cap on `mod.Message`, catalog every Helis call site currently at saturation, prescribe workaround patterns when more dynamic data is needed, and propose a build-time / authoring-time guardrail.

> First action per [`AGENTS.md`](../AGENTS.md): read [`AGENTS.md`](../AGENTS.md) banned-patterns section.

---

## Context

`mod.Message` is the engine-side constructor for any text that ships to a UI widget, world log, or notification. Its SDK signature [bf6-portal-mod-types/index.d.ts:2667-2674](../node_modules/bf6-portal-mod-types/index.d.ts#L2667) defines exactly four overloads:

| Total args | Format args | Signature |
|---|---|---|
| 1 | 0 | `mod.Message(msg)` |
| 2 | 1 | `mod.Message(msg, msgArg0)` |
| 3 | 2 | `mod.Message(msg, msgArg0, msgArg1)` |
| 4 | 3 | `mod.Message(msg, msgArg0, msgArg1, msgArg2)` |

**There is no overload for `msgArg3` or higher.** Passing 5+ arguments either silently drops the extras (in the best case) or triggers a runtime engine error.

Empirical evidence: every format template in both `strings.json` files (Helis and Conquest) uses at most `{2}` — no `{3}` or higher placeholder exists across either project. This is a hard SDK constraint, not a stylistic convention.

This plan was triggered by a user report (2026-05-27): "We're trying to show a world log with more than 3 parameters."

### Wrapper signatures already cap at 3

The 4 `broadcast*StringKey` helpers in [round-flow.ts:18-82](../src/round-flow.ts#L18) take `(stringKey, arg0?, arg1?, arg2?)` and explicitly branch through the four overloads. This is the correct shape — they cannot be called with 5 args at the type level. **No changes needed to the wrappers themselves.**

### Conquest comparison

Same scan against [conquest/src/](../../conquest/src/) — **zero violations**, zero 4-format-arg calls. The 3-format-arg ceiling is a project-wide invariant in both codebases.

## Current state assessment

**There is no existing 4+ format arg violation in Helis source as of v0.633.** If the user is seeing an engine error related to "more than 3 parameters," the source is one of:

1. **An in-progress edit** that adds a 4th format arg to one of the saturated sites or templates. Open candidates: any recently-touched call in the audit table above.
2. **A new `strings.json` template** with a `{3}` (or higher) placeholder, paired with a call site passing 4+ format args.
3. **A wrapper bypass** — code calling `mod.Message` directly with too many args, sidestepping the `broadcast*StringKey` helpers.
4. **Misattribution** — the engine error has a different root cause (e.g., undefined arg per A1, or a different mod.* call entirely).

This plan assumes the user wants both an audit (now) and a guardrail (going forward) so the constraint cannot be re-violated quietly.

## Conquest reference patterns for >3 dynamic fields

When a message must convey more than 3 dynamic fields, Conquest uses one of three patterns. Helis should adopt the same vocabulary.

### Pattern 1 — Sequential messages

Split the long message into two `mod.DisplayHighlightedWorldLogMessage` (or notification) calls. Each call's `mod.Message` stays under the cap. The two lines appear adjacent in the log surface.

Example: instead of "Player X destroyed Y's vehicle for Team Z, scoring round kill #N (overtime)", emit two lines:
- Line 1: "Player X destroyed Y's vehicle" (key + 2 format args)
- Line 2: "Team Z round kill #N (overtime)" (key + 3 format args)

Trade-off: visual fragmentation, 2 log slots consumed. World log holds at most 4 lines; this is acceptable for rare events but not for high-frequency notifications.

### Pattern 2 — Reduce dimensionality (combine fields)

Pre-combine two related fields into a single string before passing. Common case: a "record" tuple `(wins, losses, ties)` already gets passed as 3 fields to `roundRecordFormat` — to convey "Team Z record: 2-1-0", the template uses `{0} - {1} - {2}` and the call passes 3 args. To extend with a 4th field (e.g., team name), instead of `{0} {1} - {2} - {3}`, build the record-string client-side using a sub-template:

```ts
// Bad — exceeds limit
mod.Message(extendedFormat, teamName, wins, losses, ties);

// Good — pre-combine then pass 2 args
const recordStr = renderRecord(wins, losses, ties);  // returns mod.Message
mod.Message(teamRecordFormat, teamName, recordStr);
```

Caveat: pre-combining only works at the engine layer if the helper returns a `mod.Message`, not a plain string. `mod.Message` accepts `string | number | Player` as args — passing a sub-`mod.Message` is explicitly banned per project memory `reference_portal_message_api` ("NOT nested Message objects"). The practical alternative is to add a dedicated string-key template for each combined form.

### Pattern 3 — Stage via a notification + a follow-up worldlog

For result-summary messages (round-end, victory), use the dedicated dialog UI surfaces (round-end dialog, victory dialog) which support arbitrary content via individual text widgets. The world log is for short transient messages — if the data doesn't fit in 3 fields, the world log is the wrong surface.

This is the pattern Helis already uses for round-end / victory data (see [hud.ts](../src/hud.ts) victory dialog widgets at lines ~488-660).

## Proposed guardrails

Three options, ranked by build-time effort:

### Guardrail A — Comment-only update to AGENTS.md (XS)

Add to [AGENTS.md](../AGENTS.md) `## mod.Message String Key Requirement` section:

```markdown
7. **`mod.Message` accepts AT MOST 3 format arguments** (`msgArg0`, `msgArg1`, `msgArg2`).
   The SDK signature in `bf6-portal-mod-types/index.d.ts:2667-2710` overloads stop at
   3 format args. Passing 4+ silently drops extras or fires a runtime engine error.
   `strings.json` templates correspondingly cap at `{2}` — no `{3}` placeholder exists
   in either Helis or Conquest source.
8. When you need to convey more than 3 dynamic fields in one message, use one of:
   - Sequential messages (2 lines back-to-back).
   - Combine fields client-side into a single string before passing.
   - Stage via a dedicated dialog UI surface (round-end / victory) instead of world log.
```

### Guardrail B — Typed wrapper helper (S)

Add a strict typed helper in [state.ts](../src/state.ts) that callers must use instead of raw `mod.Message`:

```ts
// Type-safe wrapper around mod.Message. Compile-time check that no caller passes
// more than 3 format args (SDK limit per bf6-portal-mod-types index.d.ts:2667-2710).
function msg(key: number): mod.Message;
function msg(key: number, a0: string | number | mod.Player): mod.Message;
function msg(key: number, a0: string | number | mod.Player, a1: string | number | mod.Player): mod.Message;
function msg(key: number, a0: string | number | mod.Player, a1: string | number | mod.Player, a2: string | number | mod.Player): mod.Message;
function msg(key: number, a0?: any, a1?: any, a2?: any): mod.Message {
    if (a0 === undefined) return mod.Message(key);
    if (a1 === undefined) return mod.Message(key, a0);
    if (a2 === undefined) return mod.Message(key, a0, a1);
    return mod.Message(key, a0, a1, a2);
}
```

Then a migration pass replaces all 19 direct `mod.Message(...)` call sites in the audit table with `msg(...)`.

**Caveat**: Helis uses `// @ts-nocheck` in every source file. Overloads provide IntelliSense but **do not** prevent over-call at compile time under `@ts-nocheck`. Effectiveness of this guardrail is reduced.

### Guardrail C — Build-time linter check in `scripts/postbuild.js` (M)

Add a static check to `scripts/postbuild.js` that fails the build if any `mod.Message(` call has 5+ top-level args in the emitted bundle. Pattern: AST scan or comma-depth-counting over the bundle.

**Caveat**: complex implementation against unstructured concatenated bundle output. False positives possible.

### Recommendation

**Land Guardrail A only**, defer B and C unless violations are observed. Guardrail A is the lowest-cost defense and gives future contributors the rule explicitly. Guardrails B and C have diminishing returns given `@ts-nocheck` and bundle-text complexity.
