# Matchup + Players Per Side → Pending/Confirmed Flow

**Date**: 2026-06-01
**Status**: USER-APPROVED. User confirmed combined single-version ship (v0.732). Plan stored before implementation begins.

**Origin**: v0.731 fixed `isHeliGameMode` to return `true` unconditionally (B from the prior options) but the user observed two follow-on symptoms after live testing:

1. "All Helis - BF6 Vanilla" cycler-preview showed two Little Birds instead of an Eurocopter at slot 2.
2. "Restart / Fresh Setup" failed to teleport newly-spawned Little Birds (they slipped past `sinkAndDestroyAllEmptyVehiclesForRestart`).

Root cause for both: `applyReadyDialogModePresetForGameMode` force-spawns vehicles during cycler navigation, BEFORE the user clicks Confirm. Pre-Confirm spawn race uses stale `slot.vehicleType` from the previously-confirmed mode and creates orphans that race with cleanup. User proposal: "graduate the player and vehicle counts as mode configurations, which only apply once you press confirm."

User direction (verbatim):
- "Go ahead with making the vehicle counts and player counts to proper mode toggles, complete with red and green behavior."
- "Make a plan for this, since this is a big architectural change."
- "Is it really necessary to bundle into two builds? What risk is there by combining?"

User answer on phasing: combined single-version ship is preferred. Splitting would leave a broken interim (setters write pending, UI reads live) — same risk-reduction can be achieved by build-checkpointing within a single version.

---

## Goal

Promote `matchupPresetIndex` (vehicles per side) and `autoStartMinActivePlayers` (players per side) into the same pending/confirmed pattern that `aircraftCeiling`, `vehicleHealthMultiplier`, `soldierHpMultiplier`, and `vehicleIndexT1/T2` already use. Side effects (spawn enablement, slot force-spawn, kills-target update) fire only on Confirm. Both rows in the Ready Dialog get red/green dirty-state coloring matching the rest.

## What's wrong today

These two settings bypass the pending/confirmed dichotomy:

| Setting | Pending field | Confirmed field | Setter behavior |
|---|---|---|---|
| `aircraftCeiling` | `modeConfig.aircraftCeiling` | `modeConfig.confirmed.aircraftCeiling` | Pending only; effect on Confirm |
| `vehicleHealthMultiplier` | same pattern | same pattern | Pending only; effect on Confirm |
| `soldierHpMultiplier` | same pattern | same pattern | Pending only; effect on Confirm |
| `vehicleIndexT1/T2` | same pattern | same pattern | Pending only; effect on Confirm |
| **`matchupPresetIndex`** | **(none — direct `State.round.matchupPresetIndex`)** | **(none)** | **Immediate force-spawn** ← outlier |
| **`autoStartMinActivePlayers`** | **(none — direct `State.round.autoStartMinActivePlayers`)** | **(none)** | **Immediate live state change** ← outlier |

The two outliers are the source of the spawn-race symptoms. Promoting them removes the race.

## Phases (logical, but shipped as one v0.732 build)

### Phase 1 — schema additions

[types.ts](../src/types.ts) `ReadyDialogModeConfig`:
- Pending: `matchupPresetIndex: number`, `autoStartMinActivePlayers: number`
- Confirmed (nested): same two fields

[state.ts](../src/state.ts) modeConfig literal: seed both pending and confirmed from `DEFAULT_MATCHUP_PRESET_INDEX` and `DEFAULT_AUTO_START_MIN_ACTIVE_PLAYERS`.

[config.ts](../src/config.ts) `applyMapConfig`: no change (these don't reset per-map).

Live state `State.round.matchupPresetIndex` and `State.round.autoStartMinActivePlayers` remain — they continue to drive game logic (spawner enablement, auto-start gate, kills target). The new fields are the *previewed* knobs.

### Phase 2 — setter refactor ([ready-dialog.ts](../src/ready-dialog.ts))

Split each setter into pending-mutator + live-applier:

**`applyMatchupPreset(index, eventPlayer)`** (user-facing cycler `+/-` handler):
- Old: mutates `State.round.matchupPresetIndex`, sets `State.round.killsTarget`, calls `applySpawnerEnablementForMatchup(index, true)`, emits announce log.
- New: clamps `index` and mutates `modeConfig.matchupPresetIndex` only. Keep the `MATCHUP_CHANGE_COOLDOWN_SECONDS` cooldown (still throttles UI flicker / spam). Drop the spawn. Drop the announce log (moves to Confirm).

**`applyMatchupPresetToLiveState(index)`** (new internal helper):
- The OLD `applyMatchupPresetInternal` body. Mutates `State.round.matchupPresetIndex`, sets `State.round.killsTarget = preset.roundKillsTarget`, calls `applySpawnerEnablementForMatchup(index, true)`. Called only from Confirm and `applyReadyDialogModePresetForGameMode`'s subsequent flow path.

**`setAutoStartMinActivePlayers(value, eventPlayer)`**:
- Old: clamps + mutates `State.round.autoStartMinActivePlayers`, then `updateMatchupReadoutsForAllPlayers()` and `tryAutoStartRoundIfAllReady(eventPlayer)`.
- New: clamps + mutates `modeConfig.autoStartMinActivePlayers` only. Drop the auto-start trigger (moves to Confirm). Keep the readouts update so the dialog shows the pending value immediately.

**`applyReadyDialogModePresetForGameMode(gameModeKey)`** (preset apply on game-mode cycler):
- Old: calls `applyMatchupPresetInternal(getPresetMatchupIndexForGameMode(gameModeKey), undefined, false, true)` and mutates `State.round.autoStartMinActivePlayers` directly.
- New: mutates `modeConfig.matchupPresetIndex` and `modeConfig.autoStartMinActivePlayers` directly. No spawn. No live-state change. Just sets pending values like every other preset field.

### Phase 3 — Confirm-time application

In `confirmReadyDialogModeConfig`, after `cfg.confirmed = { ... }` snapshot block:

1. Capture `confirmedMatchup = cfg.confirmed.matchupPresetIndex`, `confirmedPlayers = cfg.confirmed.autoStartMinActivePlayers`.
2. `refreshVehicleSpawnSpecsFromModeConfig()` — already exists. Rewrites `TEAM1/2_VEHICLE_SPAWN_SPECS` from confirmed cycler indices.
3. `applyVehicleSpawnSpecsToExistingSlots()` — already exists. Rewrites `slot.vehicleType` for every spawner. **MUST run before step 4** so newly-enabled slots have correct vehicle types.
4. `applyMatchupPresetToLiveState(confirmedMatchup)` — applies the matchup row to live state, enables/disables slots, force-spawns newly-enabled ones with correct types.
5. `State.round.autoStartMinActivePlayers = confirmedPlayers` — applies the auto-start gate.
6. `updateMatchupReadoutsForAllPlayers()` — sync UI to live values.
7. Emit announce logs if pending differs from previous-confirmed (matchup, players). Use existing string keys `STR_READY_DIALOG_MATCHUP_CHANGED`, `STR_READY_DIALOG_PLAYERS_CHANGED`.
8. `tryAutoStartRoundIfAllReady(eventPlayer)` — re-evaluate auto-start gate in case players/side dropped and a countdown should fire now.

**Ordering critical**: step 3 (slot.vehicleType update) MUST precede step 4 (slot enablement + force-spawn). Otherwise newly-enabled slots use stale types — re-introducing the v0.731 wrong-vehicle bug.

### Phase 4 — dirty state

Extend `ReadyDialogModeConfigDiffState`:
```ts
matchupDirty: boolean;
playersDirty: boolean;
```

Extend `buildReadyDialogModeConfigDiffState`:
```ts
const matchupDirty = cfg.matchupPresetIndex !== c.matchupPresetIndex;
const playersDirty = cfg.autoStartMinActivePlayers !== c.autoStartMinActivePlayers;
const hasUnsavedChanges = ... || matchupDirty || playersDirty;
```

Extend `applyDirtyStateColorsForPid` to color these widgets:

| Widget ID | What it shows | Dirty source |
|---|---|---|
| `UI_READY_DIALOG_MATCHUP_LABEL_ID` | "Vehicles: X vs Y" | `matchupDirty` |
| `UI_READY_DIALOG_MATCHUP_KILLSTARGET_ID` | "Target Kills to win Round: X" | `matchupDirty` (kills target derived from matchup preset) |
| `UI_READY_DIALOG_MATCHUP_MINPLAYERS_ID` | "Players: X vs Y" | `playersDirty` |
| `UI_READY_DIALOG_MATCHUP_MINPLAYERS_TOTAL_ID` | "Minimum Players to Start: X" | `playersDirty` |

Use the existing `setValueColor` helper inside `applyDirtyStateColorsForPid`. Pattern: red when dirty, green when clean. Per the v0.722 user direction recorded in [5.31.26_heli_ceiling_punish_and_dirty_state_plans.md](./5.31.26_heli_ceiling_punish_and_dirty_state_plans.md), labels stay white — colors apply to VALUE widgets only.

### Phase 5 — render refactor

Switch render paths from live → pending. Side-effect-free unless tested wrong:

| Function | Before reads | After reads |
|---|---|---|
| `updateMatchupLabelForPid` | `State.round.matchupPresetIndex` | `State.round.modeConfig.matchupPresetIndex` |
| `updateMatchupReadoutsForPid` (kills-target, min-players, players-format) | `State.round.matchupPresetIndex`, `State.round.autoStartMinActivePlayers`, `State.round.killsTarget` | `State.round.modeConfig.matchupPresetIndex` (→ `MATCHUP_PRESETS[i]` for kills derivation), `State.round.modeConfig.autoStartMinActivePlayers` |
| `updateSettingsSummaryHudForPid` (upper-left mini-HUD) | live `State.round.matchupPresetIndex`, `State.round.autoStartMinActivePlayers` | `State.round.modeConfig.confirmed.matchupPresetIndex`, `State.round.modeConfig.confirmed.autoStartMinActivePlayers` (HUD reflects APPLIED, not previewed — matches `aircraftCeiling` / vehicle HP behavior today) |
| `isReadyDialogModePresetActive` | `State.round.matchupPresetIndex`, `State.round.autoStartMinActivePlayers` | `State.round.modeConfig.matchupPresetIndex`, `State.round.modeConfig.autoStartMinActivePlayers` (pending — for snap-back) |

The split "Ready Dialog rows show PENDING / upper-left HUD shows CONFIRMED" mirrors the existing `gameMode` / `aircraftCeiling` / vehicle HP behavior.

### Phase 6 — snap-back + reset parity

- `detectAndApplyMatchingPreset` iterates modes via `isReadyDialogModePresetActive`. Phase 5's switch to pending makes this work for free.
- `ensureCustomGameModeForManualChange` should fire from the matchup + players setters too (currently it doesn't fire from `applyMatchupPreset` or `setAutoStartMinActivePlayers` because they were live setters). Add the call to both new pending-setters so editing matchup/players flips the game mode to Custom (matches behavior of `setReadyDialogAircraftCeiling`, `setReadyDialogVehicleHealthMultiplier`, etc.).
- `triggerFreshRoundSetup` (Restart button) — does NOT touch modeConfig today. After refactor it should reset pending matchup + players back to confirmed values. Recommendation: add to the function's body alongside the existing `resetReadyStateForAllPlayers` call. Same one-line per field.

## Known non-goals (out of scope for this plan)

1. **Destroy-on-shrink behavior.** Cycling matchup DOWN (e.g., 4v4 → 1v1) and confirming does NOT despawn the extra live vehicles. Same as today. If desired, a future plan.
2. **Mid-round matchup/players change.** Current code disables setters during `isRoundLive()`. No change.
3. **Tank mode revival.** v0.731 made `isHeliGameMode` return `true` unconditionally; tank-spawn fallback is dead code. This plan does not exhume it.

## Risks

| Risk | Mitigation |
|---|---|
| Ordering bug in Confirm: enabling slot count before updating slot.vehicleType reintroduces wrong-vehicle spawn | Plan documents the required ordering (Phase 3 step 3 before step 4); enforced in code review |
| Snap-back regression: switching `isReadyDialogModePresetActive` to pending might fail to snap back when live state matches but pending doesn't | The "match" check is for the user's pending-edit values. If they edited values that don't match any preset, mode stays Custom — correct behavior. If their edits happen to match, snap-back fires. Matches existing soldier HP / vehicle HP snap-back semantics. |
| Migration: in-flight game session at the moment of the v0.731 → v0.732 deploy | Helis-only experience restarts per match; no persistent session state crosses deploys. Not a concern. |
| Performance: dirty-state diff now compares 2 more fields per render | Diff already runs every dialog refresh; adding 2 integer compares is unmeasurable |
| Cooldown semantics: `MATCHUP_CHANGE_COOLDOWN_SECONDS = 1.0` was sized for live spawn timing. With pending-only it's overly conservative but harmless. | Keep for now. Future cleanup can drop the cooldown for pending-only setters. |
